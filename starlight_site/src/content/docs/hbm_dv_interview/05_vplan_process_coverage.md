## 0. 이 장이 대응하는 공고 문장

> **필수②** Digital IP **Spec 기반으로 검증 계획 수립 및 검증 프로세스 이해** 역량
> **필수④** **Code/Functional Coverage Closure**
> **업무④** **Regression Test** 통한 Code/Func. Coverage Closure

필수 4항목 중 **둘**이 이 장에 있다. 그리고 여기가 **꼬리질문이 가장 깊게 들어오는 구간**이다 — 검증 프로세스는 연차가 쌓여야 답이 달라지는 영역이라, 4년+ 경력을 검증하는 데 가장 효율적인 질문 소재이기 때문이다.

## 1. Q1 — "스펙을 받으면 검증 계획을 어떻게 세우시나요?"

즉흥적으로 답하면 "기능을 나열하고 테스트를 매핑합니다"가 된다. 틀린 말은 아니지만 **누구나 하는 답**이다. 4단 절차로 답한다.

```
 스펙 문서
    │
 ① 경계 확정      무엇이 DUT이고 무엇이 모델인가
    │             → 경계 문서(boundary document)
    │
 ② 능력 역산      스펙의 각 규칙을 검증하려면
    │             환경에 어떤 "능력"이 있어야 하는가
    │             (자극 능력 / 관측 능력 / 판정 능력)
    │
 ③ 체크 매핑      규칙 하나하나에 "누가 이것을 잡는가"를 붙인다
    │             (SVA / scoreboard / VIP / 수동 리뷰)
    │
 ④ 잔여 항목      매핑되지 않고 남은 규칙을 목록으로 남긴다
                  → 그것이 개발 범위이자 리스크 목록
```

### ① 경계 확정 — 가장 먼저, 그리고 문서로

"DUT가 어디까지인가"를 문서로 확정하지 않고 시작하면, 나중에 "그건 우리 범위가 아니다"라는 논쟁이 반복된다. [02장 Q3](../02_hbm_domain_qna/)에서 확인했듯 **경계는 물리가 아니라 표현 형식(RTL이냐 모델이냐)이 긋는다.**

### ② 능력 역산 — 이 개념이 변별점이다

스펙 규칙을 읽고 곧바로 테스트를 적지 않는다. **먼저 "이 규칙을 검증하려면 환경에 무엇이 있어야 하는가"를 역산한다.**

| 능력 | 질문 | 없으면 벌어지는 일 |
|---|---|---|
| **자극 능력** | 이 상황을 만들 수 있는가 | 시나리오를 작성해도 조건이 발생하지 않음 |
| **관측 능력** | 그 신호/상태를 볼 수 있는가 | 위반이 일어나도 보이지 않음 (**관측 사각**) |
| **판정 능력** | 무엇이 맞는지 독립적으로 아는가 | DUT 출력을 기대값으로 쓰게 됨 |

> "테스트를 적기 전에 **환경 능력**을 먼저 적습니다. 자극·관측·판정 세 능력 중 하나라도 없으면 그 규칙은 *계획상으로만 검증됩니다*."

이 문장이 이 장에서 가장 강한 한 문장이다.

### ③ 체크 매핑 — "누가 이것을 잡는가"

규칙마다 담당 체커를 붙인다. 붙일 수 없으면 그 자체가 발견이다.

| 스펙 규칙 | 담당 체커 | 비고 |
|---|---|---|
| 핸드셰이크 규칙 | SVA (인터페이스 bind) | 관측 지점에 상주 |
| 데이터 정합성 | scoreboard (독립 재현) | DUT 출력을 신뢰하지 않음 |
| 타이밍 파라미터 | SVA | 위반 즉시 |
| 설정 효과 | 시나리오 + scoreboard | write ≠ 효과 |
| 문서에 없는 동작 | **없음 → 스펙 갭** | 설계자에게 질의 |

### ④ 잔여 항목 — 리스크를 숨기지 않는 기술

매핑되지 않은 규칙은 세 부류로 남긴다: **개발 예정 / 차단(blocked) / 스펙 갭**. 이 목록을 계획서에 남기는 것이 프로세스 이해도의 증거다.

:::tip[가산점 문장]
"검증 계획의 가치는 **덮은 것의 목록**이 아니라 **덮지 못한 것의 목록**에 있습니다. 잔여 항목이 비어 있는 계획서는 대개 아직 분석이 덜 된 것입니다."
:::

## 2. Q2 — "V-Plan에는 무엇이 들어가나요?"

항목 하나의 구조를 말할 수 있으면 충분하다.

| 필드 | 내용 |
|---|---|
| 항목 ID | 추적 단위 |
| 출처 | 스펙 조항 번호 — **추적성의 핵심** |
| 검증 목표 | 무엇이 참임을 보이려는가 |
| 자극 | 어떤 시나리오/시퀀스가 이 상황을 만드는가 |
| **체크** | 누가 판정하는가 (SVA/scoreboard/VIP) |
| **커버리지** | 어떤 bin이 "도달했다"를 증명하는가 |
| 상태 | 미착수 / 진행 / 닫힘 / 차단 |

**핵심은 체크와 커버리지가 *별도 필드*라는 것이다.** 이 둘이 한 칸에 있으면 [Q3](#3-q3--coverage가-100인데-버그가-났습니다-무엇이-잘못된-건가요-)의 함정에 빠진다.

## 3. Q3 — "Coverage가 100%인데 버그가 났습니다. 무엇이 잘못된 건가요?" ★

**이 장의 최고난도 질문이자, 이 공고에서 가장 나올 법한 질문이다.** 필수④가 "Coverage Closure"이므로 면접관은 반드시 그 이해의 깊이를 잰다.

즉답하지 말고 **세 갈래로 분해**한다.

### 갈래 A — 커버리지는 "갔다"는 뜻이지 "맞다"는 뜻이 아니다

가장 흔한 원인이다. **커버리지는 자극의 도달을 세고, 체크는 결과의 정오를 판정한다.** 둘은 다른 축이다.

```
   자극이 갔다  ────► coverage bin 히트  ✅
   결과가 맞다  ────► checker 통과       ← 이게 없으면 아무것도 보장 안 됨
```

체커가 없는 항목은 커버리지가 100%여도 **아무것도 검증하지 않은 것**이다. 그래서 V-Plan에서 체크와 커버리지를 별도 필드로 둔다.

### 갈래 B — 커버리지 축이 결함을 표현하지 못한다

bin이 잘못 설계된 경우다. 대표 사례: **채널 인덱스로만 bin을 나눈 커버리지.**

- 16개 채널을 각각 bin으로 두면 "모든 채널을 다 써봤다"는 100%가 나온다.
- 그런데 실제 버그는 **CA 버스를 공유하는 pseudo-channel 쌍의 동시 요청**에서 난다.
- 동시성 축이 bin에 없으므로, 조합은 **원리적으로 관측되지 않는다**.

> "커버리지 100%가 의미하는 것은 *제가 정의한 축을 다 덮었다*이지 *결함 공간을 다 덮었다*가 아닙니다. 축을 잘못 잡으면 100%가 오히려 안심하게 만듭니다."

### 갈래 C — Assertion이 공허하게 통과했다 (vacuous pass)

`a |-> b` 형태의 assertion은 **선행 조건 `a`가 한 번도 참이 아니면** 자동으로 통과한다. 로그에는 실패가 없고 통계에도 문제가 없다.

```systemverilog
// 이 assertion은 row_cmd_valid가 한 번도 뜨지 않으면 "통과"한다
a_ca_share: assert property (
  @(posedge clk) disable iff (!rst_n)
  (row_cmd_valid && col_cmd_valid) |-> (row_pc == col_pc)
) else `uvm_error("SVA_R3", "row/col pseudo-channel mismatch")

// 그래서 모든 assertion에 cover property를 짝지어 둔다
c_ca_share_exercised: cover property (
  @(posedge clk) disable iff (!rst_n) (row_cmd_valid && col_cmd_valid)
);
```

**대응 원칙.** "**assertion 하나에 cover property 하나**를 짝지어, 선행 조건이 실제로 발생했는지를 별도로 셉니다. 그게 없으면 assertion 개수는 안심의 근거가 되지 못합니다."

:::caution[이 세 갈래의 공통 구조]
셋 다 **지표는 초록인데 관측 경로가 결함을 볼 수 없는** 상태다. 이것을 **silent pass**라고 부르고 한 단어로 묶어 말하면, 개별 사례를 나열하는 것보다 훨씬 강하게 들린다.

"검증에서 제가 가장 경계하는 건 실패가 아니라 **조용한 통과**입니다. 실패는 보이지만 조용한 통과는 보이지 않습니다."
:::

## 4. Q4 — "Code coverage와 Functional coverage의 관계는?"

**한 줄.** 서로를 대체하지 못하고, **서로의 빈 곳을 지목**한다.

| 조합 | 의미 | 조치 |
|---|---|---|
| Code 100% + Func 낮음 | 코드는 다 밟았지만 **의도한 기능 조합**을 안 봤다 | 시나리오 추가 |
| Code 낮음 + Func 100% | 기능은 덮었는데 **도달 안 한 코드**가 있다 | 데드코드? 미검증 경로? **조사 대상** |
| 둘 다 100% | 정의한 범위를 덮었다 | **결함 공간을 덮었다는 뜻은 아니다** |

**가산점 답변.** "두 커버리지의 **불일치가 정보**입니다. Functional은 100%인데 Code가 낮은 구간은 *내 V-Plan이 그 코드 경로를 모르고 있다*는 신호라 가장 먼저 봅니다."

## 5. Q5 — "Closure는 어떻게 판단하나요? 언제 끝났다고 말합니까?"

조직 문장의 *"설계 무결성 확보"* 가 곧 sign-off 판단이다. **숫자 하나로 답하지 마라.**

### 4개 조건이 동시에 만족될 때

| 조건 | 내용 |
|---|---|
| ① **유효 coverage** | 제외(exclusion)가 **근거와 함께** 문서화된 상태에서 목표 도달 |
| ② **체크 결합** | 모든 coverage 항목에 담당 체커가 매핑되어 있음 |
| ③ **잔여 항목 처리** | 미검증 항목이 *해결* 또는 *리스크로 명시 수용* |
| ④ **회귀 안정성** | 최근 N회 회귀가 안정적으로 통과 (간헐 실패 0) |

**한 문장.** "Closure는 **숫자가 아니라 상태**입니다. 100%라는 숫자보다, *제외한 항목마다 근거가 있고 남은 리스크가 명시적으로 수용됐는가*가 판단 기준입니다."

**경험 앵커.** "Secure Boot에서 다수 양산 sign-off를 냈는데, 매번 마지막에 남는 논의는 커버리지 숫자가 아니라 **제외 항목의 근거**였습니다."

:::note[꼬리질문]
- *"목표가 100%가 아니어도 되나요?"* → 유효 coverage 기준으로는 100%를 목표로 하되, **제외를 정당화하는 것이 실무**다. 도달 불가능한 코드를 100%로 만들려는 시도가 오히려 위험하다.
- *"일정이 부족하면요?"* → 항목을 **리스크 순으로 정렬**해 닫는다. 무엇을 못 닫았는지 명시하는 것이 프로세스이지, 숫자를 맞추는 것이 프로세스가 아니다.
:::

## 6. Q6 — "커버리지가 안 오를 때 어떻게 하시나요?"

**hole을 세 부류로 분류**하는 것이 답이다. 분류 없이 "시드를 더 돌린다"고 답하면 감점이다.

| 분류 | 원인 | 조치 |
|---|---|---|
| **자극 부족** | 그 조건을 만드는 시나리오가 없음 | **directed 시퀀스** 추가 (시드 증가 아님) |
| **도달 불가** | 구조적으로 발생 불가능한 조합 | **근거를 적고 exclusion** |
| **bin 오설계** | bin이 실제 동작과 대응하지 않음 | bin 재정의 — *가장 자주 놓치는 부류* |

:::caution[면접 금지어]
**"시드를 더 돌립니다"** 는 최악의 답이다. [02장 Q4](../02_hbm_domain_qna/)에서 본 것처럼, 한 번에 하나씩만 동작시키는 시나리오는 **시드를 아무리 늘려도** 동시성 조합을 만들지 못한다.

> **시드 개수는 시나리오 구조의 결함을 보완하지 못합니다.**

이 문장을 그대로 외워 두면 좋다.
:::

**exclusion의 정당한 조건.** ⓐ 구조적으로 도달 불가함을 **설명할 수 있고**, ⓑ 근거가 **문서에 남고**, ⓒ **설계자 확인**을 거쳤을 때. 셋 중 하나라도 빠지면 exclusion이 아니라 은폐다.

## 7. Q7 — "Regression은 어떻게 운영하시나요?"

| 등급 | 주기 | 목적 | 실패 시 |
|---|---|---|---|
| **Smoke** | 커밋마다 | 기본 경로 붕괴 감지 | 즉시 차단 |
| **Nightly** | 매일 | 랜덤 시드 확장 | 아침 triage |
| **Weekly / Full** | 주 1회 | 커버리지 수집·장시간 시나리오 | 주간 리뷰 |

**말할 포인트 세 가지.**

1. **시드 관리** — 실패한 시드는 **회귀 목록에 고정**해 재현 가능하게 둔다. 랜덤 실패를 랜덤하게 흘려보내지 않는다.
2. **Triage 순서** — 같은 원인의 실패가 여러 테스트에 퍼진다. **첫 실패**를 원인 기준으로 묶어 분류한다.
3. **간헐 실패(flaky) 금지** — "가끔 실패한다"를 방치하면 회귀 신호 전체가 무의미해진다. 간헐 실패는 **버그로 취급**한다.

**경험 앵커.** "MMU에서 상용 VIP crash 때문에 회귀가 불안정했는데, 원인을 VIP로 특정한 뒤 thin agent로 대체해 **crash 0%**로 만들었습니다. 회귀가 신뢰를 잃으면 그 뒤의 모든 지표가 무의미해진다는 걸 그때 배웠습니다."

| ❌ 금지 | ✅ 권장 |
|---|---|
| "커버리지 100% 달성했습니다" | "유효 커버리지 기준으로 닫았고, 제외 항목은 근거를 문서화했습니다" |
| "시드를 더 돌립니다" | "hole을 자극 부족/도달 불가/bin 오설계로 분류하고 directed로 채웁니다" |
| "VIP가 잡아줍니다" | "VIP 검사 범위를 매핑하고 잔여 항목을 별도 관리합니다" |
| "테스트가 다 통과했습니다" | "체크가 결합된 상태에서 통과했고, assertion은 cover로 실제 발생을 확인했습니다" |
| "assertion을 N개 작성했습니다" | "assertion마다 cover property를 짝지어 **공허한 통과**를 배제했습니다" |

## 핵심 정리

- 필수 4항목 중 **둘**이 이 장에 있고, **꼬리질문이 가장 깊은 구간**이다.
- 검증 계획은 **경계 확정 → 능력 역산 → 체크 매핑 → 잔여 항목** 4단.
- **능력 역산**(자극·관측·판정)이 이 장의 최강 개념 — "세 능력 중 하나라도 없으면 그 규칙은 계획상으로만 검증된다".
- 계획의 가치는 **덮지 못한 것의 목록**에 있다.
- "coverage 100%인데 버그" → **세 갈래**: 체크 부재 / 축 오설계 / 공허한 통과. 셋을 **silent pass**로 묶어 말한다.
- **assertion 하나에 cover property 하나.**
- Closure는 **숫자가 아니라 상태** — 유효 coverage · 체크 결합 · 잔여 처리 · 회귀 안정성.
- **시드 개수는 시나리오 구조의 결함을 보완하지 못한다.**
