## 0. 왜 이 장이 1순위인가

[01장](../01_role_and_strategy/)에서 확인한 대로 공고는 같은 역량을 **두 번** 요구한다.

> **필수③** 신규 Protocol 또는 Custom IP에 대한 UVM Agent 설계/구현
> **우대①** Spec 기반 Custom UVM Agent **A-to-Z** 개발 경험

필수와 우대에 같은 항목을 겹쳐 쓰는 공고는 흔하지 않다. **지금 이 조직이 가장 필요로 하는 사람**이라는 신호다. 준비 시간의 상당 부분을 여기에 써야 한다.

## 1. 면접관이 듣고 싶은 것은 3층인데, 대부분 2층만 말한다

"Custom Agent 개발 경험이 있나요?"라는 질문에 지원자 대부분은 **설계 구조**부터 말한다. driver·monitor·sequencer를 만들었고 config로 active/passive를 나눴다는 식이다. 이건 UVM 교재에도 있다.

면접관이 실제로 채점하는 것은 세 층이다.

| 층 | 내용 | 말하는 사람 비율 | 배점 |
|---|---|---|---|
| **① 판단** | *왜* 만들었는가 — 상용 VIP를 왜 안 썼는가 | 낮음 | **높음** |
| ② 설계 | *어떻게* 만들었는가 — item·driver·monitor 구조 | 대부분 | 중 |
| ③ 결과 | 무엇이 좋아졌는가 — 숫자 | 절반 | 중 |

**만들 줄 아는 사람은 많고, 만들지 말지 판단할 줄 아는 사람은 적다.** ①을 먼저 말하는 것만으로 대부분의 지원자와 갈라진다.

:::caution[가장 흔한 실패]
"Custom Agent를 만들어봤습니다"에서 멈추면 면접관의 다음 질문은 100% 이것이다 — **"왜 상용 VIP를 안 쓰셨어요?"** 여기서 "회사에 없어서요"라고 답하면 판단이 없는 사람이 된다.
:::

## 2. Q1 — "Custom UVM Agent 개발 경험을 말해 보세요" (오프닝 60초)

먼저 통째로 외울 스크립트를 만든다. **판단 → 설계 → 결과** 순서를 지킨다.

> **[판단]** "MMU IP를 검증할 때 상용 AXI-S VIP를 붙였는데, high-stress translation 시나리오에서 메모리를 80% 넘게 점유하고 crash가 반복됐습니다. 원인을 보니 **우리가 쓰지 않는 기능까지 전부 모델링**하고 있었습니다. vendor support를 기다리면 tape-out 일정이 위험했고, 우리가 실제로 쓰는 건 데이터패스 일부라고 판단해서 자체 개발하기로 했습니다.
>
> **[설계]** 핵심 데이터패스(tdata·valid·ready)만 남긴 **thin agent**를 스펙에서 역산해 만들었습니다. item은 신호 묶음이 아니라 **의미 단위**로 잡았고, monitor는 driver의 item을 재사용하지 않고 **DUT 신호만으로 독립 재구성**하도록 했습니다.
>
> **[결과]** stress 테스트 crash가 0%가 됐고, 메모리 점유가 급감했습니다. 무엇보다 **검증 환경의 통제권을 우리가 갖게 됐습니다** — 스펙이 바뀌어도 vendor를 기다리지 않고 당일 대응할 수 있었습니다."

:::tip[이 스크립트의 설계 의도]
- 첫 문장이 **문제 상황**이다. "만들었습니다"가 아니라 "이런 문제가 있었습니다"로 시작하면 판단 서사가 열린다.
- "우리가 쓰지 않는 기능까지 모델링" — **원인 분석**을 했다는 증거
- "통제권" — 이 단어가 시니어와 주니어를 가른다. 도구에 종속되지 않는 판단
- 숫자 2개(80%, 0%)만 넣는다. 더 넣으면 기억되지 않는다
:::

## 3. Q2 — "왜 상용 VIP를 쓰지 않았나요?" (판단의 3단 절차)

즉흥적으로 답하면 "필요해서요"가 된다. **절차로 답하라.**

### 3단 절차

```
1단계  경계 판정    이 인터페이스에 상용 VIP가 존재하는가?
                    표준(AXI/APB/DDR) → 존재    비표준/고객 정의 → 부재
         │
         ├─ 존재 →  2단계  능력 역산   VIP가 제공하는 검사 범위와
         │                              우리가 필요한 검사를 매핑
         │                              → 남는 항목(residual)이 얼마인가
         │
         └─ 부재 →  3단계  공수 산정   Agent 개발 공수 vs
                                        검증 일정·재사용 범위
```

**핵심은 "사느냐 만드느냐"가 이분법이 아니라는 것이다.** 실제 답은 대개 *섞는 것*이다 — 상용 VIP를 붙이되 그것이 못 잡는 항목을 자체 assertion·monitor로 채운다.

### 의사결정 매트릭스

| 상황 | 판단 | 근거 |
|---|---|---|
| 표준 프로토콜 + 검사 범위 충분 | **도입** | 개발 공수 낭비 |
| 표준 프로토콜 + 검사 범위 부족 | **도입 + 자체 보강** | VIP는 토대, 잔여는 우리 몫 |
| 표준인데 **자원 문제**(메모리·속도) | **Thin 자체 개발** | ← MMU 사례 |
| **비표준·고객 정의** 인터페이스 | **자체 개발 (A-to-Z)** | 애초에 제품이 없다 |

:::caution[사실 정정 — 면접에서 틀리기 쉬운 지점]
"HBM은 custom이라 상용 VIP가 없습니다"라고 말하면 **틀린 답**이다. 표준 HBM(HBM2/2E/3/3E/4)용 상용 VIP는 주요 EDA 벤더가 제공하며 프로토콜 체크·커버리지·에러 주입까지 포함한다.

정확한 표현은 이렇다 — "**표준 HBM 인터페이스는 상용 VIP가 있습니다. 자체 개발이 필요한 건 고객 정의 인터페이스나 Base Die 내부의 비표준 IP 쪽입니다.**" 이 구분을 아는 사람과 모르는 사람이 여기서 갈린다. → [HBM 검증 실무 Ch04](../../hbm_dv/04_vip_strategy/)
:::

### 매핑표 — 답변에 무게를 싣는 도구

"VIP가 못 잡는 게 뭐냐"는 꼬리질문에는 **매핑표를 만들었다**고 답한다.

| 스펙 규칙 | 상용 VIP가 검사? | 잔여 조치 |
|---|---|---|
| 프로토콜 핸드셰이크 | ✅ | — |
| 타이밍 파라미터 | ✅ | — |
| **우리 시스템 고유의 설정 순서** | ❌ | 자체 assertion |
| **통합 지점(클럭·리셋·주변 IP 상호작용)** | ❌ | 자체 scoreboard |
| **고객 정의 확장 커맨드** | ❌ | 자체 Agent |

> "VIP 도입 여부를 결정하기 전에 **스펙 규칙 하나하나를 VIP 검사 범위와 매핑**했습니다. 매핑되지 않고 남는 항목을 **잔여 항목**으로 관리해서, 그 목록이 곧 자체 개발 범위가 됐습니다."

## 4. Q3 — "화이트보드에 Agent 구조를 그려 보세요" (6단계)

즉석 작성 요청이 나오면 **그리는 순서**가 곧 답변이다. 말없이 상자만 그리면 점수가 없다. 각 단계마다 한 문장씩 말한다.

```
                  ┌──────────────────────────────┐
     (1) 경계 ────┤   xxx_agent (uvm_agent)      │
                  │                              │
     (2) item ────┤  ┌────────────┐              │
                  │  │ sequencer  │              │
     (3) driver ──┤  └─────┬──────┘              │
                  │        │ seq_item_port       │
                  │  ┌─────▼──────┐              │
                  │  │  driver    │──┐           │
     (4) monitor ─┤  └────────────┘  │ vif       │
                  │  ┌────────────┐  │           │
                  │  │  monitor   │◄─┘           │
                  │  └─────┬──────┘              │
     (5) 분석 포트┤        │ analysis_port       │
                  │        ▼  ──────────────────►│──► scoreboard / coverage
     (6) config ──┤  ┌────────────┐              │
                  │  │   config   │ is_active,   │
                  │  └────────────┘ 파라미터      │
                  └──────────────────────────────┘
```

| 단계 | 그리면서 말할 문장 |
|---|---|
| **(1) 경계** | "먼저 이 Agent가 감시·구동할 **인터페이스 경계**를 정합니다. 신호 그룹이 아니라 *하나의 프로토콜 단위*가 기준입니다." |
| **(2) item** | "스펙에서 **의미 단위**를 뽑아 sequence item을 정의합니다. 신호를 그대로 필드로 옮기지 않습니다." |
| **(3) driver** | "driver는 item을 신호 타이밍으로 바꿉니다. 응답을 기다릴지 말지가 여기서 결정됩니다." |
| **(4) monitor** | "monitor는 **DUT 신호만 보고** 트랜잭션을 재구성합니다. driver가 만든 item을 절대 재사용하지 않습니다." |
| **(5) 분석 포트** | "재구성한 트랜잭션을 analysis port로 내보내 scoreboard와 coverage가 각각 구독합니다." |
| **(6) config** | "active/passive와 파라미터를 config object로 뽑아 **처음부터** 넣습니다. 나중에 넣으면 전면 수정이 됩니다." |

:::tip[여기서 가산점]
(4)와 (6)에 **이유**를 붙이는 것이 핵심이다. 나머지는 템플릿이지만 이 둘은 원칙이다.
:::

## 5. Q4 — "Sequence Item을 어떻게 정의했나요?"

**틀린 접근.** 스펙의 신호 목록을 그대로 필드로 옮긴다.

```systemverilog
// ❌ 신호를 그대로 옮긴 item — 스펙이 바뀌면 전부 깨진다
class bad_item extends uvm_sequence_item;
  rand bit        cmd_valid;
  rand bit        cmd_ready;   // ← DUT가 주는 신호를 왜 rand로?
  rand bit [7:0]  cmd_addr;
  rand bit [31:0] wdata;
  rand bit [31:0] rdata;       // ← 요청과 응답이 뒤섞임
endclass
```

**올바른 접근 — 세 가지 원칙.**

1. **경계는 의미 단위** — 트랜잭션 하나가 스펙에서 "하나의 동작"인 단위여야 한다.
2. **방향은 필드 속성으로** — 요청 필드는 `rand`, 응답 필드는 monitor가 채우는 non-rand.
3. **파라미터는 처음부터** — 폭·채널 수를 상수로 박지 않는다.

```systemverilog
class ch_cmd_item extends uvm_sequence_item;
  // --- 요청(자극) 필드: 시퀀스가 제어한다 ---
  rand cmd_kind_e     kind;      // ROW / COL
  rand bit [PC_W-1:0] pc_id;     // pseudo-channel
  rand bit [ADDR_W-1:0] addr;
  rand bit [DATA_W-1:0] wdata;

  // --- 응답 필드: monitor가 채운다 (rand 아님) ---
  bit [DATA_W-1:0]    rdata;
  rsp_status_e        status;
  time                issue_time, complete_time;

  `uvm_object_utils(ch_cmd_item)
  function new(string name="ch_cmd_item"); super.new(name); endfunction

  constraint c_pc { pc_id inside {[0:NUM_PC-1]}; }
endclass
```

:::note[꼬리질문 방어]
- *"요청과 응답을 왜 한 item에 두나요?"* → 하나의 트랜잭션 생애를 하나의 객체로 추적하면 scoreboard·coverage가 단순해진다. 다만 **out-of-order 응답**이 있으면 분리하는 편이 낫다 — 그때는 tag로 매칭한다. **선택의 근거를 말하는 것**이 정답이다.
- *"`rdata`를 왜 rand로 안 했나요?"* → DUT가 만드는 값이다. rand로 두면 시퀀스가 응답을 지정하는 모순이 생긴다.
- *"파라미터를 왜 처음부터 넣나요?"* → 나중에 넣으면 item·driver·monitor·coverage를 전부 고쳐야 한다. 재사용은 사후에 붙일 수 없다.
:::

## 6. Q5 — "Monitor는 어떻게 만들었나요?" (독립 재구성 원칙)

**이 질문이 Agent 설계 이해도의 리트머스다.**

**① 원칙.** Monitor는 **DUT 인터페이스 신호만 보고** 트랜잭션을 재구성한다. driver가 만든 item을 참조하거나 재사용하지 않는다.

**② 왜.** driver의 item을 monitor가 그대로 넘기면, **DUT가 무엇을 했든 상관없이** scoreboard는 "보낸 것 = 받은 것"을 보게 된다. 검사가 자기 자신을 검사하는 셈이라 어떤 버그도 잡지 못한다. 이것이 [02장 Q8](../02_hbm_domain_qna/)에서 말한 **silent pass**의 전형이다.

```systemverilog
task ch_monitor::run_phase(uvm_phase phase);
  forever begin
    @(posedge vif.clk);
    if (!vif.rst_n) continue;

    // DUT 신호만으로 재구성 — driver item을 참조하지 않는다
    if (vif.cmd_valid && vif.cmd_ready) begin
      ch_cmd_item tr = ch_cmd_item::type_id::create("tr");
      tr.kind   = cmd_kind_e'(vif.cmd_kind);
      tr.pc_id  = vif.cmd_pc;
      tr.addr   = vif.cmd_addr;
      tr.issue_time = $time;
      `uvm_info("MON", $sformatf("captured %s pc=%0d addr=0x%0h",
                tr.kind.name(), tr.pc_id, tr.addr), UVM_HIGH)
      ap.write(tr);
    end
  end
endtask
```

**③ 트레이드오프.** 독립 재구성은 monitor 개발 공수를 늘린다. 프로토콜 디코드 로직을 두 번(driver 인코드 / monitor 디코드) 짜는 셈이다. **그 중복이 곧 검사 능력**이라는 것이 핵심 논지다.

**④ 내 경험 앵커.** "Secure Boot에서 **DPI-C 기반 C-model**을 붙여 SW-driven 핸드셰이크를 독립적으로 재현했습니다. DUT 출력을 그대로 기대값으로 쓰지 않는다는 원칙을 그때 세웠습니다."

## 7. Q6 — "Driver가 응답을 기다리나요?"

**답변.** "인터페이스가 파이프라인이면 기다리지 않습니다."

**인과.** driver가 매 트랜잭션마다 응답까지 기다리면 요청 발행이 직렬화된다. 그러면 **파이프라인 깊이·동시 미결 트랜잭션(outstanding)** 같은 corner가 원리적으로 만들어지지 않는다. 자극 능력이 구조적으로 제한되는 것이다.

**구조.** 요청 발행과 응답 수집을 분리한다 — driver는 발행만 하고, 응답은 monitor가 잡아 scoreboard가 tag로 매칭한다.

:::note[꼬리질문]
- *"그럼 driver는 back-pressure를 어떻게 처리하나요?"* → `ready` 핸드셰이크는 지킨다. 기다리지 않는 것은 *응답(response)* 이지 *수락(accept)* 이 아니다. **이 구분을 명확히 하는 것이 답변의 핵심.**
- *"응답 순서가 뒤바뀌면요?"* → tag/ID로 매칭한다. out-of-order 지원 여부는 **스펙에서 역산**할 항목이지 구현자가 임의로 정할 것이 아니다.
:::

## 8. Q7 — "이 Agent를 다른 프로젝트에서 재사용할 수 있나요?"

재사용성은 세 가지로 답한다.

| 축 | 방법 | 말할 문장 |
|---|---|---|
| **구조 재사용** | active/passive를 config로 분리 | "같은 Agent를 자극용·감시용 양쪽으로 씁니다" |
| **파라미터 재사용** | 폭·채널 수를 파라미터/config로 | "상수를 박지 않아 세대가 바뀌어도 재사용됩니다" |
| **동작 재사용** | factory override | "특수 시나리오는 driver를 override해서 교체합니다" |

> "MMU에서 스펙이 자주 바뀌었는데, 환경을 **템플릿 + 자동 생성** 구조로 만들어서 spec 변경 대응을 days에서 hours로 줄였습니다. 재사용성은 사후에 붙이는 게 아니라 **처음부터 설계에 넣어야** 한다는 걸 그때 확인했습니다."

## 9. 자주 나오는 함정 3개

면접관이 유도 질문으로 던지는 함정이다. 미리 알고 가면 오히려 가산점이 된다.

| 함정 질문 | 잘못된 답 | 올바른 답 |
|---|---|---|
| "monitor에 driver item을 쓰면 편하지 않나요?" | "네, 그렇게도 합니다" | **"그러면 검사가 무력화됩니다."** 독립 재구성이 원칙 |
| "일단 passive로 만들고 나중에 자극을 추가하면?" | "가능합니다" | **"자극 능력은 나중에 못 붙입니다."** sequencer·driver 경로가 처음부터 있어야 함 |
| "파라미터는 나중에 빼도 되죠?" | "리팩토링하면 됩니다" | **"item·driver·monitor·coverage를 전부 고치게 됩니다."** 처음부터 |

세 함정의 공통 구조가 있다 — **"나중에 하면 된다"** 는 유혹이다. 셋 다 답은 같다: *구조적 결정은 나중에 못 바꾼다.*

:::tip[한 문장으로]
"Agent 설계에서 **나중에 붙일 수 있는 것과 없는 것**을 구분하는 게 가장 중요합니다. 커버리지 bin은 나중에 붙일 수 있지만, 자극 능력·독립 재구성·파라미터화는 처음에 넣지 않으면 전면 수정입니다."
:::

## 핵심 정리

- 이 장이 **합격선**이다 — 공고가 필수③·우대①로 같은 역량을 두 번 요구한다.
- 답변은 **판단 → 설계 → 결과** 3층. 대부분 ②만 말하므로 ①에서 갈린다.
- "왜 안 샀나"는 **3단 절차**(경계 판정 → 능력 역산 → 공수 산정)로 답한다. 이분법이 아니라 대개 *섞는다*.
- **표준 HBM용 상용 VIP는 존재한다.** "없어서 만들었다"는 틀린 전제 — 자체 개발 대상은 *비표준·고객 정의* 인터페이스다.
- Item은 신호 묶음이 아니라 **의미 단위**. 응답 필드는 `rand`가 아니다.
- Monitor는 **DUT 신호만으로 독립 재구성**한다. driver item 재사용은 검사를 무력화한다.
- **나중에 못 붙이는 것** — 자극 능력·독립 재구성·파라미터화.
