## 0. 원칙 — 같은 경험, 다른 배치

경력은 바뀌지 않는다. 바뀌는 것은 **무엇을 앞에 두는가**다.

| | DRAM 설계검증 공고 | **HBM 검증 공고 (이 코스)** |
|---|---|---|
| 1순위 카드 | AI 검증 프레임워크 (차별화) | **MMU Custom Thin VIP** |
| 2순위 | Secure Boot (깊이 증명) | Secure Boot (환경·프로세스) |
| 3순위 | DRAM Controller (도메인 연결) | DRAM Controller (우대②) |
| AI의 역할 | **최대 무기** — 공고 축② 직결 | **격하** — 환경 구축 역량의 *증거* |

**왜 AI를 내리는가.** DRAM 공고에는 *"설계 자동화 및 AI 적용, In-house Tool 개발, 차세대 검증 기술 연구"* 라는 축이 명시돼 있었다. HBM 검증 공고에는 그 축이 없다. 대신 조직 문장에 **"검증 시스템 및 환경 구축, 검증 모델 개발"** 이 있다.

그러므로 AI는 *차별화 축*이 아니라 **"환경을 시스템으로 만들어 본 사람"이라는 증거**로 쓴다. 배치를 바꾸지 않고 그대로 들고 가면, 공고에 없는 축을 길게 말하는 사람이 된다.

:::caution[가장 흔한 실수]
지난 면접에서 잘 먹혔던 순서를 그대로 재사용하는 것. **공고가 다르면 서사도 다르다.**
:::

## 1. 재배치 지도

| 프로젝트 | 대응 공고 항목 | 이 공고에서의 역할 |
|---|---|---|
| **MMU Custom Thin VIP** | 필수③ · 우대① · 업무② | **주력 카드 — 클라이맥스** |
| **Secure Boot RoT** | 필수①② · 업무③ | 환경 구축 + sign-off 프로세스 |
| **DRAM Memory Controller** | 우대② | 도메인 연결 (Follow 방어 필요) |
| **AI 검증 프레임워크** | 조직 문장(검증 시스템 구축) | 시스템 사고의 증거 |

## 2. 주력 카드 — MMU IP Custom Thin VIP (Lead)

공고가 **두 번** 요구한 역량에 정면으로 대응하는 유일한 경험이다. 가장 먼저, 가장 길게 말한다.

### STAR

- **S(상황)** 신규 MMU IP를 from-scratch로 검증. 스펙이 자주 바뀌고 일정이 빡빡했다. 상용 AXI-S VIP를 붙였는데 high-stress translation 시나리오에서 **메모리를 80% 넘게 점유**하고 crash가 반복됐다.
- **T(과제)** tape-out 일정을 지키면서 stress 검증을 안정화한다. vendor support를 기다릴 시간이 없었다.
- **A(행동)**
  - **원인 분석** — VIP가 우리가 쓰지 않는 기능까지 전부 모델링하고 있었다.
  - **판단** — 실제로 쓰는 것은 데이터패스 일부. thin agent로 충분하고 오히려 통제권을 확보한다.
  - **설계** — 핵심 데이터패스(tdata·valid·ready)만 남긴 **Custom Thin VIP**를 스펙에서 역산해 A-to-Z 개발.
  - **재사용 설계** — 표준 UVM Environment Template + 자동 생성으로 port별 컴포넌트를 찍어내 **spec 변경 대응을 days → hours**로.
  - **Dual Reference Model** — functional golden(bit-accurate) + **ideal 성능 모델**(latency/miss 상한) 두 축으로 DUT와 비교.
- **R(결과)** stress 테스트 **crash 0%**, 메모리 점유 급감, spec 변경 zero-day 대응, **TLB miss ratio 초과 구간을 발굴**해 마이크로아키텍처 병목 분석으로 연결, server급 throughput 충족.

### 꼬리질문 대비

| 질문 | 답변 |
|---|---|
| "상용 VIP를 왜 버렸나?" | "vendor support를 기다리면 tape-out이 위험했습니다. 우리가 쓰는 건 데이터패스 일부라 thin으로 충분했고, **통제권을 가져오는 판단**이었습니다" |
| "품질은 어떻게 보장했나?" | "기능을 줄인 대신 **검사는 줄이지 않았습니다.** monitor는 DUT 신호만으로 독립 재구성하고, 프로토콜 규칙은 assertion으로 별도 감시했습니다" |
| "Ideal 성능 모델이 뭔가?" | "miss 없음·최소 latency를 가정한 이론적 상한 모델입니다. **DUT와의 gap 자체가 개선 여지**가 됩니다" |
| "TLB miss 원인은?" | "시나리오별 miss 패턴을 분석해 replacement policy·엔트리 수·access 패턴의 상관을 추적, 마이크로아키텍처 병목을 특정했습니다" |
| "HBM에서도 같은 접근이 통할까?" | "**비표준·고객 정의 인터페이스에는 그대로 통합니다.** 다만 표준 HBM 인터페이스는 상용 VIP가 있으므로, 먼저 검사 범위를 매핑하고 **잔여 항목**을 자체 개발 범위로 잡는 판단이 앞섭니다" ← [03장](../03_custom_uvm_agent/) |

:::tip[마지막 질문이 결정적]
"HBM에서도 통하나"에 **"네, 똑같이 하겠습니다"** 라고 답하면 감점이다. 표준 HBM용 상용 VIP가 존재한다는 사실을 알고, **판단 절차가 먼저**라고 답해야 한다. 이 한 번의 답이 [03장](../03_custom_uvm_agent/) 전체의 이해도를 증명한다.
:::

## 3. Secure Boot — Root of Trust (Lead, 3년)

**이 공고에서의 역할**: 깊이 증명 + **환경 구축·sign-off 프로세스**(필수①②, 업무③).

### STAR

- **S** BootROM 검증이 firmware 지연 때문에 1–2개월 병목이라는 것이 팀의 **당연한 통념**이었다.
- **T** 통념을 의심하고 진짜 원인을 찾는다.
- **A**
  - **진단** — 병목의 실제 원인은 firmware 지연이 아니라 **legacy SV 테스트벤치의 재사용성·추상화 부재**였다.
  - Legacy SV → 풀스택 **UVM Framework 리팩토링** (모듈화·이식성).
  - **OTP Abstraction Layer (RAL)** — OTP map을 high-level sequence item으로 파싱해 물리 주소 의존성 제거.
  - **Active UVM Driver** — 통제된 force/release 시퀀스로 보안 공격 벡터·negative 시나리오를 **결정론적으로 재현**.
  - **DPI-C C-model** — 칩간 key exchange 등 SW-driven 핸드셰이크를 pre-silicon에서 검증.
- **R** 검증 turnaround **1개월+ 단축**, BootROM 100% functional integrity, 리팩토링 환경을 협업 프로젝트로 이식, **다수 양산 sign-off**.

### 이 공고 문맥에서 강조할 지점

| 요소 | 연결되는 공고 항목 | 말할 문장 |
|---|---|---|
| UVM Framework 리팩토링 | 업무③ 환경 구성 | "환경을 **재사용 단위로** 다시 설계한 경험입니다" |
| OTP Abstraction (RAL) | 필수① · 구성값 관리 | "물리 주소 의존성을 제거해 **map이 바뀌어도 테스트가 안 깨지게** 했습니다" |
| DPI-C C-model | **우대③ 다리** | "이종 표현을 한 시뮬레이션에서 맞물리게 한 경험" ← [06장](../06_mixed_level_gap/) |
| 양산 sign-off | 필수② 프로세스 | "**Closure는 숫자가 아니라 상태**라는 걸 여기서 배웠습니다" ← [05장](../05_vplan_process_coverage/) |

### 꼬리질문 대비

- *"force/release는 위험하지 않나?"* → "RTL 수정 없이 negative 시나리오를 재현하려면 필요했고, **driver가 release까지 보장**하도록 설계해 일반 시퀀스 경로와 분리했습니다."
- *"100% integrity를 어떻게 보장?"* → "모든 boot device(USB/UFS/SDMMC) 경로 + negative/보안 시나리오를 coverage bin으로 닫았습니다. **제외 항목은 근거를 문서화**했습니다."
- *"3년이면 길지 않나?"* → "같은 일을 3년 한 게 아니라, **통념을 반박하고 환경을 갈아엎고 양산까지** 끌고 간 3년입니다."

## 4. DRAM Memory Controller IP (Follow)

**이 공고에서의 역할**: 우대②(HBM, DDR/LPDDR Memory 검증) 대응.

- LPDDR4/5 표준 기반 functional 검증 + coverage 보강
- protocol timing(tRCD·tRP·tRAS·tRFI), refresh 시나리오, bank/rank, DFI를 **controller 관점**에서 SVA·시뮬레이션으로 검증

### Follow 지적 방어 — 3단

1. **인정** — "Follow 역할이었습니다." (숨기면 신뢰를 잃는다)
2. **깊이로 상쇄** — "다만 **timing 제약과 refresh 시나리오는 제가 직접 SVA로 작성**했고, controller 관점에서 DRAM이 어떻게 동작하는지 자신 있게 설명할 수 있습니다."
3. **HBM으로 연결** — "그 경험이 [HBM의 분리된 row/column 커맨드 인터페이스](../02_hbm_domain_qna/)를 이해하는 토대가 됐습니다. **프로토콜 규칙은 scoreboard가 아니라 관측 지점의 assertion이 잡아야 한다**는 원칙도 그때 세웠습니다."

:::note[Lead가 아닌 것을 뒤집는 법]
"제 Lead 경험은 비-DRAM이고 메모리 경험은 Follow"라는 구조는 바뀌지 않는다. 대신 **역할이 아니라 산출물**을 말한다 — "제가 작성한 SVA"는 역할과 무관하게 내 것이다.
:::

## 5. AI 검증 프레임워크 — 격하 배치

**중요: 이 공고에서는 클라이맥스가 아니다.** DVCon 2025 / DAC 2026 성과를 길게 말하면 공고에 없는 축을 파는 셈이 된다.

### 짧게, 조직 문장에 정확히 붙여서

> "조직 소개에 **'검증 시스템 및 환경 구축'** 이 있는데, 저는 검증 환경을 *하나의 프로젝트를 위한 코드*가 아니라 **시스템으로** 만들어 왔습니다. MMU에서는 환경 템플릿과 자동 생성으로 spec 변경 대응을 days에서 hours로 줄였고, 그 접근을 일반화한 연구를 DVCon과 DAC에 발표했습니다. 도구를 쓴 게 아니라 **프레임워크를 만든 쪽**입니다."

**30초.** 그 이상 말하지 않는다. 면접관이 관심을 보이면 그때 확장한다.

:::tip[동사를 관리한다]
"AI를 **활용**했습니다"(user) ❌ → "프레임워크를 **개발·구축**했습니다"(builder) ✅

같은 사실이라도 동사가 포지션을 결정한다. 이 공고는 **만드는 사람**을 뽑는다.
:::

### 확장 요청이 왔을 때만

- **Gap Detection (DVCon 2025)** — 검증 계획과 실제 구현 사이의 누락을 자동으로 찾는 접근. [05장의 잔여 항목](../05_vplan_process_coverage/) 문제를 자동화한 것.
- **SHELL (DAC 2026)** — 표준 환경 템플릿에서 port별 컴포넌트를 생성. 재사용 설계의 자동화.
- **한계도 함께 말한다** — "생성 결과를 **그대로 신뢰하지 않습니다.** 사람이 검토하는 게이트를 두고, 검증 자체의 판정에는 쓰지 않습니다." ← *한계를 말하는 것이 신뢰를 만든다*

## 6. "가장 어려웠던 디버깅" — 준비 카드 3개

거의 100% 나온다. **STAR + 숫자**로 2~3개를 암기한다. 설명은 항상 같은 흐름이다.

```
 로그 → 가설 → 파형/모델로 확인 → 근본 원인 → 수정 → 재현 방지
```

| 사례 | 한 줄 요약 | 배운 점 |
|---|---|---|
| **VIP 메모리 폭증** | 상용 VIP가 메모리 80%+ → crash. 원인 = 불필요 기능 모델링 → Thin VIP 자체 개발 → crash 0% | **도구를 의심하고 통제권을 가져온다** |
| **TLB miss 병목** | Dual model 비교로 이상 감지 → miss 패턴 추적 → 마이크로아키텍처 구조 원인 특정 | **정답 모델만으론 부족하다. 성능 모델이 corner를 드러낸다** |
| **Secure Boot 통념 반박** | "firmware 지연" 통념을 deep-dive로 반박 → 진짜 원인은 TB 재사용성 부재 | **통념을 데이터로 의심한다** |

:::caution[HBM 문맥으로 한 줄 덧붙이기]
디버깅 사례를 말한 뒤 반드시 한 문장을 붙인다.

> "HBM 검증에서도 같은 부류가 있을 거라고 봅니다 — **ECC나 RAS 기능이 결함을 가려서 조용히 통과하는 경우**입니다. 그래서 통과했다는 결과가 아니라 **통과한 경로**를 봅니다."

디버깅 경험을 지원 직무의 언어로 착지시키는 것이 재포지셔닝의 마지막 단계다. ← [02장 Q8](../02_hbm_domain_qna/)
:::

## 7. 숫자 관리 규칙

| 프로젝트 | 고정할 숫자 (2개) |
|---|---|
| MMU Thin VIP | 메모리 **80%+** → crash **0%** |
| Secure Boot | turnaround **1개월+ 단축**, **다수 양산 sign-off** |
| DRAM Controller | (숫자 없음 — 역할이 Follow) |
| AI 프레임워크 | spec 변경 **days → hours** |

**규칙 세 개.**

1. 답변 하나에 숫자는 **최대 2개**. 셋 이상이면 아무것도 기억되지 않는다.
2. 숫자에는 **비교 대상**이 있어야 한다 — "80%"가 아니라 "80% → 0%".
3. **모르는 숫자는 말하지 않는다.** 꾸민 숫자는 두 번째 꼬리질문에서 무너진다.

:::caution[정직성]
위 사례의 숫자·세부는 **본인의 실제 경험으로 최종 검증**하라. 이 문서는 준비 틀이지 사실 확인 문서가 아니다. 기억이 흐린 항목은 숫자를 빼고 정성적으로 말하는 편이 안전하다.
:::

## 핵심 정리

- 경력은 그대로, **배치가 바뀐다.** DRAM 공고의 순서를 복사하지 않는다.
- **1순위는 MMU Custom Thin VIP** — 공고가 두 번 요구한 역량에 정면 대응하는 유일한 카드.
- MMU 답변의 결정적 꼬리질문: *"HBM에서도 통하나?"* → **"판단 절차가 먼저"** 로 답한다.
- Secure Boot는 **환경 구축 + sign-off 프로세스**로, DPI-C는 **Mixed 갭의 다리**로 쓴다.
- DRAM Controller의 Follow 지적은 **인정 → 산출물(내가 쓴 SVA) → HBM 연결** 3단.
- **AI는 격하 배치**. 조직 문장의 "검증 시스템 구축"에 30초로 붙인다. 동사는 *활용*이 아니라 **개발·구축**.
- 디버깅 사례는 **로그→가설→확인→근본원인→수정→재현방지** 흐름 + **HBM 문맥 한 줄** 착지.
- 숫자는 **경험당 2개, 비교 대상과 함께, 모르면 말하지 않는다**.
