## 1. Q1 — "3rd Party VIP를 도입해 본 경험이 있나요?"

경험이 도입 쪽보다 자체 개발 쪽에 치우쳐 있다면, **평가 능력**으로 답한다. 써 본 적이 없어도 *무엇을 보고 고르는지* 말할 수 있으면 된다.

### 도입 3단계

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| **평가** | 검사 범위·커버리지·성능·지원 조건 확인 | 평가 체크리스트 |
| **매핑** | 스펙 규칙 ↔ VIP 검사 범위 대조 | 매핑표 + **잔여 항목** |
| **통합** | 환경에 붙이고 설정을 우리 구성에 맞춤 | 설정 프로파일 |

### 평가 체크리스트 — 면접에서 열거할 항목

- **검사 범위**: 어떤 프로토콜 규칙을 자동으로 검사하는가. *"전부 검사한다"는 답은 존재하지 않는다.*
- **커버리지 모델**: VIP가 제공하는 covergroup이 우리 V-Plan 항목과 대응되는가
- **에러 주입**: 음성 시나리오를 만들 수 있는가, 어느 수준까지
- **성능**: 시뮬레이션 속도·메모리 점유. **회귀 전체 시간에 직결된다**
- **설정 가능성**: 우리 구성(채널 수·모드)을 표현할 수 있는가
- **지원 조건**: 버그 수정 응답 시간. *일정 리스크의 실체*

:::note[경험 앵커 — 도입 경험이 적을 때]
"상용 AXI-S VIP를 붙여 본 경험이 있고, 그때 **성능 항목을 평가에서 놓친 것**이 문제가 됐습니다. high-stress 시나리오에서 메모리를 80% 넘게 점유해 crash가 났고, 결국 필요한 데이터패스만 남긴 thin agent로 대체했습니다. 그 이후로 VIP 평가에 **성능과 지원 응답 시간**을 반드시 넣습니다."

→ 도입 실패 경험을 **평가 기준을 배운 계기**로 전환한다. 실패담이 체크리스트가 되면 강점이 된다.
:::

## 2. Q2 — "VIP를 도입하면 그 부분은 해결된 건가요?" (함정 질문)

**아니다.** 이 질문은 VIP를 과신하는지 보려는 것이다. 세 가지 함정으로 답한다.

| 함정 | 무슨 일이 벌어지나 | 대응 |
|---|---|---|
| **검사 범위 미확인** | "VIP가 잡아주겠지" 하고 넘긴 규칙이 아무도 검사하지 않는 상태로 남는다 | 도입 **전에** 매핑표 작성, 잔여 항목 명시 |
| **VIP 커버리지 = 우리 커버리지 착각** | VIP covergroup은 *프로토콜*을 덮지 *우리 IP의 기능*을 덮지 않는다 | 두 커버리지를 **분리 집계** |
| **기본 설정으로 사용** | VIP 기본값이 우리 구성과 달라 실제와 다른 자극이 나간다 | 설정 프로파일을 명시적으로 관리 |

:::tip[가산점 문장]
"**VIP는 토대이지 답이 아닙니다.** 도입으로 닫히는 항목과 남는 항목을 매핑표로 분리하고, **잔여 항목**을 검증 계획에 명시적으로 남깁니다. 그 목록이 자체 개발 범위가 됩니다."

이 문장은 [05 — V-Plan](../05_vplan_process_coverage/)으로 자연스럽게 이어진다.
:::

## 3. Q3 — "UVM 검증 환경을 어떻게 구성하시나요?"

조직 문장이 **Mixed IP / Digital IP / Subsystem·Top Level** 세 계층을 적어 놨으므로, 계층 이야기는 반드시 나온다.

### 핵심 원칙 — 계층은 포함 관계, 차이는 설정

```
   ┌──────────────────────────────────────────────┐
   │  Top / Full-chip env                         │
   │   ┌────────────────────────────────────┐     │
   │   │  Subsystem env                     │     │
   │   │   ┌──────────────────────────┐     │     │
   │   │   │  IP-level env            │     │     │
   │   │   │   agent(active)          │     │     │
   │   │   │   scoreboard / coverage  │     │     │
   │   │   └──────────────────────────┘     │     │
   │   │   같은 env를 재사용 —              │     │
   │   │   agent만 passive로 전환           │     │
   │   └────────────────────────────────────┘     │
   │   자극원이 시퀀스 → Test Firmware로 바뀜      │
   └──────────────────────────────────────────────┘
```

**답변.** "계층마다 환경을 새로 만들지 않습니다. **상위 계층은 하위 env를 포함**하고, 달라지는 것은 **설정**입니다. IP 레벨에서 active였던 agent가 Subsystem에서는 passive로 바뀌고, 자극원이 시퀀스에서 Test Firmware로 옮겨갑니다. **체커와 커버리지는 그대로 따라 올라갑니다.**"

**왜 이게 정답인가.** 계층마다 새로 만들면 ⓐ 개발 공수가 3배, ⓑ 체커가 복제되어 계층 간 판정이 어긋난다. 반대로 full-chip 하나로 통일하면 ⓒ 시뮬레이션이 느려 corner를 못 만들고, ⓓ 디버그가 어렵다.

:::caution[여기서 03장과 연결된다]
[03장](../03_custom_uvm_agent/)에서 "**자극 능력은 나중에 못 붙인다**"고 했다. 반대 방향도 참이다 — **passive 지원이 없는 agent는 상위 계층에서 재사용할 수 없다.** Agent 설계 시점의 결정이 환경 계층 전략을 좌우한다. 이 연결을 말하면 설계를 계층까지 보고 하는 사람으로 읽힌다.
:::

## 4. Q4 — "IP 레벨에서 닫은 것을 Top에서 또 검증하나요?"

조직 문장의 3계층에서 반드시 파생되는 질문이다. **"계층마다 목적이 다르다"** 로 답한다.

| 계층 | 목적 | 자극원 | 여기서만 잡히는 것 |
|---|---|---|---|
| **IP** | 기능·프로토콜 규칙 전수 | UVM 시퀀스 | corner·에러 주입·타이밍 위반 |
| **Subsystem** | IP 간 **연결·상호작용** | 시퀀스 + 일부 FW | 통합 지점, 설정 순서, 자원 경합 |
| **Top / Full-chip** | 실제 사용 흐름 | **Test Firmware** | 초기화 순서, 클럭/리셋, 시스템 레벨 시나리오 |

**핵심 문장.** "IP 레벨은 **가능한 모든 것**을 보고, Top 레벨은 **실제로 일어나는 것**을 봅니다. IP에서 닫은 항목을 Top에서 반복하는 게 아니라, **Top에서만 관측 가능한 것**을 봅니다 — 통합 지점과 초기화 순서가 대표적입니다."

**역방향 함정.** "그럼 IP에서 다 하면 Top은 필요 없지 않나요?"라는 유도가 올 수 있다. 답은 **관측 가능성**이다. IP 레벨 환경은 주변을 모델로 대체하므로, 실제 주변 IP와의 상호작용은 원리적으로 관측되지 않는다.

## 5. Q5 — "구성값이 많은데 어떻게 관리하나요?"

HBM은 세대·스택 단수·채널 수·모드가 조합된다. 관리 원칙을 **3분류**로 답한다.

| 종류 | 예 | 성질 | 관리 |
|---|---|---|---|
| **구조 구성값** | 채널 수, 데이터 폭, 스택 단수 | 빌드 시 고정 | 파라미터 / build config |
| **프로파일 구성값** | 동작 모드, 속도 등급, 기능 on/off | 테스트 시작 시 결정 | **설정 프로파일** 객체 |
| **시나리오 구성값** | 주입할 에러 종류, 트래픽 비율 | 런타임에 변함 | 시퀀스 인자 |

**왜 나누는가.** 셋을 섞으면 ⓐ 구조 값을 런타임에 바꾸려는 시도가 생기고, ⓑ 프로파일 조합이 폭발하며, ⓒ 어떤 테스트가 어떤 설정에서 돌았는지 회귀 결과에서 추적할 수 없게 된다.

:::tip[가산점 개념 — 프로파일 독립성]
"체커는 **어떤 프로파일에서도 같은 판정**을 내려야 합니다. 프로파일마다 체커를 분기시키면, 그 분기가 곧 검증되지 않은 경로가 됩니다."

이 개념(**profile independence**)을 말하면 설정 관리를 실제로 해 본 사람으로 읽힌다. → [HBM 검증 실무 Ch06](../../hbm_dv/06_env_hierarchy/)
:::

## 6. Q6 — "Test Case를 어떻게 설계하시나요?"

가장 흔한 오답은 **"시나리오마다 테스트 클래스를 만든다"** 이다. 그러면 테스트 수가 수백 개로 늘고 서로 복사본이 된다.

### 재사용 단위는 테스트가 아니라 시퀀스다

```
  [ test ]           ← 얇다. 환경 설정 + vseq 하나 기동
      │
  [ virtual sequence ]  ← 시나리오 조립: 순서·동시성·계층 간 조정
      │
  [ sequence ]          ← 재사용 단위: "write burst", "error inject"
      │
  [ sequence item ]     ← 의미 단위 트랜잭션
```

**답변.** "테스트는 얇게 두고 **시퀀스를 재사용 단위**로 만듭니다. 새 시나리오는 기존 시퀀스를 **조합**하는 virtual sequence로 표현합니다. 그러면 시나리오가 늘어도 코드가 선형으로 늘지 않습니다."

### 뒤로 밀리기 쉬운 세 부류 — 먼저 말하면 가산점

| 부류 | 왜 밀리나 | 왜 중요한가 |
|---|---|---|
| **오류 주입** | 정상 동작부터 맞춰야 하니까 | 에러 처리 경로가 **한 번도 실행되지 않은 채** 출하될 수 있다 |
| **설정 효과 확인** | 레지스터를 썼으니 됐다고 생각 | 레지스터 write는 *접근*이지 *효과 확인*이 아니다 |
| **성능 시나리오** | 기능이 우선이니까 | 실효 대역폭 문제는 기능 테스트로 안 드러난다 |

:::caution[반드시 구분할 것]
**"레지스터에 썼다"와 "그 설정이 동작에 반영됐다"는 다른 이야기다.** RAL로 write/read-back이 맞는다고 설정 효과가 검증된 것이 아니다. 모드를 켠 뒤 **동작이 실제로 바뀌었는지**를 관측하는 시나리오가 따로 필요하다. 이 구분은 면접에서 자주 파고드는 지점이다.
:::

## 7. Q7 — "자극이 현실적인지 어떻게 보장하나요?"

**개념.** 자극 현실성(stimulus realism) — 생성한 자극이 실제 시스템에서 발생 가능한 패턴인가.

**인과.** 완전 무작위 자극은 커버리지를 빨리 올리지만 **실제로 일어나지 않는 조합**까지 포함한다. 그러면 ⓐ 존재하지 않는 버그를 쫓게 되고, ⓑ 반대로 실제로 흔한 패턴이 과소 표현된다.

**계층별 답.**

| 계층 | 현실성 확보 방법 |
|---|---|
| IP | **의도적으로 비현실적**이어도 된다 — 가능한 모든 것을 본다 |
| Subsystem | 실제 트래픽 비율을 프로파일로 반영 |
| Top | **Test Firmware**가 실제 초기화·사용 흐름을 만든다 |

**한 문장.** "IP 레벨에서는 현실성보다 **완전성**이 우선이고, 상위로 갈수록 **현실성**이 우선입니다. 이 균형을 계층별로 다르게 잡습니다."

## 8. 경험 앵커 정렬표

이 장의 질문마다 붙일 자신의 경험을 미리 정해 둔다.

| 질문 | 앵커로 쓸 경험 |
|---|---|
| VIP 평가 | 상용 AXI-S VIP 성능 문제 → 평가 기준을 배운 계기 |
| VIP 함정 | 필요 없는 기능까지 모델링된 VIP → 검사 범위 확인 습관 |
| 환경 계층 | Secure Boot UVM Framework 리팩토링(모듈화·이식성) |
| 구성값 관리 | OTP Abstraction Layer(RAL) — 물리 주소 의존성 제거 |
| Test Case 설계 | MMU 환경 템플릿 + 자동 생성 → spec 변경 days→hours |
| 자극 현실성 | Dual Reference Model — functional + **ideal 성능 모델** |

:::note[숫자는 두 개까지]
답변 하나에 숫자를 셋 이상 넣으면 아무것도 기억되지 않는다. **경험당 숫자 2개**만 고정해서 외운다.
:::

## 핵심 정리

- 이 장은 공고의 **업무②③ + 필수①** 에 직접 대응한다.
- VIP 도입은 **평가 → 매핑 → 통합** 3단계. 평가 체크리스트에 **성능·지원 응답 시간**을 반드시 넣는다.
- **VIP는 토대이지 답이 아니다.** 잔여 항목을 명시적으로 남긴다.
- 환경 계층은 **포함 관계**이고 차이는 **설정**이다. 계층마다 새로 만들지 않는다.
- **IP는 가능한 모든 것을, Top은 실제로 일어나는 것을** 본다. 반복이 아니라 관측 가능성의 문제다.
- 구성값은 **구조 / 프로파일 / 시나리오** 3분류. 체커는 **프로파일 독립**이어야 한다.
- **재사용 단위는 테스트가 아니라 시퀀스**다. 시나리오는 조합으로 표현한다.
- 뒤로 밀리기 쉬운 셋 — **오류 주입 · 설정 효과 · 성능**. 먼저 언급하면 가산점.
