## 0. 이 장의 위치 — 탈락 방지선

도메인 질문은 **가산점 구간이 아니라 탈락 방지선**이다. HBM 구조를 유창하게 말한다고 합격하지 않지만, 스택 구조를 못 그리면 그 자리에서 끝난다. 그래서 목표는 "깊이"가 아니라 **막히지 않는 것**이다.

다만 한 가지 프레임 교정이 먼저 필요하다.

:::caution[가장 위험한 오해]
**"HBM 검증 면접 = DRAM 셀·타이밍 시험"이 아니다.** 공고의 요구는 전부 SystemVerilog/UVM·Agent·Coverage로 쓰여 있다. 검증 대상은 스택 맨 아래 **Base Die 안의 digital·mixed IP**다. tRCD·tRP를 외우는 데 시간을 쓰지 말고, **"DUT가 어디인가"** 를 그릴 수 있는 데 쓰라.
:::

답변은 [01장의 4단 구조](../01_role_and_strategy/)를 따른다 — **한 줄 정의 → 인과 → 트레이드오프 → 내 경험 앵커**.

## 1. Q1 — "왜 HBM인가요? GDDR로는 안 되나요?"

**① 한 줄 정의.** HBM은 대역폭을 *클럭*이 아니라 *버스 폭*으로 푸는 메모리다 — 실리콘 관통 전극(TSV)으로 die를 쌓아 수천 개의 신호선을 짧은 거리에 배치한다.

**② 인과.** 대역폭을 늘리는 길은 두 갈래뿐이다 — 폭을 늘리거나 속도를 올리거나. 그런데 **에너지는 거리에 붙어 있다.** 패키지 밖 PCB를 지나는 신호는 거리가 길어 비트당 에너지가 크고, 속도를 올릴수록 신호 무결성 비용이 급증한다. GDDR은 속도 축으로 밀어붙인 결과 핀당 속도는 높지만 폭이 좁고 전력이 크다. HBM은 반대로 간다 — 인터포저 위 **짧은 거리**에 1024~2048개의 선을 깔아, 핀당 속도를 낮게 유지하면서 총 대역폭을 만든다.

**③ 트레이드오프.** 공짜가 아니다. ⓐ **지연은 줄지 않는다** — 대역폭과 레이턴시는 다른 축이다. ⓑ **비용이 높다** — TSV·인터포저·적층 공정. ⓒ **검증 관점에서는 상태 공간이 폭증한다** — 채널이 8→16→32로 늘면 동시성 조합이 그만큼 늘어난다.

**④ 내 경험 앵커.** "LPDDR4/5 controller를 검증할 때 채널·뱅크 조합만으로도 시나리오 설계가 어려웠는데, HBM은 그 축이 한 자릿수 늘어난다고 이해했습니다. 그래서 시드를 늘리는 방식이 아니라 자원 독립성 지도를 먼저 그려야 한다고 봅니다."

:::note[꼬리질문]
- *"그럼 HBM이 GDDR보다 무조건 좋은가요?"* → 아니다. 레이턴시 민감·비용 민감 응용(게임 GPU)은 GDDR이 여전히 맞다. **선택은 응용의 병목이 대역폭이냐 비용이냐에 달렸다.**
- *"이론 대역폭이 실효 대역폭인가요?"* → 아니다. refresh·bank conflict·bus turnaround가 실효를 깎는다. 그래서 성능 검증에는 *이상 모델*이 따로 필요하다 (→ [08 — Dual Reference Model](../08_project_star/)).
:::

## 2. Q2 — "HBM3 대역폭이 819 GB/s인 이유를 설명해 보세요"

이 질문은 **암기 여부가 아니라 계산 습관**을 본다. 식 하나만 있으면 된다.

```
대역폭 = 총 버스 폭(bit) × per-pin 속도(Gb/s) ÷ 8
```

| 세대 | 총 폭 | 채널 구성 | per-pin | 대역폭(계산) |
|---|---|---|---|---|
| HBM2 | 1024-bit | 8ch × 128-bit (16pc × 64-bit) | 2.0 Gb/s | 1024 × 2.0 ÷ 8 = **256 GB/s** |
| HBM2E | 1024-bit | 8ch × 128-bit | 3.2 Gb/s | 1024 × 3.2 ÷ 8 = **409.6 GB/s** |
| HBM3 | 1024-bit | **16ch × 64-bit (32pc × 32-bit)** | 6.4 Gb/s | 1024 × 6.4 ÷ 8 = **819.2 GB/s** |
| HBM4 | **2048-bit** | **32ch** | 8 Gb/s | 2048 × 8 ÷ 8 = **2048 GB/s ≈ 2 TB/s** |

**답변 방식.** 수치를 외워서 말하지 말고 **식을 먼저 꺼내고 그 자리에서 계산**하라. "1024비트에 6.4 Gb/s니까 8로 나누면 819.2 GB/s입니다"라고 말하면, 세대가 바뀌어도 흔들리지 않는 사람으로 보인다.

:::tip[여기서 점수가 갈린다]
HBM3에서 **폭은 그대로(1024-bit)인데 채널만 8→16으로 쪼개졌다**는 점을 짚어라. 대역폭 증가는 전적으로 per-pin 속도(3.2→6.4)에서 왔고, 채널 분할은 *대역폭이 아니라 병렬성·독립성*을 위한 것이다. 이 구분을 말하는 지원자는 드물다. → [HBM Ch02 세대 지형도](../../hbm/02_generations/)
:::

:::note[꼬리질문]
- *"HBM2 대역폭이 307 GB/s라는 자료도 있는데요?"* → per-pin 속도 가정이 다르다(2.4 Gb/s). 식에 대입해 보면 1024 × 2.4 ÷ 8 = 307.2 GB/s. **출처마다 가정이 다르므로 식으로 검산한다**고 답하면 오히려 신뢰를 얻는다.
- *"HBM4는 왜 속도가 아니라 폭을 두 배로 했나요?"* → 속도만 올리면 신호 무결성·전력 비용이 비선형으로 증가한다. 폭 확장이 에너지 효율 면에서 유리한 구간이었다.
:::

## 3. Q3 — "HBM 스택 구조를 그려 보세요. 검증 대상은 어디인가요?" ★

**이 장에서 가장 중요한 질문이다.** 공고의 DUT 정의가 여기서 나온다.

```
        [ Host SoC / GPU ]
              │  µbump
    ══════════╪══════════════════  Interposer (2.5D)
              │
   ┌──────────┴──────────┐
   │   Core Die  (DRAM)  │  ← 셀 어레이. 검증 대상 아님
   │   Core Die  (DRAM)  │     (동작 모델로 대체)
   │   Core Die  (DRAM)  │
   │   Core Die  (DRAM)  │
   ├─────────────────────┤  TSV
   │  ★ Base Die (Logic) │  ← ★ DUT — RTL이 여기 있다
   │   메모리 컨트롤러    │
   │   PHY / TSV PHY     │
   │   ECC / RAS / DFT   │
   │   (cHBM: PCIe·UCIe) │
   └─────────────────────┘
```

**① 한 줄 정의.** HBM은 여러 장의 DRAM core die를 TSV로 쌓고, 맨 아래 **Base Die(Logic Die)** 가 각 채널의 read/write·refresh·precharge를 관리하는 적층 메모리다.

**② 인과 — 왜 Base Die가 DUT인가.** 검증 대상의 경계는 물리가 아니라 **표현 형식**이 긋는다. 우리가 시뮬레이션할 수 있는 것은 RTL이고, DRAM 셀 어레이는 RTL이 아니라 동작 모델(behavioral model)로 대체된다. 따라서 파일 목록에 DRAM 셀은 없고 **Base Die의 digital·mixed IP**만 있다. 공고가 "Analog-Digital Mixed IP, Digital IP 및 Subsystem/Top Level"이라고 쓴 것이 바로 이 층이다.

**③ 트레이드오프.** 모델로 대체한다는 것은 **모델이 실물보다 관대할 수 있다**는 뜻이다. 모델이 타이밍 위반을 신고하지 않으면 테스트는 통과하지만 실리콘은 깨진다. 그래서 "모델을 DUT로 착각하지 않기"가 이 구조의 첫 번째 함정이다.

**④ 내 경험 앵커.** "MMU IP를 검증할 때도 주변 블록은 모델이었고, 모델이 DUT보다 관대해서 놓친 corner가 있었습니다. 그래서 모델의 엄격도를 별도 항목으로 관리했습니다."

:::caution[면접에서 반드시 말할 한 문장]
"**검증 대상은 DRAM 셀이 아니라 Base Die 안의 digital·mixed IP입니다.**"

이 한 문장이 "HBM 잘 모르지만 열심히 하겠습니다"와 "이 직무를 이해하고 왔습니다"를 가른다. → [HBM Ch03 스택 구조](../../hbm/03_stack_architecture/)
:::

## 4. Q4 — "채널과 pseudo-channel의 차이는 무엇인가요?"

**① 한 줄 정의.** Pseudo-channel은 하나의 채널을 데이터 경로와 뱅크 기준으로 둘로 나눈 단위이며, **CA(커맨드/주소) 버스는 공유하되 커맨드는 각자 해석·실행**하는 semi-independent 구조다.

**② 인과 — 자원별 독립성 지도.** "독립"은 켜짐/꺼짐이 아니라 자원마다 다르다.

| 자원 | 채널 간 | Pseudo-channel 간 | 검증 의미 |
|---|---|---|---|
| 데이터 I/O | 분리 | 분리 | 간섭 없음 |
| 뱅크 | 분리 | 분리 | 간섭 없음 |
| **CA 버스** | 분리 | ⚠️ **공유** | **경합·순서가 검증 대상** |
| 커맨드 decode/실행 | 독립 | 개별 수행 | semi-independent의 근거 |

**③ 트레이드오프 — 왜 어중간한 형태인가.** 완전 독립으로 만들면 CA 핀이 두 배가 된다. 완전 공유로 두면 병렬성이 죽는다. **핀 비용과 병렬성의 타협**이 semi-independent다.

**④ 검증 corner (여기가 가산점).** "설계가 비용을 아끼려고 무언가를 **공유**하면 그 지점이 그대로 검증 포인트가 됩니다. CA 버스를 공유하는 pseudo-channel 쌍의 **동시 요청**이 핵심 시나리오이고, 한 번에 하나씩 동작시키는 시나리오로는 아무리 시드를 늘려도 관측되지 않습니다."

:::note[꼬리질문]
- *"채널 하나만 철저히 검증하고 나머지는 복제로 봐도 되나요?"* → 채널 간에는 상당 부분 성립하지만 **pseudo-channel 쌍에서는 성립하지 않는다** — 공유 자원이 있기 때문이다.
- *"그럼 16채널 전 조합 2¹⁶을 다 봐야 하나요?"* → 아니다. **분리된 자원에서는 조합이 무의미**하다. 공유 자원(CA 버스)이 있는 쌍으로 조합을 좁힌다. 이 답이 coverage 설계 역량을 보여준다. → [HBM Ch04](../../hbm/04_channels_addressing/)
:::

## 5. Q5 — "HBM 커맨드 인터페이스가 DDR과 무엇이 다른가요?"

**① 한 줄 정의.** HBM은 row 계열(activate·precharge)과 column 계열(read·write)의 커맨드·주소 인터페이스가 **분리**되어 있고, HBM3에서는 독립적인 row/column 커맨드 인터페이스를 각각 제공한다.

**② 인과.** 하나의 CA 버스에 row와 column 커맨드가 섞이면 서로를 기다린다. 분리하면 **두 흐름을 병렬로 발행**할 수 있어 버스 효율이 올라간다.

**③ 트레이드오프 / 검증 corner.** 흐름이 둘이 되면 **둘 사이의 순서 규칙**이 새로운 검증 항목이 된다. 같은 pseudo-channel을 대상으로 row와 column 커맨드가 동시에 유효할 때 무엇이 보장되어야 하는가 — 이런 규칙은 데이터 비교(scoreboard)로는 잡히지 않고 **관측 지점에 상주하는 assertion**이 필요하다.

**④ 내 경험 앵커.** "LPDDR4/5 controller에서 tRCD·tRP·tRAS·tRFI와 refresh 시나리오를 **SVA로 직접 작성**했습니다. 프로토콜 규칙을 scoreboard가 아니라 인터페이스에 붙은 assertion으로 감시해야 한다는 것을 그때 배웠습니다."

:::tip[가산점 문장]
"**프로토콜 위반은 데이터 비교를 통과할 수 있습니다.**" — 잘못된 순서로 커맨드가 나가도 최종 데이터가 우연히 맞으면 scoreboard는 침묵한다. 그래서 감시자는 관측 지점(인터페이스)에 있어야 한다. → [HBM Ch05](../../hbm/05_interface_protocol/)
:::

## 6. Q6 — "HBM3와 HBM4는 무엇이 다른가요?"

변화를 **세 층위**로 나눠 답하면 표를 외운 사람과 구분된다.

| 층위 | 변화 | 검증 영향 |
|---|---|---|
| ① 파라미터 | per-pin 6.4 → 8 Gb/s | 타이밍 값만 바뀜 — **환경 재사용 가능** |
| ② 구조 | 총 폭 1024 → **2048-bit**, 채널 16 → **32** | 채널 축·주소 맵 변경 — **coverage 축 재설계** |
| ③ 공정·구성 | Base Die가 DRAM 공정 → **로직 공정**(4nm/3nm급) | Base Die에 IP가 더 들어감 — **검증 범위 자체가 확장** |

**핵심 답변.** "가장 중요한 변화는 ③입니다. Base Die가 로직 공정으로 가면 자리가 남고, 그 자리에 메모리 컨트롤러·전력관리·ECC, 나아가 고객 전용 로직까지 들어갑니다. 즉 **검증 대상이 메모리에서 작은 SoC로 확장**됩니다."

:::note[표준 규격 인용]
JESD235(HBM1/2/2E), JESD238(HBM3/3E), JESD270-4(HBM4, 2025-04). 규격 번호를 정확히 말할 자신이 없으면 **말하지 마라** — 틀린 번호는 안 말한 것보다 나쁘다. "JEDEC 규격이 세대별로 나뉘어 있고 HBM4는 2025년에 공개됐습니다" 정도면 충분하다.
:::

## 7. Q7 — "Base Die 안에는 무엇이 있고, 검증 접근이 왜 달라지나요?"

**① 한 줄 정의.** Base Die는 메모리 컨트롤러·PHY/TSV PHY·전력관리·ECC/RAS·DFT를 담은 **미니 SoC**이며, cHBM에서는 여기에 호스트 인터페이스(PCIe·UCIe)까지 들어간다.

**② 인과 — 두 축의 교차.** IP를 정리하는 축은 하나가 아니라 둘이다.

|  | **기능 축** | **출처 축** |
|---|---|---|
| 무엇 | 컨트롤러 / PHY / PMU / RAS / DFT | In-house / 3rd Party / 고객 제공 |
| 결정하는 것 | *무엇을* 검증하는가 | *어디까지 볼 수 있는가* |

검증 접근은 **두 축의 교차**에서 정해진다. In-house IP는 내부 신호까지 볼 수 있어 white-box 접근이 가능하지만, 3rd Party·고객 제공 IP는 인터페이스만 보고 black-box로 다뤄야 한다.

**③ 트레이드오프 / 함정.** "검증된 IP를 샀다"는 말은 **IP 자체**가 검증됐다는 뜻이지 **우리 시스템에 통합된 상태**가 검증됐다는 뜻이 아니다. 통합 지점(클럭·리셋·설정·주변 IP와의 상호작용)은 여전히 우리 몫이다.

**④ 내 경험 앵커.** "Secure Boot에서 3rd party 블록과의 경계를 검증할 때, IP 내부가 아니라 **핸드셰이크와 설정 순서**에서 문제가 났습니다. 통합 검증을 IP 검증과 분리해서 계획해야 한다고 배웠습니다."

:::note[공고 직결]
이 질문이 **업무①**(In-house·3rd Party·Mixed 검증)에 정확히 대응한다. 답변 끝에 "그래서 In-house VIP를 만들지 3rd Party VIP를 도입할지 판단이 필요하다"까지 연결하면 [04장](../04_vip_strategy_env/)으로 자연스럽게 넘어간다. → [HBM Ch06](../../hbm/06_base_die_soc/)
:::

## 8. Q8 — "on-die ECC가 검증에 어떤 영향을 주나요?" (심화)

이 질문이 나오면 좋은 신호다 — 검증자의 사고를 보려는 것이다.

**① 한 줄 정의.** on-die ECC는 DRAM 내부에서 단일 비트 오류를 정정하는 기능으로, HBM에서는 ECS(Error Check and Scrub)와 함께 동작한다.

**② 인과 — 검증을 *방해*한다.** ECC는 신뢰성 기능이지만 검증 관점에서는 **결함을 가린다.** 데이터패스에 비트 오류를 만드는 버그가 있어도 ECC가 정정해 버리면 테스트는 조용히 통과한다. 실리콘에서는 오류율이 예산을 초과해 문제가 드러난다.

**③ 대응.** ⓐ ECC를 **끌 수 있는 경로**(테스트 모드·TAP 레지스터)를 확보하고, ⓑ **정정 카운트를 관측**해 "정정이 일어났다"는 사실 자체를 실패로 취급하는 체크를 둔다. 즉 **통과했다는 결과가 아니라 통과한 경로**를 본다.

**④ 가산점 문장.** "이건 제가 **silent pass**라고 부르는 부류입니다 — 지표는 전부 초록인데 관측 경로가 결함을 볼 수 없게 되어 있는 상태입니다. RAS 기능이 켜진 채로 기능 검증을 하면 이 함정에 빠집니다."

:::tip[깊이는 여기까지]
ECC 코드 이론(SEC-DED·해밍거리)까지 파고들 필요는 없다. 면접관이 보려는 것은 **"신뢰성 기능이 검증을 가릴 수 있다"는 인식**이다. 더 깊이가 필요하면 [RAS 코스](../../ras/).
:::

## 핵심 정리

- 도메인 질문은 **탈락 방지선**이다. 깊이보다 *막히지 않는 것*이 목표다.
- 반드시 말해야 할 한 문장: **"검증 대상은 DRAM 셀이 아니라 Base Die 안의 digital·mixed IP입니다."**
- 수치는 외우지 말고 **식으로 계산**한다 — 총 폭 × per-pin ÷ 8.
- Pseudo-channel은 **CA 버스를 공유**한다. 공유 지점이 곧 검증 포인트다.
- 프로토콜 위반은 **데이터 비교를 통과할 수 있다** → 감시자는 인터페이스에 있어야 한다.
- ECC 같은 신뢰성 기능은 **결함을 가린다** — 통과 결과가 아니라 통과 경로를 본다.
- 모든 답변 끝에 **LPDDR4/5 controller 경험**을 앵커로 붙인다. 그것이 경력 면접이다.
