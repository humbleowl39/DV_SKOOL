## Q1. (Remember)

3rd Party VIP 평가 체크리스트에서, 후보자가 과거에 **놓쳐서 문제가 됐던** 항목은?

- [ ] A. 검사 범위
- [ ] B. 커버리지 모델
- [ ] C. 성능(시뮬레이션 속도·메모리 점유)
- [ ] D. 에러 주입 지원

<details>
<summary>정답 / 해설</summary>

**C**. MMU 프로젝트에서 상용 AXI-S VIP를 기능만 보고 도입했는데, high-stress 시나리오에서 메모리를 80% 넘게 점유하고 crash가 반복됐다. 성능은 **회귀 전체 시간에 직결**되므로 평가 항목에서 빠지면 안 된다.

이 실패는 면접에서 **"실패 경험"** 질문의 최적 소재다 — 내 판단 실수를 인정하고, 결과를 숨기지 않고, **재발 방지 장치(체크리스트에 성능·지원 응답 시간 추가)** 로 착지시킬 수 있기 때문이다.

</details>

## Q2. (Analyze)

"VIP를 도입하면 그 부분은 해결된 건가요?"라는 질문에 답할 때 지적해야 할 **세 가지 함정**은?

<details>
<summary>정답 / 해설</summary>

1. **검사 범위 미확인** — "VIP가 잡아주겠지" 하고 넘긴 규칙이 아무도 검사하지 않는 상태로 남는다. → 도입 *전에* 매핑표를 작성하고 잔여 항목을 명시한다.
2. **VIP 커버리지를 우리 커버리지로 착각** — VIP covergroup은 *프로토콜*을 덮지 *우리 IP의 기능*을 덮지 않는다. → 두 커버리지를 분리 집계한다.
3. **기본 설정으로 사용** — VIP 기본값이 우리 구성과 달라 실제와 다른 자극이 나간다. → 설정 프로파일을 명시적으로 관리한다.

한 문장 요약: **"VIP는 토대이지 답이 아닙니다."**

</details>

## Q3. (Understand)

IP → Subsystem → Top으로 계층이 올라갈 때 **바뀌는 것**과 **그대로 따라 올라가는 것**은 각각 무엇인가?

<details>
<summary>정답 / 해설</summary>

**바뀌는 것**: 설정. 구체적으로 ⓐ agent가 active → passive로 전환되고, ⓑ 자극원이 UVM 시퀀스 → Test Firmware로 옮겨간다.

**그대로 따라 올라가는 것**: **체커와 커버리지**. 계층마다 checker를 새로 짜면 판정이 어긋나고 유지보수가 3배가 된다.

원칙: **계층은 포함 관계이고, 차이는 설정으로 표현한다.** 상위 env가 하위 env를 포함하므로 계층마다 환경을 새로 만들지 않는다.

연결: [03장](../../03_custom_uvm_agent/)에서 "자극 능력은 나중에 못 붙인다"고 했는데, 반대 방향도 참이다 — **passive 지원이 없는 agent는 상위 계층에서 재사용할 수 없다.**

</details>

## Q4. (Evaluate)

"IP 레벨에서 닫은 것을 Top에서 또 검증하나요?"에 대한 가장 타당한 답은?

- [ ] A. 네, 중복 검증으로 신뢰도를 높입니다
- [ ] B. 아니요, IP에서 닫았으면 Top에서는 생략합니다
- [ ] C. 계층마다 목적이 달라서, Top에서는 Top에서만 관측 가능한 것을 봅니다
- [ ] D. 시간이 허락하는 만큼 반복합니다

<details>
<summary>정답 / 해설</summary>

**C**. **IP 레벨은 가능한 모든 것을, Top 레벨은 실제로 일어나는 것을** 본다. Top에서만 관측 가능한 것은 통합 지점, 초기화 순서, 클럭/리셋, 시스템 레벨 시나리오다.

A는 중복이 곧 신뢰가 아니고 시뮬레이션 자원만 소모한다. B는 위험하다 — **관측 가능성** 때문이다. IP 레벨 환경은 주변을 모델로 대체하므로 실제 주변 IP와의 상호작용은 원리적으로 관측되지 않는다. D는 판단 기준이 아니라 자원 배분 이야기다.

</details>

## Q5. (Apply)

검증 환경의 구성값을 **세 종류**로 나누고, 각각의 관리 방법과 "섞으면 생기는 문제"를 설명하라.

<details>
<summary>정답 / 해설</summary>

| 종류 | 예 | 관리 |
|---|---|---|
| **구조 구성값** | 채널 수, 데이터 폭, 스택 단수 | 파라미터 / build config (빌드 시 고정) |
| **프로파일 구성값** | 동작 모드, 속도 등급, 기능 on/off | 설정 프로파일 객체 (테스트 시작 시) |
| **시나리오 구성값** | 주입 에러 종류, 트래픽 비율 | 시퀀스 인자 (런타임) |

**섞으면**: ⓐ 구조 값을 런타임에 바꾸려는 시도가 생기고, ⓑ 프로파일 조합이 폭발하며, ⓒ 어떤 테스트가 어떤 설정에서 돌았는지 회귀 결과에서 추적할 수 없게 된다.

가산점 개념 — **프로파일 독립성**: 체커는 어떤 프로파일에서도 같은 판정을 내려야 한다. 프로파일마다 체커를 분기시키면 **그 분기가 곧 검증되지 않은 경로**가 된다.

</details>

## Q6. (Create)

"시나리오가 늘어도 코드가 선형으로 늘지 않게" Test Case를 설계하는 구조를 계층으로 그리고, **재사용 단위가 무엇인지** 밝혀라.

<details>
<summary>정답 / 해설</summary>

```
  test              ← 얇다. 환경 설정 + vseq 하나 기동
    └ virtual sequence   ← 시나리오 조립: 순서·동시성·계층 간 조정
        └ sequence       ← ★ 재사용 단위: "write burst", "error inject"
            └ sequence item  ← 의미 단위 트랜잭션
```

**재사용 단위는 테스트가 아니라 시퀀스다.** 흔한 오답은 "시나리오마다 테스트 클래스를 만든다"인데, 그러면 테스트가 수백 개로 늘고 서로 복사본이 된다. 새 시나리오는 기존 시퀀스를 **조합**하는 virtual sequence로 표현한다.

덧붙일 것 — 뒤로 밀리기 쉬운 세 부류: **오류 주입 · 설정 효과 확인 · 성능 시나리오**. 특히 "레지스터에 썼다"와 "그 설정이 동작에 반영됐다"는 다른 이야기이며, RAL write/read-back은 *접근* 확인이지 *효과* 확인이 아니다.

</details>
