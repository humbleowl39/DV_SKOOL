## Q1. (Remember)

HBM4의 Mode Register 개수와 폭, 그리고 PC와의 관계는?

<details>
<summary>정답 / 해설</summary>

**8비트 폭 20개**(`MR0`~`MR19`), `MA[4:0]`로 선택(§5).

**두 pseudo-channel에 공통**이다 — 레지스터 인스턴스가 채널당 하나다.

다만 **"공유"가 "내용이 PC 무관"을 뜻하지는 않는다.** `MR10`·`MR11`·`MR15`는 **하나의 레지스터 안에 PC0용 필드와 PC1용 필드**를 상·하위 절반으로 나눠 갖는다.

</details>

## Q2. (Understand)

리셋 직후 `MR0`의 `TCSR`이 기본값 Enabled라고 가정해도 되는가?

<details>
<summary>정답 / 해설</summary>

**안 된다.**

§5는 *"별도로 명시된 경우를 제외하면 Mode Register에 **기본 상태가 정의되지 않으며**, 전원 인가 시 또는 후속 칩 리셋 이후 **모든 Mode Register를 원하는 값으로 완전히 초기화해야 한다**"* 고 규정한다.

`MR0`의 `TCSR`에 "1 – Enabled (Default)"가 붙어 있는 것은 사실이지만, 그것은 **권장/기본 설정값**이라는 의미이지 **리셋 후 하드웨어가 그 값을 갖는다는 보장이 아니다.**

**검증 결론**: 초기화 시퀀스가 **20개 MR 전부를 기록하는지가 검사 대상**이다(`cp_mr_written` bin 20개). 그리고 RAL은 **`has_reset(0)`** 으로 두어 mirror가 "0"이 아니라 **"모름"** 이 되게 한다 — `reset(0)`으로 등록하면 초기화가 빼먹은 MR을 모델이 자신 있게 0으로 예측하고 회귀가 통과한다.

</details>

## Q3. (Apply)

벤더 데이터시트가 `tRAS = 32 ns`, 동작 클럭이 `tCK = 0.4 ns`다. `MR4`(RAS)에 넣을 값은? 유효한가?

<details>
<summary>정답 / 해설</summary>

```
RU{tRAS / tCK} = RU{32 / 0.4} = RU{80} = 80 nCK
```

**그런데 `MR4`의 범위는 4~63 nCK다**(Table 14). 80은 표현할 수 없다.

이것이 뜻하는 바는 둘 중 하나다.
- 이 주파수·타이밍 조합이 해당 장치의 지원 범위를 벗어난다, 또는
- 장치가 **클럭 사이클 단위 MR 정의를 지원하지 않는** 경우에 해당해 **설정이 무시된다**(Note 2).

**검증 결론**: 자극의 MR 이미지 생성 제약에 **범위 검사가 들어가야 한다.** 산출값을 필드 폭으로 무비판적으로 잘라 넣으면 자극이 스스로 타이밍 위반을 만들고, 그 결과는 **DUT 버그처럼 보인다.** 그리고 범위 밖 값은 coverage에서 `illegal_bins`다 — "아직 안 덮은 값"이 아니라 "나오면 안 되는 값"이다.

**최악의 실수**: 산출값을 무비판적으로 필드 폭으로 자르는 것(80 → 하위 6비트 = 16). 심각한 타이밍 위반이 된다.

</details>

## Q4. (Analyze)

컨트롤러가 PC0의 WDQS 듀티만 조정하려 한다. `MR11`에 어떻게 써야 하는가?

<details>
<summary>정답 / 해설</summary>

`MR11`은 **하위 절반이 WDQS0(PC0), 상위 절반이 WDQS1(PC1)** 의 DCA 코드다. 레지스터는 하나이므로 **8비트를 통째로 쓰는 `MRS` 한 번**으로 갱신된다.

따라서 PC0만 바꾸려면 **PC1의 현재 값을 보존한 채 병합**해야 한다.

```
새 MR11 = {기존 PC1 코드, 새 PC0 코드}
```

**문제**: 기능 경로(`MRS`)로는 MR을 **되읽을 수 없다**(§5). 기존 PC1 값을 알려면
- ⓐ 컨트롤러가 자신이 쓴 값을 **섀도 카피**로 보관하거나
- ⓑ IEEE 1500 **`MODE_REGISTER_DUMP_SET`** 으로 읽어와야 한다

**검증 결론**: RAL이 **필드 단위로 쪼개져 있어야** 한다. 8비트 통짜로 두면 부분 필드 갱신을 예측할 수 없고 되읽기 대조에서 어느 필드가 틀렸는지도 알 수 없다. 기능 경로로는 되읽을 수 없으므로(§5) **모델의 섀도가 유일한 기준값**이다.

</details>

## Q5. (Evaluate)

"MR을 되읽는 경로가 기능 인터페이스에 없다"는 사실이 검증·디버그에 주는 함의는?

<details>
<summary>정답 / 해설</summary>

| 경로 | 방향 |
|---|---|
| `MRS` 커맨드 | **쓰기 전용** |
| IEEE 1500 `MODE_REGISTER_DUMP_SET` | 쓰기 + **읽기** |

컨트롤러가 `MRS`로 설정을 썼는데 장치가 다른 값을 갖고 있다면, **기능 경로만으로는 그 사실을 알아낼 방법이 없다.**

이것은 [`hbm_dv`](../../../hbm_dv/08_testcase_scenarios/)에서 말한 *"레지스터에 썼다"와 "그 설정이 동작에 반영됐다"는 다른 이야기*의 **하드웨어적 근거**다. HBM4에서는 그 확인 경로가 **아예 다른 인터페이스**에 있다.

**함의**: 설정 효과를 검증하려면 ⓐ 테스트 포트를 열어 되읽거나, ⓑ **설정이 동작에 미치는 영향을 관측**해야 한다. 후자가 진짜 "설정 효과 확인"이다.

</details>

## Q6. (Understand)

"모든 값은 선택적이나 지원되는 최소~최대 범위는 연속이어야 한다"는 규칙이 컨트롤러 설계에 주는 이점은?

<details>
<summary>정답 / 해설</summary>

장치는 정의된 전 범위를 지원할 의무가 없다. 예를 들어 `RL`을 30~50만 지원할 수 있다. **다만 그 안에 구멍이 있어서는 안 된다** — 30~40과 45~50만 지원하는 식은 금지된다(Table 11~15 각 Note 1).

**이점**: 컨트롤러는 지원 범위를 **`[min, max]` 두 값으로 표현**할 수 있다. 지원 여부를 비트맵으로 관리할 필요가 없고, 범위 검사도 두 번의 비교로 끝난다.

```systemverilog
wire in_range = (calc_value >= dev_rl_min) && (calc_value <= dev_rl_max);
```

만약 연속성 보장이 없었다면 각 값의 지원 여부를 개별 비트로 들고 다녀야 했을 것이다.

</details>
