## Q1. (Apply)

`R[9:0] = 10'b0110100010`, `C[7:0] = 8'b11000101`, `ARFU = 1`일 때 `APAR`에 실어야 할 값은?

<details>
<summary>정답 / 해설</summary>

HIGH의 개수를 센다.
```
R[9:0] = 0110100010 → 4개
C[7:0] = 11000101   → 4개
ARFU   = 1          → 1개
──────────────────────────
합계                = 9  (홀수)
```

`AERR`가 LOW가 되려면 **`APAR`을 포함한 전체 합이 짝수**여야 한다(§6.4.1). 현재 9이므로 **`APAR = 1`** 을 실어 10으로 만든다.

**확인**: `APAR = 0`을 실으면 합이 9(홀수) → `AERR` HIGH → 패리티 오류로 보고된다. **다만 커맨드는 그대로 실행된다.**

**흔한 실수**: `ARFU`를 계산에서 빼는 것. 진리표에 없어 존재를 놓치기 쉽지만 패리티 대상이다.

</details>

## Q2. (Understand) ★

패리티 오류가 발생하면 장치는 어떻게 동작하는가? 그리고 그 설계가 정당한 이유는?

<details>
<summary>정답 / 해설</summary>

**차단하지 않는다.**

> HBM4 DRAM은 command/address 패리티 오류와 **무관하게 커맨드를 실행한다.** — §6.4.1
> 오류가 발생해도 write 데이터를 차단하지 않으며 **write 트랜잭션을 배열까지 정상 완료한다.** — §6.4.2

**정당한 이유**: 차단하려면 장치가 **버스트를 중간에 멈추거나 되돌릴 수 있어야** 한다. 그런데 [07장](../../07_column_commands/)에서 본 대로 HBM4는 **버스트의 중단이나 절단이 없다.**

즉 "차단 없음"은 게으른 설계가 아니라 **버스트 모델의 일관된 귀결**이다. 대신 복구를 호스트로 올려 장치를 단순하게 유지한다.

**설계 결론**:
- `AERR`는 **상시 감시** 대상이며, 커맨드가 실행되었으므로 **뱅크 상태 모델이 오염**됐을 수 있다.
- 컨트롤러는 `DERR` 보고 시점까지 **write 데이터를 버퍼에 보관**해야 한다. 깊이는 `WL + PL + tPARDQ`.

</details>

## Q3. (Analyze)

`AERR`가 HIGH로 관측됐다. row 버스와 column 버스 중 어디에서 오류가 났는지 알 수 있는가?

<details>
<summary>정답 / 해설</summary>

**알 수 없다.**

> **공통 `AERR` 출력 때문에 두 인터페이스에서 발생한 패리티 오류는 구별할 수 없다.** — §6.4.1

**대응**: 컨트롤러가 **자신이 발행한 커맨드 이력과 대조**해서 추정해야 한다. `AERR`는 오류 입력 사이클로부터 `tPARAC` 후에 1 tCK 동안 HIGH이므로, 그 깊이만큼 커맨드 이력을 보관하면 의심 커맨드를 역추적할 수 있다.

**그 다음이 더 중요하다**: 커맨드가 **실행되었으므로** 해당 뱅크의 상태 모델을 신뢰할 수 없다. 안전한 복구는 그 뱅크를 **precharge해 알려진 상태로 되돌리는 것**이다.

</details>

## Q4. (Evaluate)

컨트롤러가 `MR9`의 `MD`를 비활성화했는데, 패리티 생성 로직은 여전히 `ECC` 비트를 포함해 계산하고 있다. 무슨 일이 생기며 왜 진단이 어려운가?

<details>
<summary>정답 / 해설</summary>

**정상 데이터에서 패리티 오류가 발생한다.**

`MD`가 비활성이면 장치는 **`ECC` I/O를 패리티 검사에서 제외**한다(Table 47). 컨트롤러가 여전히 `ECC`를 넣어 `DPAR`을 계산하면, `ECC` 비트의 패리티가 홀수일 때마다 결과가 어긋나 **`DERR`가 뜬다.**

**진단이 어려운 이유**: 데이터는 실제로 멀쩡하다. write는 **정상 완료되고**(차단 없음), 나중에 읽어보면 값이 맞다. 그런데 `DERR`만 계속 뜬다. **데이터 경로를 아무리 뒤져도 원인이 안 나온다.**

**설계 결론**: 패리티 로직은 **`WDBI`·`RDBI`·`MD` 세 비트를 런타임 입력**으로 받아야 한다. 그리고 이 비트들을 바꾸는 MRS 전후로 **패리티를 잠시 비활성화**하고 `tMOD` 후 재활성화하는 편이 안전하다.

</details>

## Q5. (Understand)

`PL`(Parity Latency)이 존재하는 이유와 그 대가는?

<details>
<summary>정답 / 해설</summary>

**이유**: 패리티를 데이터와 동시에 보내지 않고 **`PL` 사이클 뒤로 미루면**, 송신 측은 데이터를 다 내보낸 뒤 패리티를 계산할 여유가 생기고 수신 측도 마찬가지다. 고속 인터페이스에서 **계산 지연을 흡수하는** 전형적 기법이다.

**대가**: 데이터가 끝난 뒤에도 `DPAR`를 주고받아야 하므로 **스트로브를 더 토글해야** 한다.

> WDQS와 RDQS 스트로브는 지연된 `DPAR`를 래치하기 위해 **동일한 preamble·postamble을 갖는 추가 스트로브 사이클**을 갖는다. — §6.4.2

`PL = 2`일 때 **4개의 추가 WDQS 펄스**가 수신된다 — **짝수**다.

**설계 함의**: `PL`을 바꾸면 스트로브 시퀀스 길이가 바뀐다. 컨트롤러의 스트로브 시퀀서는 `PL`을 파라미터로 받아야 하고, [05장](../../05_clocking_dbi/)의 **짝수 불변식 검사에도 `PL`을 반영**해야 한다.

</details>

## Q6. (Remember)

`CAPAR`·`WPAR`·`RPAR`의 비활성화 금지 구간을 각각 쓰라.

<details>
<summary>정답 / 해설</summary>

| 대상 | 금지 구간 | 기준점 |
|---|---|---|
| `CAPAR` | **`tPARAC`** 이내 | access 커맨드 |
| `WPAR` | **`WL + PL + tPARDQ + 2 tCK`** 이내 | `WRITE` 커맨드 |
| `RPAR` | **`tRDMRS`** 이내 | `READ` 커맨드 |

**세 값이 모두 다르고 기준점도 다르다.** "패리티를 끈다"는 한 동작이 **세 개의 서로 다른 대기 조건**을 갖는 셈이다.

이유는 각각 진행 중인 패리티 연산과의 충돌을 피하기 위해서다 — `WPAR`의 구간이 가장 긴 것은 write 데이터와 지연된 `DPAR`가 모두 소비될 때까지 기다려야 하기 때문이다.

</details>
