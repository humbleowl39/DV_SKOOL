- **Evaluate** 표준 HBM과 Custom HBM(cHBM)이 검증 범위와 필요 역량을 어떻게 다르게 만드는지 판단할 수 있다.

## 1. Why care? — 같은 "HBM 검증"인데 할 일이 전혀 다르다

두 명의 검증 엔지니어가 각각 프로젝트에 투입됩니다. 둘 다 직무 기술서에는 "HBM 검증"이라고 적혀 있습니다.

- **A**: 기존 HBM3 프로젝트의 테스트벤치를 **HBM3E로 이관**하는 일
- **B**: **Custom HBM4의 base die**를 검증하는 일

A는 2주 만에 회귀 테스트를 돌리기 시작합니다. 기존 환경 대부분이 그대로 동작했고, 트레이닝 관련 파라미터와 타이밍 마진 몇 가지만 조정하면 됐습니다.

B는 두 달이 지나도 회귀를 못 돌립니다. 검증해야 할 대상 안에 **표준 VIP가 존재하지 않는 인터페이스**가 있고, 고객 요구로 들어온 IP들의 연결을 확인할 방법부터 설계해야 하며, 채널 수가 두 배가 되면서 기존 coverage 모델이 의미를 잃었기 때문입니다.

둘 다 "HBM 검증"인데 왜 이렇게 다를까요? 세대 표를 외워서는 이 질문에 답할 수 없습니다. **세대 간 변화에는 층위가 있고, 층위마다 검증에 미치는 파급이 다르기 때문**입니다. 이 챕터는 그 층위를 구분하는 법을 다룹니다.

## 2. 직관 — 세대 표를 외우는 것으로는 부족하다

### 순진한 접근 — 스펙 표를 외운다

가장 먼저 하게 되는 일은 세대별 수치를 표로 정리하는 것입니다. 속도가 얼마고 용량이 얼마인지.

**어디서 막히나?** 표만 봐서는 앞의 A와 B가 왜 다른 일을 하게 되는지 설명할 수 없습니다. 표에서 HBM3 → HBM3E는 "6.4 → 9.6 Gb/s"이고 HBM3E → HBM4는 "1024 → 2048-bit"입니다. 둘 다 숫자가 커진 것으로 보입니다. 그런데 실무 난이도는 자릿수 단위로 다릅니다.

### 개선 시도 — 두 레버로 분류한다

Ch01에서 얻은 도구를 씁니다. 대역폭은 폭과 속도 두 레버에서 나오므로, 각 세대가 **어느 레버를 당겼는지**로 분류해 봅니다.

- **속도를 당긴 세대**: HBM2 → 2E, HBM3 → 3E
- **폭을 당긴 세대**: HBM2 → HBM3(채널 재분할), HBM3E → HBM4(1024 → 2048-bit)

훨씬 나아졌습니다. 속도만 오르면 인터페이스 구조가 그대로이므로 테스트벤치 골격이 유지되고, 폭이 바뀌면 채널 구성이 달라져 검증 축을 다시 짜야 한다는 것이 보입니다.

**그런데 여전히 부족합니다.** 이 분류로는 B의 두 달을 설명하지 못합니다. 폭이 두 배가 된 것만으로는 "표준 VIP가 없는 인터페이스"가 왜 생겼는지 알 수 없기 때문입니다.

### 일반화 — 변화에는 세 층위가 있다

빠진 것은 **무엇으로 만드는가**의 변화입니다. HBM4 세대에서 base die는 DRAM 공정을 떠나 **로직 공정**으로 이동합니다. 로직 공정에서는 트랜지스터 밀도가 달라 훨씬 많은 회로를 넣을 수 있고, 그러자 메모리 컨트롤러·전력 관리·ECC, 나아가 **고객 전용 회로**까지 스택 안으로 들어오기 시작했습니다. B가 마주한 "표준 VIP가 없는 인터페이스"는 여기서 나온 것입니다.

정리하면 세대 변화는 세 층위로 나뉩니다.

```d2
direction: down

L1: "① 전기적 변화\nper-pin 속도 상승\n예: HBM3 → HBM3E (6.4 → 9.6 Gb/s)" {
  style.fill: "#e8f5e9"
  impact: "검증 영향: 낮음\nPHY 트레이닝 파라미터 · 타이밍 마진 조정\nTB 골격 재사용 가능"
}

L2: "② 구조적 변화\n버스 폭 · 채널 수 변경\n예: HBM3E → HBM4 (1024 → 2048-bit, 16 → 32ch)" {
  style.fill: "#fff8e1"
  impact: "검증 영향: 중간\n주소맵 · coverage 축 · 동시성 모델 재설계\nTB 골격은 유지, 설정과 모델은 재작업"
}

L3: "③ 공정 · 아키텍처 변화\nBase Die가 DRAM 공정 → 로직 공정\n예: HBM4 이후, Custom HBM" {
  style.fill: "#ffebee"
  impact: "검증 영향: 높음\n검증 대상 자체가 SoC로 전환\n표준 VIP 부재 · Custom Agent 필요"
}

L1 -> L2 -> L3: "층위가 올라갈수록\n재사용 가능 범위가 줄어든다"
```

**정의.** 세대를 읽는다는 것은 숫자를 외우는 것이 아니라, **그 변화가 세 층위 중 어디에 해당하는지 판정하는 것**입니다. 그 판정이 곧 "이번 프로젝트에서 테스트벤치를 얼마나 재사용할 수 있는가"의 답입니다.

## 3. 작은 예 — 세대 표를 읽되, 산술로 검산하며 읽기

이제 표를 봅니다. 다만 그냥 받아 적지 않고 Ch01의 산식으로 검산하면서 읽습니다.

| 세대 | 표준 | per-pin | 총 폭 | 채널 구성 | per-stack BW | 대표 용량 |
|---|---|---|---|---|---|---|
| HBM1 | JESD235 | ~1 Gb/s | 1024 bit | 8 ch × 128-bit | ~128 GB/s | 1 GB (4-high) |
| HBM2 | JESD235 계열 | 2.0 / 2.4 Gb/s | 1024 bit | 8 ch × 128-bit | 256 / 307 GB/s | 8 GB |
| HBM2E | (2020 정식화) | 3.6 Gb/s | 1024 bit | 8 ch × 128-bit | ~461 GB/s *추론(산술)* | 16 GB |
| **HBM3** | **JESD238** (2022-01) | 6.4 Gb/s | 1024 bit | **16 ch × 64-bit / 32 pc** | 최대 819 GB/s | 16 GB |
| HBM3E | JESD238 계열 | 9.2~9.8 (최대 12.4) | 1024 bit | 16 ch × 64-bit / 32 pc | 1.2 TB/s 이상 | 24 GB (8H×3) / 36 GB (12H×3) |
| **HBM4** | **JESD270-4** (2025-04) | 최대 8 Gb/s | **2048 bit** | **32 ch × 2 pc** | 최대 2 TB/s | — |

표에서 층위를 읽어봅시다.

- HBM1 → HBM2 → HBM2E: 폭과 채널 구성이 **모두 그대로**, 속도만 상승 → **① 전기적 변화**
- HBM2 → HBM3: 총 폭은 1024로 같지만 **채널 구성이 8×128에서 16×64로 재분할** → **② 구조적 변화**
- HBM3 → HBM3E: 구성 그대로, 속도만 상승 → **① 전기적 변화**
- HBM3E → HBM4: 폭이 두 배, 채널 수가 두 배 → **② 구조적 변화**, 그리고 base die 공정 전환이 겹쳐 **③ 공정·아키텍처 변화**

HBM4가 유독 어려운 이유가 여기서 보입니다. ②와 ③이 **동시에** 일어난 유일한 세대입니다.

:::note[🤔 잠깐 — 표의 수치가 충돌합니다]
HBM2 행에 per-pin이 "2.0 / 2.4 Gb/s", 대역폭이 "256 / 307 GB/s"로 두 값씩 적혀 있습니다. 실제로 공개 자료마다 "HBM2는 256 GB/s"라는 서술과 "HBM2는 2.4 Gb/s"라는 서술이 섞여 나옵니다.

Ch01의 산식으로 이 충돌을 판정해 보세요. 두 값은 모순입니까, 아니면 둘 다 맞습니까?

<details>
<summary>정답 / 해설</summary>

**둘 다 맞습니다. 서로 다른 시점의 HBM2를 가리키는 것입니다.**

산식으로 검산하면:

- `1024 × 2.0 ÷ 8 = 256 GB/s` → "256 GB/s"는 **2.0 Gb/s** 기준
- `1024 × 2.4 ÷ 8 = 307.2 GB/s` → "2.4 Gb/s"는 **307 GB/s**에 대응

따라서 "HBM2 = 2.4 Gb/s = 256 GB/s"라고 **한 문장에 섞어 쓰면 틀립니다.** 실제로 그렇게 쓴 공개 자료가 존재합니다. HBM2는 초기 2.0 Gb/s로 출발해 이후 2.4 Gb/s 급 제품으로 확장되었고, 자료마다 어느 시점을 기준으로 삼았는지가 다른 것입니다.

**교훈**: 세대 표의 수치는 출처마다 다를 수 있습니다. 그럴 때 판정 기준은 권위 있는 출처가 아니라 **산술의 자기 일관성**입니다. 폭·속도·대역폭 세 값 중 둘을 알면 나머지가 정해지므로, 세 값이 동시에 주어졌을 때 서로 맞는지 반드시 확인하세요. 검증 계획의 성능 목표를 잘못된 수치로 잡으면 그 오류가 sign-off까지 따라갑니다.

</details>
:::

## 4. 일반화 — 왜 HBM4는 이 형태를 택했나

### 대안 A — HBM4가 폭 대신 속도를 택했다면?

1024-bit를 유지하고 per-pin을 16 Gb/s로 올려도 산술적으로는 2 TB/s가 나옵니다(`1024 × 16 ÷ 8 = 2048 GB/s`). 폭을 두 배로 늘리는 것보다 핀도 TSV도 적게 들므로 언뜻 유리해 보입니다.

**왜 택하지 않았나**: Ch01에서 본 에너지 문제입니다. 스택은 die가 수직으로 쌓여 열이 빠질 경로가 좁은데, per-pin 속도를 올리면 비트당 에너지가 늘어 그 열이 스택 안에 갇힙니다. 폭을 늘리는 쪽은 면적과 TSV를 더 요구하지만 전력 밀도를 악화시키지 않습니다.

**검증 관점의 함의**: 만약 속도 경로를 택했다면 검증의 무게중심이 **PHY와 트레이닝**에 쏠렸을 것입니다. 폭 경로를 택했기 때문에 무게중심이 **채널 관리 로직과 동시성**으로 옮겨갔습니다. 어느 레버를 당겼는지가 검증 인력 배치까지 바꿉니다.

### 대안 B — Base Die를 계속 DRAM 공정에 두었다면?

HBM3까지처럼 base die를 DRAM 공정으로 계속 만들 수도 있었습니다. 공정을 바꾸지 않으면 제조 흐름이 단순하고 검증도 기존 방식을 유지할 수 있습니다.

**왜 택하지 않았나**: DRAM 공정은 셀 집적에 최적화되어 있어 로직 밀도가 낮습니다. HBM4의 2048-bit PHY와 클럭 네트워크를 넣는 것만으로도 부담인데, 여기에 메모리 컨트롤러나 고객 전용 회로를 더 넣을 여지가 없습니다. 로직 공정(Samsung 4nm, TSMC 3nm 급)으로 옮기면 그 여지가 생기고, 이것이 **Custom HBM 사업 자체를 가능하게** 만듭니다.

**검증 관점의 함의**: 이 결정 하나가 직무의 성격을 바꿨습니다. base die가 로직 SoC가 되면서 검증은 "DRAM 스펙 준수 확인"에서 "**IP 통합 검증**"으로 이동했습니다. 직무 기술서가 UVM·VIP·Coverage Closure의 언어로 쓰인 이유입니다.

### 채택된 형태와 그 파생

| 결정 | 파생된 것 |
|---|---|
| 폭을 2048-bit로 두 배 | 채널 32개, PHY 규모 두 배 → 동시성 검증 축 확대 |
| Base die를 로직 공정으로 | 컨트롤러·PMU·ECC·고객 회로 통합 여지 → **Custom HBM** 성립 |
| 인터포저 원가 부담 | **SPHBM4** — 512-bit 협폭 변형으로 유기 기판 사용을 노리는 별도 표준 |

## 5. 디테일 — 세대 판정을 틀렸을 때 벌어지는 일

### 실패 1 — 층위를 구분하지 않고 테스트벤치 재사용을 약속한다

"HBM3E도 했으니 HBM4도 비슷하게 되겠지"라고 일정을 잡는 경우입니다.

**관측되는 증상**: 기존 환경이 빌드는 되지만 coverage 리포트가 이상하게 나옵니다. 채널 수가 16에서 32로 늘었는데 covergroup의 bin이 16개 기준으로 정의되어 있어, 나머지 절반의 채널은 **아예 측정되지 않은 채** coverage 100%가 보고됩니다. 측정되지 않은 영역은 "통과"로 보이므로, 이 오류는 조용히 sign-off까지 갑니다.

### 실패 2 — ③ 층위 변화를 ② 층위로 오판한다

"HBM4는 폭이 두 배인 HBM3E"라고 요약하고 검증 범위를 산정하는 경우입니다.

**관측되는 증상**: 검증 계획에 **base die 내부 IP 통합 항목이 통째로 빠집니다.** 메모리 컨트롤러가 스택 안으로 들어왔고 고객 전용 로직이 붙었는데, 계획서에는 DRAM 인터페이스 준수 항목만 있습니다. 프로젝트 중반에 "이건 누가 검증하나요"가 나오고, 그때부터 환경을 다시 설계합니다.

### 실패 3 — 표준 HBM의 계획을 Custom HBM에 그대로 적용한다

표준 HBM은 JEDEC 스펙 준수가 검증의 중심이므로 상용 VIP로 상당 부분을 덮을 수 있습니다. Custom HBM은 다릅니다.

**관측되는 증상**: "VIP를 구매하면 커버된다"고 가정하고 예산과 일정을 잡았는데, 정작 고객 요구로 들어온 인터페이스에는 **파는 VIP가 존재하지 않습니다.** 그 시점에 Custom UVM Agent를 처음부터 만들기 시작하며, 이는 직무 기술서가 *"신규 Protocol 또는 Custom IP에 대한 UVM Agent 설계·구현"* 과 *"Spec 기반 Custom UVM Agent A-to-Z 개발 경험"* 을 요구하는 이유이기도 합니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "세대가 오르면 항상 대역폭이 오른다" | 맞지만, **어느 레버로 올렸는지**가 검증에 훨씬 중요합니다 |
| "HBM3E는 HBM4의 하위 버전이다" | 다른 표준입니다. HBM3E는 JESD238 계열의 속도 확장, HBM4는 **JESD270-4**라는 별도 표준입니다 |
| "HBM4 = 폭 두 배" | 그것만 보면 ③ 층위(base die 로직 공정 전환)를 놓칩니다. 실무 난이도는 여기서 옵니다 |
| "Custom HBM은 표준 HBM에 옵션 몇 개 추가한 것" | 스택 안에 **고객 전용 로직**이 들어옵니다. 표준 VIP가 닿지 않는 영역이 생깁니다 |
| "스택 단수가 높으면 최신 세대" | 단수는 **용량** 축입니다. HBM3E도 8-high와 12-high가 공존합니다 |

## 🔍 이 구조가 만드는 검증 문제

**① 세대 판정이 곧 테스트벤치 재사용 범위 산정이다**

프로젝트 착수 시 가장 먼저 답해야 할 질문은 "이번 변화가 세 층위 중 어디인가"입니다. ①이면 파라미터 조정, ②면 coverage 모델과 주소맵 재설계, ③이면 검증 방법론 자체의 재검토가 필요합니다. 이 판정을 건너뛰면 일정 산정이 처음부터 틀립니다.

**② 채널 수 변경은 coverage 모델을 조용히 무력화한다**

16 → 32채널 변화에서 위험한 것은 테스트가 **깨지는** 것이 아니라 **깨지지 않는** 것입니다. 기존 bin 정의가 그대로 통과하면서 새 채널이 측정 대상에서 빠집니다. 세대 이관 시 coverage 모델이 새 구성을 반영하는지 확인하는 절차가 필요합니다.

**③ Custom HBM은 "표준 VIP 부재 구간"을 만든다**

표준 준수 검증은 상용 VIP로 덮이지만, 고객 전용 인터페이스는 덮이지 않습니다. 이 구간을 프로젝트 초기에 식별하지 못하면 Custom Agent 개발 공수가 계획에서 누락됩니다. **어디까지가 표준이고 어디부터가 커스텀인지 경계를 그리는 일** 자체가 검증 계획의 첫 작업입니다.

**④ 여러 세대를 하나의 환경에서 지원해야 한다**

실무에서는 HBM3E 제품과 HBM4 제품이 동시에 진행됩니다. 채널 수·폭·타이밍이 다른 구성을 하나의 테스트벤치에서 다루려면 이 값들이 **하드코딩이 아니라 설정 객체로** 분리되어 있어야 합니다. 세대별로 환경을 복사하는 방식은 유지보수 비용이 세대 수에 비례해 늘어납니다.

## 7. 핵심 정리

- 세대 변화는 세 층위로 나뉜다 — **① 전기적**(속도) / **② 구조적**(폭·채널) / **③ 공정·아키텍처**(base die 공정 전환)
- 층위가 올라갈수록 테스트벤치 재사용 범위가 줄어든다. 실무 난이도는 층위가 결정한다
- HBM4는 ②와 ③이 **동시에** 일어난 유일한 세대다 — 폭 두 배 + base die 로직 공정 전환
- 표준 번호로 구분하면: HBM1/2/2E는 JESD235 계열, HBM3/3E는 **JESD238**, HBM4는 **JESD270-4**(2025-04)
- 공개 수치가 충돌하면 권위가 아니라 **산술의 자기 일관성**으로 판정한다 (HBM2의 256 vs 307 GB/s)
- Custom HBM은 스택 안에 고객 전용 로직을 들여온다 → **표준 VIP가 닿지 않는 구간**이 생기고, 그것이 Custom UVM Agent 역량을 요구하는 직무 요건의 근거다

:::note[🤔 마무리 자가 점검]
당신의 팀은 HBM3E 프로젝트의 UVM 환경을 보유하고 있고, 다음 프로젝트로 **HBM4 표준 제품**(Custom 아님)을 맡게 되었습니다.

기존 환경에서 **가장 크게 손봐야 할 것**과 **비교적 그대로 쓸 수 있는 것**을 각각 하나씩 꼽고, 그 근거를 층위로 설명하세요.

<details>
<summary>정답 / 해설</summary>

**가장 크게 손봐야 할 것 — 채널 구성에 의존하는 모든 것 (② 구조적 변화)**

채널이 16 → 32, 폭이 1024 → 2048-bit로 바뀝니다. 따라서:

- **Coverage 모델**: 채널 인덱스 bin, 채널 간 cross가 32 기준으로 재정의되어야 합니다. 방치하면 새 채널이 측정에서 조용히 빠집니다
- **주소 맵과 설정**: 채널 수·폭이 하드코딩되어 있다면 설정 객체로 분리해야 합니다
- **동시성 시나리오**: 동시 활성 채널 수의 범위가 달라져 부하 시나리오를 다시 설계해야 합니다

**비교적 그대로 쓸 수 있는 것 — 트랜잭션 레벨 구조와 scoreboard 비교 로직**

read/write 트랜잭션의 의미와 데이터 정합성 비교 방식은 세대가 바뀌어도 유지됩니다. 채널이 몇 개든 "쓴 데이터가 그대로 읽히는가"의 검사 논리는 동일합니다. 시퀀스 라이브러리의 상당 부분도 채널 수를 파라미터로 받는 구조라면 재사용됩니다.

**주의 — 표준 제품이라 ③ 층위를 피했지만 완전히는 아니다**

문제에서 "Custom 아님"이라고 했으므로 고객 전용 IP 통합 검증은 빠집니다. 다만 HBM4는 표준 제품이라도 base die가 로직 공정으로 이동하므로, PHY 규모와 내부 구조 변화의 영향은 별도로 확인해야 합니다. **③ 층위를 완전히 피할 수 있는 것은 HBM3E까지입니다.**

</details>
