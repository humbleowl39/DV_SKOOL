## 1. Why care? — 파형에는 위반이 보이는데 테스트는 통과했다

디버깅 중 파형을 열어 봅니다. DUT가 어떤 뱅크에 activate를 낸 직후, 규정된 간격이 지나기 전에 그 뱅크로 read를 발행한 것이 보입니다. 명백한 위반입니다.

그런데 이 테스트는 **통과**했습니다. 시뮬레이션은 오류를 내지 않았고, scoreboard도 불평하지 않았으며, 회귀 결과는 초록색이었습니다.

왜 그랬을까요? Ch03에서 본 원리가 여기서 다시 작동합니다. DRAM 모델이 타이밍 제약을 검사하지 않고 요청받은 데이터를 성실히 반환했다면, **읽은 값은 기대값과 일치합니다.** scoreboard는 데이터를 비교하는 장치이므로 "값이 맞다"고 판정하고 넘어갑니다.

여기서 근본적인 구분이 하나 필요해집니다.

> **데이터는 "무엇이 저장되고 읽혔는가"이고, 프로토콜은 "무엇을 언제 어떤 순서로 보냈는가"이다.**
> 이 둘은 다른 종류의 정보이며, 데이터를 비교하는 장치로는 프로토콜을 검사할 수 없다.

이 챕터는 HBM 인터페이스에 어떤 신호와 규칙이 있는지 살펴보고, 그로부터 **무엇이 데이터 비교로 잡히고 무엇이 잡히지 않는지**를 가려냅니다. 잡히지 않는 항목의 목록이 곧 assertion이 담당해야 할 몫입니다.

## 2. 직관 — 프로토콜을 검사하는 주체는 누구여야 하는가

### 순진한 시도 1 — Scoreboard가 다 잡아 주겠지

가장 흔한 출발점입니다. 테스트벤치의 중심에 scoreboard를 두고 기대값과 실제값을 비교합니다.

**어디서 막히나?** 도입부의 상황이 정확히 그것입니다. scoreboard의 입력은 "어떤 주소에 어떤 값이 쓰였고 읽혔는가"이지, "커맨드가 규정된 간격을 지켰는가"가 아닙니다. **관측하지 않는 것은 판정할 수 없습니다.**

### 순진한 시도 2 — 모델을 엄격하게 만들어서 모델이 신고하게 하자

DRAM 모델이 타이밍 위반을 검사하고 오류를 내도록 만들면 됩니다. 실제로 좋은 모델은 이 기능을 갖추고 있습니다.

**어디서 막히나?** 세 가지가 걸립니다.

첫째, **모델은 자기가 보는 것만 검사합니다.** DRAM 모델은 자신에게 도착한 커맨드를 봅니다. 그런데 검증하고 싶은 규칙 중에는 base die 내부의 두 인터페이스 사이의 관계처럼 모델의 시야 밖에 있는 것이 있습니다.

둘째, **3rd party 모델은 고칠 수 없습니다.** 상용 모델이 어떤 규칙을 검사하지 않는다면 그 구멍은 그대로 남습니다. Ch03의 "모델 품질이 검증 신뢰도의 상한"이 여기서 반복됩니다.

셋째, **위반 시점과 원인을 추적하기 어렵습니다.** 모델이 "잘못된 데이터 요청"이라고 신고해도, 그것이 몇 사이클 전 어떤 커맨드 때문인지는 별도로 파헤쳐야 합니다.

### 일반화 — 감시자는 관측 지점에 상주해야 한다

두 시도가 놓친 것은 **검사가 일어나는 위치**입니다. 데이터 비교는 트랜잭션이 끝난 뒤 결과를 놓고 하는 사후 판정이고, 모델의 검사는 모델의 시야 안에서만 이루어집니다. 프로토콜 규칙은 **신호가 오가는 바로 그 지점에서, 매 사이클, 상시** 확인되어야 합니다.

> **정의.** 프로토콜 검사는 인터페이스에 상주하는 **별도의 감시자**가 담당한다 — 시뮬레이션 내내 규칙을 감시하다가 위반 순간에 즉시 신고하는 장치. SystemVerilog에서는 **assertion**이 이 역할을 맡는다.

그리고 그 감시자가 무엇을 감시해야 하는지는 **인터페이스의 구조에서 도출**됩니다. 다음 절에서 그 구조를 봅니다.

## 3. 작은 예 — 인터페이스를 신호 그룹으로 갈라 보기

### 신호 그룹

```d2
direction: right

HOST: "호스트 측" { style.fill: "#ffe0b2"; style.font-color: "#0A0F25" }

CA: "CA — 커맨드/주소\nrow 계열 (activate, precharge)\ncolumn 계열 (read, write)\n→ semi-independent 인터페이스 2벌" {
  style.fill: "#bbdefb"
  style.font-color: "#0A0F25"
}

CAP: "CA parity\nHBM2E: 커맨드 안에 인코딩\nHBM3: CA 버스의 별도 신호로 분리" {
  style.fill: "#ffcdd2"
  style.font-color: "#0A0F25"
}

DQ: "DQ — 데이터\n+ DBI(ac) 인코딩\n+ data bus parity" {
  style.fill: "#c8e6c9"
  style.font-color: "#0A0F25"
}

CLK: "클럭 / 스트로브\nCK_t/CK_c · WDQS · RDQS\n데이터 정렬 기준" { style.fill: "#e1bee7"; style.font-color: "#0A0F25" }

META: "메타데이터 (HBM4)\nECC 4 · SEV 4\n오류 심각도를 데이터와 함께 전송" { style.fill: "#fff9c4"; style.font-color: "#0A0F25" }

ERR: "에러 출력 (HBM4)\nAERR 1 · DERR 2\n장치 → 호스트 역방향 보고" { style.fill: "#ffe0b2"; style.font-color: "#0A0F25" }

RED: "여분 레인 (HBM4)\nRD[3:0] · 여분 주소 1\nlane repair 대상" { style.fill: "#d7ccc8"; style.font-color: "#0A0F25" }

BASE: "Base Die\n(DUT)" { style.fill: "#90caf9"; style.font-color: "#0A0F25" }

HOST -> CA -> BASE
HOST -> CAP -> BASE
HOST -> DQ: "양방향"
DQ -> BASE
META -> BASE: "양방향"
BASE -> ERR: "역방향"
RED -> BASE
HOST -> CLK -> BASE
```

각 그룹이 나르는 것과, 검증에서 무엇이 문제가 되는지 정리합니다.

**① CA — 커맨드와 주소**

HBM은 row 계열 커맨드와 column 계열 커맨드의 **주소 핀이 분리**되어 있고, HBM3에서는 여기서 더 나아가 row 커맨드 인터페이스와 column 커맨드 인터페이스를 각각 제공합니다. 덕분에 어떤 뱅크를 activate하면서 동시에 다른 뱅크에서 read를 진행할 수 있습니다.

규격이 쓰는 정확한 용어는 **semi-independent**입니다 (JESD270-4 §2 Features, §3.1.3). "독립"이라고 하면 서로 제약이 없다는 뜻이 되어 버리는데, 실제로는 **발행 경로만 둘이고 뱅크 상태는 하나**입니다. 이 절 전체가 다루는 순서 제약이 곧 *semi-* 가 가리키는 내용입니다.

Ch04에서 확인한 대로 이 CA 버스는 **같은 채널의 두 pseudo-channel이 공유**합니다. 즉 CA 위에서는 두 가지 종류의 동시성이 겹칩니다 — row/column 흐름의 병렬 진행, 그리고 pseudo-channel 간의 버스 공유.

**② CA parity — 세대 간 변화가 일어난 지점**

커맨드가 전송 중 손상되었는지 확인하는 수단입니다. 여기에 세대 간 구조 변화가 있습니다.

| 세대 | 방식 |
|---|---|
| HBM2E | parity가 **커맨드 안에 인코딩**됨 |
| HBM3 | parity가 **CA 버스의 별도 신호**로 분리됨 |

이 변화는 Ch02의 분류로 보면 ① 전기적 변화가 아니라 **구조적 변화**입니다. 신호가 별도로 분리되면 그 신호와 커맨드 사이의 타이밍 관계가 새로 생기고, 기존에 커맨드 디코딩과 함께 처리하던 검사 로직의 위치가 달라집니다. **세대를 이관할 때 parity 관련 체커를 재작성해야 하는 이유**입니다.

**③ DQ — 데이터, DBI, data parity**

데이터 버스에는 두 가지 부가 기능이 함께 옵니다. **DBI(ac)** 는 동시에 전환하는 비트 수를 줄이기 위해 데이터를 조건부로 반전시켜 보내는 인코딩이고, **data bus parity**는 데이터의 전송 오류를 검출합니다. 둘 다 HBM2E에서 HBM3로 계승되었습니다.

**④ 클럭과 스트로브**

데이터가 어느 시점을 기준으로 유효한지를 정하는 신호입니다. 상세한 전기적 특성은 본 코스 범위 밖이지만, **정렬(alignment)이 어긋나면 데이터가 깨진다**는 사실과 그것을 맞추는 과정이 트레이닝이라는 점은 알아둘 필요가 있습니다.

**⑤ 그리고 HBM4가 추가한 세 갈래**

위 네 그룹만 보면 HBM3까지의 그림입니다. HBM4의 채널당 신호를 실제로 세어 보면(JESD270-4 §3.1.1 Table 1, **채널당 120 마이크로범프**) 성격이 다른 세 갈래가 더 있습니다.

| 그룹 | 신호 | 개수 | 무엇이 새로운가 |
|---|---|---|---|
| **메타데이터** | `ECC`, `SEV` | 4 + 4 | 데이터와 **함께** 오류 정보가 흐른다 (PC당 2개씩) |
| **에러 출력** | `AERR`, `DERR` | 1 + 2 | 장치가 호스트로 **역방향** 보고한다 |
| **여분 레인** | `RD[3:0]`, 여분 주소 | 4 + 1 | 고장난 레인을 대체하는 **예비 배선** |

세 갈래가 각각 다른 것을 말해 줍니다.

- **`SEV`(severity)** 는 read 데이터와 함께 **오류 심각도**를 실어 보냅니다. 즉 "데이터가 왔다"와 별개로 "그 데이터가 정정된 것인지"가 인터페이스에 드러납니다 → Ch06과 [`hbm_dv` Ch11](../../hbm_dv/11_dft_ras/)의 주제
- **`AERR`/`DERR`** 는 방향이 반대입니다. 지금까지 본 신호는 전부 호스트 → 장치였는데, 이 둘은 **장치 → 호스트**입니다. parity 오류를 검출한 장치가 그 사실을 되돌려 알리는 경로입니다
- **여분 레인**은 신호선 자체가 **교체 가능한 자원**이라는 뜻입니다. 어느 레인이 실제로 쓰이는지가 부팅 시점에 정해지므로, 테스트벤치의 신호 매핑이 고정이 아닐 수 있습니다

:::tip[검증 관점에서 이것이 왜 큰가]
**관측점이 규격에 핀으로 박혀 있다**는 뜻입니다.

지금까지 이 챕터의 논지는 *"프로토콜은 데이터 비교로 안 잡히니 assertion이라는 감시자를 따로 두어야 한다"* 였습니다. 그런데 HBM4는 그 감시 결과의 일부를 **장치가 직접 핀으로 내보냅니다.**

이것이 검증을 쉽게 만들어 주는 것은 아닙니다. 오히려 검증 항목이 **하나 늘어납니다** — 이제 "장치가 오류를 올바르게 검출했는가"뿐 아니라 **"검출한 것을 올바른 핀에 올바른 타이밍으로 실었는가"** 까지 확인해야 합니다. 보고 경로가 생기면 그 보고 경로 자체가 검증 대상입니다.
:::

### 버스트 — 한 번의 전송 단위

읽기/쓰기는 한 비트씩이 아니라 여러 사이클에 걸친 묶음으로 이루어집니다. HBM2의 pseudo-channel 모드에서는 64-bit 세그먼트 위에서 **4 사이클에 걸쳐 256비트**를 전송합니다.

:::note[🤔 잠깐 — 유도해 보세요]
HBM2의 pseudo-channel은 64-bit이고, 버스트로 한 번에 **256비트**(= 32바이트)를 전송합니다.

Ch04에서 확인했듯 HBM3의 pseudo-channel은 **32-bit**로 절반이 되었습니다. 만약 **한 번의 접근으로 옮기는 양(32바이트)을 그대로 유지**하려 한다면, 버스트는 몇 사이클이어야 합니까?

그리고 이 값이 **검증에서 왜 중요합니까?**

<details>
<summary>정답 / 해설</summary>

**8 사이클** — `256 bit ÷ 32 bit = 8`

폭이 절반이 되었으므로 같은 양을 옮기려면 사이클 수가 두 배여야 합니다.

**왜 중요한가 — 세 가지**

1. **접근 단위(access granularity)는 시스템 설계의 계약입니다.** 캐시 라인 크기나 메모리 컨트롤러의 전송 단위와 맞물려 있어 함부로 바꿀 수 없습니다. 폭이 바뀌어도 이 단위를 유지하려는 압력이 존재합니다
2. **버스트 길이는 타이밍 규칙의 기준입니다.** "이 전송이 끝나기 전에 다음 커맨드를 내면 안 된다" 같은 규칙이 버스트 길이에 의존하므로, 이 값을 잘못 알면 assertion 자체가 틀리게 작성됩니다
3. **세대마다 달라질 수 있는 값입니다.** 따라서 테스트벤치에서 **상수가 아니라 설정값**이어야 합니다 — Ch02·Ch03·Ch04에서 반복된 파라미터화 요구가 여기서도 나타납니다

**원문 확인 결과 — 가정이 맞았습니다.** 위 계산은 "접근 단위를 유지한다면"이라는 가정 위에서 나온 값이었는데, JESD270-4가 이를 직접 규정합니다 — §2 Features가 **`BL = 8`** 과 *"메모리 read/write 접근당 **256 bit prefetch**"* 를 명시합니다. PC 폭 32-bit이므로 `256 ÷ 32 = 8`, 접근 단위 32바이트가 그대로 유지됐습니다.

**그래도 유도와 확인은 별개입니다.** 여기서는 가정이 맞았지만, 맞았다는 것은 **확인한 뒤에야** 알 수 있는 사실입니다. 게다가 규격은 read 버스트와 write 버스트 각각에 대해 *"버스트의 **중단(interruption)도 절단(truncation)도 없다**"* 고 못 박는데(§6.3.3, §6.3.4), 이런 단서는 산술로는 절대 유도되지 않습니다 — **버스트를 중간에 끊는 시나리오가 애초에 유효하지 않다**는 뜻이고, 이는 곧 그런 자극을 만드는 테스트가 규격 위반 자극이라는 판정입니다. **값은 유도할 수 있어도 그 값에 붙은 조건은 원문에만 있습니다.**

</details>
:::

### Mode register와 저전력 모드

인터페이스에는 데이터를 나르는 신호 외에 **동작 방식을 바꾸는 설정**이 있습니다. mode register에 값을 쓰면 이후의 동작이 달라집니다 — 지연 파라미터, 기능의 켜짐/꺼짐 등이 여기에 속합니다.

또한 유휴 상태에서 전력을 줄이는 저전력 모드와, self-refresh처럼 DRAM이 스스로 데이터를 유지하는 상태가 존재합니다. 이들은 **상태 전이**를 갖습니다 — 진입 조건, 진입 중 허용되는 커맨드, 복귀 절차, 복귀 후 유효해지기까지의 시간.

검증 관점에서 이 두 가지는 성격이 다릅니다. mode register는 **설정 공간**을 만들고(조합이 늘어남), 저전력 모드는 **상태 기계**를 만듭니다(전이 경로가 늘어남). 둘 다 데이터 비교로는 전혀 확인되지 않습니다.

### 감시 대상 분류표 — 이 챕터의 산출물

| 검사 항목 | 성격 | 데이터 비교로 잡히나 | 필요한 수단 |
|---|---|---|---|
| 커맨드 간 타이밍 간격 | 타이밍 규칙 | ❌ | assertion |
| row/column 흐름 간 순서 | 순서 규칙 | ❌ | assertion |
| pseudo-channel 간 CA 중재 | 경합 규칙 | ❌ | assertion |
| CA parity 검출·보고 | 에러 처리 | ❌ | **에러 주입** + `AERR` 관측 |
| data parity 검출·보고 | 에러 처리 | ❌ | **에러 주입** + `DERR` 관측 |
| **에러 보고 핀의 타이밍** | 보고 경로 | ❌ | **에러 주입** + assertion (HBM4) |
| **`SEV` 심각도 인코딩** | 메타데이터 | ❌ | **에러 주입** + 버스트 위치별 확인 (HBM4) |
| DBI 인코딩 정확성 | 데이터 변환 | △ 간접적 | 인코딩 재현 비교 |
| 버스트 길이·정렬 | 전송 단위 | △ 부분적 | assertion + scoreboard |
| Mode register 반영 | 설정 → 동작 | ❌ | 설정 후 **동작 변화 확인** |
| 저전력 상태 전이 | 상태 기계 | ❌ | FSM coverage + assertion |
| 읽은 데이터 값 | 데이터 정합성 | ✅ | scoreboard |

**표에서 ✅는 여전히 단 한 줄입니다.** 데이터 비교가 담당하는 영역은 인터페이스 검증 전체에서 작은 조각이며, 나머지는 다른 수단이 맡아야 합니다. 이것이 이 챕터의 결론입니다.

**그리고 HBM4에서 표가 줄어든 것이 아니라 늘었습니다.** `AERR`/`DERR`/`SEV`가 생기면서 "장치가 오류를 검출했는가"에 더해 **"검출 결과를 규정된 핀에 규정된 타이밍으로 실었는가"** 가 항목으로 추가됐습니다. 관측 수단이 늘어나면 그 관측 수단 자체가 검증 대상이 됩니다 — 이것은 HBM4에만 해당하는 이야기가 아니라 **RAS 기능을 추가할 때마다 반복되는 패턴**입니다.

## 4. 일반화 — 왜 이런 인터페이스 형태인가

### 대안 A — row/column 커맨드 인터페이스를 하나로 유지했다면?

커맨드 인터페이스를 하나만 두면 핀이 줄고 구조가 단순해집니다.

**왜 택하지 않았나**: 커맨드 대역폭이 병목이 되기 때문입니다. 인터페이스가 하나면 activate와 read가 **직렬화**됩니다. 뱅크를 여는 동안 다른 뱅크의 읽기를 시작할 수 없으므로, 데이터 버스가 준비되어 있어도 커맨드가 못 따라가 놀게 됩니다. Ch01에서 본 **이론 대역폭과 실효 대역폭의 간극**이 정확히 이 지점에서 벌어집니다.

**검증에 남긴 것**: 병렬 발행이 가능해진 대가로 **두 흐름 사이의 순서 제약**이 생겼습니다. "activate가 완료되기 전에 그 뱅크로 read가 나가면 안 된다" 같은 규칙은 두 인터페이스에 걸쳐 있으므로, 어느 한쪽만 보는 검사로는 확인할 수 없습니다.

### 대안 B — CA parity를 커맨드 안에 인코딩한 채로 두었다면?

HBM2E의 방식을 유지하는 선택입니다. 별도 신호가 없으니 핀이 절약됩니다.

**왜 택하지 않았나**: 커맨드 인코딩 공간을 parity가 잠식하고, 속도가 올라갈수록 커맨드를 디코딩한 뒤에야 parity를 확인할 수 있다는 구조가 부담이 됩니다. 신호를 분리하면 커맨드 해석과 무관하게 parity를 확인할 수 있습니다.

**검증에 남긴 것**: 세대 이관 시 이 부분의 검사 로직을 **재작성**해야 합니다. Ch02에서 "구조적 변화는 재설계를 요구한다"고 한 것의 구체적 사례입니다.

### 정리 — 설계의 선택이 검증 항목을 만든다

| 설계 선택 | 얻은 것 | 검증에 남긴 것 |
|---|---|---|
| row/column 인터페이스 분리 | 커맨드 병렬 발행 → 실효 대역폭 | 두 흐름 간 순서 제약 (assertion) |
| CA 버스를 pseudo-channel이 공유 | 핀 비용 절감 | 중재·경합 규칙 (assertion) |
| CA parity를 별도 신호로 | 커맨드와 무관하게 검출 | 신호-커맨드 타이밍 관계, 세대별 체커 재작성 |
| DBI · data parity | 전력·신뢰성 | 인코딩 재현, 에러 주입 시나리오 |
| Mode register | 유연한 설정 | 설정 조합 공간 |
| 저전력 모드 | 전력 절감 | 상태 전이 경로 |

Ch04에서 얻은 원리 — *"설계가 무언가를 공유하면 그 지점이 검증 포인트"* — 가 여기서 확장됩니다. **설계가 무언가를 얻으려고 복잡도를 추가하면, 그 복잡도가 그대로 검증 항목이 됩니다.**

## 5. 디테일 — 프로토콜을 안 보면 벌어지는 일

### 실패 1 — 프로토콜 위반이 데이터 비교를 통과한다

도입부의 사례입니다.

**관측되는 증상**: 시뮬레이션 전부 통과, 데이터 완전 일치, 커버리지 목표 달성. 그런데 실리콘에서 특정 조건에서만 데이터가 깨집니다. 파형을 열어 보면 위반이 명확히 보이는데, 왜 시뮬레이션이 못 잡았는지 설명하지 못합니다.

**원인**: 관측하지 않는 것은 판정할 수 없습니다. 데이터 경로만 보는 환경에서 커맨드 타이밍은 **측정 대상이 아니었던 것**이지 통과한 것이 아닙니다.

### 실패 2 — 에러 검출 기능이 한 번도 동작하지 않는다

CA parity와 data parity는 **오류가 발생했을 때** 동작하는 기능입니다. 정상 시나리오만 돌리면 이 경로는 시뮬레이션 내내 한 번도 활성화되지 않습니다.

**관측되는 증상**: 회귀가 전부 통과하고 코드 커버리지도 높게 나옵니다. 그런데 실리콘에서 실제 parity 오류가 발생했을 때 **검출 로직이 오작동**하거나, 검출은 했는데 보고 경로가 동작하지 않습니다. 검증된 적이 없는 코드였기 때문입니다.

**왜 커버리지가 못 잡나**: 코드 커버리지는 "이 줄이 실행되었는가"를 봅니다. 검출 로직이 매 사이클 평가된다면 그 줄은 실행된 것으로 집계될 수 있습니다 — **조건이 참이 된 적은 없어도** 말입니다. 그래서 에러 검출 기능은 **에러를 의도적으로 주입하는 시나리오**가 반드시 있어야 하며, 이것이 검증 계획의 독립된 항목이 되어야 합니다.

### 실패 3 — Mode register를 쓰기만 하고 효과를 확인하지 않는다

설정 레지스터에 값을 쓰는 시퀀스는 있는데, 그 설정이 실제 동작을 바꿨는지는 확인하지 않는 경우입니다.

**관측되는 증상**: 레지스터 읽기/쓰기 테스트는 통과합니다. 값을 쓰고 다시 읽으면 그 값이 나옵니다. 그런데 그 설정이 가리키는 **동작은 바뀌지 않았습니다.** 레지스터 비트는 저장되었지만 그 비트를 참조하는 로직이 연결되지 않았거나 잘못 연결되어 있어도, 읽기/쓰기 테스트는 아무 문제 없이 통과합니다.

**무엇이 필요한가**: 설정을 바꾼 뒤 **동작이 실제로 달라졌는지**를 확인하는 시나리오. 즉 "레지스터 검증"과 "설정 효과 검증"은 별개의 항목입니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "데이터가 맞으면 프로토콜도 맞다" | 데이터와 프로토콜은 다른 종류의 정보입니다. 관대한 모델 위에서는 위반이 통과합니다 |
| "모델을 엄격하게 하면 assertion은 불필요" | 모델은 **자기 시야 안**만 봅니다. 3rd party 모델은 고칠 수도 없습니다 |
| "코드 커버리지가 높으면 에러 처리도 검증됐다" | 조건이 **참이 된 적이 없어도** 그 줄은 실행된 것으로 집계될 수 있습니다 |
| "레지스터 read/write가 통과하면 설정 검증 완료" | 값이 저장되는 것과 그 값이 **동작에 반영되는 것**은 다릅니다 |
| "CA parity는 세대가 바뀌어도 같은 방식" | HBM2E는 커맨드 인코딩, HBM3는 **별도 신호**입니다. 체커를 재작성해야 합니다 |
| "버스트 길이는 외워 두면 되는 상수" | 세대·구성마다 달라질 수 있는 **설정값**입니다. 스펙에서 확인하세요 |

## 🔍 이 구조가 만드는 검증 문제

**① Assertion은 선택이 아니라 필수다**

감시 대상 분류표에서 데이터 비교(✅)가 담당하는 항목은 한 줄뿐이었습니다. 나머지 대부분은 인터페이스에 상주하는 감시자가 없으면 **측정 자체가 되지 않습니다.** 따라서 검증 환경 설계에서 assertion은 "여유가 있으면 추가하는 것"이 아니라 기본 구성요소입니다.

**② 에러 검출 기능은 에러 주입 없이 검증할 수 없다**

parity 계열 기능은 오류 상황에서만 동작하므로, 정상 시나리오를 아무리 많이 돌려도 검증되지 않습니다. **에러 주입이 시나리오 라이브러리의 독립된 축**이어야 하며, 주입 후 "검출했는가 / 올바르게 보고했는가 / 이후 동작이 규정대로인가"까지 확인해야 합니다.

**③ Mode register는 설정 공간을, 저전력 모드는 상태 공간을 만든다**

두 가지는 다른 방식으로 검증 부담을 늘립니다. 설정은 **조합**이 늘어나므로 어떤 조합을 확인할지 선별해야 하고(전수는 불가능), 상태 기계는 **전이 경로**가 늘어나므로 전이 커버리지가 필요합니다.

**④ 설정 값과 그 효과는 별개 항목이다**

레지스터 접근 검증과 설정 효과 검증을 분리해서 계획에 넣어야 합니다. 전자만 있으면 실패 3이 그대로 발생합니다.

**⑤ 세대 이관 시 프로토콜 체커의 재작성 범위를 판정해야 한다**

CA parity처럼 신호 구조가 바뀌는 항목은 체커를 다시 만들어야 합니다. Ch02에서 배운 층위 분류를 **인터페이스 항목 단위로** 다시 적용해, 어느 체커가 재사용 가능하고 어느 것이 재작성 대상인지 가려야 합니다.

## 7. 핵심 정리

- **데이터와 프로토콜은 다른 종류의 정보다** — 데이터를 비교하는 장치로 프로토콜을 검사할 수 없다
- 프로토콜 검사는 인터페이스에 **상주하는 감시자**(assertion)가 맡는다. 모델의 검사는 시야가 제한되고 3rd party는 고칠 수 없다
- 신호 그룹: **CA**(row/column 분리 — 규격 용어는 **semi-independent**, 발행 경로만 둘이고 뱅크 상태는 하나) / **CA parity**(HBM2E 인코딩 → HBM3 별도 신호) / **DQ**(+DBI, data parity) / 클럭·스트로브
- 감시 대상 분류표에서 **데이터 비교로 잡히는 항목은 한 줄뿐**이다
- 에러 검출 기능(parity)은 **에러 주입 없이는 원리적으로 검증되지 않는다** — 코드 커버리지가 높아도 마찬가지
- mode register는 **설정 조합**을, 저전력 모드는 **상태 전이 경로**를 검증 부담으로 추가한다
- 확장된 원리: *설계가 무언가를 얻으려고 복잡도를 추가하면, 그 복잡도가 그대로 검증 항목이 된다*

:::note[🤔 마무리 자가 점검]
프로젝트 리뷰에서 이런 보고가 올라왔습니다.

> "회귀 5,000 시드 전부 통과. 데이터 불일치 0건. 코드 커버리지 96%, 기능 커버리지 92%. 인터페이스 검증은 완료로 봅니다."

이 보고만으로는 **검증되었다고 말할 수 없는 항목**을 세 가지 이상 꼽고, 각각 왜 이 지표들이 그것을 보증하지 못하는지 설명하세요.

<details>
<summary>정답 / 해설</summary>

**① 커맨드 타이밍·순서 규칙**

데이터 불일치 0건은 프로토콜 준수를 뜻하지 않습니다. 모델이 관대하면 위반해도 올바른 데이터가 돌아옵니다. **assertion이 환경에 있었는지, 그것이 실제로 평가되었는지**가 확인되지 않으면 이 항목은 미검증입니다.

**② CA parity / data parity 검출 경로**

에러가 주입된 적이 없다면 검출 로직은 한 번도 참이 된 적이 없습니다. 코드 커버리지 96%는 이것을 보증하지 못합니다 — 평가되는 줄은 실행된 것으로 집계되기 때문입니다. **에러 주입 시나리오가 있었는지**를 따로 확인해야 합니다.

**③ Mode register 설정의 실제 효과**

레지스터 읽기/쓰기가 통과해도 그 설정이 동작에 반영되는지는 별개입니다. 설정을 바꾼 뒤 **동작 변화를 관측한 시나리오**가 있었는지 확인이 필요합니다.

**④ 저전력 모드의 상태 전이** (추가로 꼽을 수 있는 것)

진입·복귀 경로와 그 사이의 규칙은 전이 커버리지로 측정해야 하며, 기능 커버리지 92%라는 총계로는 이 항목이 포함되었는지 알 수 없습니다.

**⑤ 동시성** (Ch04 연계)

5,000 시드가 전부 순차 시나리오였다면 채널·pseudo-channel 동시 활성 상황은 여전히 미검증입니다.

**리뷰어가 던져야 할 질문**

"커버리지 92%"라는 숫자보다 중요한 것은 **커버리지 모델에 무엇이 들어 있는가**입니다. 모델에 없는 항목은 아무리 많은 시드를 돌려도 0%로 잡히는 것이 아니라 **아예 집계되지 않습니다**. 따라서 리뷰의 초점은 "몇 %인가"가 아니라 **"이 표에 있어야 할 항목이 모델에 들어 있는가"** 여야 합니다.

</details>
:::
