## 1. Why care? — 파일 목록에 DRAM 셀이 없다

HBM 검증 프로젝트에 처음 투입된 엔지니어가 소스 파일 목록을 받습니다. "HBM을 검증한다"고 들었으니 DRAM 셀 어레이나 sense amplifier 관련 코드를 예상합니다. 그런데 목록에는 그런 것이 없습니다. 대신 이런 것들이 있습니다.

- 채널별 커맨드를 받아 처리하는 컨트롤 로직
- 호스트 인터페이스 관련 블록
- 테스트·리페어 제어 블록
- PHY 관련 모듈 — 그런데 일부는 RTL이 아니라 다른 형식

그리고 DRAM 셀 어레이가 있어야 할 자리에는 **`model`이라는 이름이 붙은 파일**이 하나 놓여 있습니다.

여기서 던져야 할 질문은 "DRAM 코드는 어디 있나요?"가 아닙니다. **"내가 검증할 코드는 이 스택의 어디에 있고, 나머지는 왜 모델로 대체되어 있나?"** 입니다. 이 질문에 답하지 못하면 다음 두 가지가 동시에 벌어집니다. 검증하지 않아도 될 것을 검증하느라 시간을 쓰고, 정작 검증해야 할 것을 놓칩니다.

이 챕터는 그 경계를 확정합니다. 이후의 모든 챕터, 그리고 후속 토픽 [HBM 검증 실무](../../hbm_dv/)의 모든 내용이 여기서 그은 선 위에서 전개됩니다.

## 2. 직관 — DUT 경계는 어디에 그어지는가

### 순진한 시도 1 — "HBM 스택 전체가 DUT다"

가장 자연스러운 출발점입니다. 검증 대상 제품이 HBM이니 HBM 전체를 시뮬레이션하면 될 것 같습니다.

**어디서 막히나?** 스택의 대부분을 차지하는 **Core die**(DRAM die)는 셀 어레이와 그 주변 아날로그 회로로 이루어져 있고, DRAM 전용 공정의 커스텀 회로로 구현됩니다. 이것은 RTL로 기술된 디지털 로직이 아닙니다. 논리 시뮬레이터에 넣을 수 있는 형태가 아니며, 억지로 넣는다 해도 셀 하나하나의 전기적 동작을 논리 시뮬레이션으로 재현하는 것은 의미가 없습니다.

게다가 스택 하나에 core die가 8장, 12장씩 들어갑니다. 설령 가능하다 해도 시뮬레이션 시간이 감당되지 않습니다.

### 순진한 시도 2 — "그럼 Base die 전체가 DUT다"

Core die를 제외하면 남는 것은 스택 최하단의 **Base die**입니다. 여기에 제어 로직이 있으니 이것이 DUT라고 보는 것은 큰 진전입니다. 절반은 맞습니다.

**어디서 막히나?** Base die 안도 균질하지 않습니다. 커맨드를 해석하고 스케줄링하는 **디지털 로직**이 있는가 하면, 호스트와 신호를 주고받는 **PHY**처럼 아날로그 회로와 디지털 로직이 섞인 영역이 있고, 전력 관리처럼 상당 부분이 아날로그인 블록도 있습니다. 이들을 하나의 방법으로 검증할 수 없습니다. 순수 디지털 시뮬레이션으로 다룰 수 있는 것과 그렇지 않은 것이 한 die 안에 공존합니다.

### 일반화 — 경계는 물리가 아니라 표현 형식이 긋는다

두 시도가 공통으로 놓친 것이 있습니다. **DUT 경계는 물리적인 die 경계를 따라 그어지지 않습니다.** 실제로 경계를 긋는 기준은 이것입니다.

> **DUT = RTL로 기술되어 논리 시뮬레이션으로 동작을 확인할 수 있는 영역**
>
> 그 경계 바깥은 **모델로 대체**된다 — 실물의 동작을 흉내 내되 검증 대상은 아닌 코드로.

이 관점에서 보면 검증 환경의 구성이 명확해집니다.

- **안쪽(DUT)**: base die의 디지털 IP, 그리고 mixed IP의 디지털 부분
- **바깥쪽(모델)**: DRAM core die → **DRAM behavioral model**, 호스트 프로세서 → **VIP/BFM**
- **경계 위(mixed)**: PHY처럼 아날로그와 디지털이 섞인 영역 → **mixed-level 검증**이라는 별도 방법 필요
- **범위 밖**: 인터포저·기판의 전기적 특성 → 신호 무결성/전력 무결성 해석의 영역

여기서 중요한 귀결이 하나 나옵니다. **모델은 검증 대상이 아니지만, 검증 신뢰도의 상한을 결정합니다.** DRAM 모델이 실제 DRAM보다 관대하게 동작하면, DUT가 규칙을 어겨도 모델이 받아주므로 테스트는 통과합니다. 이 문제는 뒤에서 다시 다룹니다.

## 3. 작은 예 — 스택을 잘라서 보기

### 물리적 구조

```d2
direction: up

substrate: "패키지 기판 (organic substrate)" {
  style.fill: "#eceff1"
  style.font-color: "#0A0F25"
}

interposer: "실리콘 인터포저 (2.5D)\nHBM 스택과 호스트를 µm 거리로 연결" {
  style.fill: "#e0e0e0"
  style.font-color: "#0A0F25"
}

base: "Base Die (Logic Die)\n채널별 read/write 관리 · refresh 주기 · 트레이닝\nprecharge/activate 발행 · 호스트 인터페이스" {
  style.fill: "#bbdefb"
  style.font-color: "#0A0F25"
}

core0: "Core Die 0 (DRAM)" { style.fill: "#f5f5f5"; style.font-color: "#0A0F25" }
core1: "Core Die 1 (DRAM)" { style.fill: "#f5f5f5"; style.font-color: "#0A0F25" }
coreN: "… Core Die N-1 (8-high / 12-high)" { style.fill: "#f5f5f5"; style.font-color: "#0A0F25" }

host: "호스트 (GPU / ASIC)" { style.fill: "#ffe0b2"; style.font-color: "#0A0F25" }

substrate -> interposer
interposer -> base: "µbump"
base -> core0: "TSV (직경 10~20 µm)"
core0 -> core1: "TSV + µbump (pitch ~40 µm)"
core1 -> coreN: "TSV"
interposer -> host: "인터포저 배선"
```

각 요소를 정리하면:

| 요소 | 무엇인가 | 왜 있는가 |
|---|---|---|
| **Core die** | DRAM die. 셀 어레이와 뱅크 | 실제 데이터가 저장되는 곳. 8-high, 12-high 등 단수가 **용량**을 결정 |
| **Base die** | 스택 최하단의 로직 die | 채널별 read/write 관리, refresh 주기 운영, 트레이닝, 호스트 인터페이스 |
| **TSV** | 실리콘을 수직 관통하는 배선 (직경 10~20 µm) | die를 쌓고도 짧은 배선으로 연결하기 위한 수단 — Ch01의 "폭은 넓게, 배선은 짧게" |
| **Microbump** | die 사이를 접합하는 미세 범프 (pitch ~40 µm) | 물리적·전기적 접합. 최근 Cu-Cu 직접 접합(하이브리드 본딩)으로 전환 진행 중 |
| **인터포저** | HBM 스택과 호스트를 나란히 얹는 실리콘 기판 | 두 칩을 µm 거리로 잇는 2.5D 구성의 핵심 |

### 검증 환경에서의 구조 — 같은 스택, 다른 시선

같은 그림을 검증 엔지니어의 시선으로 다시 그리면 이렇게 됩니다.

```d2
direction: right

TB: "테스트벤치 (UVM)" {
  style.fill: "#f3e5f5"
  style.font-color: "#0A0F25"
  vip: "Host VIP / BFM\n호스트를 흉내 내어 커맨드 발행"
  model: "DRAM Behavioral Model\ncore die를 흉내 내어 응답"
  sb: "Scoreboard · Coverage · SVA"
}

DUT: "DUT — 검증 대상" {
  style.fill: "#bbdefb"
  style.font-color: "#0A0F25"
  dig: "Base die Digital IP\n(RTL — 순수 디지털 시뮬레이션)"
  mix: "Base die Mixed IP\n(PHY 등 — mixed-level 검증)"
}

OUT: "범위 밖" {
  style.fill: "#eceff1"
  style.font-color: "#0A0F25"
  phys: "인터포저 · 기판 전기 특성\nTSV 전기 특성 · 열 특성\n→ SI/PI · 패키지 해석 영역"
}

TB -> DUT: "자극 인가"
DUT -> TB: "응답 관측"
DUT -> OUT: "여기서부터는\n다른 도구의 몫"
```

**핵심 매핑표** — 이 표가 이 챕터의 산출물입니다.

| 스택 구성요소 | 물리적 실체 | 검증 환경에서의 취급 |
|---|---|---|
| Core die 셀 어레이 | DRAM 공정 아날로그 | **DRAM behavioral model** (DUT 아님) |
| Core die 주변 회로 | DRAM 공정 커스텀 | 모델에 포함되거나 별도 방법으로 검증 |
| TSV / µbump | 물리 배선 | 논리적 **연결성**은 모델이 반영, **전기 특성**은 범위 밖 |
| **Base die — Digital IP** | **RTL** | ⭐ **DUT — 여기가 본진** |
| **Base die — Mixed IP (PHY 등)** | schematic + RTL | ⭐ **DUT — 단, mixed-level 검증 필요** |
| 인터포저 · 기판 | 패키지 | 범위 밖 (SI/PI 해석) |
| 호스트 프로세서 | 상대편 칩 | **VIP / BFM으로 대체** |

:::note[🤔 잠깐 — 경계를 직접 그어보세요]
어떤 팀이 "HBM 검증 환경을 구축했다"며 다음 구성을 보고했습니다.

> "DRAM behavioral model을 붙이고, base die RTL을 DUT로 놓고, 호스트 측은 직접 만든 BFM으로 커맨드를 발행합니다. 시뮬레이션이 돌고 read/write 데이터가 일치합니다."

이 구성에서 **아직 검증되지 않은 채 남아 있는 영역**은 어디입니까? 위 매핑표를 보고 답하세요.

<details>
<summary>정답 / 해설</summary>

**Base die의 Mixed IP(PHY 등)가 빠져 있습니다.**

보고된 구성은 순수 디지털 시뮬레이션입니다. 그런데 매핑표에서 DUT는 두 줄입니다 — digital IP와 **mixed IP**. PHY처럼 아날로그와 디지털이 섞인 블록은 논리 시뮬레이션만으로는 동작을 확인할 수 없습니다. 이 구성에서 PHY는 십중팔구 **디지털 동작만 흉내 내는 간이 모델**로 대체되어 있을 것이고, 그렇다면 실제 PHY의 동작은 검증되지 않은 상태입니다.

이것이 직무 기술서가 *"Analog-Digital Mixed IP … 검증"* 과 우대사항 *"Full-Chip Mixed-Level Design (Schematic & RTL) 검증"* 을 별도로 명시하는 이유입니다. 순수 디지털 검증 환경 하나로는 base die를 덮지 못합니다.

**추가로 짚을 것** — "read/write 데이터가 일치한다"는 것은 생각보다 약한 증거입니다. DRAM behavioral model이 타이밍 규칙을 느슨하게 구현했다면, DUT가 타이밍을 어겨도 모델이 데이터를 정상 반환합니다. 데이터 일치는 통과하지만 실제 실리콘에서는 깨집니다. 다음 절에서 다룹니다.

</details>
:::

## 4. 일반화 — 왜 이런 경계가 합리적인가

### 대안 A — 스택 전체를 하나의 시뮬레이션으로 다룬다면?

core die의 아날로그 회로까지 포함해 스택 전체를 통합 시뮬레이션하는 방법을 생각할 수 있습니다. 그러면 모델의 부정확성 문제가 사라집니다.

**왜 택하지 않나**: 시간 때문입니다. 아날로그 회로 시뮬레이션은 논리 시뮬레이션보다 자릿수 단위로 느립니다. 여기에 core die가 8~12장 곱해집니다. 커맨드 몇 개를 주고받는 데 며칠이 걸린다면 회귀 시험은 불가능하고, **회귀를 돌릴 수 없는 검증은 검증이 아닙니다.** 무작위 시나리오를 수천 개 돌려 coverage를 닫는 방식 자체가 성립하지 않습니다.

그래서 실무는 **계층을 나누고 각 계층에 맞는 도구를 쓰는** 쪽을 택합니다. 디지털 로직은 논리 시뮬레이션으로 빠르게 대량 검증하고, 아날로그가 섞인 경계 영역만 mixed-level로 다루며, 전기적 특성은 아예 다른 도구(SI/PI 해석)로 넘깁니다.

### 대안 B — Base die 없이 각 core die가 알아서 한다면?

제어 로직을 base die에 모으지 않고 각 core die에 분산시키는 구조도 상상할 수 있습니다.

**왜 택하지 않나**: 세 가지가 걸립니다. 첫째, 같은 로직이 die 수만큼 중복되어 면적과 전력을 낭비합니다. 둘째, 호스트와의 인터페이스를 누가 맡을지 애매해집니다 — 결국 한 die가 대표해야 하고, 그러면 그것이 base die입니다. 셋째, core die는 DRAM 공정이라 로직 밀도가 낮아 복잡한 제어 회로를 넣기에 불리합니다.

**검증 관점의 함의**: 제어가 base die에 **중앙집중**되어 있다는 사실이 검증을 가능하게 만듭니다. 검증해야 할 디지털 로직이 한 곳에 모여 있어 DUT를 하나로 정의할 수 있습니다. 만약 분산 구조였다면 die 간 협조 프로토콜까지 검증 대상이 되어 상태 공간이 훨씬 커졌을 것입니다.

:::note[규격은 base die를 요구하지 않는다]
위의 논의는 **왜 실제 제품이 base die 구조를 택하는가**에 대한 것입니다. 그런데 JEDEC 규격 자체는 그것을 **요구하지 않습니다.**

> DRAM 벤더는 스택 최하단에 신호 재분배 등의 기능을 제공하는 **선택적 인터페이스 다이를 요구하도록 선택할 수 있다.** (…) **본 표준은 그러한 해법을 명시적으로 요구하지도, 금지하지도 않는다.** — JESD270-4 §3 (요약)

규격이 정의하는 것은 호스트가 보는 **인터페이스와 동작**이고, 그것을 어떤 물리 구조로 만족시킬지는 벤더의 몫입니다. 이 사실이 두 가지를 동시에 설명합니다.

- **Custom HBM이 성립하는 이유** — base die가 규격 밖에 있으므로 벤더가 거기에 무엇이든 넣을 수 있습니다.
- **표준 검증 IP가 존재할 수 없는 이유** — 표준이 정의하지 않은 것에 대한 상용 VIP는 만들어질 수 없습니다. 그래서 [`hbm_dv`](../../hbm_dv/03_custom_uvm_agent/)에서 Custom UVM Agent를 직접 만들어야 합니다.

조문 수준의 상세는 [HBM4 JEDEC Deep-Dive Ch01](../../hbm4_jedec_dd/01_landscape_organization/)에서 다룹니다.
:::

### 그리고 Ch02와 이어지는 지점

Base die가 로직 공정으로 이동하면(② 참고: Ch02의 ③ 층위) 이 die에 들어갈 수 있는 로직의 양이 늘어납니다. 메모리 컨트롤러가 들어오고, 전력 관리가 들어오고, 고객 전용 회로가 들어옵니다. **DUT의 경계는 그대로인데 그 안의 내용물이 급격히 불어나는 것**입니다. 이것이 HBM 검증이 SoC 검증의 성격을 띠게 된 경로입니다. Ch06에서 그 내용물을 열어봅니다.

## 5. 디테일 — 경계를 잘못 그었을 때 벌어지는 일

### 실패 1 — 모델을 DUT로 착각한다

DRAM behavioral model에서 이상 동작이 관측되면 이것을 DUT 버그로 보고하는 경우입니다.

**관측되는 증상**: 디버깅 시간의 상당 부분이 엉뚱한 곳에서 소모됩니다. 파형에서 DRAM 응답이 이상하니 설계팀에 이슈를 올렸는데, 확인해 보니 모델이 특정 커맨드 조합을 지원하지 않았던 것입니다. 반대 방향의 사고도 있습니다 — DUT가 낸 이상한 커맨드를 모델이 조용히 받아주는 바람에 아무도 문제를 눈치채지 못하는 경우입니다.

**왜 생기나**: 검증 환경 안에 있는 코드가 전부 DUT라고 암묵적으로 가정하기 때문입니다. **"이 파일은 DUT인가 모델인가"** 를 구분해 두지 않으면 디버깅의 첫 단추부터 어긋납니다.

### 실패 2 — 모델이 실물보다 관대해서 통과가 통과가 아니다

이것이 스택 구조에서 오는 가장 위험한 실패입니다.

DRAM behavioral model은 실제 DRAM을 흉내 내지만 완전하지 않습니다. 예를 들어 모델이 타이밍 제약 위반을 검사하지 않고 요청받은 데이터를 성실히 반환하도록 작성되었다고 해봅시다. DUT가 규정보다 짧은 간격으로 커맨드를 발행해도 모델은 정상 응답합니다.

**관측되는 증상**: 시뮬레이션에서는 모든 테스트가 통과하고 데이터도 완벽히 일치합니다. 그런데 실제 칩에서는 특정 조건에서 데이터가 깨집니다. 시뮬레이션이 잡지 못한 이유는 **DUT가 아니라 모델이 관대했기 때문**입니다.

**핵심 원리**: **모델의 엄격함이 검증의 상한을 정합니다.** 모델이 검사하지 않는 규칙은 아무리 많은 테스트를 돌려도 검증되지 않습니다. 그래서 검증 환경 구축에서 "어떤 모델을 쓰는가"는 부차적 결정이 아니라 **신뢰도를 결정하는 1차 결정**입니다. 직무 기술서가 *"In-house VIP 개발"* 과 *"3rd Party VIP 도입 및 활용"* 을 나란히 요구하는 배경이기도 합니다.

### 실패 3 — 스택 단수와 채널 매핑을 환경에서 고정해 버린다

12-high 제품으로 환경을 만들면서 단수와 채널-die 매핑을 코드에 직접 써 넣는 경우입니다.

**관측되는 증상**: 8-high 파생 제품이 나왔을 때 환경이 동작하지 않거나, 더 나쁘게는 **동작하지만 잘못된 주소로 접근**합니다. 스택 단수는 용량과 주소 맵에 영향을 주므로, 단수를 바꾸면 어느 채널이 어느 die의 어느 영역에 대응하는지가 달라집니다. 이 매핑이 고정되어 있으면 파생 제품마다 환경을 복사하게 되고, 유지보수 비용이 제품 수에 비례해 늘어납니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "HBM 검증 = DRAM 셀·타이밍 검증" | DRAM core die는 **모델로 대체**됩니다. 검증 대상은 base die의 로직입니다 |
| "검증 환경 안의 코드는 전부 DUT다" | VIP·BFM·behavioral model은 DUT가 아니라 **DUT를 둘러싸는 장치**입니다 |
| "모델은 그냥 있으면 되는 보조물" | 모델의 엄격함이 **검증 신뢰도의 상한**입니다. 관대한 모델은 false pass를 만듭니다 |
| "Base die는 디지털이니 논리 시뮬레이션이면 충분" | base die 안에 mixed IP(PHY 등)가 있어 **mixed-level 검증**이 별도로 필요합니다 |
| "스택 단수가 높을수록 대역폭이 크다" | 단수는 **용량** 축입니다 (Ch01 마무리 문제 참고). 대역폭은 폭 × 속도 |
| "TSV는 물리 구조라 검증과 무관하다" | 전기적 특성은 범위 밖이지만, **논리적 연결성과 채널-die 매핑**은 환경이 반영해야 합니다 |

## 🔍 이 구조가 만드는 검증 문제

**① DUT 경계 확정이 검증 계획의 0번 작업이다**

검증 계획을 세우기 전에 "무엇이 DUT이고, 무엇이 모델이며, 무엇이 범위 밖인가"를 문서로 확정해야 합니다. 이 선이 흐릿하면 검증 항목이 중복되거나 누락되고, 디버깅 시 책임 소재를 판단할 수 없습니다. 이 경계 문서가 곧 V-Plan의 첫 장이 됩니다.

**② 모델 품질이 검증 신뢰도의 상한을 정한다**

DUT를 아무리 잘 검증해도 모델이 관대하면 그만큼의 구멍이 남습니다. 따라서 검증 항목에는 **DUT를 검사하는 항목뿐 아니라 모델이 충분히 엄격한지 확인하는 항목**도 필요합니다. 상용 VIP를 도입할 때 "무엇을 검사해 주는가"를 확인하는 일이 여기에 해당합니다.

**③ Mixed IP는 별도의 검증 방법을 요구한다**

base die 안에 순수 디지털로 다룰 수 없는 영역이 존재한다는 사실은, 검증 환경이 **하나가 아니라 여러 개**가 되어야 함을 뜻합니다. 디지털 회귀 환경과 mixed-level 환경이 공존하고, 각각이 다루는 범위를 명확히 나눠야 중복과 누락을 피할 수 있습니다.

**④ 호스트 측은 실물이 아니라 대체물이다**

DUT의 자극원은 실제 GPU가 아니라 VIP 또는 BFM입니다. 따라서 "실제 호스트가 이런 커맨드 순서를 낼 수 있는가"는 자동으로 보장되지 않으며, 시나리오의 현실성은 검증 엔지니어가 책임져야 합니다. 지나치게 이상적인 자극만 주면 실제 시스템에서 나타나는 문제를 재현하지 못합니다.

**⑤ 스택 구성은 설정값이어야 한다**

단수·채널 수·채널-die 매핑은 제품마다 다릅니다. 환경에 고정하지 말고 설정으로 분리해야 파생 제품을 같은 환경으로 다룰 수 있습니다. 이는 Ch02의 🔍 ④(여러 세대 동시 지원)와 같은 요구의 다른 표현입니다.

## 7. 핵심 정리

- 실제 제품의 HBM 스택 = **Core die × N** (데이터 저장) + **Base die × 1** (제어) + TSV·µbump (수직 연결) + 인터포저 (호스트와 연결)
- 단 **base die는 규격이 요구하는 것이 아니다** — JESD270-4 §3은 이를 *선택적*으로 두고 요구도 금지도 하지 않는다. 규격이 정의하는 것은 호스트가 보는 **인터페이스와 동작**이며, 물리 구조는 벤더의 몫이다. 위 구성은 **관행이지 규정이 아니다**
- **DUT 경계는 물리적 die 경계가 아니라 "RTL로 표현되는 영역"의 경계**로 그어진다
- 검증 대상: **base die의 digital IP + mixed IP**. 그 밖은 모델 대체(core die → DRAM model, 호스트 → VIP/BFM) 또는 범위 밖(인터포저·전기 특성)
- **모델은 DUT가 아니지만 검증 신뢰도의 상한을 결정한다** — 관대한 모델은 조용한 false pass를 만든다
- Mixed IP의 존재 때문에 검증 환경은 하나로 끝나지 않는다 — 디지털 회귀 환경 + mixed-level 환경
- 스택 단수는 **용량** 축이며, 단수 변경은 주소 맵과 채널-die 매핑에 영향을 준다 → 설정으로 분리할 것

:::note[🤔 마무리 자가 점검]
제품 라인업이 **HBM3E 12-high(36 GB)** 에서 **HBM3E 8-high(24 GB)** 파생으로 확장됩니다. 세대는 그대로이고 단수만 줄어듭니다.

기존 검증 환경에서 **다시 확인해야 할 항목**과 **그대로 유효한 항목**을 각각 두 가지씩 꼽고 근거를 대세요.

<details>
<summary>정답 / 해설</summary>

**다시 확인해야 할 항목**

1. **주소 맵과 채널-die 매핑** — 단수가 줄면 총 용량이 36 GB에서 24 GB로 바뀌고, 어느 주소가 어느 die로 가는지가 달라집니다. 환경에 매핑이 고정되어 있다면 잘못된 영역에 접근하면서도 오류 없이 동작할 수 있어 위험합니다
2. **용량 경계 시나리오** — 주소 범위 상한이 달라지므로, 경계 주소 접근·범위 초과 접근 시나리오를 새 용량 기준으로 다시 만들어야 합니다

(추가로 꼽을 수 있는 것: TSV 경로 길이 변화에 따른 타이밍 파라미터, 열 특성 차이 — 다만 후자는 본 코스 범위 밖입니다)

**그대로 유효한 항목**

1. **호스트 인터페이스 검증 전반** — Ch01 마무리 문제에서 확인했듯 대역폭과 인터페이스 폭은 단수와 무관합니다. 호스트가 보는 인터페이스는 base die가 제공하며 단수가 바뀌어도 동일합니다
2. **커맨드 프로토콜·데이터 정합성 검사 로직** — read/write의 의미와 scoreboard 비교 방식은 단수와 무관하게 유지됩니다

**핵심 판정 근거**

**base die가 제공하는 인터페이스는 단수에 무관하고, core die 쪽으로 향하는 매핑은 단수에 의존합니다.** 이 한 문장이 재검증 범위를 가릅니다. DUT 경계를 명확히 그어 두었다면 이 판정을 몇 분 안에 내릴 수 있고, 그렇지 않다면 전체를 다시 돌려보는 수밖에 없습니다 — 경계를 그어 두는 일의 실질적 이득이 여기서 나옵니다.

</details>
:::
