## 1. Why care? — IP 목록 옆에 적힌 "출처"

Ch03에서 파일 목록을 받았던 그 엔지니어가 이제 한 단계 위의 문서를 봅니다. Base die에 들어가는 **IP 목록**입니다. 그런데 각 항목 옆에 한 칸이 더 있습니다. **출처**입니다.

| IP | 출처 |
|---|---|
| 채널 컨트롤 로직 | in-house |
| HBM PHY | in-house |
| 표준 인터페이스 IP (PCIe 등) | 3rd party (구매) |
| 전용 가속 로직 | **고객 제공** |
| 테스트·리페어 제어 | in-house + 툴 생성 |

이 칸이 왜 있을까요? 검증 대상이라는 점에서는 다 같은데 말입니다.

같지 않습니다. **출처가 다르면 알 수 있는 것이 다르고, 알 수 있는 것이 다르면 검증 방법이 다릅니다.** in-house IP는 설계자에게 직접 물어볼 수 있고 소스를 볼 수 있습니다. 구매한 IP는 문서와 벤더 지원이 전부이며, 대신 "이미 검증되었다"는 전제가 붙습니다 — 그 전제를 어디까지 믿을지 판단해야 합니다. 고객이 준 IP는 우리 조직에 아는 사람이 없고, **그 인터페이스를 다루는 상용 검증 도구도 존재하지 않습니다.**

직무 기술서의 첫 줄이 이렇게 쓰인 이유가 여기 있습니다.

> *"HBM 내 **In-house, 3rd Party Digital IP 및 Mixed 설계**를 검증 합니다"*

세 종류를 굳이 나열한 것은 수사가 아니라 **일이 세 가지로 갈린다는 뜻**입니다. 이 챕터는 그 갈림을 정리하고, 여섯 챕터에 걸쳐 모아온 검증 문제들을 하나의 목록으로 종합합니다.

## 2. 직관 — 하나의 축으로는 IP를 정리할 수 없다

### 순진한 시도 1 — "Base die는 하나의 DUT니 하나의 검증 계획으로"

Ch03에서 DUT 경계를 base die로 확정했으니, 그 안을 하나의 대상으로 보고 검증 계획을 하나 세우는 것이 자연스러워 보입니다.

**어디서 막히나?** 계획을 쓰기 시작하면 곧 막힙니다. "이 IP의 내부 동작을 어디까지 검증할 것인가"라는 질문에 IP마다 답이 다르기 때문입니다. 소스를 볼 수 있는 IP와 볼 수 없는 IP에 같은 계획을 적용할 수 없습니다.

### 순진한 시도 2 — "기능별로 나누자"

Controller, PHY, RAS, 전력 관리, DFT처럼 기능으로 분류합니다. 훨씬 나아졌습니다. 기능이 다르면 검증 방법도 다르니 합리적입니다.

**어디서 막히나?** 기능이 같아도 할 일이 다릅니다. 같은 "인터페이스 IP"라도 우리가 만든 것이면 내부 동작까지 검증하지만, 구매한 것이면 **연결과 설정이 맞는지**가 초점입니다. 기능 축만으로는 이 차이가 드러나지 않습니다.

### 일반화 — 두 축의 교차에서 검증 접근이 정해진다

필요한 것은 두 축입니다.

- **기능 축** — 이 IP가 무엇을 하는가 (검증 **방법**을 결정: 디지털? mixed? 상태 기계?)
- **출처 축** — 누가 만들었고 우리가 무엇을 알 수 있는가 (검증 **깊이와 초점**을 결정)

```d2
direction: right

FUNC: "**기능 축**\nController · PHY · RAS\n전력 · DFT · 고객 로직\n→ 검증 *방법*을 정한다" {
  style.fill: "#bbdefb"
}

SRC: "**출처 축**\nin-house · 3rd party · 고객 제공\n→ 검증 *깊이와 초점*을 정한다" {
  style.fill: "#c8e6c9"
}

PLAN: "**검증 접근**\n무엇을 어디까지\n어떤 도구로" {
  style.fill: "#fff9c4"
}

FUNC -> PLAN
SRC -> PLAN
```

> **정의.** Base die의 검증 계획은 IP 목록이 아니라 **기능 × 출처 교차표**에서 나온다. 같은 칸에 들어가는 IP끼리는 접근을 공유할 수 있고, 다른 칸은 다른 계획이 필요하다.

## 3. 작은 예 — Base die를 열어 보기

### 기능 축 — 안에 무엇이 있는가

공개 자료들은 base die의 기능을 크게 **Controller · 전력 전달(PDN) · RAS · PHY**의 네 갈래로 정리합니다. 여기에 검증 관점에서 반드시 추가해야 할 두 가지가 더 있습니다 — **DFT/테스트 제어**, 그리고 Custom HBM의 **고객 전용 로직**입니다.

| 기능 블록 | 하는 일 | 검증 성격 |
|---|---|---|
| **Controller** | 채널별 read/write 관리, refresh 주기 운영, precharge/activate 발행, 커맨드 스케줄링 | 순수 디지털. Ch04·Ch05의 동시성·프로토콜 항목이 여기로 집중 |
| **PHY** | 호스트와의 물리 인터페이스. HBM4는 **2048-bit I/O**와 클럭 네트워크를 탑재 | **Mixed** — 순수 디지털 시뮬레이션으로 불가 |
| **RAS** | on-die ECC, 오류 검사·정정, 오류 보고 | 디지털이지만 **오류 주입** 없이는 검증 불가 |
| **전력 관리** | 로직 공정 전환으로 on-die 전력 관리 탑재 여지 발생 | Mixed 성격. 상태 전이 검증 |
| **DFT / 테스트 제어** | IEEE 1500 TAP, MBIST, repair 제어 | 별도 동작 모드. 기능 검증과 분리되기 쉬움 |
| **고객 전용 로직** (cHBM) | 고객 요구에 따른 가속기·커스텀 PHY·통합 컨트롤러 | 스펙 기반 전면 검증. **표준 VIP 없음** |

### 로직 공정 전환이 만든 것 — Ch02 ③ 층위의 귀결

지금까지 base die는 **DRAM 공정**으로 만들어졌습니다. DRAM 공정은 셀 집적에 최적화되어 로직 밀도가 낮으므로, base die에 넣을 수 있는 회로의 양이 제한적이었습니다.

HBM4 세대에서 이것이 바뀝니다. Base die가 **로직 공정**(Samsung 4nm급, TSMC 3nm급)으로 이동하면서 넣을 수 있는 것이 크게 늘어납니다. 그 결과:

- **메모리 컨트롤러가 스택 안으로** 들어옵니다 (C-HBM4E의 경우 컨트롤러 통합 + 완전 커스텀 PHY + custom D2D PHY)
- **on-die 전력 관리, ECC**를 넣을 여지가 생깁니다
- **고객 전용 가속기**까지 탑재 가능해집니다

여기에 SoC 성격의 인터페이스 IP가 결합합니다. Custom HBM base die는 호스트·칩렛과 연결되기 위해 **PCIe·CXL** 같은 오프칩 인터페이스나 **UCIe·OpenHBI·BoW** 같은 칩렛 인터페이스 IP를 함께 통합하게 됩니다.

> **이 코스의 결론**: Base die는 더 이상 "DRAM 스택의 바닥 판"이 아닙니다. 컨트롤러와 PHY와 표준 인터페이스 IP와 고객 로직이 내부 버스로 연결된 **작은 SoC**입니다. 검증 대상이 그렇게 바뀌었기 때문에, 직무 기술서가 *UVM · VIP · Coverage Closure*의 언어로 쓰인 것입니다.

### 출처 축 — 무엇을 알 수 있는가

| 출처 | 우리가 아는 것 | 검증 초점 | 검증 도구 |
|---|---|---|---|
| **In-house** | 소스, 내부 스펙, 설계자와 직접 소통 | 기능·프로토콜 **전면 검증** | 자체 개발 VIP·TB |
| **3rd Party (구매)** | 문서, 벤더 지원. 소스는 제한적 | **통합** — 연결·설정·클럭/리셋·인터페이스 정합 | 상용 VIP 존재 (표준 프로토콜) |
| **고객 제공 (cHBM)** | 고객 스펙, 고객과의 소통 | 스펙 기반 **전면 검증** | ⚠️ **상용 VIP 없음 → 직접 개발** |

마지막 줄의 ⚠️ 가 직무 기술서의 역량 요구와 정확히 대응합니다.

> *"신규 Protocol 또는 Custom IP에 대한 UVM Agent 설계/구현 역량"*
> *"Spec 기반 Custom UVM Agent A-to-Z 개발 경험" (우대)*

### 교차표 — 이 챕터의 산출물

| IP 예시 | 기능 축 | 출처 축 | 검증 접근 |
|---|---|---|---|
| 채널 컨트롤 로직 | Controller | in-house | 전면 검증. 동시성·프로토콜 assertion 집중 |
| HBM PHY | PHY (mixed) | in-house | **Mixed-level 검증** (Schematic & RTL) |
| PCIe / UCIe IP | 표준 인터페이스 | 3rd party | **통합 검증** — 상용 VIP 활용 |
| 고객 전용 가속 로직 | 커스텀 | 고객 제공 | 전면 검증 + **Custom UVM Agent 자체 개발** |
| ECC / RAS 로직 | RAS | in-house | **오류 주입** 기반 검증 |
| MBIST · IEEE 1500 TAP | DFT | in-house + 툴 | **테스트 모드** 동작 검증 |

:::note[🤔 잠깐 — 직접 분류해 보세요]
새 Custom HBM 프로젝트에 다음 세 IP가 추가되었습니다.

- **(A)** 고객이 요구한 전용 데이터 변환 블록. 인터페이스 규격은 고객이 문서로 제공했고, 업계 표준은 아님
- **(B)** 벤더에서 구매한 표준 오프칩 인터페이스 IP. 벤더가 "완전 검증됨" 인증서를 제공
- **(C)** 사내에서 개발한 채널 중재 로직

각각에 대해 **검증 초점**과 **VIP를 사는지 만드는지**를 판정하세요.

<details>
<summary>정답 / 해설</summary>

**(A) 고객 전용 데이터 변환 블록**
- 초점: **전면 검증**. 고객 스펙이 유일한 근거이므로 스펙에서 검증 항목을 직접 도출해야 합니다
- VIP: **직접 개발**. 업계 표준이 아니므로 상용 VIP가 존재하지 않습니다. Custom UVM Agent(item·driver·monitor·coverage)를 A-to-Z로 만들어야 하며, **이 공수를 프로젝트 초기에 반드시 계획에 넣어야 합니다** (Ch02 실패 3)

**(B) 구매한 표준 인터페이스 IP**
- 초점: **통합 검증**. IP 내부 기능을 재검증하는 것은 비용 대비 효과가 낮습니다. 대신 연결·설정·클럭/리셋·인터페이스 폭 정합·다른 IP와의 상호작용을 봅니다
- VIP: **구매**. 표준 프로토콜이므로 상용 VIP가 존재합니다

**단, "완전 검증됨" 인증서를 어디까지 믿을 것인가** — 이것이 핵심 판단입니다. 벤더가 검증한 것은 **그 IP를 벤더의 환경에서** 검증한 것입니다. 우리 설계에서의 설정값 조합, 우리 클럭/리셋 구조, 우리가 붙인 주변 로직과의 상호작용은 벤더가 본 적이 없습니다. **"IP는 맞지만 통합이 틀린" 경우가 실제 문제의 대부분입니다.**

**(C) 사내 개발 채널 중재 로직**
- 초점: **전면 검증**. 소스를 볼 수 있고 설계자와 소통할 수 있으므로 내부 상태까지 검증합니다
- VIP: **자체 개발**. 다만 (A)와 달리 내부 인터페이스이므로, 이미 보유한 사내 VIP 자산을 재사용할 여지가 큽니다

**세 가지에서 얻는 일반 원리**: 출처가 결정하는 것은 "얼마나 열심히 검증하는가"가 아니라 **"무엇을 검증 대상으로 삼는가"** 입니다. 3rd party IP에서 내부 기능을 파고드는 것은 낭비이고, 고객 IP에서 통합만 보는 것은 누락입니다.

</details>

### RAS와 DFT — 검증을 방해하는 기능들

Base die에는 **정상 동작을 돕지만 검증을 어렵게 만드는** 기능들이 있습니다.

**on-die ECC** — HBM3부터 각 DRAM die 내부에서 오류를 검출·정정합니다. 데이터가 호스트로 나가기 전에 die 안에서 고쳐지므로 신뢰성이 올라갑니다. 그런데 검증 관점에서는 곤란한 성질이 하나 있습니다. **ECC가 오류를 조용히 고쳐 버리면, 그 오류를 만든 결함도 함께 감춰집니다.** 테스트는 정상 데이터를 받고 통과합니다.

이 문제는 실제로 인지되어 있어서, 오류 검사·정리 동작(ECS)의 결과를 **IEEE 1500 테스트 액세스 포트(TAP)의 ECC 투명성 레지스터**를 통해 읽을 수 있게 되어 있습니다. "투명성(transparency)"이라는 이름 자체가 **ECC가 가린 것을 다시 보이게 한다**는 목적을 말해 줍니다.

**MBIST와 repair** — 메모리 자체를 시험하는 내장 테스트 회로입니다. 여기서도 ECC와의 상호작용이 나타납니다. on-die ECC가 켜져 있으면 단일 비트 오류는 ECC가 가려 버리므로 MBIST는 **다중 비트 오류가 난 행만** 식별하게 되고, 호스트가 그 결과를 받아 리페어 절차를 개시합니다.

**검증에 주는 함의**: 이 기능들은 **별도의 동작 모드**를 만듭니다. 기능 검증(mission mode)과 테스트 모드는 서로 다른 상태이며, 그 사이의 전이 — 테스트 모드 진입, 진입 중 기능 동작의 처리, mission mode 복귀 — 자체가 검증 항목입니다. 기능 검증 계획에서 테스트 모드를 "우리 일이 아니다"라고 분류하면 이 전이가 통째로 누락됩니다.

## 4. 일반화 — 왜 이렇게 복잡해졌는가

### 대안 A — 메모리 컨트롤러를 호스트에 그대로 두었다면?

전통적 구조에서 메모리 컨트롤러는 호스트(GPU/CPU) 쪽에 있고, HBM은 표준 인터페이스로 응답하는 역할만 합니다. 이 구조를 유지할 수도 있었습니다.

**왜 바뀌고 있나**: 컨트롤러를 스택 안으로 옮기면 호스트의 부담이 줄고, 메모리 특성에 맞춘 최적화를 메모리 쪽에서 할 수 있으며, 고객마다 다른 요구를 반영할 여지가 생깁니다. C-HBM4E가 이 방향을 명시적으로 취합니다.

**검증에 남긴 것**: 예전에는 "표준 인터페이스를 준수하는가"가 검증의 중심이었습니다. 컨트롤러가 안으로 들어오면 **컨트롤러의 정책과 스케줄링 품질**까지 검증 대상이 됩니다. 검증 범위가 프로토콜 준수에서 **동작 정책**으로 확장되는 것입니다.

### 대안 B — 모든 IP를 사내에서 개발한다면?

출처가 하나면 검증이 단순해집니다. 소스를 다 볼 수 있고 설계자가 전부 사내에 있습니다.

**왜 택하지 않나**: PCIe·UCIe 같은 표준 인터페이스는 규격이 방대하고 검증에도 막대한 자원이 듭니다. 이미 검증된 IP를 구매하는 것이 합리적입니다. 고객 전용 로직은 애초에 고객의 자산입니다.

**검증에 남긴 것**: 다양한 출처가 한 die에 모이면서 **통합 지점**이 늘어납니다. 각 IP는 자기 환경에서 정상이었는데 붙여 놓으니 문제가 생기는 부류의 결함이 주된 관심사가 됩니다. 이것이 SoC 검증의 전형적 성격입니다.

## 5. 디테일 — 출처를 오해했을 때 벌어지는 일

### 실패 1 — "검증된 IP"라는 말을 통합까지 포함한 것으로 받아들인다

벤더가 검증 완료를 보증했으니 그 IP 관련 검증은 생략하는 경우입니다.

**관측되는 증상**: IP 자체는 정상 동작하는데 시스템에서 문제가 생깁니다. 원인은 대개 경계에 있습니다 — 설정값 조합이 우리 시스템에서만 나타나는 것이었거나, 클럭·리셋 순서가 IP가 가정한 것과 달랐거나, 인터페이스 폭·엔디안·타이밍 가정이 어긋났거나. **벤더는 자기 환경에서 검증했고, 우리 환경은 본 적이 없습니다.**

### 실패 2 — 고객 제공 IP에 상용 VIP를 기대한다

Ch02 실패 3의 구체화입니다. 계획 단계에서 "VIP를 구매해 커버한다"고 잡았는데, 정작 그 인터페이스는 표준이 아니어서 파는 물건이 없습니다.

**관측되는 증상**: 프로젝트 중반에 Custom UVM Agent를 처음부터 만들기 시작합니다. Agent 하나를 제대로 만들려면 트랜잭션 정의·driver·monitor·coverage·시퀀스 라이브러리가 모두 필요하고, 이 공수가 계획에 없었으므로 일정이 밀립니다.

**어떻게 막나**: 프로젝트 착수 시 IP 목록에 **출처 칸과 "상용 VIP 존재 여부" 칸을 함께** 만드는 것으로 대부분 예방됩니다. 도입부의 표에 출처 칸이 있던 이유입니다.

### 실패 3 — ECC가 결함을 가려서 테스트가 통과한다

앞서 본 on-die ECC의 성질입니다.

**관측되는 증상**: 데이터가 항상 정확하게 나오므로 테스트가 전부 통과합니다. 그런데 실제로는 어딘가에서 지속적으로 단일 비트 오류가 발생하고 있고 ECC가 매번 고치고 있었습니다. 오류율이 임계를 넘는 조건에서는 정정 능력을 초과해 데이터가 깨집니다.

**핵심 원리**: 이것은 Ch03(관대한 모델), Ch04(주소 디코드), Ch05(프로토콜 위반)에 이어 **네 번째 "조용한 통과"** 입니다. 네 번 모두 원인이 같습니다 — **관측 경로가 결함을 볼 수 없게 되어 있었던 것**이지 결함이 없었던 것이 아닙니다. ECC 투명성 레지스터처럼 **가려진 것을 다시 보는 수단**을 검증 환경이 확보해야 합니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "Base die는 DRAM 스택의 바닥 판" | 컨트롤러·PHY·표준 I/F IP·고객 로직이 내부 버스로 연결된 **작은 SoC**입니다 |
| "IP는 다 같은 검증 대상" | **출처**에 따라 검증 대상 자체가 달라집니다 (내부 기능 vs 통합) |
| "구매 IP는 검증됐으니 통합도 안전" | 벤더는 **자기 환경**에서 검증했습니다. 우리 환경은 본 적이 없습니다 |
| "ECC가 있으면 데이터 신뢰성이 확보된다" | 검증 관점에서는 ECC가 **결함을 가립니다**. 투명성 확보 수단이 필요합니다 |
| "DFT·MBIST는 테스트팀 일이라 기능 검증과 무관" | 테스트 모드 **진입·복귀 전이**는 기능 검증의 대상입니다 |
| "고객 전용 IP도 결국 표준 비슷하니 VIP가 있을 것" | 표준이 아니면 **없습니다**. Custom Agent 개발 공수를 계획에 넣어야 합니다 |

## 🔍 이 구조가 만드는 검증 문제

**① 출처별로 검증 전략이 갈린다**

in-house는 전면 검증, 3rd party는 통합 검증, 고객 제공은 전면 검증 + 도구 자체 개발. IP 목록에 출처 칸이 없으면 이 분기가 계획에 반영되지 않습니다.

**② VIP는 "사느냐 만드느냐"의 판단 대상이다**

표준 인터페이스는 상용 VIP를 도입하는 것이 합리적이고, 커스텀 인터페이스는 만들 수밖에 없습니다. 이 판단을 프로젝트 초기에 내려야 공수 산정이 맞습니다. 직무 기술서의 *"In-house VIP 개발 및 3rd Party VIP 도입 및 활용"* 이 이 판단을 요구합니다.

**③ Custom Agent가 필요한 구간을 초기에 식별해야 한다**

"어디까지가 표준이고 어디부터가 커스텀인가"의 경계를 긋는 일이 검증 계획의 첫 작업 중 하나입니다.

**④ 통합 검증은 IP 검증과 별개 항목이다**

각 IP가 정상이어도 붙였을 때 문제가 생깁니다. 설정 조합·클럭/리셋 순서·인터페이스 정합이 독립된 검증 항목이어야 합니다.

**⑤ 오류 정정 기능은 관측 경로를 막는다**

ECC가 가린 것을 볼 수단(투명성 레지스터 등)을 환경이 확보하지 못하면, 결함이 있어도 테스트는 통과합니다.

**⑥ 테스트 모드와 mission mode의 전이가 검증 대상이다**

DFT를 범위 밖으로 미루면 이 전이가 누락됩니다.

**⑦ Mixed IP는 별도 환경을 요구한다**

PHY는 순수 디지털 시뮬레이션으로 다룰 수 없습니다 — Ch03에서 확인한 사실이 여기서 IP 단위로 구체화됩니다. 직무 기술서의 우대사항 *"Full-Chip Mixed-Level Design (Schematic & RTL) 검증"* 이 이 항목입니다.

## 7. 핵심 정리 — 그리고 여섯 챕터의 종합

- Base die는 **Controller · PHY · RAS · 전력 · DFT · (고객 로직)** 으로 구성된 **작은 SoC**다
- HBM4의 **로직 공정 전환**이 이 변화를 만들었다 — 넣을 수 있는 것이 늘자 컨트롤러·가속기·표준 I/F IP가 들어왔다
- 검증 계획은 **기능 축 × 출처 축**의 교차에서 나온다. 출처가 정하는 것은 노력의 양이 아니라 **검증 대상 자체**다
- **네 번째 "조용한 통과"**: 관대한 모델(Ch03) → 주소 디코드(Ch04) → 프로토콜 위반(Ch05) → **ECC 마스킹(Ch06)**. 모두 관측 경로의 문제였다
- 이것이 HBM 검증이 **SoC 검증**인 이유이며, 직무 기술서가 UVM·VIP·Coverage의 언어로 쓰인 근거다

### 여섯 챕터의 🔍 종합 — V-Plan의 씨앗

후속 토픽 `hbm_dv`는 이 목록을 실제 UVM 환경으로 옮기는 과정을 다룹니다.

이 코스 전체를 관통하는 질문입니다.

> **"HBM 검증"이 왜 UVM·VIP·Coverage Closure의 일이 되었는가?**

여섯 챕터의 내용을 인과 사슬로 연결해 답하세요.

<details>
<summary>정답 / 해설</summary>

**인과 사슬**

1. **(Ch01)** AI 워크로드가 요구하는 대역폭을 클럭 상승으로는 감당할 수 없었다 — 배선 길이에서 오는 에너지 벽. 그래서 **폭으로 푸는 길**을 택했고, 그 폭을 감당하려 3D 적층과 인터포저를 끌어들였다
2. **(Ch01→Ch03)** 폭으로 풀자 관리할 채널이 많아졌고, 이들을 통제할 **로직이 스택 안에 필요**해졌다. 그것이 스택 최하단의 **Base Die**다
3. **(Ch03)** DRAM core die는 아날로그이므로 논리 시뮬레이션 대상이 아니다 → **모델로 대체**된다. 남는 검증 대상은 base die의 digital·mixed IP다
4. **(Ch04→Ch05)** 그 base die 안에는 semi-independent한 채널 구조와 분리된 커맨드 인터페이스가 있어, **동시성과 프로토콜 규칙**이라는 SoC적 검증 과제가 생겼다
5. **(Ch02→Ch06)** HBM4에서 base die가 **로직 공정**으로 이동하자 컨트롤러·전력 관리·표준 인터페이스 IP·고객 전용 로직까지 들어왔다. DUT의 경계는 그대로인데 **내용물이 SoC가 된 것**이다
6. **(Ch06)** 그 결과 검증 업무는 **여러 출처의 IP를 통합 검증하고, 없는 도구는 만들고, 커버리지로 닫는 일**이 되었다

**따라서**: 직무 기술서의 *"In-house·3rd Party Digital IP 및 Mixed 설계 검증 / VIP 개발·도입 / UVM 환경·Test Case / Coverage Closure"* 는 HBM이라는 제품이 걸어온 구조적 진화의 **직접적 귀결**입니다. 메모리 회사의 직무인데 SoC 검증의 언어로 쓰여 있는 것이 이상한 일이 아니라, **HBM이 그렇게 변했기 때문**입니다.

**한 문장 요약**: 폭으로 대역폭을 푸는 선택 → 채널 관리 로직 필요 → base die 등장 → 로직 공정 전환 → base die가 SoC화 → **HBM 검증 = SoC 검증**.

</details>

## 코스를 마치며

여섯 챕터를 통해 **검증 대상으로서의 HBM**을 확정했습니다. 무엇이 DUT이고, 그 안에 무엇이 있으며, 그 구조가 어떤 검증 문제를 만드는지까지 왔습니다.

이 코스는 여기서 멈춥니다. **문제를 푸는 방법 — UVM 환경을 어떻게 구성하고, Custom Agent를 어떻게 설계하며, VIP를 어떻게 고르고, Coverage를 어떻게 닫는지 — 는 후속 토픽 `hbm_dv`의 몫입니다.** 위의 21개 항목 표를 손에 들고 다음 코스로 넘어가면, 각 항목이 실제 코드와 계획으로 바뀌는 과정을 따라갈 수 있습니다.

:::caution[범위와 인용에 대하여]
Base die의 내부 구성은 **공개 자료 기준의 일반적 구조**이며, 특정 제조사의 실제 구현은 공개되지 않습니다. 본 챕터는 어떤 회사의 내부 설계도 추측하지 않으며, 업계 공통으로 보고된 기능 분류와 그 검증 함의만 다룹니다. Custom HBM의 구성은 고객·프로젝트마다 다르므로 여기 제시한 IP 목록은 **유형의 예시**입니다. 공정 노드 표기(4nm, 3nm 등)는 공개 발표 기준이며 변동될 수 있습니다.
:::
