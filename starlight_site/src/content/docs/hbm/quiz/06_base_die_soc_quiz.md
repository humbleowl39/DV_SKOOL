## Q1. (Remember)

공개 자료가 정리하는 Base die의 네 가지 주요 기능 갈래는?

- [ ] A. Controller / PDN / RAS / PHY
- [ ] B. Cell Array / Sense Amp / Decoder / Buffer
- [ ] C. CPU / GPU / NPU / DSP
- [ ] D. Fetch / Decode / Execute / Writeback

<details>
<summary>정답 / 해설</summary>

**A. Controller / PDN(전력 전달) / RAS / PHY**.

검증 관점에서는 여기에 두 가지를 더해야 합니다 — **DFT/테스트 제어**(IEEE 1500 TAP, MBIST, repair)와 Custom HBM의 **고객 전용 로직**입니다.

B는 **core die**(DRAM die)의 구성요소입니다.

</details>

## Q2. (Understand)

IP의 "출처 축"(in-house / 3rd party / 고객 제공)이 결정하는 것은?

- [ ] A. 검증에 투입하는 인력의 수
- [ ] B. 무엇을 검증 대상으로 삼는가 (내부 기능인가 통합인가)
- [ ] C. 시뮬레이터의 종류
- [ ] D. 검증에 소요되는 시뮬레이션 시간

<details>
<summary>정답 / 해설</summary>

**B**. 출처가 결정하는 것은 **"얼마나 열심히 검증하는가"가 아니라 "무엇을 검증 대상으로 삼는가"** 입니다.

| 출처 | 검증 초점 | VIP |
|---|---|---|
| In-house | 전면 검증 | 자체 개발 |
| 3rd party | **통합** — 연결·설정·클럭/리셋 | 상용 존재 |
| 고객 제공 | 전면 검증 | **없음 → 직접 개발** |

3rd party IP에서 내부 기능을 파고드는 것은 낭비이고, 고객 IP에서 통합만 보는 것은 누락입니다.

</details>

## Q3. (Apply)

Custom HBM 프로젝트에 다음 IP가 추가되었습니다. 각각의 검증 초점과 VIP 조달 방식을 판정하세요.

- **(A)** 고객이 요구한 전용 데이터 변환 블록 (인터페이스는 고객 문서로 제공, 업계 표준 아님)
- **(B)** 벤더 구매 표준 오프칩 인터페이스 IP ("완전 검증됨" 인증서 제공)
- **(C)** 사내 개발 채널 중재 로직

<details>
<summary>정답 / 해설</summary>

**(A) 고객 전용 데이터 변환 블록**
- 초점: **전면 검증**. 고객 스펙이 유일한 근거이므로 스펙에서 검증 항목을 직접 도출
- VIP: **직접 개발**. 업계 표준이 아니므로 상용 VIP가 존재하지 않습니다. Custom UVM Agent를 A-to-Z로 만들어야 하며, **이 공수를 프로젝트 초기에 계획에 반영**해야 합니다

**(B) 구매한 표준 인터페이스 IP**
- 초점: **통합 검증**. IP 내부 기능 재검증은 비용 대비 효과가 낮습니다. 연결·설정·클럭/리셋·인터페이스 폭 정합·다른 IP와의 상호작용을 봅니다
- VIP: **구매**. 표준 프로토콜이므로 상용 VIP가 존재합니다

**핵심 판단 — "완전 검증됨"을 어디까지 믿을 것인가**: 벤더가 검증한 것은 **그 IP를 벤더의 환경에서** 검증한 것입니다. 우리 설계의 설정값 조합, 우리 클럭/리셋 구조, 우리가 붙인 주변 로직과의 상호작용은 벤더가 본 적이 없습니다. **"IP는 맞지만 통합이 틀린" 경우가 실제 문제의 대부분입니다.**

**(C) 사내 개발 채널 중재 로직**
- 초점: **전면 검증**. 소스를 볼 수 있고 설계자와 소통할 수 있으므로 내부 상태까지 검증
- VIP: **자체 개발**. 다만 (A)와 달리 내부 인터페이스이므로 보유한 사내 VIP 자산을 재사용할 여지가 큽니다

</details>

## Q4. (Analyze)

on-die ECC는 신뢰성을 높이는 기능인데, 검증 관점에서는 오히려 문제를 만듭니다. 그 메커니즘과 대응 수단을 설명하세요.

<details>
<summary>정답 / 해설</summary>

**메커니즘 — ECC가 결함을 가린다**

on-die ECC는 데이터가 호스트로 나가기 전에 DRAM die 내부에서 오류를 정정합니다. 그런데 **오류를 조용히 고쳐 버리면 그 오류를 만든 결함도 함께 감춰집니다.**

어딘가에서 지속적으로 단일 비트 오류가 발생하고 있어도 ECC가 매번 고치므로 테스트는 정상 데이터를 받고 통과합니다. 오류율이 임계를 넘어 정정 능력을 초과하는 조건에서야 데이터가 깨집니다.

**대응 수단 — 가려진 것을 다시 보기**

이 문제는 실제로 인지되어 있어서, 오류 검사·정리 동작(**ECS**)의 결과를 **IEEE 1500 테스트 액세스 포트(TAP)의 ECC 투명성 레지스터**로 읽을 수 있게 되어 있습니다. **"투명성(transparency)"이라는 이름 자체가 ECC가 가린 것을 다시 보이게 한다는 목적을 말해 줍니다.**

검증 환경은 이 관측 경로를 확보해야 하며, 그렇지 못하면 결함이 있어도 테스트는 통과합니다.

**패턴 인식**: 이것은 코스의 **네 번째 "조용한 통과"** 입니다 — 관대한 모델(Ch03) → 주소 디코드(Ch04) → 프로토콜 위반(Ch05) → **ECC 마스킹(Ch06)**. 네 번 모두 원인이 같습니다: 관측 경로가 결함을 볼 수 없게 되어 있었던 것이지 결함이 없었던 것이 아닙니다.

</details>

## Q5. (Analyze)

MBIST와 on-die ECC가 함께 켜져 있을 때 나타나는 상호작용은 무엇이며, 그것이 검증 계획에 어떤 항목을 만듭니까?

<details>
<summary>정답 / 해설</summary>

**상호작용**: on-die ECC가 켜져 있으면 **단일 비트 오류는 ECC가 가려 버리므로** MBIST는 다중 비트 오류가 발생한 행만 식별하게 됩니다. 호스트는 그 결과를 받아 리페어 절차를 개시합니다.

**검증 계획에 만드는 항목**

1. **동작 모드 간 전이** — 기능 검증(mission mode)과 테스트 모드는 서로 다른 상태입니다. 테스트 모드 **진입**, 진입 중 기능 동작의 처리, mission mode **복귀** 자체가 검증 항목입니다
2. **ECC 활성/비활성 조합** — ECC가 켜진 상태와 꺼진 상태에서 MBIST 결과가 달라지므로, 두 조건을 모두 확인해야 합니다
3. **리페어 절차의 정상 동작** — 식별된 행에 대한 리페어가 올바르게 수행되고 이후 접근이 정상인지

**흔한 누락**: DFT를 "테스트팀 일"로 분류해 기능 검증 범위에서 제외하면, 위의 **모드 전이가 통째로 빠집니다.** 테스트 모드 자체는 테스트팀 소관일 수 있지만, 그 모드로 들어가고 나오는 경로는 기능 검증의 대상입니다.

</details>

## Q6. (Evaluate)

이 코스 전체를 관통하는 질문입니다.

> **"HBM 검증"이 왜 UVM · VIP · Coverage Closure의 일이 되었는가?**

여섯 챕터의 내용을 인과 사슬로 연결해 답하세요.

<details>
<summary>정답 / 해설</summary>

**인과 사슬**

1. **(Ch01)** AI 워크로드가 요구하는 대역폭을 클럭 상승으로는 감당할 수 없었다 — 배선 길이에서 오는 에너지 벽. 그래서 **폭으로 푸는 길**을 택했고, 그 폭을 감당하려 3D 적층과 인터포저를 끌어들였다
2. **(Ch01→Ch03)** 폭으로 풀자 관리할 채널이 많아졌고, 이들을 통제할 **로직이 스택 안에 필요**해졌다. 그것이 **Base Die**다
3. **(Ch03)** DRAM core die는 아날로그이므로 논리 시뮬레이션 대상이 아니다 → **모델로 대체**된다. 남는 검증 대상은 base die의 digital·mixed IP다
4. **(Ch04→Ch05)** base die 안에는 semi-independent한 채널 구조와 분리된 커맨드 인터페이스가 있어 **동시성과 프로토콜 규칙**이라는 SoC적 검증 과제가 생겼다
5. **(Ch02→Ch06)** HBM4에서 base die가 **로직 공정**으로 이동하자 컨트롤러·전력 관리·표준 인터페이스 IP·고객 전용 로직까지 들어왔다. DUT의 경계는 그대로인데 **내용물이 SoC가 된 것**이다
6. **(Ch06)** 그 결과 검증 업무는 **여러 출처의 IP를 통합 검증하고, 없는 도구는 만들고, 커버리지로 닫는 일**이 되었다

**결론**: 직무 기술서의 *"In-house·3rd Party Digital IP 및 Mixed 설계 검증 / VIP 개발·도입 / UVM 환경·Test Case / Coverage Closure"* 는 HBM이라는 제품이 걸어온 구조적 진화의 **직접적 귀결**입니다. 메모리 회사의 직무인데 SoC 검증의 언어로 쓰여 있는 것이 이상한 일이 아니라, **HBM이 그렇게 변했기 때문**입니다.

**한 문장 요약**: 폭으로 대역폭을 푸는 선택 → 채널 관리 로직 필요 → base die 등장 → 로직 공정 전환 → base die가 SoC화 → **HBM 검증 = SoC 검증**.

</details>
