## Q1. (Remember)

HBM4를 규정하는 JEDEC 표준 번호는?

- [ ] A. JESD235
- [ ] B. JESD238
- [ ] C. JESD270-4
- [ ] D. JESD79-5

<details>
<summary>정답 / 해설</summary>

**C. JESD270-4** (2025-04 공표).

A(JESD235) 계열은 HBM1·HBM2·HBM2E, B(JESD238)는 HBM3·HBM3E입니다. D(JESD79-5)는 HBM이 아니라 **DDR5**입니다.

HBM3E와 HBM4가 **다른 표준 문서**라는 점이 중요합니다 — HBM4는 HBM3E의 상위 버전이 아니라 별도 규격입니다.

</details>

## Q2. (Understand)

본 코스가 제시한 세대 변화의 **세 층위**를 검증 파급이 작은 순서대로 올바르게 나열한 것은?

- [ ] A. 구조적 → 전기적 → 공정·아키텍처
- [ ] B. 전기적 → 구조적 → 공정·아키텍처
- [ ] C. 공정·아키텍처 → 구조적 → 전기적
- [ ] D. 전기적 → 공정·아키텍처 → 구조적

<details>
<summary>정답 / 해설</summary>

**B**.

- **① 전기적**(per-pin 속도 상승): PHY 트레이닝 파라미터·타이밍 마진 조정. TB 골격 재사용 가능
- **② 구조적**(폭·채널 수 변경): 주소맵·coverage 축·동시성 모델 재설계. 골격은 유지
- **③ 공정·아키텍처**(base die가 로직 공정으로): 검증 대상 자체가 SoC로 전환. 방법론 재검토

층위가 올라갈수록 재사용 가능 범위가 줄어듭니다.

</details>

## Q3. (Apply)

어떤 자료가 "HBM2는 per-pin 2.4 Gb/s이고 대역폭은 256 GB/s"라고 서술합니다. 이 진술을 산술로 검증하면?

- [ ] A. 정확하다
- [ ] B. 2.4 Gb/s는 307 GB/s에 대응하므로 두 값을 한 문장에 함께 쓰면 틀리다
- [ ] C. 256 GB/s가 맞고 2.4 Gb/s가 틀렸다
- [ ] D. 총 폭을 모르면 검증할 수 없다

<details>
<summary>정답 / 해설</summary>

**B**. HBM2의 총 폭은 1024-bit이므로:

- `1024 × 2.0 ÷ 8 = 256 GB/s` → 256은 **2.0 Gb/s** 기준
- `1024 × 2.4 ÷ 8 = 307.2 GB/s` → 2.4 Gb/s는 **307 GB/s**에 대응

두 값 각각은 실재하는 HBM2 사양이지만(초기 2.0 Gb/s, 이후 2.4 Gb/s 급), **한 문장에 섞어 쓰면 자기모순**입니다. 실제로 그렇게 서술한 공개 자료가 존재합니다.

C가 틀린 이유: 어느 한쪽이 틀린 것이 아니라 **조합이 틀린** 것입니다. D가 틀린 이유: 총 폭 1024-bit는 세대 표에서 확인할 수 있습니다.

**교훈**: 공개 수치가 충돌할 때 판정 기준은 출처의 권위가 아니라 **산술의 자기 일관성**입니다.

</details>

## Q4. (Analyze)

기존 HBM3 검증 환경을 보유한 팀이 (가) HBM3E 이관과 (나) HBM4 이관을 각각 맡습니다. 어느 쪽이 재작업이 크며 그 이유는 무엇입니까? (서술)

<details>
<summary>정답 / 해설</summary>

**(나) HBM4 쪽이 압도적으로 큽니다.**

**(가) HBM3 → HBM3E**: 총 폭 1024-bit, 16채널 / 32 pseudo-channel 구성이 **그대로**이고 per-pin만 6.4 → 9.6 Gb/s로 오릅니다. **① 전기적 변화**에 해당하므로 트레이닝 파라미터와 타이밍 마진 조정 수준에서 대부분 해결됩니다.

**(나) HBM3E → HBM4**: 두 층위가 **동시에** 바뀝니다.
- **② 구조적**: 폭 1024 → 2048-bit, 채널 16 → 32개. coverage 모델·주소맵·동시성 시나리오 재설계 필요
- **③ 공정·아키텍처**: base die가 로직 공정으로 이동하면서 컨트롤러·전력 관리·표준 인터페이스 IP 등이 들어옴. 검증 범위 자체가 확장

**핵심**: HBM4는 ②와 ③이 동시에 일어난 **유일한 세대**입니다. "폭이 두 배인 HBM3E"로 요약하면 ③을 놓치고, 그 결과 base die 내부 IP 통합 검증 항목이 계획에서 통째로 빠집니다.

</details>

## Q5. (Analyze)

HBM3E 환경을 HBM4로 이관할 때, 테스트가 **깨지지 않는데도** 위험한 상황이 발생할 수 있습니다. 무엇이며 왜 위험합니까?

<details>
<summary>정답 / 해설</summary>

**Coverage 모델이 조용히 무력화되는 상황입니다.**

채널이 16 → 32개로 늘었는데 covergroup의 bin이 16개 기준으로 정의되어 있으면, 새로 추가된 절반의 채널은 **아예 측정 대상에서 빠집니다.** 그런데 기존 bin은 모두 채워지므로 커버리지 리포트는 **100%를 보고합니다.**

**왜 위험한가**: 테스트가 실패하면 누군가 조사합니다. 그러나 이 경우 아무것도 실패하지 않고 지표는 오히려 좋아 보입니다. 측정되지 않은 영역은 "통과"로 읽히므로 **이 오류는 조용히 sign-off까지 갑니다.**

**예방**: 세대 이관 체크리스트에 "coverage 모델이 새 구성을 반영하는지 확인"을 명시적 항목으로 넣어야 합니다. 구성값이 파라미터화되어 있으면 이 문제 자체가 발생하지 않습니다.

</details>

## Q6. (Evaluate)

Custom HBM 프로젝트의 검증 계획을 리뷰합니다. 계획서에 "인터페이스 검증은 상용 VIP를 구매하여 커버한다"고 적혀 있습니다. 이 계획의 가장 큰 리스크는?

- [ ] A. 상용 VIP의 라이선스 비용이 예산을 초과할 수 있다
- [ ] B. 고객 전용 인터페이스에는 상용 VIP가 존재하지 않아 Custom Agent 개발 공수가 누락된다
- [ ] C. 상용 VIP는 시뮬레이션 속도가 느리다
- [ ] D. 상용 VIP는 커버리지를 지원하지 않는다

<details>
<summary>정답 / 해설</summary>

**B**.

Custom HBM은 base die에 **고객 요구에 맞춘 로직**이 통합됩니다. 그 인터페이스는 업계 표준이 아니므로 **파는 VIP가 존재하지 않습니다.** 계획이 이를 반영하지 않으면, 프로젝트 중반에 Custom UVM Agent를 처음부터 만들기 시작하게 되고 그 공수는 계획에 없습니다.

Agent 하나를 제대로 만들려면 트랜잭션 정의·driver·monitor·coverage·시퀀스 라이브러리가 모두 필요합니다. 이것이 직무 기술서가 *"신규 Protocol 또는 Custom IP에 대한 UVM Agent 설계/구현 역량"* 과 우대사항 *"Spec 기반 Custom UVM Agent A-to-Z 개발 경험"* 을 요구하는 이유입니다.

**예방책**: 프로젝트 착수 시 IP 목록에 **"출처"** 칸과 **"상용 VIP 존재 여부"** 칸을 함께 만들면 대부분 방지됩니다.

</details>
