## Q1. (Remember)

HBM 스택에서 Base Die가 담당하는 역할로 옳지 **않은** 것은?

- [ ] A. 채널별 read/write 관리
- [ ] B. refresh 주기 운영
- [ ] C. 호스트 인터페이스
- [ ] D. 데이터 비트를 셀 커패시터에 저장

<details>
<summary>정답 / 해설</summary>

**D**. 데이터 저장은 **Core die**(DRAM die)의 셀 어레이가 담당합니다.

Base die는 스택 최하단에서 채널별 읽기·쓰기 관리, refresh 주기 운영, 트레이닝, precharge/activate 발행, 호스트 인터페이스를 맡습니다. 저장이 아니라 **제어**가 base die의 일입니다.

</details>

## Q2. (Understand)

검증 대상(DUT)의 경계를 긋는 기준으로 가장 정확한 것은?

- [ ] A. 물리적인 die 경계
- [ ] B. RTL로 기술되어 논리 시뮬레이션으로 동작을 확인할 수 있는 영역의 경계
- [ ] C. 우리 회사가 설계한 부분과 아닌 부분의 경계
- [ ] D. 패키지 내부와 외부의 경계

<details>
<summary>정답 / 해설</summary>

**B**.

A가 틀린 이유: base die라는 **하나의 die 안에도** 순수 디지털 로직과 mixed IP가 공존하며, 이들은 서로 다른 방법으로 검증됩니다. die 경계는 검증 방법의 경계와 일치하지 않습니다.

C는 출처의 구분으로, Ch06에서 다루는 **다른 축**입니다. 검증 대상 여부가 아니라 검증 초점을 결정합니다.

경계 바깥은 **모델로 대체**됩니다 — core die는 DRAM behavioral model로, 호스트는 VIP/BFM으로.

</details>

## Q3. (Apply)

어떤 팀이 다음과 같이 보고했습니다.

> "DRAM behavioral model을 붙이고, base die RTL을 DUT로 놓고, 호스트 측은 자체 BFM으로 커맨드를 발행합니다. 시뮬레이션이 돌고 read/write 데이터가 일치합니다."

이 구성에서 **검증되지 않은 채 남은** DUT 영역은?

- [ ] A. 채널 컨트롤 로직
- [ ] B. Base die의 Mixed IP (PHY 등)
- [ ] C. Core die의 셀 어레이
- [ ] D. 인터포저 배선

<details>
<summary>정답 / 해설</summary>

**B**.

보고된 구성은 **순수 디지털 시뮬레이션**입니다. 그런데 DUT는 두 부분입니다 — digital IP와 **mixed IP**. PHY처럼 아날로그와 디지털이 섞인 블록은 논리 시뮬레이션만으로 동작을 확인할 수 없으므로, 이 구성에서 PHY는 십중팔구 간이 모델로 대체되어 있고 실제 동작은 미검증 상태입니다.

C는 **DUT가 아닙니다**(모델 대체). D는 **범위 밖**입니다(SI/PI 해석 영역).

이것이 직무 기술서가 *"Analog-Digital Mixed IP … 검증"* 과 우대사항 *"Full-Chip Mixed-Level Design (Schematic & RTL) 검증"* 을 별도로 명시하는 이유입니다.

</details>

## Q4. (Analyze)

"DRAM 모델이 관대하면 검증이 실패한다"는 명제의 메커니즘을 설명하고, 이것이 검증 계획에 어떤 항목을 추가하게 만드는지 서술하세요.

<details>
<summary>정답 / 해설</summary>

**메커니즘**

DRAM behavioral model은 실제 DRAM을 흉내 내지만 완전하지 않습니다. 모델이 타이밍 제약 위반을 **검사하지 않고** 요청받은 데이터를 성실히 반환하도록 작성되었다고 합시다.

이때 DUT가 규정보다 짧은 간격으로 커맨드를 발행해도 모델은 정상 응답합니다. scoreboard는 **데이터를 비교하는 장치**이므로 "값이 맞다"고 판정합니다. 시뮬레이션은 전부 통과하고 데이터도 완벽히 일치하는데, 실제 칩에서는 그 조건에서 데이터가 깨집니다.

**핵심 원리**: **모델의 엄격함이 검증의 상한을 정합니다.** 모델이 검사하지 않는 규칙은 아무리 많은 테스트를 돌려도 검증되지 않습니다.

**계획에 추가되는 항목**

1. **모델 자체의 엄격함을 확인하는 항목** — 이 모델이 어떤 규칙을 검사하고 어떤 것을 검사하지 않는지 목록화
2. **상용 VIP 도입 시 "무엇을 검사해 주는가" 확인** — 벤더 문서의 검사 범위 확인이 도입 판단의 일부
3. **모델에 의존하지 않는 독립 감시 수단** — 인터페이스에 상주하는 assertion (Ch05)

이것이 직무 기술서가 *"In-house VIP 개발"* 과 *"3rd Party VIP 도입 및 활용"* 을 나란히 요구하는 배경입니다.

</details>

## Q5. (Analyze)

제품이 **HBM3E 12-high(36 GB)** 에서 **8-high(24 GB)** 파생으로 확장됩니다. 세대는 그대로입니다. 재검증이 필요한 항목과 그대로 유효한 항목을 가르는 **판정 기준**은 무엇입니까?

<details>
<summary>정답 / 해설</summary>

**판정 기준 한 문장**:

> **base die가 제공하는 인터페이스는 단수에 무관하고, core die 쪽으로 향하는 매핑은 단수에 의존한다.**

**재검증 필요**
- **주소 맵과 채널-die 매핑** — 총 용량이 36 → 24 GB로 바뀌어 어느 주소가 어느 die로 가는지가 달라집니다. 환경에 매핑이 고정되어 있으면 잘못된 영역에 접근하면서도 오류 없이 동작할 수 있어 위험합니다
- **용량 경계 시나리오** — 주소 범위 상한이 달라지므로 경계·범위 초과 접근 시나리오를 새 용량 기준으로 재작성

**그대로 유효**
- **호스트 인터페이스 검증 전반** — 대역폭과 인터페이스 폭은 단수와 무관합니다(Ch01). 호스트가 보는 인터페이스는 base die가 제공합니다
- **커맨드 프로토콜·데이터 정합성 검사 로직** — read/write의 의미와 비교 방식은 단수와 무관

**실질적 이득**: DUT 경계를 명확히 그어 두었다면 이 판정을 몇 분 안에 내릴 수 있습니다. 그렇지 않으면 전체를 다시 돌려보는 수밖에 없습니다.

</details>

## Q6. (Evaluate)

"모델의 부정확성이 문제라면, core die의 아날로그 회로까지 포함해 스택 전체를 통합 시뮬레이션하면 되지 않나?"라는 제안을 평가하세요.

<details>
<summary>정답 / 해설</summary>

**원리적으로는 옳지만 실용적으로 불가능합니다.**

아날로그 회로 시뮬레이션은 논리 시뮬레이션보다 **자릿수 단위로** 느립니다. 여기에 core die가 8~12장 곱해집니다. 커맨드 몇 개를 주고받는 데 며칠이 걸린다면:

- 무작위 시나리오를 수천 개 돌려 coverage를 닫는 방식 자체가 성립하지 않습니다
- **회귀를 돌릴 수 없는 검증은 검증이 아닙니다**

**그래서 실무가 택한 것**: 계층을 나누고 각 계층에 맞는 도구를 씁니다.

| 계층 | 도구 |
|---|---|
| 디지털 로직 | 논리 시뮬레이션 (빠르게 대량) |
| 아날로그가 섞인 경계 | Mixed-level 검증 |
| 전기적 특성 | SI/PI 해석 (별도 도구) |

**대가**: 모델의 부정확성이라는 위험을 감수하게 됩니다. 그 위험을 관리하는 것이 Q4에서 다룬 "모델의 엄격함 확인" 항목입니다. 즉 **완벽함을 포기하고 속도를 얻은 뒤, 포기한 부분을 별도 항목으로 관리**하는 구조입니다.

</details>
