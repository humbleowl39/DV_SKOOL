## 1. Why care? — 부분을 아는 것과 전체를 아는 것

여기까지 부품을 하나씩 봤습니다. 셀([01장](../01_dram_operation/)), 대역폭의 논리([02장](../02_memory_wall/)), TSV([03장](../03_stacking_tsv/)), 인터포저([04장](../04_interposer/)), 스택 구조([05장](../05_stack_anatomy/)).

그런데 부품을 안다는 것과 **전체가 어떻게 움직이는지** 아는 것은 다릅니다.

이 장은 요청 하나를 **끝까지 따라갑니다.** 호스트가 "이 주소를 읽어라"라고 말한 순간부터 데이터가 손에 들어오는 순간까지, 어디를 지나고 각 구간에서 무슨 일이 일어나며 시간을 얼마나 쓰는지 봅니다.

그리고 마지막에 뜻밖의 결론이 하나 나옵니다 — **거리를 줄인 것의 진짜 이득은 지연이 아니었습니다.**

## 2. 직관 — 여정의 지도

경로를 다섯 구간으로 나눌 수 있습니다.

```d2
direction: down

REQ: "① 호스트 · 메모리 컨트롤러\n물리 주소를 필드로 쪼갠다" {
  style.fill: "#e3f2fd"; style.font-color: "#0A0F25"
}
INTP: "② 인터포저\n수 mm · 미세 배선" {
  style.fill: "#f3e5f5"; style.font-color: "#0A0F25"
}
BASED: "③ Base Die\n커맨드를 해석해 목적지를 정한다" {
  style.fill: "#bbdefb"; style.font-color: "#0A0F25"
}
TSVSEG: "④ TSV + µbump\n수십 µm · 층을 오른다" {
  style.fill: "#ffe0b2"; style.font-color: "#0A0F25"
}
COREDIE: "⑤ Core Die\n행을 열고 열을 고른다" {
  style.fill: "#e8f5e9"; style.font-color: "#0A0F25"
}

REQ -> INTP: "커맨드 · 주소"
INTP -> BASED
BASED -> TSVSEG: "SID 로 목적지 선택"
TSVSEG -> COREDIE
COREDIE -> TSVSEG: "데이터 256 비트"
TSVSEG -> BASED
BASED -> INTP: "DQ 32 핀 · 8 UI 버스트"
INTP -> REQ
```

**가는 길과 오는 길이 같은 구간을 씁니다.** 다만 실어 보내는 것이 다릅니다 — 갈 때는 **커맨드와 주소**, 올 때는 **데이터**입니다.

그리고 이 그림에서 주목할 것 하나 — **②와 ④는 거리 구간**이고 **③과 ⑤는 동작 구간**입니다. 이 구분이 §4에서 결정적으로 쓰입니다.

## 3. 작은 예 — 주소 하나를 끝까지 따라간다

구체적인 구성을 하나 잡습니다.

| 항목 | 값 |
|---|---|
| 스택 | HBM4 **8-high**, core die 밀도 **32 Gb** → 스택 **32 GB** |
| 채널 | **32개**, 채널당 64비트 |
| PC | 채널당 **2개**, PC당 32 DQ |
| SID | `SID[0]` 1비트 (8-high) → 채널당 뱅크 **32개** |
| 전송률 | **6.4 Gb/s** (핀당) |

호스트가 **32바이트**를 읽으려 합니다.

### 단계 ① — 주소를 쪼갠다 (호스트 쪽)

메모리 컨트롤러가 물리 주소를 필드로 나눕니다.

```
물리 주소
  ├─ 채널  (5비트)  →  32채널 중 하나          예: 채널 7
  ├─ PC    (1비트)  →  그 채널의 두 PC 중 하나  예: PC 1
  ├─ SID   (1비트)  →  어느 die 묶음인가        예: SID 0
  ├─ 뱅크  (4비트)  →  BA[3:0]                 예: 뱅크 5
  ├─ 행    (14비트) →  RA[13:0]                예: 행 3,412
  └─ 열    (5비트)  →  CA[4:0]                 예: 열 9
```

두 가지를 짚어 둡니다.

- **`{SID, BA}` 가 실제 뱅크 인덱스입니다.** [05장](../05_stack_anatomy/)에서 본 대로 SID는 뱅크 주소의 확장 비트입니다. 여기서는 `{0, 5}` → 뱅크 인덱스 5.
- **버스트 안의 위치를 고르는 하위 비트는 장치로 보내지 않습니다.** 한 번의 읽기가 32바이트를 통째로 돌려주므로, 그 안에서 어느 바이트를 쓸지는 호스트가 알아서 합니다.

### 단계 ② — 인터포저를 건넌다

커맨드와 주소가 채널 7의 신호선을 타고 base die로 갑니다.

- 거리 **수 mm**, 배선 폭 약 **1 µm** ([04장](../04_interposer/))
- 이 구간은 **광폭 버스가 사는 곳**입니다. 채널 32개의 신호가 모두 여기를 지나며, 패키지로는 내려가지 않습니다.

### 단계 ③ — Base die가 목적지를 정한다

base die가 커맨드를 받아 판단합니다.

- 채널 7의 커맨드다 → 채널 7 경로로 보낸다
- `SID = 0` 이다 → 아래쪽 die 묶음으로 올려 보낸다
- PC 1이다 → 그 PC의 뱅크 집합을 대상으로 한다

[05장](../05_stack_anatomy/)에서 base die를 *"커맨드를 각 층으로 배분한다"* 고 했습니다. 그 배분이 여기서 일어납니다.

### 단계 ④ — TSV를 타고 오른다

해당 core die까지 **수십 µm**를 오릅니다. TSV와 µbump를 번갈아 지납니다([03장](../03_stacking_tsv/)).

### 단계 ⑤ — 행을 열고 열을 고른다

이제 [01장](../01_dram_operation/)의 내용이 그대로 일어납니다.

1. **`ACT`** — 뱅크 5의 word line 3,412번을 켠다. 그 행의 셀이 전부 열려 전하를 내놓고, sense amplifier가 받아 붙든다. **`tRCD` 대기.**
2. **`RD`** — Row Buffer에서 열 9에 해당하는 구간을 골라 내보낸다. HBM4는 PC당 **256비트**를 한 번에 꺼냅니다.

**여기서 32바이트가 나옵니다** — 256비트 = 32바이트. 요청과 정확히 맞습니다.

### 되돌아오는 길

256비트가 32개의 DQ 핀으로 나가야 합니다.

```
256 비트 ÷ 32 핀 = 핀당 8 비트
→ 8 UI 에 걸쳐 나간다  =  버스트 길이 8 (BL8)
```

전송률 6.4 Gb/s에서 1 UI = 약 **156 ps**이므로, 버스트 전체가 **약 1.25 ns** 만에 나갑니다 **[개략]**.

그 데이터가 TSV를 내려오고, base die를 지나, 인터포저를 건너 호스트에 도착합니다.

## 4. 일반화 — 시간은 어디서 쓰이나

여정을 다 봤으니 이제 **비용**을 봅니다. 각 구간이 시간을 얼마나 쓰는지 규모로 비교합니다 **[개략]**.

| 구간 | 성격 | 대략 소요 | 비중 |
|---|---|---|---|
| ① 주소 쪼개기 | 호스트 로직 | 1 사이클 미만 | 무시 |
| ② 인터포저 통과 | **거리** | **약 0.03 ns** | **거의 0** |
| ③ Base die 처리 | 동작 | 수 ns | 작음 |
| ④ TSV 통과 | **거리** | **약 0.001 ns** | **거의 0** |
| ⑤ `ACT` + `tRCD` | **동작** | **십수 ns** | **지배적** |
| ⑤ `RD` → 데이터 출력 | 동작 | 수~십수 ns | 큼 |
| 되돌아오기 (버스트) | 직렬화 | 약 1.25 ns | 작음 |

### ★ 전파 지연은 병목이 아니다

②와 ④를 보세요. **거리 구간의 비용이 사실상 0입니다.**

전기 신호는 배선에서 대략 **광속의 절반** 정도로 진행합니다. 그러면

```
인터포저 5 mm  →  약 0.03 ns
TSV 50 µm      →  약 0.0003 ns
비교: 옛 방식의 PCB 5 cm  →  약 0.3 ns
```

가장 긴 경우조차 **0.3 ns**입니다. 그런데 전체 읽기 지연은 **수십 ns**입니다. 거리를 100배 줄여도 **전체 지연은 1 % 도 줄지 않습니다.**

:::caution[그러면 거리를 줄인 이득은 무엇이었나]
여기가 이 코스에서 가장 뒤집히기 쉬운 지점입니다. [02장](../02_memory_wall/)에서 *"거리를 줄이면 두 벽이 물러난다"* 고 했는데, 그 벽은 **지연의 벽이 아니었습니다.**

| 거리를 줄여서 얻은 것 | 얻지 못한 것 |
|---|---|
| **비트당 에너지가 낮아진다** | ❌ 지연 |
| **신호가 덜 뭉개진다** → 낮은 전송률로도 안정 | |
| **배선을 가늘고 촘촘하게** → 폭을 넓힐 수 있다 | |

즉 거리를 줄인 이득은 **에너지와 폭**이고, 그 폭이 **대역폭**을 줍니다. **지연은 처음부터 대상이 아니었습니다.**

그래서 [02장](../02_memory_wall/)의 오해 *"대역폭이 크면 지연도 짧다"* 가 틀린 것입니다. HBM의 지연은 DDR과 비슷하거나 오히려 조금 깁니다 — base die를 한 번 더 거치기 때문입니다.
:::

### 지연의 정체 — 대부분의 시간에 아무것도 이동하지 않는다

`tRCD` 동안 무슨 일이 일어나는지 다시 보면 이 결론이 자연스럽습니다.

`tRCD`는 **신호가 어디로 이동하는 시간이 아닙니다.** word line이 켜지고, 셀의 미세한 전하가 bit line에 퍼지고, sense amplifier가 그 차이를 판정 가능한 크기로 키우는 **물리적 동작에 걸리는 시간**입니다.

> **DRAM 지연의 대부분은 "거리"가 아니라 "동작"이다.**

[01장](../01_dram_operation/)에서 *"메모리는 값을 그냥 꺼내지 않는다"* 고 했습니다. 그 문장의 정량적 근거가 이 표입니다. 그리고 이것이 **DRAM 지연이 수십 년간 개선되지 않은 이유**이기도 합니다 — 물리적 동작 시간은 배선을 짧게 해서 줄일 수 없습니다.

### 그러면 대역폭은 어디서 나오나

지연이 그대로인데 대역폭이 큰 이유를 이제 정확히 말할 수 있습니다. **여정이 겹치기 때문**입니다.

```
채널 0  :  ACT ──tRCD── RD ──── 데이터
채널 1  :     ACT ──tRCD── RD ──── 데이터
채널 2  :        ACT ──tRCD── RD ──── 데이터
   ...
채널 31 :                        ... (32개가 동시에 진행)
```

채널 32개가 **서로 독립**이므로 32개의 여정이 동시에 진행됩니다. 각 채널 안에서도 PC 2개, 뱅크 32개가 대기 시간을 겹칩니다([01장](../01_dram_operation/)의 뱅크 인터리빙).

**요청 하나의 지연은 수십 ns 그대로이고, 동시에 진행되는 요청의 개수가 대역폭을 만듭니다.**

## 5. 디테일 — 여정의 특이점들

### 쓰기는 무엇이 다른가

방향이 반대이고, 결정적인 차이가 하나 있습니다 — **쓰기는 언제 끝났는지가 애매합니다.**

읽기는 데이터가 호스트에 도착하면 끝입니다. 쓰기는 데이터가 장치에 도착한 뒤에도 **셀에 실제로 기록되는 시간**이 남습니다. 그 시간이 [01장](../01_dram_operation/)에서 본 `tWR`이고, 이것이 끝나기 전에 행을 닫으면 데이터가 온전히 저장되지 않습니다.

그래서 컨트롤러는 쓰기 커맨드를 보낸 뒤에도 **얼마나 기다려야 하는지 계산해야** 합니다.

### 되돌아오는 길의 반직관 — 읽기 데이터를 부르는 것은 쓰기 스트로브다

기초 단계에서 알아 둘 만한 특이점이 하나 있습니다.

데이터가 오갈 때는 "지금이 유효한 비트다"를 알려 주는 **스트로브** 신호가 함께 갑니다. 쓰기용(WDQS)과 읽기용(RDQS)이 따로 있습니다.

그런데 HBM4에서 **읽기 데이터를 끌어내는 것은 읽기 스트로브가 아니라 쓰기 스트로브**입니다. 읽기 스트로브가 쓰기 스트로브에서 만들어지기 때문입니다.

결과: **호스트는 읽기만 하는 동안에도 쓰기 스트로브를 계속 공급해야** 합니다. "읽기 중에는 쓰기 신호가 필요 없다"는 직관이 여기서 깨집니다.

상세는 [`hbm4_jedec_dd` Ch07](../../hbm4_jedec_dd/07_column_commands/)에 있습니다. 여기서는 **여정에 겉보기와 다른 의존이 있다**는 것만 기억하면 됩니다.

### 두 번째 요청은 훨씬 빠를 수 있다

방금 읽은 것과 **같은 행**을 다시 읽는다면, 단계 ⑤의 `ACT`와 `tRCD`가 필요 없습니다. 행이 이미 열려 있으니 `RD`만 보내면 됩니다 — [01장](../01_dram_operation/)의 **행 히트**입니다.

반대로 **같은 뱅크의 다른 행**이면 `PRE` → `tRP` → `ACT` → `tRCD`를 다시 거칩니다 — **행 충돌**이고 가장 비쌉니다.

전체 여정에서 이 차이가 어디에 있는지 보면 **단계 ⑤ 안**입니다. ①~④는 매번 같습니다. 즉 **성능 변동의 대부분이 셀 접근 구간에서 나옵니다.**

### base die를 지날 때 일어나는 일이 더 있다

이 장에서는 base die를 "커맨드를 배분한다"로만 다뤘지만, 실제로는 지나가는 데이터에 대해 더 많은 일을 합니다 — 오류 검출·정정, 온도 감시, 테스트 경로 관리 등입니다.

특히 **오류 정정**은 되돌아오는 데이터 경로에 실제로 개입합니다. 어떻게 개입하고 무엇을 대가로 치르는지는 이 코스의 범위를 넘습니다 — [`hbm` Ch06](../../hbm/06_base_die_soc/)과 [`hbm4_jedec_dd` Ch09](../../hbm4_jedec_dd/09_ecc_ecs_sev/)에서 다룹니다.

## 6. 흔한 오해

:::caution[넷]
**① "거리를 줄였으니 지연도 줄었다"**
아닙니다. 전파 지연은 인터포저 5 mm에서 약 **0.03 ns**, 옛 PCB 5 cm에서도 약 **0.3 ns**입니다. 전체 지연 수십 ns에 비해 **무시할 수준**입니다. 거리를 줄여 얻은 것은 **에너지와 폭**입니다.

**② "메모리 지연은 신호가 멀리 이동하기 때문이다"**
아닙니다. 지연의 대부분은 **이동이 아니라 동작**입니다 — `tRCD`는 센스앰프가 미세한 전하 차이를 키우는 물리적 시간입니다.

**③ "대역폭이 크면 요청 하나도 빨리 온다"**
아닙니다. 요청 하나의 지연은 그대로이고, **동시에 진행되는 요청의 개수**가 대역폭을 만듭니다.

**④ "읽기 중에는 쓰기 관련 신호가 필요 없다"**
아닙니다. HBM4에서 읽기 스트로브는 쓰기 스트로브에서 생성되므로, **읽기 중에도 쓰기 스트로브를 공급해야** 합니다.
:::

---

## 7. 핵심 정리

- 읽기 여정은 다섯 구간 — ① 주소 쪼개기 → ② 인터포저 → ③ base die → ④ TSV → ⑤ core die. **가는 길과 오는 길이 같은 구간을 쓰고**, 실어 보내는 것만 다르다.
- 물리 주소는 **채널 · PC · SID · 뱅크 · 행 · 열**로 쪼개진다. **`{SID, BA}` 가 실제 뱅크 인덱스**이며, 버스트 안의 위치를 고르는 하위 비트는 **장치로 보내지 않는다.**
- 한 번의 `RD`가 PC당 **256비트 = 32바이트**를 꺼내고, 32개 DQ 핀으로 **8 UI(BL8)** 에 걸쳐 나간다. 6.4 Gb/s에서 약 **1.25 ns**.
- ★ **거리 구간의 비용은 사실상 0이다** — 인터포저 약 **0.03 ns**, TSV 약 **0.001 ns**. 전체 지연 수십 ns의 **1 % 미만**이다.
- ★ 따라서 **거리를 줄인 이득은 지연이 아니라 에너지와 폭**이었다. 그 폭이 대역폭을 준다. HBM의 지연은 DDR과 비슷하거나 **오히려 조금 길다**(base die를 더 거치므로).
- ★ **DRAM 지연의 대부분은 "거리"가 아니라 "동작"이다.** `tRCD`는 센스앰프가 전하 차이를 키우는 물리적 시간이며, 배선을 짧게 해서 줄일 수 없다 — 지연이 수십 년간 개선되지 않은 이유다.
- 대역폭은 **여정이 겹쳐서** 나온다. 채널 32개가 독립이고, 각 채널 안에서 PC 2개와 뱅크 32개가 대기 시간을 겹친다. **지연은 그대로, 동시 진행 개수가 대역폭이다.**
- **쓰기는 끝나는 시점이 애매하다** — 데이터가 도착한 뒤에도 셀에 기록되는 시간(`tWR`)이 남는다.
- 성능 변동의 대부분은 **단계 ⑤ 안**에서 나온다 — 행 히트/미스/충돌. ①~④는 매번 같다.
- HBM4에서 **읽기 스트로브는 쓰기 스트로브에서 만들어진다.** 읽기 중에도 쓰기 스트로브 공급이 필요하다.
