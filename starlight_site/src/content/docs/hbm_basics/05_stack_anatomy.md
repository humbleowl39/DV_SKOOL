## 1. Why care? — 완성된 스택은 어떻게 생겼나

[03장](../03_stacking_tsv/)과 [04장](../04_interposer/)에서 물리적 연결이 이어졌습니다. TSV가 die를 관통하고, µbump가 die 사이를 붙이고, 인터포저가 스택과 프로세서를 잇습니다.

이제 **완성된 스택의 구조**를 봅니다. 그리고 이 장에서 가장 놓치기 쉬운 것을 다룹니다.

[01장](../01_dram_operation/)에서 뱅크와 행/열을 배웠습니다. 그것들이 이 여러 층에 어떻게 배치될까요? 그리고 "채널"이라는 단어가 자주 나오는데, **채널과 die는 같은 것일까요?**

답은 아닙니다. 그리고 그 어긋남이 이 장의 핵심입니다.

---

## 2. 직관 — 두 종류의 die, 그리고 두 종류의 단위

### 스택에는 성격이 다른 die가 두 종류 있다

| | **Core die** (DRAM die) | **Base die** (Logic die) |
|---|---|---|
| 개수 | 여러 장 (4·8·12·16) | **1장**, 스택 최하단 |
| 담고 있는 것 | **셀 어레이** — 실제 데이터 | **인터페이스 로직** — 데이터 없음 |
| 하는 일 | 뱅크·행·열을 갖고 데이터를 저장한다 | 호스트와 통신하고, 커맨드를 각 층으로 배분한다 |
| 호스트와의 관계 | **직접 보지 않는다** | **유일하게 마주본다** |

[03장](../03_stacking_tsv/)의 그림에서 최하단 하나만 색이 달랐던 이유입니다. 호스트는 base die만 보고, core die는 base die 뒤에 숨어 있습니다.

### 그리고 단위가 두 종류다

여기가 혼동의 근원입니다.

| 단위 | 성격 | 무엇을 세는가 |
|---|---|---|
| **die** | **물리** | 실리콘 몇 장을 쌓았나 |
| **채널** | **논리** | 독립적으로 동작하는 인터페이스가 몇 개인가 |

직관적으로는 "die 하나가 채널 하나"일 것 같습니다. **그렇지 않습니다.**

HBM4 규격은 채널을 **32개로 고정**합니다. 스택이 4층이든 16층이든 **32개**입니다. 그런데 32채널을 만들려면 **die가 최소 4장** 필요합니다.

그러면 8층으로 쌓으면 무슨 일이 생길까요? 채널이 64개가 되지 않습니다. **여전히 32개**이고, 대신 **채널 하나가 die 두 장에 걸칩니다.**

### 한 장 그림 — 채널이 die를 가로지른다

```d2
direction: down

HOSTSIDE: "호스트" { style.fill: "#e3f2fd"; style.font-color: "#0A0F25" }

BASE: "Base Die\n호스트와 마주보는 유일한 층\n커맨드를 각 층으로 배분한다" {
  style.fill: "#bbdefb"; style.font-color: "#0A0F25"
}

SID0: "채널 0  ·  SID = 0\ncore die 아래쪽 한 장\n뱅크 16개" {
  style.fill: "#e8f5e9"; style.font-color: "#0A0F25"
}
SID1: "채널 0  ·  SID = 1\ncore die 위쪽 한 장\n뱅크 16개" {
  style.fill: "#e8f5e9"; style.font-color: "#0A0F25"
}

OTHERS: "채널 1 ~ 31\n각각 같은 방식으로 die 두 장에 걸친다" {
  style.fill: "#eceff1"; style.font-color: "#0A0F25"
}

HOSTSIDE -> BASE: "인터포저 경유"
BASE -> SID0: "SID = 0"
BASE -> SID1: "SID = 1"
BASE -> OTHERS
```

**채널 0은 die 하나에 있지 않습니다.** 두 장에 걸쳐 있고, 어느 쪽인지는 **SID(Stack ID)** 라는 주소 비트로 고릅니다.

그래서 SID는 "몇 번째 층인가"를 고르는 신호처럼 보이지만, 실제로는 **뱅크 주소의 확장 비트**입니다. 채널 입장에서는 뱅크가 16개에서 32개로 늘어난 것이고, 그 늘어난 절반이 물리적으로 다른 die에 있을 뿐입니다.

## 3. 작은 예 — 스택 높이가 무엇을 바꾸는가

숫자로 확인합니다. 규격이 정한 관계는 이렇습니다.

- 채널 수 = **32** (고정)
- 32채널을 만들려면 core die **최소 4장**
- 4장을 넘는 die는 **용량·SID·뱅크**를 늘린다 — **채널은 늘리지 않는다**

이 셋에서 표가 유도됩니다.

| 스택 높이 | core die | SID 비트 | SID 유효값 | 채널당 뱅크 | 채널 수 |
|---|---|---|---|---|---|
| **4-high** | 4 | **없음** | 1 | 16 × 1 = **16** | 32 |
| **8-high** | 8 | `SID[0]` | 2 | 16 × 2 = **32** | 32 |
| **12-high** | 12 | `SID[1:0]` | **3** | 16 × 3 = **48** | 32 |
| **16-high** | 16 | `SID[1:0]` | 4 | 16 × 4 = **64** | 32 |

두 가지를 짚어 둡니다.

**① 12-high의 SID 유효값이 3개인 이유** — `SID[1:0]`은 2비트라 네 값을 표현할 수 있지만, 규격은 **`SID[1:0] = 11`을 무효**로 둡니다. 12-high는 die가 12장(=4×3)이므로 SID로 구분할 그룹이 3개뿐이고, 남는 조합 하나를 무효로 만든 것입니다.

**② 뱅크 수가 16의 배수인 이유** — die 4장 묶음 하나가 채널당 16뱅크를 제공하고, 묶음이 늘어날 때마다 16개씩 더해집니다. 규격이 채널당 뱅크를 **16 / 32 / 48 / 64** 로 정의한 것이 이 산술과 정확히 맞습니다.

### 용량은 어떻게 되나

core die 하나의 밀도가 **24 Gb** 또는 **32 Gb** 입니다(규격 Table 4). 스택 용량은 단순한 곱셈입니다.

```
스택 용량 = die 밀도 × die 수 ÷ 8   (Gb → GB)
```

| die 밀도 | 4-high | 8-high | 12-high | 16-high |
|---|---|---|---|---|
| **24 Gb** | 12 GB | 24 GB | 36 GB | 48 GB |
| **32 Gb** | 16 GB | 32 GB | 48 GB | **64 GB** |

**12 GB ~ 64 GB** 범위가 나옵니다.

### 대역폭은 어떻게 되나

[02장](../02_memory_wall/)의 공식을 그대로 씁니다.

```
버스 폭 = 32채널 × 64비트 = 2,048 비트
대역폭 = 2,048 비트 × 전송률 ÷ 8
```

| 전송률 (핀당) | 스택 하나의 대역폭 |
|---|---|
| 4.8 Gb/s (규격 최저 등급) | 약 **1.2 TB/s** |
| 6.4 Gb/s | 약 **1.6 TB/s** |
| 8.0 Gb/s (규격 최고 등급) | 약 **2.0 TB/s** |

:::caution[여기서 index의 오해가 완전히 풀린다]
표를 나란히 놓으면 분명해집니다.

| 스택을 높이면 | 결과 |
|---|---|
| 용량 | **늘어난다** (12 → 64 GB) |
| 채널당 뱅크 | **늘어난다** (16 → 64) |
| 채널 수 | **그대로** (32) |
| 버스 폭 | **그대로** (2,048 비트) |
| **대역폭** | **그대로** |

**스택 높이는 대역폭을 바꾸지 않습니다.** 대역폭을 바꾸는 것은 **전송률**뿐이고, 폭은 채널 수 × 채널 폭으로 고정입니다.

[02장](../02_memory_wall/)에서 *"쌓기는 폭을 얻기 위한 수단"* 이라고 했습니다. 이 표가 그 문장의 정확한 의미입니다 — **쌓기 자체가 대역폭을 주는 것이 아니라, 쌓을 수 있는 구조(짧은 거리·미세 배선)가 넓은 버스를 가능하게** 한 것입니다. 일단 그 구조를 얻은 뒤에는, 더 쌓아도 대역폭은 그대로이고 용량만 늡니다.
:::

## 4. 일반화 — 채널이 물리 층과 어긋나면 무엇이 따라오나

### 요구사항 하나가 강제된다 — 동일 레이턴시

채널 하나가 die 여러 장에 걸친다는 사실에서 문제가 하나 나옵니다.

16-high 구성에서 채널 0은 **die 4장**에 걸쳐 있습니다. 그런데 base die에서 각 die까지의 물리적 거리가 다릅니다 — 가장 아래 die는 TSV 한 구간, 가장 위 die는 네 구간을 지나야 합니다.

그러면 **SID에 따라 응답 시간이 달라질까요?**

규격은 그것을 금지합니다.

> 한 채널 내의 모든 접근은 **동일한 레이턴시**를 가져야 한다. — HBM4 규격 §3 (요약)

즉 SID가 0이든 3이든 호스트가 보는 지연은 **같아야** 합니다.

이 요구가 벤더에게 강제하는 것이 있습니다 — **짧은 경로에 의도적으로 지연을 넣어 균등화해야** 합니다. 결과적으로 **레이턴시는 가장 먼 경로에 맞춰 고정**됩니다.

:::tip[왜 이런 규정을 두는가]
호스트 입장에서 생각하면 답이 보입니다. 만약 SID마다 지연이 다르면, 메모리 컨트롤러는 **어느 주소가 어느 die에 있는지 알고 스케줄링해야** 합니다. 컨트롤러가 스택의 물리적 구성에 종속되는 것입니다.

레이턴시를 균등화하면 컨트롤러는 **die 위치를 알 필요가 없습니다.** 채널을 하나의 균일한 저장 공간으로 다루면 됩니다. 규격이 복잡함을 장치 쪽으로 밀어 넣고 호스트를 단순하게 유지한 것입니다.

대가는 **성능**입니다 — 가까운 die도 먼 die만큼 기다립니다. 규격이 그 대가를 지불할 만하다고 판단한 것입니다.
:::

### 물리적 배치는 벤더가 정한다

규격은 채널 32개가 있어야 한다고만 말하고, **그 채널들을 die에 어떻게 나눠 담을지는 정하지 않습니다.** 4-high에서 die 하나에 8채널을 균등 배치할 수도 있고 다르게 할 수도 있습니다.

그래서 같은 "HBM4 16-high 32 Gb" 제품이라도 **벤더마다 내부 배치가 다를 수 있습니다.** 호스트가 보는 인터페이스와 동작만 같으면 규격을 만족합니다.

### Pseudo-channel — 채널 아래의 또 한 층

채널이 논리 단위라는 이야기에 층이 하나 더 있습니다. 각 채널은 다시 **두 개의 pseudo-channel(PC)** 로 나뉩니다.

```
채널 하나  =  64비트 데이터 버스
             ├─ Pseudo-channel 0  →  DQ[31:0]   (32비트)
             └─ Pseudo-channel 1  →  DQ[63:32]  (32비트)
```

두 PC는 **각자의 뱅크 집합**에 접근하므로 독립적으로 동작합니다. 그런데 완전히 독립은 아닙니다 — **커맨드 버스와 클럭, 그리고 설정 레지스터를 공유**합니다.

기초 단계에서 기억할 것은 두 가지입니다.

- 스택 하나에 **32채널 × 2 PC = 64개**의 준독립 단위가 있다
- "독립"에 **정도**가 있다 — 채널은 완전 독립, PC는 준독립

이 "정도"의 차이가 실제로 무엇을 뜻하는지는 [`hbm` Ch04](../../hbm/04_channels_addressing/)에서, 규격 조문 수준의 상세는 [`hbm4_jedec_dd` Ch01](../../hbm4_jedec_dd/01_landscape_organization/)에서 다룹니다.

## 5. 디테일 — Base die가 특별한 이유

### 하는 일이 다르다

core die는 셀을 담습니다. base die는 데이터를 담지 않고 **인터페이스와 관리**를 담당합니다.

| 기능 | 내용 |
|---|---|
| 호스트 인터페이스 | 인터포저를 통해 오는 신호를 받고 내보낸다 |
| 커맨드 배분 | 어느 채널·어느 SID로 갈 커맨드인지 판단해 TSV로 올려 보낸다 |
| 테스트·복구 | [03장](../03_stacking_tsv/)에서 본 불량 레인 복구, 배열 자체 복구 |
| 온도 감시 | 스택 온도를 호스트에 보고한다 → [07장](../07_thermal/) |
| 신뢰성 | 오류 검출·정정 관련 기능 |

### 공정이 갈라진다

여기서 흥미로운 일이 생깁니다. DRAM 공정과 로직 공정은 최적화 방향이 다릅니다 — DRAM 공정은 **커패시터를 잘 만드는 데** 특화되어 있고, 로직 공정은 **트랜지스터를 빠르고 촘촘하게** 만드는 데 특화되어 있습니다.

base die에는 셀이 없습니다. 로직만 있습니다. 그러면 **DRAM 공정으로 만들 이유가 없습니다.**

그래서 HBM4 세대에서 base die가 **로직 공정으로 이동**합니다. 결과가 둘입니다.

- 같은 면적에 **훨씬 많은 로직**이 들어간다 → 자리가 남는다
- 그 남는 자리에 **무엇을 넣을지**가 제품 차별화 지점이 된다

메모리 컨트롤러를 내리거나, 전력 관리를 넣거나, 고객 전용 연산 로직을 얹는 선택이 가능해집니다. 이것이 "Custom HBM"이라고 불리는 흐름입니다.

### 그런데 규격은 base die를 요구하지 않는다

이 장에서 가장 뜻밖의 사실입니다.

> DRAM 벤더는 스택 최하단에 신호 재분배 등의 기능을 제공하는 **선택적 인터페이스 다이를 요구하도록 선택할 수 있다.** **본 표준은 그러한 해법을 명시적으로 요구하지도, 금지하지도 않는다.** — HBM4 규격 §3 (요약)

**base die는 규격의 필수 구성이 아닙니다.**

규격이 정의하는 것은 **호스트가 보는 인터페이스와 동작**입니다. 그것을 어떤 물리 구조로 만족시킬지는 벤더의 몫입니다. 실제 제품에는 거의 항상 base die가 있지만, **규격이 그것을 강제한 것은 아닙니다.**

:::tip[이 조문이 산업 구조를 만든다]
규격이 "요구하지도 금지하지도 않는다"고 쓴 자리가 곧 **벤더가 자유롭게 쓸 수 있는 공간**입니다. base die가 규격 밖에 있으므로 벤더는 거기에 무엇이든 넣을 수 있고, 그래서 Custom HBM이 성립합니다.

같은 이유로, 검증 관점에서는 **base die 내부에 표준 참조 모델이 존재할 수 없습니다.** 표준이 정의하지 않은 것에 대한 표준 모델은 만들어질 수 없기 때문입니다. 이 귀결이 왜 중요한지는 [`hbm` Ch06](../../hbm/06_base_die_soc/)에서 다룹니다.
:::

## 6. 흔한 오해

:::caution[다섯]
**① "die 하나가 채널 하나다"**
아닙니다. HBM4는 채널이 **32개로 고정**이고, 32채널을 만들려면 **die가 최소 4장** 필요합니다. 8-high면 채널 하나가 **die 두 장에 걸칩니다.**

**② "스택을 높이면 채널이 늘어난다"**
아닙니다. 4장을 넘는 die는 **용량·SID·뱅크**를 늘리고 **채널은 늘리지 않습니다.** 채널 수는 항상 32입니다.

**③ "스택을 높이면 대역폭이 올라간다"**
아닙니다. 버스 폭이 2,048비트로 고정이므로 **대역폭도 그대로**입니다. 늘어나는 것은 **용량**입니다.

**④ "SID는 층을 고르는 신호다"**
층을 고르는 효과는 있지만, 실제로는 **뱅크 주소의 확장 비트**입니다. 채널 입장에서는 뱅크가 16개에서 32·48·64개로 늘어난 것이고, 그 일부가 다른 die에 있을 뿐입니다.

**⑤ "base die는 HBM의 필수 구성이다"**
규격은 그것을 **요구하지도 금지하지도 않습니다.** 실제 제품에는 거의 항상 있지만, 규격이 정의하는 것은 호스트가 보는 인터페이스와 동작뿐입니다.
:::

---

## 7. 핵심 정리

- 스택에는 성격이 다른 die가 둘 — **core die**(셀 어레이, 여러 장)와 **base die**(인터페이스 로직, 최하단 1장). 호스트는 **base die만 마주봅니다.**
- ★ **채널은 논리 단위, die는 물리 단위이며 둘은 일치하지 않습니다.** HBM4는 채널이 **32개 고정**이고, 32채널을 만들려면 **core die 최소 4장**이 필요합니다.
- 4장을 넘는 die는 **용량·SID·뱅크**를 늘립니다. **채널은 늘지 않습니다.**
- 그래서 채널 하나가 **die 여러 장에 걸칩니다.** 어느 die인지는 **SID**로 고르며, SID는 층 선택 신호가 아니라 **뱅크 주소 확장 비트**입니다.
- 유도되는 표 — 스택 높이 4/8/12/16 → SID 유효값 1/2/**3**/4 → 채널당 뱅크 **16/32/48/64**. (12-high가 3인 것은 `SID[1:0]=11`이 무효이기 때문)
- 용량 = die 밀도(24 또는 32 Gb) × die 수 ÷ 8 → **12 GB ~ 64 GB**.
- 대역폭 = 32채널 × 64비트 = **2,048비트** × 전송률 ÷ 8 → 4.8~8.0 Gb/s에서 약 **1.2 ~ 2.0 TB/s**.
- ★ **스택 높이는 대역폭을 바꾸지 않습니다.** 폭이 고정이므로 전송률만이 대역폭을 바꿉니다. 쌓기는 **넓은 버스를 가능하게 한 구조적 전제**였을 뿐입니다.
- 채널이 여러 die에 걸치므로 **"한 채널 내 동일 레이턴시"** 가 강제됩니다. 벤더는 짧은 경로에 지연을 넣어 균등화하고, 그 대가로 **레이턴시가 가장 먼 경로에 고정**됩니다. 이득은 컨트롤러가 die 위치를 몰라도 된다는 것입니다.
- 채널 아래에 **pseudo-channel** 층이 하나 더 있습니다 — 채널당 2개, 스택당 **64개**. 채널은 완전 독립이지만 PC는 **준독립**(커맨드 버스·클럭·설정 공유)입니다.
- base die는 HBM4에서 **로직 공정으로 이동**하며, 남는 자리가 제품 차별화 공간이 됩니다. 그런데 **규격은 base die를 요구하지도 금지하지도 않습니다.**
