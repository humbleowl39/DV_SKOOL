## 1. Why care? — 항목별로 닫는 것과 전체가 굴러가는 것은 다르다

앞의 11챕터가 21개 항목을 각각 닫았습니다. 경계표를 만들었고, Agent를 만들었고, V-Plan을 썼고, assertion과 커버리지 모델을 설계했습니다.

각각은 맞습니다. 그런데 **순서와 타이밍이 있습니다.**

- V-Plan을 쓰려면 매핑표(Ch04)가 있어야 하는데, 매핑표를 만들려면 VIP를 골라야 하고, VIP를 고르려면 요구 목록이 있어야 하고, 요구 목록은 V-Plan의 일부입니다 — **어디서 시작합니까?**
- Agent 개발(Ch03)은 몇 주가 걸립니다. 그동안 시나리오(Ch08)는 무엇을 대상으로 씁니까?
- 프로파일 P1(Ch05)을 초기에 세우라고 했는데, 그때 DUT RTL이 아직 없다면?

**조각이 맞는다고 조립되는 것은 아닙니다.** 그리고 실제 프로젝트에서는 조각이 다 준비되기 전에 시작해야 합니다.

이 챕터는 `hbm_ch_ctrl` 프로젝트를 **처음부터 끝까지** 따라갑니다. 각 시점에서 무엇을 하고 무엇을 미루는지, 실패가 나왔을 때 어떻게 분류하는지, 그리고 마지막에 **무엇이 검증되지 않았는지 어떻게 말하는지**까지 갑니다.

## 2. 직관 — 순환 의존을 푸는 법

### 순진한 시도 — 순서대로 완성하며 진행한다

경계표를 완성하고, V-Plan을 완성하고, 환경을 완성하고, 시나리오를 완성합니다.

**어디서 막히나?** 위의 순환 의존입니다. 그리고 각 단계를 "완성"하려면 다음 단계의 정보가 필요한 경우가 많습니다. 완성을 기다리면 착수 자체가 늦어집니다.

### 일반화 — 얕게 한 바퀴 돌고, 깊게 다시 돈다

> **모든 산출물을 초기에 **얕게** 한 번씩 만들고, 프로젝트가 진행되며 **깊게** 갱신한다.**

| 산출물 | 1차 (착수 주) | 갱신 |
|---|---|---|
| 경계표 | IP 목록 수준 | VIP 확정·프로파일 추가 시 |
| V-Plan | 스펙 규칙만 나열 | 매핑표·통합·성능 항목 추가 |
| 매핑표 | 후보 VIP 기준 추정 | 도입 후 실측 |
| 환경 | 골격만 (Agent 스텁) | Agent 완성 후 교체 |
| 프로파일 | P0만 | P1 스모크 추가 |

**얕은 1차의 목적은 정확성이 아니라 구조 확보**입니다. 자리가 있으면 채워집니다. 자리가 없으면 나중에 만들 자리를 찾지 못합니다.

이것이 Ch05에서 *"P1을 최소 규모로라도 초기에 세우라"* 고 한 것, Ch07에서 *"V-Plan은 변경 이력이 있는 살아 있는 문서"* 라고 한 것의 통합된 형태입니다.

## 3. 프로젝트 관통 — `hbm_ch_ctrl` 검증

### Phase 1 — 착수: 경계를 긋는다 (Ch01·Ch02)

**받은 것**: `hbm_ch_ctrl` 스펙(부록 A), RTL 초기 버전, IP 목록.

**첫 작업은 코드가 아니라 경계표**입니다.

| 대상 | 분류 | 조달 | 담당 |
|---|---|---|---|
| `hbm_ch_ctrl` RTL | **DUT** | — | 설계팀 |
| CCI 상대편 | 모델·VIP | ⚠️ **자체 개발** | 우리 (3주 예상) |
| DRAM | 모델·VIP | 구매 검토 | 우리 |
| PHY 아날로그 | 범위 밖 | — | mixed-level (Ch05) |

**여기서 즉시 나오는 결정 두 가지**

1. **CCI Agent 개발 3주**를 일정에 넣습니다. 넣지 않으면 Ch02 실패 2가 그대로 발생합니다
2. DRAM VIP **조달 절차를 지금 시작**합니다. 구매는 리드타임이 있습니다

**동시에 Handoff 체크리스트(H1~H6)** 를 3rd party IP에 대해 발송합니다. 답이 오는 데 시간이 걸리므로 일찍 보냅니다.

### Phase 2 — 계획: V-Plan 1차 (Ch04·Ch07)

VIP 후보 문서로 **매핑표 1차**를 만듭니다. 아직 도입 전이므로 추정이지만, **잔여 목록의 규모**를 알 수 있습니다.

> 표준 타이밍(R4~R8)은 VIP가 담당 → **잔여: R1~R3, R9~R20, 통합 I1~I8, 성능**

**V-Plan 1차**를 씁니다. 이 시점의 목표는 완성이 아니라 **항목 목록 리뷰를 받는 것**입니다.

리뷰에서 실제로 나오는 지적들:

- *"R14가 한 행인데 sticky 확인이 빠진 것 아닌가"* → 3행으로 분할 (Ch07)
- *"성능 항목에 목표치가 없다"* → 제품 요구에서 가져와야 함
- *"테스트 모드 항목이 없다"* → R17~R20 추가
- *"통합 항목은 어디 있나"* → I1~I8 절 신설

**이 리뷰가 이 프로젝트에서 가장 값싼 시점의 가장 큰 이득**입니다. 지금 빠진 항목을 찾는 비용은 몇 시간이고, 6개월 뒤에 찾는 비용은 몇 주입니다.

**게이트: 계획 리뷰 통과** — 경계표 확정, 항목 목록 리뷰 완료, 조달 계획 확정.

### Phase 3 — 환경: 골격부터 (Ch03·Ch05·Ch06)

**병렬로 진행합니다.**

| 트랙 | 내용 | 기간 |
|---|---|---|
| A | CCI Agent 개발 (Ch03) | 3주 |
| B | 환경 계층 골격 + config 구조 (Ch06) | 1주 |
| C | DRAM VIP 도입·연결 | 조달 후 1주 |

**B가 A보다 먼저 끝납니다.** 그동안 Agent 자리에는 스텁을 둡니다. 골격이 서 있으면 A가 완성되는 즉시 교체만 하면 됩니다.

**Agent 개발에서 실제로 하는 일**은 코드 작성이 아니라 **능력 역산표부터**입니다 (Ch03 §2).

| 스펙 규칙 | 필요 능력 | 구조 |
|---|---|---|
| R12·R13 | 틀린 패리티 전송 | `inject_*` rand 필드 |
| R11 | 다수 미해결 | driver non-blocking |
| R9 | id 매칭 | monitor 미해결 테이블 |
| #2 (성능) | 지연 측정 | `t_req`·`t_rsp` 필드 |

**마지막 행이 중요합니다.** 성능 측정은 Ch08에서야 쓰이지만, **지금 넣지 않으면 그때 item과 monitor를 고쳐야 합니다.**

**P1 스모크도 지금 세웁니다** (Ch05). 시나리오 하나만 돌면 됩니다. 목적은 검증이 아니라 **환경이 성립함을 확인**하는 것입니다.

**게이트: 환경 준비** — 스모크 통과, P0·P1 최소 구성 성립, Agent 자가 점검(monitor 재구성 값이 driver 의도와 일치하는지).

### Phase 4 — 구현: 세 수단을 함께 (Ch08·Ch09·Ch10)

여기서 흔한 실수는 **시나리오를 먼저 다 만들고 assertion을 나중에** 하는 것입니다. 그러면 Ch09의 마무리 문제 상황(cover 0%)이 발생합니다.

**함께 만듭니다.**

| V-Plan 항목 | 시나리오 | Assertion | Coverage |
|---|---|---|---|
| R3 CA 공유 | 동시 부하 | `a_ca_share` + **cover** | 동시 활성 조합 |
| R12~R14 오류 | 오류 주입 | — | 오류 종류 × 검사 활성 |
| R17~R20 모드 | 모드 전이 | `a_test_mode_quiet` + cover | **전이 bin** |
| #2 성능 | 부하 패턴 | — | `SCHED_MODE` |

**한 행을 세로로 완성하고 다음 행으로 갑니다.** 그러면 각 항목이 자극·감시·측정을 모두 갖춘 상태로 닫힙니다. 가로로(모든 시나리오 → 모든 assertion) 가면 마지막에 cover가 비어 있는 것을 발견합니다.

### Phase 5 — 회귀와 디버깅

회귀가 돌기 시작하고 실패가 나옵니다. **세 건이 동시에 올라옵니다.**

:::note[🤔 잠깐 — 세 실패를 분류하세요]
**실패 A**: `a_trcd` assertion 위반. `ACT` 후 3사이클에 `RD` 발행, `tRCD_CYC`는 8.

**실패 B**: 시나리오가 `len=15`인 CSR 쓰기를 생성해 DUT가 `INTERNAL_ERR`로 응답. 스펙 A.4 제약을 보니 CSR 접근은 단일 beat여야 함.

**실패 C**: DRAM VIP가 특정 `SCHED_MODE`에서 나온 커맨드 순서에 대해 *"지원하지 않는 조합"* 경고를 냄.

각각 **DUT 버그 / TB 버그 / 모델 한계** 중 무엇이며, 무엇을 해야 합니까?

<details>
<summary>정답 / 해설</summary>

**실패 A → DUT 버그**

경계표에서 `hbm_ch_ctrl` RTL은 **DUT** 칸입니다. 스펙 R6 위반이 명확하므로 설계팀에 보고합니다.

*보고에 포함할 것*: 위반 시점, 그 시점의 `tRCD_CYC` 설정값, 재현 시드, 관련 파형 구간. Ch09에서 assertion 메시지에 컨텍스트(pc·bank·경과·기준)를 넣어 둔 것이 여기서 값을 합니다.

**실패 B → TB 버그**

시나리오가 **스펙이 금지한 조합**을 생성했습니다. Ch03의 item에 `c_csr_len` 제약(`CSR 접근은 len == 0`)을 넣었는데, 이 시나리오가 그것을 우회했거나 제약이 누락된 것입니다.

*이것이 Ch06 #12(자극의 현실성)의 사례*입니다 — 자극이 **너무 넓어** 실제로 불가능한 입력을 만들었습니다. 조사 시간이 낭비되었고, 이런 실패가 반복되면 팀이 실패 보고를 신뢰하지 않게 됩니다.

*조치*: 제약을 고칩니다. 그리고 **왜 우회되었는지** 확인합니다 — `randomize() with`가 제약을 덮어썼을 수 있습니다.

**실패 C → 모델 한계**

VIP가 *"지원하지 않는 조합"* 이라고 말하고 있습니다. 이것은 DUT 버그도 TB 버그도 아닐 수 있습니다. 세 가지 가능성을 순서대로 확인합니다.

1. **우리 구성이 VIP 지원 범위 밖인가** → Ch02 H1의 답을 확인. 범위 밖이면 **그 조합은 우리가 검증**해야 하며 V-Plan에 항목이 있어야 합니다
2. **VIP 설정이 잘못되었나** → Ch04 실패 3(기본 설정 사용). 사전 구성이 우리 제품과 맞는지 확인
3. **정말로 DUT가 이상한 커맨드를 냈나** → 그렇다면 DUT 버그

*중요*: **VIP 경고를 무시하지 않습니다.** Ch04에서 본 대로 오탐이 쌓이면 팀이 경고 전체를 무시하기 시작하고, 그때 진짜 문제가 묻힙니다.

**세 실패를 분류할 수 있었던 이유**

**Phase 1에서 경계표를 만들어 뒀기 때문**입니다. 경계표가 없으면 세 건 모두 *"뭔가 이상하다"* 로 시작해 각각 원인을 처음부터 추적해야 합니다. Ch01에서 *"경계 문서의 가치는 작성 시점이 아니라 디버깅 시점에 발생한다"* 고 한 것이 이것입니다.

### Phase 6 — Closure와 Sign-off (Ch10)

회귀가 안정되고 커버리지를 닫습니다.

**커버리지 hole 분석에서 나오는 세 종류**

| Hole 종류 | 처리 |
|---|---|
| 시나리오 부족 | 시나리오 추가 |
| **도달 불가** | exclusion + **정당화 문서** (설계 동결 후) |
| **자극 불가** | ⚠️ 도달 불가와 **구분**해야 함 — Agent 능력 부족일 수 있음 |

세 번째가 함정입니다. Ch10 마무리 문제에서 본 대로, **자극하지 못한 것을 "도달 불가"로 처리하면** 미검증이 검증된 것으로 둔갑합니다.

**Sign-off 리뷰에서 보고하는 것**

Ch10의 형식을 따릅니다.

```
기능 항목:   통과 N / 구현중 N / 차단 N(사유) / Waive N(승인)
Assertion:   전부 PASS, cover 충족 N/N          ← 미충족이 있으면 그 규칙은 미측정
Coverage:    DUT 기능 X% (모델 항목 N개)
             VIP 프로토콜 Y%                      ← 출처 분리
             프로파일 P0 / P1 별도                ← 프로파일 분리
성능:        대역폭 실측/목표, 지연 평균·최악/목표
Exclusion:   N건, 전부 정당화 승인
차단 항목:   T-02, T-06 — 스펙 미정의 (Ch11)     ← 아래
```

**마지막 줄이 이 프로젝트의 정직한 상태입니다.**

Ch11에서 발견한 스펙 미정의 구간 두 건이 아직 **차단** 상태입니다. 설계에 질문했고 답을 기다리는 중입니다. 임의 해석해서 "통과"로 만들지 않았습니다.

**Sign-off 판단**: 차단 항목의 위험도를 평가하고, 감수하고 진행할지 답을 기다릴지 결정합니다. **이 결정은 검증이 아니라 프로젝트가 합니다.** 검증의 역할은 **무엇이 미검증인지 정확히 제시하는 것**입니다.

### Phase 7 — Silicon 이슈

칩이 나왔습니다. 몇 주 뒤 이슈가 올라옵니다.

> *"특정 워크로드에서 간헐적으로 데이터 손상. 테스트 모드 진입·복귀를 반복하는 진단 루틴 실행 직후에 재현율이 높음."*

**"테스트 모드 진입·복귀 직후"** — 익숙한 문구입니다. Ch11에서 **T-06(복귀 후 뱅크 상태)** 을 스펙 미정의로 기록하고 차단 상태로 둔 그 항목입니다.

**대응이 빨랐던 이유**

1. **이미 알고 있었습니다.** 차단 항목 목록에 있었으므로 후보를 좁히는 데 시간이 들지 않았습니다
2. **재현 시나리오를 즉시 만들 수 있었습니다.** Ch08의 모드 전이 시나리오가 이미 있고, 복귀 직후 접근 패턴만 추가하면 됐습니다
3. **관측 수단이 준비되어 있었습니다.** Ch09의 assertion과 Ch11의 투명성 레지스터 조회가 이미 환경에 있었습니다

**하루 만에 시뮬레이션에서 재현**되었습니다. 원인은 복귀 후 뱅크 상태에 대한 **설계와 펌웨어의 가정 불일치**였습니다.

만약 T-06을 *"RTL이 유지하니까 유지가 맞겠지"* 로 임의 해석하고 통과 처리했다면, 이 이슈는 **"검증에서 통과했는데 왜"** 로 시작해 훨씬 오래 걸렸을 것입니다.

## 4. 일반화 — 검증이 완벽할 수 없다면

### 대안 A — 모든 것을 검증하고 sign-off한다면?

이상적입니다. 그러나 Ch01의 대안 B에서 본 대로 **끝나지 않습니다.** 모델의 정확성, 자극의 완전성, 스펙의 완결성 중 어느 것도 100%가 아닙니다.

### 대안 B — 완벽하지 않으니 적당히 하고 넘긴다면?

무엇이 검증되지 않았는지 모른 채 넘기는 것입니다. 이슈가 나왔을 때 **후보가 전체**가 되고, 대응이 느립니다.

### 채택 — 무엇을 모르는지 정확히 아는 상태로 넘긴다

> **좋은 검증은 모든 것을 잡는 것이 아니라, 무엇을 잡지 않았는지 정확히 아는 것이다.**

이 코스가 만든 산출물들이 전부 이 방향을 향합니다.

| 산출물 | 무엇을 명시적으로 만드는가 |
|---|---|
| 경계표 (Ch01) | 검증 **대상이 아닌 것** |
| 매핑표 (Ch04) | VIP가 **검사하지 않는 것** |
| 프로파일 한계표 (Ch05) | 각 프로파일이 **답하지 못하는 질문** |
| V-Plan 상태 (Ch07) | **차단·waive** 항목 |
| Cover property (Ch09) | **자극되지 않은** 규칙 |
| Exclusion 정당화 (Ch10) | **제외한 것과 그 이유** |
| 스펙 빈틈 기록 (Ch11) | **정의되지 않은** 동작 |

**전부 "모르는 것"을 가시화하는 장치입니다.** 검증의 산출물이 "통과했다"는 주장만이 아니라 **"여기까지 봤고 여기부터는 안 봤다"** 는 지도인 이유입니다.

## 5. 디테일 — 프로젝트에서 실제로 벌어지는 일

### 실패 1 — 산출물을 순서대로 완성하려 한다

경계표를 완벽히 하고 나서 V-Plan을, 그것을 완벽히 하고 나서 환경을 만드는 방식입니다.

**관측되는 증상**: 착수가 몇 주 늦어지고, 그럼에도 완벽해지지 않습니다. VIP 도입 전에는 매핑표를 확정할 수 없고, Agent 개발 전에는 자극 범위를 알 수 없기 때문입니다.

**처방**: **얕게 한 바퀴, 깊게 다시** (§2). 1차의 목적은 정확성이 아니라 **자리 확보**입니다.

### 실패 2 — 가로로 진행한다

모든 시나리오를 만들고, 그 다음 모든 assertion을 만들고, 마지막에 커버리지 모델을 만드는 방식입니다.

**관측되는 증상**: 마지막 단계에서 **cover가 비어 있는 항목이 무더기로 발견**됩니다. Ch09·Ch10의 마무리 문제 상황입니다. 그리고 그때는 시나리오를 다시 손봐야 하는데 일정이 없습니다.

**처방**: **세로로 완성**합니다. 한 V-Plan 항목의 시나리오·assertion·cover를 함께 닫고 다음으로 갑니다.

### 실패 3 — 차단 항목을 흐지부지 넘긴다

스펙 미정의로 차단해 둔 항목이 답을 못 받은 채 sign-off를 맞이합니다. 그리고 *"일단 넘어가자"* 로 목록에서 사라집니다.

**관측되는 증상**: Phase 7에서 이슈가 나왔을 때 **그 항목이 후보 목록에 없습니다.** 차단으로 기록해 둔 이득이 사라지고, 처음부터 원인을 찾습니다.

**처방**: 차단 항목은 **sign-off 리포트에 반드시 남깁니다.** 감수하고 진행하는 것과 잊어버리는 것은 다릅니다. 전자는 결정이고 후자는 사고입니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "산출물을 순서대로 완성해야 한다" | **얕게 한 바퀴 → 깊게 다시.** 1차는 자리 확보가 목적 |
| "시나리오 먼저, assertion은 나중에" | cover가 비어 있는 채 끝납니다. **항목별로 세로 완성** |
| "Agent가 완성돼야 환경을 만든다" | 골격을 먼저 세우고 **스텁으로 대기**합니다 |
| "미검증 항목은 sign-off 전에 없애야 한다" | 없앨 수 없습니다. **정확히 아는 상태로** 넘깁니다 |
| "차단 항목은 일정에 밀리면 뺀다" | 빼면 이슈 대응 시 후보에서 사라집니다. **리포트에 남깁니다** |
| "검증의 목표는 모든 버그를 잡는 것" | **무엇을 잡지 않았는지 아는 것**입니다 |

## 🔧 이 챕터가 확인하는 것

> **캡스톤은 새 항목을 닫지 않습니다.** 앞의 11챕터가 닫은 것들이 하나의 프로젝트 안에서 실제로 맞물리는지를 확인합니다.

### 산출물이 쓰이는 시점

| Phase | 쓰이는 산출물 | 출처 |
|---|---|---|
| 1 착수 | 경계표, Handoff 체크리스트 | Ch01·Ch02 |
| 2 계획 | 매핑표, V-Plan, 항목 목록 리뷰 | Ch04·Ch07 |
| 3 환경 | 능력 역산표, 환경 계층, 프로파일 | Ch03·Ch05·Ch06 |
| 4 구현 | 시나리오 라이브러리, assertion+cover, 커버리지 모델 | Ch08·Ch09·Ch10 |
| 5 디버깅 | **경계표** (실패 분류) | Ch01 |
| 6 Closure | exclusion 정당화, sign-off 게이트 | Ch10·Ch07 |
| 7 Silicon | **차단 항목 목록**, 재현 시나리오, 관측 수단 | Ch11·Ch08·Ch09 |

**Phase 5와 7에서 Ch01과 Ch11의 산출물이 다시 쓰인다**는 점을 주목하세요. 가장 앞에서 만든 것과 가장 정직하게 남긴 것이 **가장 급할 때** 값을 합니다.

### 진행 원칙

- **얕게 한 바퀴, 깊게 다시** — 1차는 자리 확보
- **세로로 완성** — 항목별로 시나리오·assertion·cover를 함께
- **병렬 트랙** — Agent 개발 중에 환경 골격을 진행
- **초기에 세우는 것들** — P1 스모크, 항목 목록 리뷰, 조달 절차
- **차단은 끝까지 남긴다** — 감수한 결정과 잊어버린 사고는 다르다

## 7. 핵심 정리

- **조각이 맞는다고 조립되는 것은 아니다.** 순서와 타이밍이 있고, 순환 의존이 있다
- **얕게 한 바퀴, 깊게 다시.** 1차 산출물의 목적은 정확성이 아니라 **자리 확보**다
- 구현은 **세로로** — 한 항목의 시나리오·assertion·cover를 함께 닫는다. 가로로 가면 마지막에 cover가 빈다
- 회귀 실패는 **DUT 버그 / TB 버그 / 모델 한계**로 분류된다. **경계표가 그 분류를 가능하게 한다**
- **자극 불가와 도달 불가를 구분한다.** 혼동하면 미검증이 검증으로 둔갑한다
- Sign-off는 *"다 됐다"* 가 아니라 **"여기까지 봤고 여기부터는 안 봤다"** 를 제시하는 것이다
- **차단 항목은 sign-off 리포트에 남긴다.** 감수한 결정과 잊어버린 사고는 다르다
- **좋은 검증은 모든 것을 잡는 것이 아니라 무엇을 잡지 않았는지 정확히 아는 것이다**

:::note[🤔 마무리 자가 점검 — 이 코스의 마지막 문제]
Phase 7의 silicon 이슈를 사후 분석(postmortem)합니다. 원인은 **T-06(복귀 후 뱅크 상태)의 설계·펌웨어 가정 불일치**였습니다.

다음 두 질문에 답하세요.

**(a)** 이 이슈는 검증의 **실패**입니까?
**(b)** 다시 한다면 무엇을 다르게 하겠습니까? 21항목 체계의 어느 단계를 보강해야 합니까?

<details>
<summary>정답 / 해설</summary>

**(a) 부분적으로는 실패이고, 부분적으로는 검증이 제 역할을 한 사례입니다.**

**제 역할을 한 부분**: T-06을 **발견했고, 기록했고, 임의 해석하지 않았습니다.** 그래서 이슈가 왔을 때 후보를 즉시 좁혔고 하루 만에 재현했습니다. Ch11의 4단계 절차가 값을 했습니다.

**실패한 부분**: 발견해 놓고 **답을 받지 못한 채 sign-off까지 갔습니다.** 차단 항목을 리포트에 남긴 것은 옳았지만, 그것만으로는 부족했습니다 — **미정의 구간이 실제로 위험한지 평가하지 않았습니다.**

T-06은 *"복귀 후 뱅크 상태"* 이고, 뱅크 상태는 R4(IDLE 뱅크에 RD 금지)와 직결됩니다. 즉 **이 미정의 구간은 데이터 정합성에 직접 영향을 주는 위치**였습니다. 위험도를 평가했다면 우선순위가 올라가 답을 재촉했을 것입니다.

**(b) 세 가지를 보강합니다.**

**① 차단 항목에 위험도를 매긴다** (Ch07 보강)

차단 상태만으로는 부족합니다. *"이 항목이 미검증일 때 무엇이 깨질 수 있는가"* 를 함께 기록합니다. T-06이라면 *"R4와 직결 — 복귀 직후 잘못된 뱅크 접근 가능 → 데이터 손상"* 입니다. 이 문장이 있었다면 sign-off 리뷰에서 다르게 다뤄졌을 것입니다.

**② 스펙 빈틈에 마감 기한을 둔다** (Ch11 보강)

*"질문했고 답을 기다린다"* 는 상태가 무한정 지속될 수 있습니다. 각 빈틈에 **답변 기한**을 정하고, 기한을 넘기면 에스컬레이션합니다. 답이 안 오는 것도 결정이어야 합니다.

**③ 미정의 구간에 대해 "양쪽 다 동작하는지" 확인한다** (Ch08 보강)

이것이 실무적으로 가장 유용합니다. 답을 못 받았더라도 **두 해석 모두에서 시스템이 안전한지** 확인할 수는 있습니다.

- 복귀 후 상태가 **유지**된다고 가정한 시나리오
- 복귀 후 상태가 **초기화**된다고 가정한 시나리오

두 시나리오를 모두 돌려 **어느 쪽에서 문제가 생기는지** 보면, 그 자체가 설계에 대한 강력한 질문이 됩니다. *"초기화 가정에서는 펌웨어가 깨집니다"* 라는 데이터를 들고 가면 답이 훨씬 빨리 옵니다.

**그리고 이 사후 분석 자체가 산출물입니다.**

*"차단 항목에 위험도를 매긴다"* 는 다음 프로젝트의 V-Plan 템플릿에 들어갑니다. *"스펙 빈틈에 기한을 둔다"* 는 프로세스 게이트에 들어갑니다. 21항목 목록이 선행 코스에서 나왔듯, **이슈 사후 분석에서 나온 항목이 다음 프로젝트의 체크리스트가 됩니다.**

검증 체계는 완성되는 것이 아니라 **누적되는 것**입니다.

</details>
:::
