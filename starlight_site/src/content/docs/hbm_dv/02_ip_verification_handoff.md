## 1. Why care? — "완전 검증됨" 인증서를 받았는데도 터진다

Base die에 표준 오프칩 인터페이스 IP를 통합하기로 했습니다. 벤더에서 구매했고, **검증 완료 인증서**와 커버리지 리포트가 함께 왔습니다. 리포트의 숫자는 훌륭합니다.

검증 계획을 세우면서 판단합니다. *"이건 이미 검증된 IP다. 우리가 다시 볼 이유가 없다."* 그 IP 관련 항목을 계획에서 뺍니다. 합리적으로 보입니다 — 실제로 IP 내부를 재검증하는 것은 낭비니까요.

석 달 뒤, 시스템 레벨에서 문제가 나옵니다. 특정 조건에서 그 IP가 응답하지 않습니다. 벤더에 문의하니 회신이 옵니다.

> *"해당 설정 조합은 저희 검증 범위에 포함되어 있지 않습니다."*

**IP는 정상이었습니다.** 벤더도 거짓말하지 않았습니다. 그들은 **자기 환경에서** 검증했고, 우리 시스템의 설정 조합·클럭 구조·주변 로직은 본 적이 없습니다.

여기서 구분해야 할 것이 드러납니다.

> **"IP를 검증했다"와 "IP가 우리 시스템에서 동작한다"는 다른 명제다.**

앞의 것은 벤더가 할 수 있지만, **뒤의 것은 우리 말고 아무도 할 수 없습니다.** 이 챕터는 그 경계를 다룹니다.

## 2. 직관 — 검증 대상은 IP가 아니라 "IP + 문맥"이다

### 순진한 시도 1 — "모든 IP를 똑같이 철저히 검증한다"

품질만 생각하면 옳은 태도입니다. 출처가 무엇이든 우리 칩에 들어가는 이상 우리 책임입니다.

**어디서 막히나?** 세 가지가 동시에 걸립니다. 구매한 IP는 **소스가 암호화되어** 내부를 볼 수 없는 경우가 많습니다. 볼 수 있다 해도 벤더가 이미 수행한 검증을 반복하는 것은 **비용 대비 효과가 낮습니다.** 그리고 결정적으로, **시간이 무한하지 않습니다** — 여기에 쓴 시간은 다른 곳에서 빠집니다.

### 순진한 시도 2 — "그럼 in-house만 검증하고 구매 IP는 믿는다"

도입부의 판단입니다. 효율적으로 보입니다.

**어디서 막히나?** 도입부에서 본 대로 **통합 지점**에서 터집니다. 그리고 이 실패는 늦게, 시스템 레벨에서, 디버깅이 가장 어려운 형태로 나타납니다.

### 일반화 — 두 개의 축이 있고, 출처는 하나만 바꾼다

두 시도가 놓친 것은 **검증 대상이 두 겹**이라는 사실입니다.

| 축 | 무엇을 보는가 | 출처가 바꾸는가 |
|---|---|---|
| **① IP 내부 기능** | 이 IP가 자기 스펙대로 동작하는가 | ✅ **바뀐다** |
| **② 통합** | 이 IP가 **우리 시스템 안에서** 동작하는가 | ❌ **바뀌지 않는다** |

```d2
direction: right

SRC: "**출처**" {
  style.fill: "#e8f5e9"
  a: "in-house"
  b: "3rd party"
  c: "고객 제공"
}

AX1: "**축 ① IP 내부 기능**\nin-house → 전면 검증\n3rd party → 벤더에 위임 (확인만)\n고객 제공 → 전면 검증" {
  style.fill: "#fff8e1"
}

AX2: "**축 ② 통합**\n출처 무관 — **항상 우리 책임**\n연결 · 설정 · 클럭/리셋 · 상호작용" {
  style.fill: "#ffcdd2"
}

SRC -> AX1: "출처에 따라 달라짐"
SRC -> AX2: "출처와 무관"
```

**정의.** IP 검증과 통합 검증은 **별개의 항목**이다. 출처는 ① 축의 무게만 바꾸며, ② 축은 어떤 출처에서도 우리가 수행한다. 계획에서 ①을 줄일 수는 있어도 ②를 줄일 수는 없다.

도입부의 실패는 정확히 이것이었습니다 — ①을 뺀 것은 옳았는데, **②까지 함께 빠진 것**이 문제였습니다.

## 3. 작은 예 — Handoff에서 무엇을 받고 무엇을 묻는가

IP가 넘어오는 시점을 **handoff**라고 합니다. 이때 무엇을 확보하느냐가 이후 검증의 질을 결정합니다.

### 받아야 할 산출물

| 산출물 | 왜 필요한가 | 없으면 |
|---|---|---|
| RTL 또는 암호화 RTL / netlist | 시뮬레이션 대상 | 시작 불가 |
| Datasheet · Integration Guide | 연결·설정 방법 | 통합 검증의 근거가 없음 |
| **검증 계획 / 커버리지 리포트** | **벤더가 무엇을 봤는지** 알 수 있음 | ⚠️ 무엇이 미검증인지 알 수 없음 |
| **알려진 이슈 목록(errata)** | 이미 아는 문제를 다시 찾지 않음 | 알려진 버그를 몇 주 걸려 재발견 |
| 지원 설정 파라미터와 **유효 조합** | 우리 조합이 범위 안인지 판정 | 도입부의 실패가 발생 |
| 클럭 / 리셋 요구사항 | 통합 검증 항목의 원본 | 순서 문제를 놓침 |
| 검증 환경 자산 (VIP·모델 등) | 통합 검증에 재사용 | 처음부터 만들어야 함 |

**가장 자주 빠지는 것이 굵게 표시한 세 가지**입니다. RTL과 datasheet는 반드시 오지만, **커버리지 리포트·errata·유효 설정 조합**은 요구하지 않으면 오지 않는 경우가 많습니다. 그런데 검증 계획에 직접 영향을 주는 것은 오히려 이 셋입니다.

### 물어야 할 질문 — Handoff 체크리스트

| # | 질문 | 답이 검증 계획에 미치는 영향 |
|---|---|---|
| H1 | **어떤 설정 조합이 검증되었는가?** 우리가 쓸 조합이 그 안에 있는가 | 밖이면 → 그 조합은 **우리가 검증**해야 함 |
| H2 | **어떤 규칙을 검사하고 무엇을 검사하지 않는가** | 검사하지 않는 것 → assertion으로 메움 (Ch09) |
| H3 | 알려진 이슈와 그 회피 방법은? | 회피 조건이 곧 **시나리오 제약** |
| H4 | 클럭·리셋 순서에 어떤 가정이 있는가 | 통합 검증 항목으로 직행 |
| H5 | 어떤 시뮬레이터·버전에서 검증되었는가 | 우리 환경과 다르면 **재현 확인** 필요 |
| H6 | 커버리지 리포트의 **모델에 무엇이 들어 있는가** | 숫자가 아니라 항목을 봄 (선행 코스 Ch05) |

H6가 특히 중요합니다. 선행 코스에서 확립한 원리 — *"모델에 없는 항목은 0%로 잡히는 것이 아니라 아예 집계되지 않는다"* — 가 남의 커버리지 리포트를 읽을 때도 그대로 적용됩니다. **95%라는 숫자보다 그 95%가 무엇의 95%인지가 중요합니다.**

:::note[🤔 잠깐 — 어떤 질문을 해야 합니까]
벤더에서 IP와 함께 다음 자료가 왔습니다.

> - RTL (암호화)
> - Datasheet, Integration Guide
> - "Functional Coverage 98.7%, Code Coverage 96.2% 달성" 요약 리포트 1장

이 상태에서 통합을 시작해도 됩니까? 부족하다면 **무엇을 추가로 요구**해야 합니까?

<details>
<summary>정답 / 해설</summary>

**시작하면 안 됩니다. 최소 세 가지를 더 요구해야 합니다.**

**① 커버리지 리포트의 상세 — 모델 항목 목록** (H6)

"98.7%"는 그 자체로는 정보가 거의 없습니다. 알아야 할 것은 **커버리지 모델에 무엇이 들어 있는가**입니다. 우리가 쓸 기능이 애초에 모델에 없었다면 98.7%는 그 기능과 무관한 숫자입니다.

**② 검증된 설정 조합의 범위** (H1)

우리 시스템의 설정 조합이 벤더 검증 범위 안인지 확인해야 합니다. 밖이라면 **그 조합의 검증은 우리 몫**이며, 이것은 계획의 공수 항목입니다. 도입부의 실패가 정확히 이 지점이었습니다.

**③ 알려진 이슈 목록(errata)** (H3)

errata 없이 시작하면 이미 알려진 버그를 몇 주에 걸쳐 재발견하게 됩니다. 회피 조건이 있다면 그것은 곧 시나리오 제약이 되어 테스트 작성에 영향을 줍니다.

**추가로 요구하면 좋은 것**: 검증 계획 문서(H2 — 무엇을 검사하고 무엇을 안 하는지), 검증에 쓰인 시뮬레이터·버전(H5), 그리고 가능하다면 벤더의 검증 환경 자산.

**핵심 태도**: 이 질문들은 벤더를 의심하는 것이 아니라 **경계를 확인하는 것**입니다. 벤더의 책임 범위가 어디서 끝나는지 알아야 우리 책임이 어디서 시작하는지 알 수 있습니다.

</details>

### 통합 검증 항목 — 출처와 무관하게 우리가 하는 것

축 ②에 해당하는 항목들입니다. **어떤 출처의 IP에도 동일하게 적용**됩니다.

| # | 통합 검증 항목 | 대표적 실패 |
|---|---|---|
| I1 | **연결 정합** — 신호 폭, 방향, 비트 순서 | 폭이 달라 상위 비트가 잘림 |
| I2 | **클럭 도메인** — 도메인 교차 지점과 동기화 | 비동기 경계에서 간헐적 데이터 손상 |
| I3 | **리셋 순서** — 어느 블록이 먼저 풀리는가 | IP가 리셋 중인데 요청이 도착 |
| I4 | **설정값 조합** — 우리 시스템 고유의 조합 | 도입부의 실패 |
| I5 | **주소맵** — 겹침·구멍 | 두 IP가 같은 주소에 응답 |
| I6 | **오류·인터럽트 보고 경로** | IP는 오류를 냈는데 상위에 전달 안 됨 |
| I7 | **자원 경합** — 다른 IP와 공유하는 것 | 선행 코스의 CA 공유와 같은 구조 |
| I8 | **저전력·테스트 모드 상호작용** | 한 IP만 저전력에 들어가 상태 불일치 |

`hbm_ch_ctrl`의 경우 I7이 특히 중요합니다 — 스펙 [R3](../appendix_a_hbm_ch_ctrl_spec/)의 CA 공유 규칙이 바로 자원 경합이고, 이것은 IP 하나만 놓고는 관측되지 않습니다.

## 4. 일반화 — 두 극단을 다시 검토한다

### 대안 A — 3rd party IP 내부까지 우리가 재검증한다면?

품질을 최우선으로 두면 가능한 선택입니다.

**보통 택하지 않는 이유**: 암호화 RTL이면 애초에 불가능하고, 가능하더라도 벤더가 수행한 작업의 반복입니다. 그 시간은 우리만 할 수 있는 일(통합 검증, in-house IP, custom 로직)에서 빠집니다.

**그럼에도 하는 경우**: 세 가지 상황에서는 정당화됩니다.
1. 벤더 검증 범위 밖의 설정을 쓸 때 — 그 부분에 한해 (H1)
2. errata가 많거나 벤더 대응이 느려 신뢰가 낮을 때
3. 안전·인증 요구가 있어 자체 증거가 필요할 때

**판단 기준**: "전부 다시 볼 것인가"가 아니라 **"어느 부분을 다시 볼 것인가"** 입니다. H1·H2의 답이 그 범위를 정합니다.

### 대안 B — 통합 검증을 full-chip에서만 한다면?

IP별 통합 검증을 생략하고 최종 full-chip 환경에서 한꺼번에 확인하는 방식입니다. 환경을 하나만 만들면 되니 효율적으로 보입니다.

**왜 안 되나**: 두 가지가 걸립니다.

**발견 시점이 늦습니다.** full-chip 환경은 프로젝트 후반에야 준비되므로, 연결 폭 불일치 같은 단순한 문제도 늦게 발견됩니다.

**디버깅 난이도가 폭발합니다.** full-chip에서 실패가 나오면 후보 원인이 수십 개입니다. IP별 통합 환경에서 같은 실패가 나오면 후보는 몇 개로 줄어듭니다. 이것이 Ch06에서 다룰 **환경 계층**(IP → Subsystem → Full-chip)이 존재하는 이유입니다.

**올바른 처리**: 통합 검증을 **계층별로 나눠** 각 계층에서 그 계층에서만 보이는 것을 확인합니다. full-chip은 최종 확인이지 첫 확인이 아닙니다.

## 5. 디테일 — Handoff에서 실제로 벌어지는 일

### 실패 1 — "검증 완료"를 통합까지 포함한 것으로 읽는다

도입부의 사례입니다.

**관측되는 증상**: IP 자체는 어떤 테스트에서도 정상입니다. 그런데 시스템에서만 특정 조건에 실패합니다. 원인을 IP 내부에서 찾느라 시간을 쓰고, 결국 경계 밖(설정 조합·클럭 순서·주변 로직 상호작용)에서 발견됩니다.

**왜 반복되나**: "검증됨"이라는 단어가 **범위를 명시하지 않기** 때문입니다. 벤더의 진술은 "우리 환경에서 우리 검증 계획대로 검증됨"인데, 받는 쪽은 "이 IP는 문제없음"으로 읽습니다. **H1·H2를 문서로 받아 두면** 이 오해가 구조적으로 차단됩니다.

### 실패 2 — 문서는 받고 검증 자산은 받지 않는다

datasheet와 integration guide만 받고 커버리지 리포트·errata·검증 계획은 요구하지 않은 경우입니다.

**관측되는 증상**: 어디까지가 검증된 영역인지 알 수 없으므로, **불안해서 전부 다시 보거나(비용 초과) 믿고 아무것도 안 봅니다(구멍).** 두 극단 사이의 합리적 지점을 잡을 근거가 없습니다.

**처방**: handoff를 **이벤트가 아니라 체크리스트**로 다룹니다. H1~H6에 답이 채워지기 전에는 handoff가 완료되지 않은 것으로 간주합니다.

### 실패 3 — 고객 제공 IP를 3rd party처럼 다룬다

Custom HBM에서 고객이 제공한 로직을, 구매 IP와 같은 방식으로 "통합만 확인"하는 경우입니다.

**관측되는 증상**: 내부 기능이 **아무에게도 검증되지 않은 채** 넘어갑니다. 구매 IP에는 "벤더가 검증했다"는 전제가 있지만 고객 제공 IP에는 그 전제가 없거나 약합니다. 고객은 자기 알고리즘의 정확성을 봤을 수는 있어도, 그것이 **우리 base die 안에서 RTL로 동작하는지**는 확인한 적이 없을 수 있습니다.

**처방**: 경계표(Ch01)와 handoff 체크리스트를 **출처별로 다르게** 적용합니다. 고객 제공 IP는 축 ①도 우리 몫이며, 그 도구(Custom Agent)까지 만들어야 합니다 (Ch03).

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "검증 완료 IP는 다시 볼 필요가 없다" | ① 축은 줄일 수 있지만 **② 통합 축은 못 줄입니다** |
| "커버리지 98%면 충분히 검증된 것" | 숫자가 아니라 **모델에 무엇이 들어 있는가**를 봐야 합니다 |
| "handoff는 파일을 받는 이벤트" | **체크리스트**입니다. H1~H6에 답이 없으면 미완료입니다 |
| "고객 제공 IP는 고객이 검증했을 것" | 고객이 본 것은 알고리즘일 수 있고, **RTL 동작은 아닐 수 있습니다** |
| "통합 검증은 full-chip에서 하면 된다" | 발견이 늦고 디버깅 후보가 폭증합니다. **계층별로** 나눕니다 |
| "IP 내부를 재검증하는 건 언제나 낭비" | 벤더 검증 범위 **밖의 설정**을 쓴다면 그 부분은 우리 몫입니다 |

## 🔧 이 문제를 이렇게 푼다

> **닫는 항목: #19 — 출처별 검증 전략 분기 / #21 — 통합 검증을 IP 검증과 별개 항목으로**

### #19 — 출처별 전략표

경계표(Ch01)의 "DUT" 칸을 출처로 다시 나누고, 각 칸에서 **무엇을 하는지**를 확정합니다.

| 출처 | 축 ① 내부 기능 | 축 ② 통합 | 검증 도구 | 계획에 잡을 공수 |
|---|---|---|---|---|
| **In-house** | **전면 검증** — 내부 상태까지 | **우리** | 자체 VIP·TB (사내 자산 재사용) | 큼 |
| **3rd Party** | **위임 + 확인** — H1~H6로 범위 확인, 범위 밖만 자체 검증 | **우리** | 상용 VIP | 통합 위주 |
| **고객 제공** | **전면 검증** — 스펙에서 항목 도출 | **우리** | ⚠️ **Custom Agent 자체 개발** (Ch03) | 큼 + 도구 개발 |

**판정 순서**
1. 이 IP의 출처는 무엇인가 → 축 ①의 방침 결정
2. 3rd party라면 **H1~H6를 문서로 확보** → 위임 범위와 자체 검증 범위 확정
3. 축 ②는 출처와 무관하게 **항상 계획에 넣는다**
4. 검증 도구가 없는 칸(고객 제공)은 **도구 개발 공수를 별도 항목**으로 잡는다

### #21 — 통합 검증 체크리스트

축 ②를 항목화하여 **IP마다** 적용합니다. IP 검증 항목과 **분리된 절**로 V-Plan에 넣습니다 (Ch07).

| # | 항목 | 확인 방법 |
|---|---|---|
| I1 | 연결 정합 (폭·방향·비트 순서) | 연결성 확인 시나리오 |
| I2 | 클럭 도메인 교차 | 도메인 경계 시나리오 + assertion |
| I3 | 리셋 순서·해제 타이밍 | 리셋 시퀀스 변형 시나리오 |
| I4 | **설정값 조합** (우리 시스템 고유) | H1의 답 밖에 있는 조합을 우선 |
| I5 | 주소맵 겹침·구멍 | 경계 주소 접근 |
| I6 | 오류·인터럽트 보고 경로 | **에러 주입** (Ch08) |
| I7 | 자원 경합 | 동시 활성 시나리오 + assertion (Ch09) |
| I8 | 저전력·테스트 모드 상호작용 | 모드 전이 시나리오 (Ch11) |

### 운영 규칙

- **handoff는 이벤트가 아니라 체크리스트다** — H1~H6에 답이 채워져야 완료
- 축 ②는 **어떤 출처에서도 삭제하지 않는다** — 계획 리뷰에서 "이 IP의 통합 항목은 어디 있나"를 묻는다
- 벤더 커버리지 리포트는 **숫자가 아니라 모델 항목**을 확인한다
- 통합 검증은 **계층별로** 배치한다 (Ch06) — full-chip은 최종 확인이지 첫 확인이 아니다

## 7. 핵심 정리

- **"IP를 검증했다"와 "IP가 우리 시스템에서 동작한다"는 다른 명제다.** 앞은 벤더가 할 수 있고 뒤는 우리만 할 수 있다
- 검증 대상은 두 축 — **① IP 내부 기능**(출처가 바꿈) / **② 통합**(출처 무관, 항상 우리)
- 계획에서 ①은 줄일 수 있어도 **②는 줄일 수 없다**
- Handoff에서 자주 빠지지만 가장 중요한 세 가지: **커버리지 리포트 상세 · errata · 검증된 설정 조합**
- 남의 커버리지 리포트도 **"숫자가 아니라 모델에 무엇이 들어 있는가"** 로 읽는다
- 고객 제공 IP는 "검증됨" 전제가 없다 — **축 ①도 우리 몫이고 도구까지 만들어야 한다**
- 통합 검증은 **계층별로** 배치한다. full-chip은 최종 확인이지 첫 확인이 아니다

- **(A)** 사내 개발 `hbm_ch_ctrl`
- **(B)** 벤더 구매 표준 인터페이스 IP — 커버리지 리포트와 errata 확보 완료. 우리가 쓸 설정 조합 중 **하나가 벤더 검증 범위 밖**
- **(C)** 고객 제공 전용 로직 — 인터페이스 규격 문서만 있음

세 IP 각각에 대해 **계획에 넣을 검증 항목**을 축 ①/② 기준으로 배분하세요.

<details>
<summary>정답 / 해설</summary>

**(A) `hbm_ch_ctrl` — 사내 개발**
- **축 ①**: 전면 검증. 스펙 R1~R20 전부가 검증 항목. 내부 상태(뱅크 상태 머신, 중재 로직)까지 관측
- **축 ②**: 통합 항목 I1~I8 전부. 특히 **I7(자원 경합)** — R3의 CA 공유 규칙이 여기 해당

**(B) 벤더 구매 IP — 검증 범위 밖 설정이 하나 있음**
- **축 ①**: 원칙적으로 위임. **단 범위 밖 설정 조합 하나는 우리가 검증한다** — H1의 답이 이 범위를 정해 줌
- **축 ②**: I1~I8 **전부**. 구매 IP라고 줄이지 않음
- 도구: 상용 VIP 활용
- **계획에 명시할 것**: "설정 조합 X는 벤더 검증 범위 밖 → 자체 검증" 을 **항목으로 적어 둡니다.** 적지 않으면 나중에 아무도 그 사실을 기억하지 못합니다

**(C) 고객 제공 로직 — 규격 문서만 있음**
- **축 ①**: **전면 검증.** "검증됨" 전제가 없습니다. 고객 문서에서 검증 항목을 직접 도출해야 합니다
- **축 ②**: I1~I8 전부
- 도구: ⚠️ **상용 VIP 없음 → Custom UVM Agent 자체 개발.** 이 공수를 **별도 항목으로** 계획에 넣습니다 (Ch03)
- 추가로 확보할 것: 고객에게도 H1~H6에 해당하는 질문을 합니다 — 어떤 조건에서 동작을 확인했는지, 알려진 제약이 있는지

**세 IP를 관통하는 것**

축 ②는 **셋 모두 동일하게 I1~I8 전부**입니다. 출처가 바꾼 것은 축 ①의 무게와 **도구 조달 방법**뿐입니다.

그리고 계획 문서에는 세 IP 모두 **"통합 검증" 절이 별도로** 있어야 합니다. IP별 검증 항목 아래에 섞어 넣으면, 일정이 밀릴 때 가장 먼저 잘려 나가는 것이 통합 항목입니다.
