## 1. Why care? — 디지털 회귀는 잘 돌지만 PHY가 그 안에 없다

프로젝트가 순조롭습니다. 디지털 회귀가 야간에 1만 job 돌고, 커버리지도 올라가고 있습니다.

그런데 환경 구성을 다시 보면 한 가지가 눈에 걸립니다. **PHY가 그 환경에 없습니다.** 정확히는, PHY 자리에 디지털 동작만 흉내 내는 간이 모델이 들어가 있습니다. Ch01의 경계표에서 PHY를 "범위 밖(디지털 환경 기준)"으로 분류했던 그 결과입니다.

여기서 두 가지 사실이 충돌합니다.

- **실제 PHY를 넣지 않으면** 선행 코스 Ch03이 경고한 대로 base die의 절반(mixed IP)이 미검증으로 남습니다
- **실제 PHY를 넣으면** 시뮬레이션이 자릿수 단위로 느려져 **1만 job 회귀가 불가능**합니다

"둘 다 하자"는 답은 성립하지 않습니다. 하나의 환경에서 둘을 동시에 만족할 수 없기 때문입니다. 그런데 둘 다 필요합니다.

이 모순을 어떻게 푸느냐가 이 챕터의 주제입니다. 그리고 답은 환경을 더 좋게 만드는 것이 아니라, **환경이 하나여야 한다는 가정을 버리는 것**입니다.

## 2. 직관 — 하나의 환경으로 풀리지 않는다

### 순진한 시도 1 — 전부 디지털로 두고 간다

지금 상태입니다. 빠르고, 회귀가 대량으로 돌고, 커버리지도 잘 쌓입니다.

**어디서 막히나?** PHY의 실제 동작이 검증되지 않습니다. 그리고 이 누락은 **조용합니다** — 간이 모델이 정상 응답하므로 테스트가 깨지지 않습니다. 선행 코스가 정리한 "조용한 통과"의 또 다른 형태입니다.

특히 위험한 것은 **디지털 로직과 PHY 사이의 인터페이스**입니다. 제어 시퀀스, 트레이닝 핸드셰이크, 상태 보고 — 이들은 양쪽이 다 있어야 확인됩니다. 간이 모델은 우리가 만들었으므로 **우리가 기대한 대로** 반응하고, 실제 PHY가 다르게 반응할 여지는 검사되지 않습니다.

### 순진한 시도 2 — 전부 실물 수준으로 올린다

PHY를 회로 수준으로 두고 시뮬레이션합니다. 정확합니다.

**어디서 막히나?** 선행 코스 [Ch03의 대안 A](../../hbm/03_stack_architecture/)에서 이미 결론이 났습니다 — **회귀를 돌릴 수 없는 검증은 검증이 아닙니다.** 무작위 시나리오 수천 개로 커버리지를 닫는 방식이 성립하지 않습니다.

### 일반화 — 환경을 복수로 두고, 수준을 구성으로 다룬다

두 시도는 **같은 환경으로 다른 질문에 답하려 한 것**입니다. 질문이 다르면 환경도 달라야 합니다.

| 질문 | 필요한 것 | 감당 가능한 규모 |
|---|---|---|
| "동시성·프로토콜 규칙이 지켜지는가" | 빠른 디지털 시뮬레이션 | 수천~수만 job |
| "PHY와 디지털의 인터페이스가 맞물리는가" | 양쪽이 실동작하는 환경 | 수십~수백 |
| "실제 회로와 정합하는가" | 회로 수준 표현 | 수~수십 |

> **정의.** Mixed-level 검증은 **하나의 환경이 아니라 "표현 수준 조합의 집합"** 이다. 각 조합을 **구성 프로파일**이라 부르고, 프로파일마다 답할 질문을 배정한다.

핵심은 이것이 **환경을 여러 개 만드는 것이 아니라 하나의 환경에 구성 전환을 두는 것**이라는 점입니다. 여러 개 만들면 유지보수가 배수로 늘고 시나리오가 중복됩니다.

## 3. 작은 예 — 구성 프로파일 정의하기

### 블록별 표현 수준 옵션

Base die를 블록으로 나누고, 각 블록이 취할 수 있는 표현 수준을 나열합니다.

| 블록 | 취할 수 있는 수준 |
|---|---|
| 디지털 로직 (`hbm_ch_ctrl` 등) | **RTL** (고정 — 검증 대상이므로 항상 실물) |
| **PHY** | ① 디지털 동작 모델 · ② RNM · ③ 회로 수준 |
| DRAM | 간이 behavioral model · 상용 VIP (Ch04) |
| 전력 관리 등 아날로그 | 모델 · 회로 수준 |

디지털 로직만 수준이 고정입니다. **검증 대상은 항상 실물이어야** 하기 때문입니다 — 이것이 Ch01 경계표의 직접적 귀결입니다.

### 프로파일 — 이 챕터의 산출물

```d2
direction: right

P0: "P0 — 순수 디지털\nDigital: RTL\nPHY: 간이 디지털 모델\nDRAM: 상용 VIP\n\n용도: 기능 · 동시성 · 커버리지\n규모: 수천~수만 job" { style.fill: "#e8f5e9"; style.font-color: "#0A0F25" }

P1: "P1 — PHY 실동작\nDigital: RTL\nPHY: RNM\nDRAM: 상용 VIP\n\n용도: PHY–디지털 인터페이스\n규모: 수십~수백 job" { style.fill: "#fff8e1"; style.font-color: "#0A0F25" }

P2: "P2 — Full Mixed\nDigital: RTL\nPHY: 회로 수준\nDRAM: 간이 모델\n\n용도: 실회로 정합\n규모: 수~수십 job" { style.fill: "#ffcdd2"; style.font-color: "#0A0F25" }

P0 -> P1: "동일 시나리오 재사용"
P1 -> P2: "선별된 시나리오만"
```

| 프로파일 | 답하는 질문 | 답하지 **못하는** 질문 |
|---|---|---|
| **P0** | 프로토콜 규칙·동시성·기능 커버리지 | PHY 실동작, 아날로그 상호작용 |
| **P1** | PHY 제어 시퀀스·트레이닝 핸드셰이크·상태 보고 | 회로 수준 타이밍·레벨 정합 |
| **P2** | 실회로와의 정합 | 대량 시나리오, 커버리지 closure |

**"답하지 못하는 질문" 칸이 중요합니다.** 각 프로파일의 한계를 명시해 두지 않으면, P0 회귀가 통과했을 때 그것이 무엇을 보증하는지 과대평가하게 됩니다.

### 검증 항목을 프로파일에 배치하기

우리 규칙 목록을 프로파일에 배정합니다. 이것이 계획 작업입니다.

| 검증 항목 | 배치 | 근거 |
|---|---|---|
| 스펙 R1~R20 (CCI·CA·타이밍·오류·모드) | **P0** | 전부 디지털 로직의 규칙 |
| 21항목 #1 동시 활성 조합 커버리지 | **P0** | 대량 회귀 필요 |
| #2 실효 대역폭 측정 | **P0** | 디지털 수준에서 측정 가능 |
| 통합 항목 I1~I6 | **P0** | 디지털 연결·설정·오류 경로 |
| **PHY 제어 시퀀스·트레이닝 핸드셰이크** | **P1** | 양쪽 실동작 필요 |
| **PHY 상태 보고와 디지털의 반응** | **P1** | 인터페이스 동작 |
| I8 저전력·테스트 모드 상호작용 | P0 + **P1** | 디지털 전이는 P0, 아날로그 연동은 P1 |
| **실회로 타이밍·레벨 정합** | **P2** | 회로 수준만 가능 |

`hbm_ch_ctrl` 자체는 순수 디지털이므로 **스펙 R1~R20 전부가 P0에서 검증됩니다.** Mixed-level이 필요해지는 것은 그 위 계층 — base die 전체를 볼 때입니다.

:::note[🤔 잠깐 — 어느 프로파일에 배치합니까]
다음 세 항목을 P0 / P1 / P2 중 어디에 배치하고, 그 이유는 무엇입니까?

- **(A)** 스펙 R3 — `row_cmd_valid && col_cmd_valid`일 때 `row_pc == col_pc`
- **(B)** PHY 트레이닝이 완료되기 전에 디지털 로직이 데이터 커맨드를 내보내지 않는지 확인
- **(C)** 저전력 모드에서 복귀할 때 디지털 상태 기계가 올바른 순서로 재개하는지 확인

<details>
<summary>정답 / 해설</summary>

**(A) R3 → P0**

CA 공유 규칙은 순수하게 디지털 로직 내부의 중재 규칙입니다. PHY의 표현 수준과 무관하며, 이 규칙을 자극하려면 **많은 동시 요청 조합**이 필요하므로 대량 회귀가 가능한 P0이 적합합니다. P1이나 P2에서 돌리는 것은 낭비입니다.

**(B) PHY 트레이닝 완료 전 커맨드 금지 → P1**

이 항목은 **양쪽이 다 실동작해야** 확인됩니다. 간이 PHY 모델은 "트레이닝 완료"를 우리가 정한 시점에 알리므로, 실제 PHY가 다른 타이밍에 완료를 보고하거나 중간 상태를 거치는 경우가 검사되지 않습니다.

주의할 점: **P0에서도 일부는 확인 가능합니다** — "완료 신호가 0인 동안 커맨드를 내지 않는다"는 규칙 자체는 P0에서 assertion으로 검사할 수 있습니다. P1이 추가로 답하는 것은 *"실제 PHY가 그 신호를 어떻게 움직이는가"* 입니다. **두 프로파일이 같은 항목의 다른 측면을 담당**하는 사례입니다.

**(C) 저전력 복귀 시 디지털 상태 기계 → P0** (아날로그 연동 부분만 P1)

상태 기계의 전이 순서는 디지털 로직의 문제이므로 P0에서 대량으로 확인합니다. 다만 전원이 실제로 안정화되는 시점과 디지털의 재개 시점이 맞물리는지는 P1의 몫입니다.

**공통 원리**: 배치 기준은 *"이 항목을 확인하려면 무엇이 실물이어야 하는가"* 입니다. 실물이 더 필요할수록 상위 프로파일로 가고, 그만큼 돌릴 수 있는 규모가 줄어듭니다. **그래서 상위 프로파일에는 선별된 시나리오만 올립니다.**

</details>

### 시나리오는 프로파일에 독립적이어야 한다

프로파일 사이를 오갈 수 있어야 위 배치가 실제로 작동합니다. 그러려면 시나리오가 **표현 수준을 알지 못해야** 합니다.

| 나쁜 패턴 | 문제 |
|---|---|
| 시나리오가 PHY 내부 신호를 직접 참조 | 표현 수준이 바뀌면 그 신호가 없어져 컴파일 실패 |
| 시나리오가 특정 지연 사이클 수를 하드코딩 | P1·P2에서 타이밍이 달라 실패 |
| 시나리오가 간이 모델의 백도어 함수를 호출 | 실물에는 그 함수가 없음 |

| 좋은 패턴 | 이유 |
|---|---|
| 인터페이스의 **공개 신호·트랜잭션**만 사용 | 모든 수준에 존재 |
| 대기 조건을 **상태 신호**로 표현 (고정 사이클 수 대신) | 타이밍이 달라도 동작 |
| 백도어 접근을 **추상 계층**으로 감싸 수준별로 구현 교체 | 시나리오 코드는 그대로 |

**결과**: P0에서 작성한 시나리오를 P1·P2에서 **그대로 재사용**할 수 있습니다. 재사용이 안 되면 상위 프로파일용 시나리오를 처음부터 다시 만들어야 하고, 그 시점(보통 프로젝트 후반)에 그럴 여유는 없습니다.

## 4. 일반화 — 두 가지 잘못된 단순화

### 대안 A — 프로파일을 하나로 통일한다면?

"관리가 복잡하니 중간 수준 하나로 통일하자"는 판단입니다. PHY를 RNM으로 고정하는 식입니다.

**왜 안 되나**: **두 목적 모두 실패합니다.** RNM은 순수 디지털보다 느려 대량 회귀가 어렵고, 회로 수준보다는 부정확해 실회로 정합을 보증하지 못합니다. 양쪽 요구의 중간은 **양쪽 모두를 만족하지 못하는 지점**입니다.

**교훈**: 서로 다른 질문에 답해야 할 때 하나로 통일하는 것은 타협이 아니라 **둘 다 포기하는 것**입니다.

### 대안 B — 프로파일마다 환경을 따로 만든다면?

각 프로파일용 테스트벤치를 별도로 구축합니다. 각각 최적화할 수 있습니다.

**왜 안 되나**: 유지보수가 프로파일 수에 비례합니다. 그리고 더 나쁜 것은 **시나리오와 checker가 중복**된다는 점입니다. 규칙 하나를 고치면 세 곳을 고쳐야 하고, 곧 세 환경이 서로 다르게 동작하기 시작합니다.

**올바른 처리**: **하나의 환경 + 구성 전환**입니다. 프로파일은 설정값이며, 블록별 표현 수준을 파라미터로 선택합니다. 21항목 **#8(구성값 파라미터화)** 이 여기서도 적용됩니다 — Ch06에서 환경 구조로 다룹니다.

## 5. 디테일 — Mixed-level 운영에서 실제로 벌어지는 일

### 실패 1 — 상위 프로파일을 프로젝트 말미로 미룬다

P0으로 먼저 진행하고 P1·P2는 나중에 하자는 계획입니다. 자연스러워 보입니다 — 디지털이 안정돼야 mixed를 돌릴 의미가 있으니까요.

**관측되는 증상**: 프로젝트 후반에 P1을 처음 돌리는데, **환경이 서지 않습니다.** 경계 신호 연결이 맞지 않거나, 시나리오가 간이 모델에 종속되어 있거나, 실제 PHY의 초기화 시퀀스가 우리 가정과 다릅니다. 이 문제들을 푸는 데 걸리는 시간이 일정에 없습니다.

**처방**: P1·P2를 **최소 규모로라도 초기에 한 번 세웁니다.** 시나리오 한두 개만 돌아가도 됩니다. 목적은 검증이 아니라 **환경이 성립함을 확인하는 것**이며, 이것을 "스모크 프로파일"로 회귀에 넣어 두면 경계 구조가 깨지는 순간 바로 드러납니다.

### 실패 2 — 시나리오가 프로파일에 종속된다

간이 모델의 백도어 함수를 시나리오에서 직접 호출하거나, 특정 지연 사이클을 하드코딩한 경우입니다.

**관측되는 증상**: P1로 전환하는 순간 **대부분의 시나리오가 컴파일되지 않거나 실패**합니다. 원인이 DUT가 아니라 시나리오 자신이므로 고쳐야 할 파일이 수십 개입니다.

**처방**: 백도어 접근은 **추상 계층**으로 감싸고 수준별 구현을 교체합니다. 대기는 사이클 수가 아니라 **상태 조건**으로 씁니다. 이 규칙을 코드 리뷰 항목으로 둡니다.

### 실패 3 — 프로파일별 결과를 합쳐 보고한다

Ch04의 라이선스 사례와 **같은 구조**의 실패입니다.

**관측되는 증상**: "회귀 1만 500 job 통과"라고 보고되는데, 그중 P1은 400개, P2는 100개입니다. 합친 숫자에서는 **P0의 규모가 전체를 대표**하게 되고, PHY 관련 검증이 실제로 얼마나 얕은지가 가려집니다.

**처방**: 프로파일별로 **분리 보고**합니다. 그리고 각 프로파일 옆에 *"답하지 못하는 질문"* 을 함께 적으면 리뷰어가 위험을 판단할 수 있습니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "Mixed-level은 하나의 특별한 환경" | **표현 수준 조합의 집합**입니다. 프로파일로 관리합니다 |
| "중간 수준으로 통일하면 관리가 쉽다" | 대량 회귀도 실회로 정합도 못 얻습니다. **둘 다 포기하는 선택**입니다 |
| "프로파일마다 환경을 만들어야 한다" | 하나의 환경 + **구성 전환**입니다. 따로 만들면 시나리오가 중복됩니다 |
| "P0이 통과하면 디지털은 끝" | P0은 PHY 실동작을 **답하지 못합니다.** 한계를 명시해 둬야 합니다 |
| "Mixed는 디지털이 안정된 후에" | 최소 규모라도 **초기에 세웁니다.** 환경 성립 자체가 리스크입니다 |
| "시나리오는 어차피 프로파일마다 다르다" | 독립적으로 쓰면 **재사용됩니다.** 종속되면 후반에 다시 만듭니다 |

## 🔧 이 문제를 이렇게 푼다

> **닫는 항목: #11 — Mixed-level 환경을 별도로 구성**

선행 코스는 *"base die 안에 순수 디지털로 다룰 수 없는 영역이 있으므로 검증 환경이 하나가 아니라 여러 개가 되어야 한다"* 고 했습니다. 그 "여러 개"의 구체적 형태를 정의합니다.

### 1단계 — 프로파일 정의

블록별 표현 수준의 조합에 이름을 붙이고, **답하는 질문**과 **답하지 못하는 질문**을 함께 적습니다.

| 프로파일 | 구성 | 답하는 질문 | 한계 | 회귀 규모 |
|---|---|---|---|---|
| P0 | Digital RTL + PHY 간이 + DRAM VIP | 프로토콜·동시성·커버리지 | PHY 실동작 | 수천~수만 |
| P1 | Digital RTL + PHY RNM + DRAM VIP | PHY–디지털 인터페이스 | 회로 정합 | 수십~수백 |
| P2 | Digital RTL + PHY 회로 + DRAM 간이 | 실회로 정합 | 대량 시나리오 | 수~수십 |

*프로파일 수와 구성은 프로젝트마다 다릅니다. 중요한 것은 **각 프로파일의 한계를 명시**하는 것입니다.*

### 2단계 — 항목 배치

각 검증 항목에 대해 *"확인하려면 무엇이 실물이어야 하는가"* 를 묻고 최소 프로파일에 배치합니다. **불필요하게 상위 프로파일에 올리지 않습니다** — 규모가 줄어 자극이 얕아집니다.

### 3단계 — 프로파일 독립성 확보

시나리오와 checker가 표현 수준을 알지 못하도록 만듭니다.

- 인터페이스의 **공개 신호·트랜잭션**만 사용
- 대기는 **상태 조건**으로 (고정 사이클 수 금지)
- 백도어 접근은 **추상 계층**으로 감싸고 수준별 구현 교체
- 위 세 항목을 **코드 리뷰 체크리스트**에 넣음

### 4단계 — 운영 규칙

- **P1·P2를 초기에 최소 규모로 세운다** — 스모크 프로파일을 회귀에 상주시켜 경계 구조 붕괴를 조기 감지
- **프로파일별로 분리 보고**한다 — 합친 숫자는 P0 규모가 전체를 대표하게 만든다
- 프로파일 구성은 **설정값**으로 관리하고 리뷰 대상으로 삼는다
- 각 프로파일의 **한계를 보고서에 함께 적는다**

## 7. 핵심 정리

- 하나의 환경으로 **대량 디지털 회귀와 실회로 정합을 동시에** 만족할 수 없다. 질문이 다르면 환경도 다르다
- Mixed-level은 하나의 환경이 아니라 **표현 수준 조합의 집합**이며, 각 조합을 **구성 프로파일**로 관리한다
- 검증 대상인 **디지털 로직은 항상 실물(RTL)** 이다. 수준이 바뀌는 것은 주변 블록이다
- 프로파일마다 **답하는 질문과 답하지 못하는 질문**을 함께 적어야 결과를 과대평가하지 않는다
- 항목 배치 기준은 *"확인하려면 무엇이 실물이어야 하는가"*. 불필요하게 상위로 올리지 않는다
- **시나리오는 프로파일에 독립적으로** 쓴다 — 공개 신호만, 상태 조건으로 대기, 백도어는 추상 계층
- 프로파일을 하나로 통일하는 것은 타협이 아니라 **둘 다 포기하는 것**이다
- 환경을 프로파일마다 따로 만들면 시나리오·checker가 중복된다 → **하나의 환경 + 구성 전환**

:::note[🤔 마무리 자가 점검]
프로젝트 일정이 3개월 남았고 현재 상태는 다음과 같습니다.

> - P0 회귀: 8,000 job 안정 운영, 커버리지 82%
> - P1: **아직 환경을 세우지 않음.** "디지털이 안정되면 착수" 계획
> - P2: 미착수

팀장이 *"P0 커버리지를 90%까지 올리는 데 집중하고, P1은 마지막 3주에 하자"* 고 제안합니다. 이 계획의 **가장 큰 리스크**는 무엇이며 어떻게 조정하겠습니까?

<details>
<summary>정답 / 해설</summary>

**가장 큰 리스크: 마지막 3주에 P1 "검증"이 아니라 P1 "환경 구축"을 하게 됩니다.**

P1을 한 번도 세워 본 적이 없다면, 처음 돌릴 때 나오는 문제는 DUT 버그가 아니라 **환경 문제**입니다.

- 경계 신호 연결 불일치
- 시나리오가 간이 모델에 종속되어 컴파일 실패 (실패 2)
- 실제 PHY의 초기화 시퀀스가 우리 가정과 다름
- 시뮬레이션 시간 추정이 틀려 계획한 job 수를 못 돌림

이 문제들을 푸는 데 3주가 다 갈 수 있고, 그러면 **PHY–디지털 인터페이스는 실질적으로 미검증 상태로 출하**됩니다. 게다가 이 시점에는 되돌릴 여유가 없습니다.

**조정안**

1. **지금 P1을 최소 규모로 세운다** — 시나리오 1~2개만 돌아가면 됩니다. 목적은 검증이 아니라 **환경이 성립함을 확인**하는 것입니다. 이 작업에서 나오는 문제가 곧 숨은 리스크의 목록입니다
2. **그 최소 P1을 회귀에 상주시킨다**(스모크) — 이후 누군가 시나리오를 프로파일 종속적으로 작성하면 **그 순간 깨져서** 알려집니다. 3개월 뒤에 수십 개를 고치는 것보다 훨씬 쌉니다
3. **P0 커버리지 82 → 90%의 가치를 P1 리스크와 견준다** — 82%에서 남은 8%가 무엇인지 봐야 합니다. 그것이 PHY 인터페이스와 무관한 항목이라면, 8%를 올리는 것보다 P1을 세우는 것이 **검증 공백을 더 많이 줄입니다.** 커버리지 숫자를 올리는 일과 실제 위험을 줄이는 일이 항상 같은 방향은 아닙니다
4. **P2는 범위를 명시적으로 좁힌다** — 3개월 안에 P2를 제대로 하기 어렵다면, 무엇을 P2에서 확인하지 못한 채 넘어가는지 **문서로 남깁니다.** 미검증을 아는 것과 모르는 것은 다릅니다

**핵심 판단**: "안정된 뒤에 시작한다"는 순서는 **검증에는 맞지만 환경 구축에는 틀립니다.** 환경은 검증보다 먼저, 그리고 얕게라도 미리 세워 둬야 합니다.

</details>
