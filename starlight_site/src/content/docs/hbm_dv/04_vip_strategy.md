## 1. Why care? — "VIP 사면 DRAM 쪽은 해결되는 거죠?"

[Ch01의 마무리 문제](../01_what_we_verify/)에서 이런 상황을 봤습니다. DUT가 `ACT` 후 3 사이클 만에 같은 뱅크로 `RD`를 발행했는데(스펙 R6 위반, 설정값은 8), **테스트는 통과**했습니다. DRAM 모델이 타이밍을 검사하지 않았기 때문입니다.

그때 결론은 *"모델이 무엇을 검사하는지 목록화하는 것 자체가 우리의 검증 항목"* 이었습니다. 이제 그것을 실제로 합니다.

도입 결정 회의가 열립니다. 상용 HBM VIP를 사자는 제안이 올라옵니다. 실제로 존재하는 제품입니다 — Synopsys와 Cadence 모두 HBM 계열 VIP를 판매하며, 프로토콜 체크·커버리지·오류 주입까지 포함한다고 명시하고 있습니다.

그리고 누군가 묻습니다.

> **"이거 사면 DRAM 쪽은 해결되는 거죠?"**

회의실이 조용해집니다. 아무도 확답하지 못합니다. 왜냐하면 이 질문에 답하려면 **VIP가 정확히 무엇을 검사하는지** 알아야 하는데, 그것을 확인한 사람이 없기 때문입니다.

이 챕터는 그 확인을 절차로 만듭니다. 그리고 **VIP 도입은 구매 결정이 아니라 검증 범위 결정**이라는 것을 보입니다.

## 2. 직관 — "사느냐 만드느냐"는 잘못된 질문이다

### 순진한 시도 1 — "상용 VIP는 검증된 제품이니 붙이면 끝"

돈으로 해결되는 문제라면 가장 효율적인 선택입니다.

**어디서 막히나?** Ch01의 tRCD 사례가 그대로 재현됩니다. VIP를 붙였는데도 **어떤 규칙이 검사되고 어떤 규칙이 검사되지 않는지 모르면**, 우리 검증 범위가 어디까지인지 알 수 없습니다. 통과한 테스트가 무엇을 보증하는지 말할 수 없다면 그 통과는 의미가 약합니다.

이것은 Ch02의 *"검증 완료 인증서"* 문제와 같은 구조입니다 — **범위가 명시되지 않은 보증**은 받는 쪽이 범위를 확인해야 합니다.

### 순진한 시도 2 — "그럼 자체 모델을 만들어 원하는 검사를 다 넣자"

우리가 만들면 무엇을 검사하는지 정확히 압니다. Ch03에서 CCI Agent를 만들었듯이요.

**어디서 막히나?** 두 가지가 다릅니다.

첫째, **규모**입니다. CCI는 우리가 스펙을 쓴 인터페이스라 범위가 통제됩니다. HBM DRAM 모델은 JEDEC 표준 전체의 동작을 구현해야 하며, 타이밍 파라미터·모드 레지스터·리프레시·트레이닝까지 포함됩니다.

둘째, **보증의 출처**입니다. 우리가 만든 모델이 스펙대로인지는 누가 확인합니까? 그것을 검증하려면 또 다른 기준이 필요하고 — Ch01에서 본 **무한 후퇴**입니다.

### 일반화 — 판단은 이분법이 아니라 3단 절차다

두 시도가 놓친 것은 질문 자체가 잘못되었다는 점입니다. "사느냐 만드느냐"는 **결론**이지 **절차**가 아닙니다.

> **VIP 판단 3단 절차**
> **① 요구 목록** — 우리는 무엇이 검사되기를 원하는가
> **② 커버 매핑** — 후보(상용/자체/기존 자산)가 그중 무엇을 덮는가
> **③ 잔여 처리** — 덮이지 않는 것을 어떻게 메울 것인가

```d2
direction: right

REQ: "① 요구 목록\n스펙 규칙 R1~R20\n+ 통합 항목 I1~I8\n+ 우리 DUT 고유 규칙" { style.fill: "#e3f2fd"; style.font-color: "#0A0F25" }
MAP: "② 커버 매핑\n후보가 무엇을 검사하는가\n(문서·평가판으로 확인)" { style.fill: "#fff8e1"; style.font-color: "#0A0F25" }
GAP: "③ 잔여 처리\n덮이지 않는 규칙\n→ 자체 assertion (Ch09)\n→ 자체 시나리오 (Ch08)" { style.fill: "#ffcdd2"; style.font-color: "#0A0F25" }

REQ -> MAP -> GAP
GAP -> REQ: "잔여가 과도하면\n후보 재검토"
```

**정의.** VIP 도입은 구매 결정이 아니라 **검증 범위 결정**이다. 무엇을 사든 만들든, ③의 잔여 목록이 곧 **우리가 직접 해야 할 일**이며 그것이 계획에 들어가야 한다.

## 3. 작은 예 — 상용 HBM VIP가 주는 것과 남는 것

### 상용 HBM VIP가 제공한다고 밝히는 것

벤더 제품 문서 기준으로 정리합니다. *(특정 제품을 추천하는 것이 아니라 상용 VIP 일반의 제공 범위를 보이기 위한 것입니다.)*

| 제공 항목 | 검증에서의 의미 |
|---|---|
| **네이티브 SystemVerilog / UVM 지원** | 우리 환경에 바로 결합 |
| **JEDEC 표준 및 벤더 파트번호 기반 사전 구성** | 대상 제품에 맞는 설정을 골라 씀 |
| **내장 프로토콜 체크** | ⭐ 표준 규칙 위반을 VIP가 직접 신고 |
| **커버리지 모델** | 프로토콜 관점의 커버리지 |
| **오류 주입 기능** | 오류 경로 시나리오 지원 |
| 검증 계획(verification plan) 문서 | 무엇을 검사하는지의 근거 자료 |
| 다중 플랫폼 — 시뮬레이션·형식검증·하드웨어 가속 | 환경 확장 시 재사용 |

지원 세대도 넓습니다 — HBM2·HBM2E·HBM3·HBM3E·HBM4 계열이 제품별로 커버되며, 표준 번호(JESD235 계열 / JESD238 계열 / JESD270-4 계열)로 명시됩니다. 컨트롤러와 PHY 사이의 인터페이스(DFI)용 VIP도 별도로 존재합니다.

**굵게 표시한 "내장 프로토콜 체크"가 핵심입니다.** Ch01의 tRCD 사례가 통과한 이유는 모델이 검사하지 않았기 때문인데, 프로토콜 체크를 갖춘 VIP를 쓰면 그런 위반이 **VIP 쪽에서 신고**됩니다. 이것이 상용 VIP를 사는 가장 큰 실질적 이유입니다 — 코드를 아끼는 것이 아니라 **검증 신뢰도의 상한을 올리는 것**입니다.

### 그럼에도 남는 것

여기가 이 챕터의 요점입니다. 상용 VIP는 **HBM 표준**을 압니다. 그러나 다음은 원리적으로 모릅니다.

| 남는 항목 | 왜 VIP가 못 하나 |
|---|---|
| **우리 DUT 고유 규칙** — 예: 스펙 R3(CA 공유 시 `row_pc == col_pc`) | R3은 `hbm_ch_ctrl`의 내부 설계 규칙이지 HBM **표준**이 아닙니다 |
| **우리 시스템 통합 항목** — Ch02의 I1~I8 | VIP는 우리 클럭·리셋 구조와 주변 IP를 모릅니다 |
| **우리 설정 조합** | 사전 구성에 없는 조합은 우리가 확인합니다 |
| **CCI 쪽 전부** | 비표준 인터페이스 — Ch03에서 만든 이유 |
| ⭐ **성능·스케줄링 품질** | VIP는 *"규칙을 어겼는가"* 를 봅니다. *"효율적으로 했는가"* 는 보지 않습니다 |

마지막 항목을 강조합니다. 21항목 **#2(실효 대역폭·스케줄링 효율 측정)** 는 **어떤 상용 VIP도 주지 않습니다.** VIP 관점에서 `SCHED_MODE`가 무엇이든 규칙만 지키면 정상이기 때문입니다. 성능 검증은 처음부터 끝까지 우리 몫이며, Ch08에서 다룹니다.

### 매핑표 만들기 — #10을 닫는 실제 작업

요구 목록(①)과 VIP 제공 범위(②)를 표로 대조합니다. `hbm_ch_ctrl`의 예시입니다.

| 우리 규칙 | 성격 | 상용 HBM VIP가 검사? | 잔여 처리 |
|---|---|---|---|
| R6·R7·R8 (tRCD/tRP/tRAS) | HBM 표준 타이밍 | ✅ 프로토콜 체크에 포함 | — |
| R4·R5 (뱅크 상태 전이) | HBM 표준 | ✅ | — |
| **R3 (CA 공유 `row_pc==col_pc`)** | **우리 IP 규칙** | ❌ | **자체 assertion (Ch09)** |
| **R1·R2 (CCI 핸드셰이크)** | **비표준 I/F** | ❌ | **자체 assertion (Ch09)** |
| **R9·R10·R11 (응답·OoO)** | **비표준 I/F** | ❌ | **자체 assertion + scoreboard (Ch09)** |
| **R12~R16 (CCI 오류 처리)** | **우리 IP 규칙** | ❌ | **오류 주입 시나리오 (Ch08)** |
| **R17~R20 (테스트 모드)** | **우리 IP 규칙** | ❌ | **모드 전이 시나리오 (Ch08·Ch11)** |
| I1~I8 (통합) | 우리 시스템 | ❌ | **통합 시나리오 (Ch02·Ch06)** |
| #2 (실효 대역폭) | 성능 | ❌ (원리적으로) | **성능 시나리오 (Ch08)** |

**이 표가 답입니다.** 도입부의 질문 *"VIP 사면 DRAM 쪽은 해결되는 거죠?"* 에 대해 이제 답할 수 있습니다.

> **DRAM 표준 준수는 해결됩니다. 그러나 R1~R3·R9~R20, 통합 항목, 성능은 그대로 남습니다.**
> 그리고 그 잔여 목록이 이 코스의 Ch08·Ch09가 다루는 내용입니다.

VIP가 수집하는 커버리지는 **HBM 프로토콜 관점의 커버리지**입니다. 어떤 커맨드 조합이 오갔는지, 어떤 타이밍 조건이 발생했는지 같은 것입니다. 이것은 유용하지만 **우리 DUT가 무엇을 했는지의 척도가 아닙니다.**

- **R3(CA 공유)** 조합이 얼마나 나왔는지 — VIP 모델에 그런 항목이 없습니다
- **CCI 쪽** 트랜잭션 다양성 — VIP는 CCI를 보지 않습니다
- **`SCHED_MODE` 3종**이 각각 얼마나 사용됐는지 — 우리 IP의 설정이지 HBM 표준이 아닙니다

- **동시 활성 채널 조합**(#1) — 우리 coverage 모델의 축입니다

선행 코스에서 확립한 원리가 여기서도 그대로입니다.

> **모델에 없는 항목은 0%로 잡히는 것이 아니라 아예 집계되지 않는다.**

VIP의 94%는 **VIP의 모델 기준 94%** 입니다. 우리 DUT의 기능 커버리지는 우리가 별도로 모델을 만들어 측정해야 하며, 그것이 Ch10의 주제입니다.

**올바른 진술로 고치면**: *"HBM 프로토콜 준수 측면의 커버리지는 VIP 기준 94%입니다. 우리 DUT 기능 커버리지는 별도 모델로 측정 중이며 현재 X%입니다."*

### VIP 평가 체크리스트

도입 전에 확인할 항목입니다. Ch02의 handoff 체크리스트(H1~H6)와 같은 성격이며, 상용 VIP도 결국 **외부에서 오는 검증 자산**이기 때문입니다.

| # | 확인 항목 | 확인하지 않으면 |
|---|---|---|
| V1 | 지원 표준·세대가 우리 대상과 일치하는가 | 세대 이관 시 재구매 |
| V2 | **내장 프로토콜 체크의 목록** | 매핑표를 만들 수 없음 → #10 미해결 |
| V3 | **커버리지 모델에 무엇이 들어 있는가** | 위 자가 점검의 오해 발생 |
| V4 | 오류 주입 능력의 범위 | 우리 오류 시나리오와 중복·누락 |
| V5 | 우리 시뮬레이터·버전 지원 | 통합 단계에서 발견 |
| V6 | 우리 구성이 사전 구성에 있는가 | 없으면 그 구성은 자체 확인 (Ch02 H1) |
| V7 | 시뮬레이션 속도와 라이선스 모델 | 회귀 규모에서 병목·비용 초과 |
| V8 | 지원·업데이트 주기, errata | 이슈 대응 지연 |

**V2와 V3가 핵심**입니다. 이 둘의 답이 없으면 매핑표를 만들 수 없고, 매핑표가 없으면 우리 검증 범위를 말할 수 없습니다.

## 4. 일반화 — 언제 만들고 언제 사는가

### 대안 A — DRAM 모델을 자체 개발한다면?

**왜 보통 안 하나**: 규모와 보증의 출처 문제(§2). 표준 전체를 구현해야 하고, 그 정확성을 보증할 기준이 따로 없습니다.

**그럼에도 정당화되는 경우**:
1. **표준 외 구성**을 쓸 때 — 상용이 지원하지 않는 특수 구성
2. **초기 탐색 단계** — VIP 도입 전 간이 모델로 환경 골격을 먼저 세울 때. 단 **임시임을 명시**하고 교체 시점을 계획에 둡니다
3. **라이선스 제약** — 회귀 병렬도가 라이선스 수를 초과할 때 일부를 간이 모델로 대체

3번은 실무에서 자주 나옵니다. 이때 주의할 점은 **간이 모델로 돌린 회귀와 VIP로 돌린 회귀가 서로 다른 것을 검증한다**는 사실을 계획에 명시하는 것입니다. 그러지 않으면 "회귀 1만 개 통과"라는 숫자가 실제보다 강하게 읽힙니다.

### 대안 B — VIP 없이 단순 모델 + 자체 assertion 전량

DRAM 쪽을 아주 단순한 메모리 모델로 두고, 표준 규칙까지 전부 우리 assertion으로 검사하는 방식입니다.

**장점**: 무엇을 검사하는지 완전히 통제합니다. 라이선스 비용이 없습니다.

**대가**: **표준 준수 검증 전체를 우리가 짊어집니다.** JEDEC 타이밍 규칙을 우리가 읽고 assertion으로 옮겨야 하며, 그 assertion이 스펙을 정확히 반영하는지는 다시 우리 책임입니다. Ch03에서 CCI에 대해 한 작업을 **표준 전체 규모로** 하는 셈입니다.

**판단 기준**: 검사해야 할 규칙이 **표준에 속하는가, 우리 설계에 속하는가**로 갈립니다.

| 규칙의 출처 | 권장 |
|---|---|
| 업계 표준 (JEDEC 등) | **상용 VIP** — 표준 해석의 책임을 위임 |
| 우리 IP 설계 규칙 | **자체 assertion** — 우리만 아는 규칙 |
| 우리 시스템 통합 | **자체 시나리오** — 우리만 재현 가능 |
| 성능·효율 | **자체 측정** — VIP가 원리적으로 안 봄 |

---

## 5. 디테일 — VIP 도입에서 실제로 벌어지는 일

### 실패 1 — 검사 범위를 확인하지 않고 도입한다

Ch01의 tRCD 사례가 도입 후에도 반복되는 경우입니다.

**관측되는 증상**: VIP를 붙였는데도 특정 부류의 위반이 계속 실리콘에서 발견됩니다. 조사해 보면 그 규칙은 VIP의 체크 목록에 **처음부터 없었습니다.** 아무도 목록을 본 적이 없었으므로 있다고 가정했을 뿐입니다.

**처방**: V2·V3의 답을 **문서로** 받고 매핑표를 만듭니다. 매핑표는 V-Plan의 일부입니다 (Ch07).

### 실패 2 — VIP 커버리지를 우리 커버리지로 착각한다

위 자가 점검의 상황입니다.

**관측되는 증상**: 커버리지 지표가 높게 보고되어 sign-off 논의가 빨라집니다. 그런데 그 숫자에 우리 DUT의 기능 축(동시성·설정 조합·오류 경로)이 **애초에 들어 있지 않습니다.** 실리콘에서 그 축의 결함이 나옵니다.

**처방**: 커버리지 리포트를 **출처별로 분리**해 보고합니다 — "VIP 프로토콜 커버리지"와 "DUT 기능 커버리지"를 한 숫자로 합치지 않습니다.

### 실패 3 — VIP를 기본 설정으로 쓴다

VIP를 인스턴스화만 하고 설정을 손대지 않는 경우입니다.

**관측되는 증상**: 두 방향으로 문제가 납니다. 일부 체크가 **기본값으로 꺼져** 있어 검사되지 않거나, 반대로 우리 구성과 다른 사전 구성이 적용되어 **잘못된 기준으로 위반을 신고**합니다. 후자는 오탐이 쏟아져 팀이 VIP 경고를 무시하기 시작하는 더 나쁜 결과로 이어집니다.

**처방**: VIP 설정도 **환경 설정값**으로 관리합니다 — 어떤 체크를 켰는지, 어떤 사전 구성을 골랐는지가 코드 리뷰 대상이어야 합니다. 그리고 그 설정이 매핑표의 전제와 일치하는지 확인합니다.

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "VIP를 사면 그쪽은 해결된다" | 표준 준수만 해결됩니다. **우리 IP 규칙·통합·성능은 남습니다** |
| "VIP 커버리지가 높으면 검증이 진척된 것" | VIP 커버리지는 **프로토콜 관점**입니다. DUT 기능 커버리지와 별개입니다 |
| "사느냐 만드느냐를 먼저 정한다" | 먼저 **요구 목록**을 만듭니다. 결론은 매핑 후에 나옵니다 |
| "VIP는 붙이면 동작한다" | **설정이 검증 범위를 바꿉니다.** 체크가 꺼져 있을 수 있습니다 |
| "성능도 VIP가 봐 줄 것" | VIP는 *규칙 위반*을 봅니다. *효율*은 원리적으로 안 봅니다 |
| "간이 모델로 돌린 회귀도 같은 회귀" | 검증한 범위가 다릅니다. **계획에 구분해 적습니다** |

## 🔧 이 문제를 이렇게 푼다

> **닫는 항목: #20 — VIP를 사느냐 만드느냐 판단 / #10 — 모델의 엄격함 자체를 검증 항목으로**

### #20 — 3단 절차와 의사결정 매트릭스

**절차**
1. **요구 목록 작성** — 스펙 규칙(R1~R20) + 통합 항목(I1~I8) + 성능 요구를 한 목록으로
2. **후보별 커버 매핑** — V1~V8로 각 후보가 무엇을 덮는지 확인
3. **잔여 도출** — 덮이지 않는 항목을 Ch08(시나리오)·Ch09(assertion)로 배정

**매트릭스**

| 조건 | 판단 |
|---|---|
| 업계 표준 + 상용 존재 + 우리 구성 지원 | **구매** |
| 업계 표준 + 상용 존재 + 우리 구성이 범위 밖 | 구매 **+ 범위 밖 부분 자체 보강** |
| 업계 표준 + 사내 자산 존재 | 자산 재사용 검토 후 결정 |
| **비표준 · 고객 전용** | **자체 개발** (Ch03) |
| 성능·효율 측정 | **항상 자체** (VIP가 안 줌) |

### #10 — 검사 범위 매핑표

**만드는 법**
1. VIP·모델 문서에서 **내장 체크 목록**을 추출한다 (V2)
2. 우리 규칙 목록과 나란히 놓고 **덮임/안 덮임**을 표시한다
3. 안 덮이는 항목마다 **처리 방법과 담당 챕터**를 적는다
4. 이 표를 **V-Plan에 포함**한다 (Ch07)

**갱신 규칙**
- VIP 버전이 올라가면 체크 목록이 바뀔 수 있다 → **매핑표 재확인**
- 모델을 교체하면(간이 → 상용) 잔여 목록이 줄어든다 → **중복 작업 정리**
- 새 규칙이 스펙에 추가되면 매핑표에 행을 추가한다

### 보고 규칙

- 커버리지는 **출처별로 분리 보고**한다 — VIP 프로토콜 커버리지 ≠ DUT 기능 커버리지
- 간이 모델로 돌린 회귀와 VIP로 돌린 회귀를 **구분해 집계**한다
- VIP 설정(켠 체크·선택한 사전 구성)을 **환경 설정값으로 관리**하고 리뷰 대상으로 삼는다

## 7. 핵심 정리

- **VIP 도입은 구매 결정이 아니라 검증 범위 결정이다**
- 판단은 이분법이 아니라 **3단 절차** — 요구 목록 → 커버 매핑 → 잔여 처리
- 상용 HBM VIP는 **표준 준수**를 덮는다. 내장 프로토콜 체크가 검증 신뢰도의 상한을 올린다
- 그러나 **우리 IP 고유 규칙·시스템 통합·설정 조합·성능**은 남는다. 특히 **성능은 원리적으로** VIP가 주지 않는다
- **VIP 커버리지 ≠ DUT 기능 커버리지.** 출처별로 분리해 보고한다
- 규칙의 **출처**가 판단 기준이다 — 표준이면 사고, 우리 설계 규칙이면 만든다
- 매핑표는 한 번 만들고 끝이 아니다. **VIP 버전·모델 교체·스펙 변경 시 갱신**한다

:::note[🤔 마무리 자가 점검]
프로젝트 중간 리뷰에서 다음 상황이 보고되었습니다.

> "상용 HBM VIP를 도입했습니다. 다만 라이선스가 4개뿐이라 야간 회귀 200 job 중 **180개는 자체 간이 DRAM 모델**로, 20개만 VIP로 돌립니다. 전체 회귀 통과율 99.5%입니다."

(a) 이 보고의 **위험한 지점**은 어디입니까? (b) 어떻게 고쳐 보고해야 합니까? (c) 운영을 어떻게 바꾸는 것이 좋습니까?

<details>
<summary>정답 / 해설</summary>

**(a) "전체 회귀 통과율 99.5%"가 실제보다 강하게 읽힙니다.**

180개와 20개는 **서로 다른 것을 검증한 회귀**입니다. 간이 모델로 돌린 180개는 프로토콜 체크가 없거나 약하므로, 그 통과는 *"데이터가 맞았다"* 정도만 보증합니다. Ch01의 tRCD 위반 같은 결함은 그 180개에서 **원리적으로 발견되지 않습니다.**

두 종류를 하나의 통과율로 합치면, 실제로는 20개만이 담당하는 표준 준수 검증이 **200개가 담당한 것처럼** 보입니다.

**(b) 출처별로 분리 보고합니다.**

> "VIP 기반 회귀 20 job — 통과율 X%, 프로토콜 체크 활성.
> 간이 모델 기반 회귀 180 job — 통과율 Y%, **프로토콜 체크 없음(데이터 정합성만)**.
> 표준 준수 검증은 VIP 기반 20 job에만 의존하고 있음."

마지막 문장이 핵심입니다. 이 문장이 있어야 리뷰어가 **위험의 크기**를 판단할 수 있습니다.

**(c) 세 가지 개선 방향**

1. **역할을 명시적으로 나눈다** — 간이 모델 회귀는 *기능·데이터 정합성 스윕*, VIP 회귀는 *프로토콜 준수 확인*으로 목적을 분리하고, 각각 다른 시나리오 집합을 돌립니다. 같은 시나리오를 나눠 돌리는 것보다 낫습니다
2. **잔여를 자체 assertion으로 메운다** — 간이 모델 회귀에도 **우리 assertion**(Ch09)은 항상 붙습니다. R1~R3·R9~R20은 어차피 VIP가 안 보는 항목이므로, 이들은 180개 회귀에서도 검사됩니다. 즉 **잔여 목록을 성실히 메워 두면 라이선스 제약의 타격이 줄어듭니다**
3. **라이선스 병목을 계획 리스크로 올린다** — 4개가 적정한지 판단하려면 "표준 준수 검증에 필요한 회귀 규모"가 근거가 되어야 하고, 그 근거는 매핑표에서 나옵니다

**일반 교훈**: 검증 자산이 섞여 있을 때 **집계를 합치지 않는 것**이 원칙입니다. 합친 숫자는 항상 약한 쪽이 강한 쪽에 묻어가는 방향으로 오해를 만듭니다.

</details>
:::
