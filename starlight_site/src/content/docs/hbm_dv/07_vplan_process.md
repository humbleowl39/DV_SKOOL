## 1. Why care? — "지금 몇 % 됐어요?"

주간 회의에서 질문이 옵니다. 검증 진척도를 알려 달라는 것입니다.

준비해 둔 답이 있습니다.

> *"계획된 테스트 120개 중 90개를 작성했습니다. 75%입니다."*

숫자가 있으니 답변으로 성립하는 것 같습니다. 그런데 이 보고에는 문제가 있습니다.

**75%의 분모가 "우리가 계획한 테스트 개수"입니다.** 그 120개가 검증해야 할 것을 다 덮는지는 아무도 확인하지 않았습니다. 만약 스펙 R17~R20(테스트 모드)에 대한 테스트를 처음부터 계획에 넣지 않았다면, 그 항목은 **0%로 보고되는 것이 아니라 아예 집계에서 빠집니다.** 그리고 진척도는 오히려 **좋아 보입니다** — 분모가 작으니까요.

선행 코스에서 커버리지에 대해 확립한 원리가 진척도에도 그대로 적용됩니다.

> **모델에 없는 항목은 0%로 잡히는 것이 아니라 아예 집계되지 않는다.**

이 문제를 푸는 방법은 **분모를 테스트가 아니라 검증 항목으로 바꾸는 것**입니다. 그리고 그 항목 목록이 V-Plan입니다.

다행히 우리는 이미 재료를 다 갖고 있습니다. 앞의 여섯 챕터가 만든 산출물들이 흩어져 있을 뿐입니다. 이 챕터는 그것들을 하나의 문서로 묶습니다.

## 2. 직관 — V-Plan의 행은 무엇인가

### 순진한 시도 1 — 테스트 목록을 V-Plan으로 삼는다

작성할 테스트를 나열하고 그것을 계획이라 부릅니다. 실행 가능하고 진척도도 바로 나옵니다.

**어디서 막히나?** 도입부의 문제입니다. **분모가 우리 상상력의 크기**가 됩니다. 빠뜨린 것은 계획에도 없고 진척도에도 없으므로, 누락을 발견할 수단이 **계획 안에 존재하지 않습니다.**

### 순진한 시도 2 — 스펙 문장마다 항목을 만든다

스펙을 문장 단위로 쪼개 각각을 검증 항목으로 만듭니다. 누락이 없어 보입니다.

**어디서 막히나?** 두 가지가 걸립니다.

**스펙 문장은 측정 가능 단위가 아닙니다.** *"컨트롤러는 요청을 효율적으로 처리해야 한다"* 같은 문장은 그대로는 판정할 수 없습니다. 측정 가능한 형태로 다시 써야 합니다.

**스펙에 없는 항목이 있습니다.** 통합 항목(I1~I8)은 우리 시스템의 문제이므로 IP 스펙에 없습니다. 성능 목표도, 세대 이관 대응도 스펙 문서에는 없습니다. 스펙만 따라가면 이들이 통째로 빠집니다.

### 일반화 — 행은 "측정 가능한 검증 항목"이다

> **V-Plan의 한 행은 측정 가능한 검증 항목이며, 다음 다섯 가지를 반드시 갖는다.**
> ① **무엇을** 확인하는가 · ② **어떻게** 측정하는가 · ③ **어디서**(계층·프로파일) · ④ **무엇으로**(테스트·assertion·coverage) · ⑤ **현재 상태**

②와 ④를 구분하는 것이 중요합니다. 선행 코스 Ch05가 *"감시 대상 10개 중 데이터 비교로 잡히는 것은 1개뿐"* 이라고 했으므로, 측정 수단이 **테스트만이 아닙니다.**

| 측정 수단 | 적합한 항목 |
|---|---|
| 테스트(시나리오) | 특정 조건을 만들어야 하는 것 — 오류 주입, 모드 전이 |
| **Assertion** | 상시 감시가 필요한 것 — 타이밍·순서·경합 규칙 |
| **Coverage bin** | 다양성이 확보되었는지 — 조합·상태 전이 |
| 측정·집계 | 성능 — 대역폭·지연 |
| 리뷰 | 문서·구조 — 경계표 확정, 매핑표 갱신 |

**항목마다 수단이 다르며, 수단이 정해지지 않은 항목은 아직 계획이 아닙니다.**

## 3. 작은 예 — 앞 챕터 산출물을 행으로 펼치기

V-Plan은 새로 만드는 것이 아닙니다. **이미 있는 것을 행으로 펼친 것**입니다.

| 입력 산출물 | 출처 | V-Plan에서의 위치 |
|---|---|---|
| **경계표** (DUT/모델/범위 밖 + 조달) | Ch01 | **0장 — 전제** |
| 스펙 규칙 R1~R20 | 부록 A | 기능 항목 |
| Handoff 답 H1~H6 | Ch02 | 3rd party 위임 범위 / 자체 검증 범위 |
| 통합 항목 I1~I8 | Ch02 | **통합 절 (별도)** |
| 검사범위 매핑표의 **잔여** | Ch04 | 자체 항목으로 승격 |
| 프로파일 배치 | Ch05 | 각 행의 **③ 어디서** |
| 환경 계층 배치 | Ch06 | 각 행의 **③ 어디서** |
| 성능 목표 | 선행 코스 #2 | **성능 절 (별도)** |

### V-Plan 행 예시

```
[0장 — 전제]
  경계표: DUT=hbm_ch_ctrl RTL / 모델=CCI Agent(자체), DRAM VIP(구매) / 범위 밖=PHY 아날로그, 인터포저
  검사범위 매핑표: 상용 VIP가 R4~R8 담당, R1~R3·R9~R20은 자체
```

| ID | 항목 | 출처 | 측정 수단 | 계층·프로파일 | 상태 |
|---|---|---|---|---|---|
| F-01 | ACT→RD 간격이 `tRCD_CYC` 이상 | R6 | **Assertion** (자체) | IP / P0 | 통과 |
| F-02 | `row_pc == col_pc` (CA 공유) | **R3** | **Assertion** (자체) | IP / P0 | 구현중 |
| F-03 | 패리티 오류 시 `PARITY_ERR` 응답 | R12 | 테스트(**오류 주입**) | IP / P0 | 미착수 |
| F-04 | `PAR_CHK_EN=0`이면 미검사 | R13 | 테스트(오류 주입+설정) | IP / P0 | 미착수 |
| F-05 | `rsp_id`가 미해결 요청 중 하나 | R9 | Assertion + Scoreboard | IP / P0 | 통과 |
| F-06 | 테스트 모드 진입 시 커맨드 정지 | R18 | 테스트(모드 전이) | IP / P0 | 미착수 |
| C-01 | 동시 활성 채널 조합 다양성 | #1 | **Coverage bin** | Subsys / P0 | 구현중 |
| C-02 | `SCHED_MODE` 3종 모두 사용 | A.7 | **Coverage bin** | IP / P0 | 미착수 |
| C-03 | 테스트 모드 전이 경로 전수 | #18 | **Coverage(전이)** | IP / P0 | 미착수 |
| I-01 | 연결 정합 (폭·방향) | I1 | 테스트(연결성) | Subsys / P0 | 통과 |
| I-04 | 우리 설정 조합 (벤더 범위 밖) | I4, H1 | 테스트 | Subsys / P0 | 구현중 |
| I-07 | 채널 간 자원 경합 | I7 | Assertion + Coverage | Subsys / P0 | 미착수 |
| **P-01** | **실효 대역폭 ≥ 목표치** | **#2** | **측정·집계** | Subsys / P0 | 미착수 |
| **P-02** | **읽기 지연 ≤ 목표치** | **#4** | **측정·집계** | Subsys / P0 | 미착수 |
| M-01 | PHY 제어 시퀀스 정합 | Ch05 배치 | 테스트 | Full / **P1** | 미착수 |
| D-01 | 경계표·매핑표 최신 상태 | Ch01·Ch04 | **리뷰** | — | 통과 |

**보이는 것들**

- **측정 수단이 테스트가 아닌 행이 절반 이상**입니다 — assertion, coverage bin, 측정, 리뷰. 테스트 개수로 진척도를 세면 이들이 집계에서 빠집니다
- **성능 항목(P-01·P-02)이 별도 접두어**를 갖습니다 — 성격이 다르기 때문입니다(다음 절)
- **D-01처럼 문서 항목도 행**입니다 — 경계표가 최신이 아니면 나머지 판정의 근거가 흔들립니다

### 성능 항목은 왜 별도인가 — #4

기능 항목과 성능 항목은 판정 방식이 다릅니다.

| | 기능 항목 | 성능 항목 |
|---|---|---|
| 판정 | **이진** — 맞다/틀리다 | **연속값 + 목표치** |
| 실패의 의미 | 규칙 위반 (버그) | 목표 미달 (튜닝 대상일 수도) |
| 측정 수단 | assertion·테스트 | 측정·집계 |
| 필요한 것 | 규칙 | **목표치와 측정 조건** |

그리고 **지연과 대역폭은 서로 다른 축**입니다. 선행 코스 Ch01이 *"HBM은 대역폭 기술이지 지연 기술이 아니다"* 라고 한 것이 계획에도 반영되어야 합니다. 한 항목으로 묶으면 대역폭이 좋아서 통과했는데 지연이 나빠진 것을 놓칩니다.

**측정 방법은 이미 준비되어 있습니다.** Ch03에서 item에 `t_req`·`t_rsp`를 넣어 둔 것을 기억하십니까?

| 성능 항목 | 측정 방법 |
|---|---|
| **지연** | 트랜잭션별 `t_rsp - t_req`의 분포 (평균·최악) |
| **대역폭** | 단위 시간당 완료 beat 수 |
| 스케줄링 효율 | `SCHED_MODE`별 위 두 값의 비교 |

`SCHED_MODE`(스펙 A.7)를 바꿔 가며 측정하면 **설정이 성능에 미치는 영향**이 나오고, 이것이 21항목 #17(설정 효과)과 #2(실효 대역폭)를 동시에 다룹니다.

:::note[🤔 잠깐 — V-Plan 행으로 만들어 보세요]
스펙 R14는 이렇게 규정합니다.

> *"패리티 오류 발생 시 `MR_ERR_STS.PAR_ERR`이 set되며, 1을 써야 clear된다(W1C)."*

이것을 V-Plan 행으로 만드세요. **① 무엇을 ② 어떻게 ③ 어디서 ④ 무엇으로** 를 채우고, **몇 개의 행이 필요한지** 판단하세요.

<details>
<summary>정답 / 해설</summary>

**한 행으로는 부족합니다. 최소 세 행이 필요합니다.**

R14는 한 문장이지만 **서로 다른 세 가지 동작**을 규정하고 있습니다.

| ID | ① 무엇을 | ② 어떻게 | ③ 어디서 | ④ 무엇으로 |
|---|---|---|---|---|
| F-14a | 패리티 오류 발생 시 `PAR_ERR`이 **set**된다 | 오류 주입 후 CSR 읽기 | IP / P0 | 테스트(오류 주입) |
| F-14b | set된 `PAR_ERR`이 **읽기만으로는 clear되지 않는다**(sticky) | 여러 번 읽어도 유지 확인 | IP / P0 | 테스트 |
| F-14c | `PAR_ERR`에 **1을 쓰면 clear**된다 (W1C) | 1 write 후 읽어 0 확인 | IP / P0 | 테스트 |

**왜 나눠야 하는가**

세 동작 중 하나만 틀려도 R14 위반인데, 한 행으로 두면 *"R14 통과"* 가 세 가지 모두를 확인했다는 뜻인지 알 수 없습니다. 특히 **F-14b(sticky)** 는 빠뜨리기 쉽습니다 — set과 clear만 확인하고 넘어가면, 읽을 때마다 자동으로 clear되는 구현 오류를 놓칩니다.

**추가로 필요한 행**

| ID | 항목 | 수단 |
|---|---|---|
| C-14 | `PAR_ERR`의 set/clear 상태 전이가 모두 발생 | **Coverage(전이)** |

테스트가 있어도 **실제로 그 경로를 밟았는지**는 커버리지가 알려 줍니다.

**일반 원리**: **스펙 문장 수와 V-Plan 행 수는 1:1이 아닙니다.** 한 문장이 여러 동작을 규정하면 나누고, 여러 문장이 하나의 측정으로 확인되면 묶습니다. 기준은 문장이 아니라 **독립적으로 판정 가능한 단위**입니다.

</details>

### 진행 추적 — 항목 기반 보고

| 상태 | 의미 |
|---|---|
| 미착수 | 수단이 정해졌으나 구현 전 |
| 구현중 | 작성 중 |
| 통과 | 측정되어 기준 충족 |
| **차단** | 외부 요인으로 진행 불가 (RTL 미비, IP 미도착 등) |
| **Waive** | 검증하지 않기로 결정 — **근거 필수** |

**진척도 = 통과 항목 / 전체 항목.** 테스트 개수가 아닙니다.

그리고 이 정의에도 함정이 남습니다 — **항목 목록 자체가 불완전하면** 분모가 작아 진척도가 좋아 보입니다. 그래서 **항목 목록 리뷰가 별도 게이트**여야 합니다.

### 프로세스 게이트

| 게이트 | 통과 조건 |
|---|---|
| **계획 리뷰** | 경계표 확정 · **항목 목록 리뷰 완료** · 조달 계획(Custom Agent·VIP) 확정 |
| **환경 준비** | 스모크 통과 · 프로파일 최소 구성 성립(Ch05) · Agent 자가 점검 |
| **기능 완료** | 기능 항목(F-*) 통과 · assertion 활성 확인 |
| **Coverage 완료** | Coverage 항목(C-*) 목표 달성 또는 **waive 근거 기재** |
| **성능 확인** | 성능 항목(P-*) 목표 달성 또는 목표 재협의 |
| **Sign-off** | 전 게이트 통과 · 미해결 이슈 정리 · **waive 목록 승인** |

"계획 리뷰" 게이트에 **항목 목록 리뷰**를 명시한 것이 핵심입니다. 이 리뷰가 도입부의 문제(누락이 진척도를 좋게 만드는 현상)를 막는 유일한 지점입니다.

## 4. 일반화 — 두 가지 계획 방식의 한계

### 대안 A — V-Plan 없이 테스트 목록으로 관리한다면?

가볍고 즉시 시작할 수 있습니다. 작은 프로젝트에서는 실제로 충분할 수 있습니다.

**한계**: 누락을 감지할 수단이 없습니다. 그리고 assertion·coverage·성능처럼 **테스트가 아닌 수단으로 확인되는 항목**이 계획에서 사라집니다. 선행 코스 결론(감시 대상의 90%가 데이터 비교 밖)을 고려하면 이것은 계획의 대부분이 빠지는 것입니다.

### 대안 B — 스펙 문장과 1:1로 매핑한다면?

추적성이 명확해 인증·감사 상황에서 선호됩니다.

**한계**: 측정 불가한 문장이 그대로 항목이 되고, 스펙 밖 항목(통합·성능·세대 대응·문서)이 빠집니다.

**실무적 절충**: 스펙 문장에 대한 **추적성은 유지**하되(각 행의 "출처" 칸), 행의 단위는 **독립 판정 가능 단위**로 잡습니다. 위 자가 점검의 R14 → 3행 분할이 그 예입니다. 그리고 스펙 밖 항목은 별도 절(통합·성능·문서)로 둡니다.

## 5. 디테일 — 계획 운영에서 실제로 벌어지는 일

### 실패 1 — 진척도를 테스트 개수로 보고한다

도입부의 사례입니다.

**관측되는 증상**: 진척도가 꾸준히 올라가고 일정도 맞아 보입니다. 그런데 후반에 *"이건 누가 검증하나요"* 가 나옵니다. 계획에 없던 항목이 발견된 것이며, 그 시점에는 넣을 자리가 없습니다.

**왜 위험한가**: 이 실패는 **지표가 좋아 보이는 방향으로** 작동합니다. 누락이 많을수록 분모가 작아 진척도가 높습니다. 지표를 보는 사람에게는 위험 신호가 전혀 보이지 않습니다.

### 실패 2 — 성능 항목이 기능 항목에 섞인다

성능 관련 항목을 다른 기능 항목과 같은 목록에 두는 경우입니다.

**관측되는 증상**: 성능 항목이 **목표치 없이** "통과"로 처리됩니다. 시나리오가 돌았고 오류가 없었으므로 통과라고 본 것인데, 실제로는 **무엇과 비교했는지가 없습니다.** 실리콘에서 대역폭이 목표에 못 미치는 것이 발견되고, 그때 *"검증에서는 통과했는데"* 라는 말이 나옵니다.

**처방**: 성능 항목은 **별도 절 + 목표치 + 측정 조건**을 갖습니다. 목표치가 없는 성능 항목은 항목이 아니라 관찰입니다.

### 실패 3 — V-Plan을 초기에 쓰고 갱신하지 않는다

계획 리뷰를 통과한 뒤 문서를 덮어 두는 경우입니다.

**관측되는 증상**: 프로젝트 중간에 여러 변화가 생깁니다 — VIP를 교체했고, 프로파일을 추가했고, 스펙 개정으로 규칙이 하나 바뀌었습니다. V-Plan은 그대로입니다. 결과적으로 **계획이 가리키는 상태와 실제 환경이 다르고**, 진척도 보고가 무엇을 근거로 하는지 알 수 없게 됩니다.

**처방**: V-Plan을 **변경 이력이 있는 문서**로 관리하고, 다음 사건마다 갱신을 트리거로 둡니다.

| 트리거 | 갱신할 것 |
|---|---|
| VIP·모델 교체 | 검사범위 매핑표 → 잔여 항목 재산정 (Ch04) |
| 프로파일 추가·변경 | 각 행의 "어디서" |
| 스펙 개정 | 해당 행과 assertion |
| **세대 이관** | 아래 #5 절차 |
| 경계 변경 | 0장 전제 |

## 6. 흔한 오해

| 오해 | 실제 |
|---|---|
| "V-Plan은 테스트 목록이다" | 행은 **측정 가능한 검증 항목**이며, 수단은 테스트만이 아닙니다 |
| "진척도 = 작성한 테스트 / 계획한 테스트" | 분모가 상상력의 크기가 됩니다. **항목 기준**으로 셉니다 |
| "스펙 문장 하나 = 항목 하나" | R14처럼 한 문장이 **여러 동작**을 규정하면 나눕니다 |
| "성능은 기능 항목에 넣으면 된다" | 목표치 없이 "통과"가 됩니다. **별도 절 + 목표치** |
| "지연과 대역폭은 같은 성능 항목" | **다른 축**입니다. 묶으면 한쪽 악화를 놓칩니다 |
| "V-Plan은 초기 산출물" | **변경 이력이 있는 살아 있는 문서**입니다 |
| "커버리지 100%면 계획 완료" | 항목 목록이 불완전하면 100%도 불완전합니다 |

## 🔧 이 문제를 이렇게 푼다

> **닫는 항목: #4 — 지연과 대역폭을 분리해 계획에 반영 / #5 — 세대 변화의 층위 판정 → TB 재사용 범위 산정**

### #4 — 성능 절의 구조

성능 항목은 **별도 절**에 두고, 각 행이 다음을 갖습니다.

| 필수 요소 | 예 |
|---|---|
| 측정량 | 실효 대역폭 (GB/s) / 읽기 지연 (사이클) |
| **목표치** | *(제품 요구에서 유래)* |
| 측정 조건 | 접근 패턴·부하 수준·`SCHED_MODE`·계층 |
| 측정 방법 | 대역폭: 단위 시간당 완료 beat / 지연: `t_rsp - t_req` 분포 |
| 판정 | 목표 대비 |

**두 축을 분리하는 규칙**

- 대역폭 항목과 지연 항목을 **같은 행에 넣지 않는다**
- 두 값을 **함께 보고**한다 — 한쪽 개선이 다른 쪽 악화를 대가로 했을 수 있다
- `SCHED_MODE`별로 측정해 **설정 효과**를 함께 확인한다 (#17과 연결)

### #5 — 세대 이관 시 V-Plan 갱신 절차

선행 코스 Ch02의 3층위 판정을 **절차**로 만듭니다.

**1단계 — 층위 판정**

| 층위 | 변화 | V-Plan 영향 |
|---|---|---|
| ① 전기적 (속도) | per-pin 상승 | 타이밍 기준값 행만 |
| ② 구조적 (폭·개수) | 채널 수·폭 변경 | 구성값·coverage·동시성 행 |
| ③ 공정·아키텍처 | base die 성격 변화 | **신규 절 추가** (IP 통합 등) |

**2단계 — 행을 3분류**

| 분류 | 처리 |
|---|---|
| **그대로 유효** | 상태 유지. 재검증만 |
| **파라미터만 수정** | 구성값 변경 (Ch06의 (b) 항목) |
| **재작성** | 규칙·구조가 바뀐 행 (예: CA parity 방식 변경 → assertion 재작성) |

**3단계 — Coverage 모델 필수 재검토**

Ch06 마무리 문제의 결론입니다. **파라미터화가 잘 되어 있어도 coverage bin이 새 구성을 반영하는지는 별개**이며, 반영되지 않으면 **조용히 100%가 보고됩니다.**

**4단계 — 신규 항목 추가**

③ 층위라면 이전 세대에 없던 항목이 생깁니다. 항목 목록 리뷰를 다시 거칩니다.

### 운영 규칙

- **진척도는 항목 기준**으로 보고한다. 테스트 개수는 참고 지표로만
- **항목 목록 리뷰를 게이트로** 둔다 — 누락을 잡는 유일한 지점
- 성능 항목은 **목표치 없이 통과 처리하지 않는다**
- V-Plan은 **변경 이력**과 함께 관리하고, 위 트리거마다 갱신한다
- **Waive에는 근거를 기재**하고 sign-off에서 별도 승인한다

## 7. 핵심 정리

- **테스트 개수는 진척도가 아니다.** 분모가 상상력의 크기가 되어, 누락이 많을수록 지표가 좋아 보인다
- V-Plan의 행은 **측정 가능한 검증 항목**이며 다섯 요소를 갖는다 — 무엇을·어떻게·어디서·무엇으로·상태
- **측정 수단은 테스트만이 아니다** — assertion·coverage bin·측정·리뷰. 수단이 없는 항목은 아직 계획이 아니다
- V-Plan은 새로 쓰는 것이 아니라 **앞 챕터 산출물을 행으로 펼친 것**이다
- 스펙 문장과 행은 **1:1이 아니다.** 독립 판정 가능 단위로 나눈다
- **성능 항목은 별도 절**이며 목표치와 측정 조건을 갖는다. **지연과 대역폭은 다른 축**이다
- 세대 이관은 **층위 판정 → 행 3분류 → coverage 필수 재검토 → 신규 항목** 순서로 처리한다
- **항목 목록 리뷰가 게이트**여야 한다 — 누락을 잡는 유일한 지점

:::note[🤔 마무리 자가 점검]
다음 진척도 보고를 평가하고, **어떻게 다시 써야 하는지** 제시하세요.

> "V-Plan 항목 140개 중 126개 통과, **90% 달성**. 남은 14개는 다음 주 완료 예정입니다. Coverage는 91%입니다. 계획대로 sign-off 가능할 것으로 봅니다."

<details>
<summary>정답 / 해설</summary>

**형식은 올바릅니다** — 테스트 개수가 아니라 **항목 기준**으로 보고했습니다. 그러나 판단하기에 정보가 부족하고, 몇 가지를 반드시 물어야 합니다.

**질문 1 — 남은 14개가 무엇인가**

14개가 사소한 항목인지 **핵심 항목**인지에 따라 위험이 전혀 다릅니다. 예를 들어 그 안에 F-02(R3 CA 공유 assertion)나 P-01(실효 대역폭)이 있다면, 90%라는 숫자는 위험을 전혀 반영하지 않습니다. **항목의 개수가 아니라 성격**이 중요합니다.

**질문 2 — Waive와 차단이 몇 개인가**

"126개 통과"에 waive가 섞여 있으면 실제 검증된 항목은 더 적습니다. 차단(외부 요인)도 분리해야 합니다. 보고는 이렇게 나뉘어야 합니다.

> 통과 X / 구현중 Y / 미착수 Z / **차단 W** / **Waive V (근거 기재 여부)**

**질문 3 — 성능 항목의 상태는 어디에 있는가**

140개 안에 성능 항목이 섞여 있으면 목표치 대비 판정이 보이지 않습니다. 성능은 **별도로** 보고해야 합니다 — 대역폭 실측 대 목표, 지연 실측 대 목표.

**질문 4 — 항목 목록 리뷰는 언제 했는가**

가장 중요한 질문입니다. 140개가 **덮어야 할 것을 덮는지**는 항목 목록 리뷰에서만 확인됩니다. 리뷰를 하지 않았다면 90%의 분모 자체가 검증되지 않은 것입니다.

**질문 5 — Coverage 91%의 모델에 무엇이 들어 있는가**

선행 코스와 Ch04에서 반복한 원리입니다. 91%보다 **모델에 무엇이 들어 있는가**가 중요합니다. 특히 최근 구성 변경이 있었다면 bin이 새 구성을 반영하는지 확인해야 합니다.

**다시 쓴 보고**

> - **기능 항목**: 통과 X / 구현중 Y / 미착수 Z / 차단 W(사유) / Waive V(근거 승인 여부)
> - **잔여 핵심 항목**: F-02(CA 공유 assertion), I-07(자원 경합) — **핵심 경로**
> - **성능**: 대역폭 실측 A GB/s (목표 B) · 지연 실측 C 사이클 (목표 D)
> - **Coverage**: 91% — 모델 항목 수 N개, 최근 구성 변경 반영 확인 완료/미완료
> - **항목 목록 리뷰**: (일자) 수행, 이후 추가 항목 M개
> - **Sign-off 판단**: 게이트별 통과 여부로 제시

**핵심 교훈**: 하나의 백분율은 **위험의 분포를 감춥니다.** 좋은 보고는 숫자를 줄이는 대신 **판단에 필요한 구조**를 보여 줍니다.

</details>
