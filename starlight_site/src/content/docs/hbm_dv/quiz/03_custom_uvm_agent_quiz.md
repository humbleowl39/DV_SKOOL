## Q1. (Remember)

Sequence item에서 `rand`가 **아니어야** 하는 필드는?

- [ ] A. `op`, `addr`, `len`
- [ ] B. `inject_req_par_err`
- [ ] C. `rdata`, `err`
- [ ] D. `wdata`

<details>
<summary>정답 / 해설</summary>

**C**. `rdata`와 `err`는 **DUT가 만드는 값**이며 monitor가 채웁니다. `rand`로 두면 시퀀스가 응답을 "생성"하게 되어 의미가 무너집니다.

B는 오류 주입 제어로, **시퀀스가 골라야 하므로 `rand`여야** 합니다.

</details>

## Q2. (Understand)

Item의 경계를 긋는 기준은?

- [ ] A. 인터페이스의 신호 그룹
- [ ] B. 트랜잭션의 의미 단위
- [ ] C. 클럭 사이클
- [ ] D. 버스트 beat

<details>
<summary>정답 / 해설</summary>

**B**. 하나의 요청과 그에 딸린 데이터, 그리고 그 결과가 **하나의 item**입니다. 서로 다른 방향은 필드의 `rand` 속성으로 구분합니다.

A로 나누면(채널마다 item) *"주소 X에 Y를 썼고 결과가 Z"* 라는 하나의 사건이 세 조각으로 흩어지고, 이어 붙이는 로직이 결국 어딘가에 생깁니다.

</details>

## Q3. (Apply)

`inject_req_par_err`를 item의 `rand` 필드가 아니라 **driver의 설정값**으로 두면 어떤 시나리오를 만들 수 없습니까?

<details>
<summary>정답 / 해설</summary>

**"특정 트랜잭션만 골라 손상시키는" 시나리오 전부입니다.**

driver 플래그는 켜져 있는 동안 **모든** 요청에 적용됩니다. 그런데 필요한 시나리오는:

- 정상 요청 사이에 **오류 하나**를 섞어, 그 트랜잭션만 실패하고 나머지는 정상 처리되는지 (R12)
- 두 pseudo-channel 중 **한쪽에만** 주입해 다른 쪽이 영향받지 않는지
- 검사를 끈 상태에서 주입해 **검사하지 않는지** (R13)
- 오류 후 상태 레지스터가 sticky로 유지되고 **W1C로만 지워지는지** (R14)

전부 *"어느 트랜잭션에 넣을지"* 를 시퀀스가 골라야 가능합니다.

**일반 원리**: 검증에 필요한 능력은 **Agent 설계 단계에 구조로 확보**합니다. 나중에 추가하려면 item·driver·시퀀스를 모두 고쳐야 하고 기존 시나리오도 영향받습니다.

</details>

## Q4. (Analyze)

Driver가 응답을 받은 뒤에 `item_done()`을 부르면 어떤 검증이 **원리적으로 불가능**해집니까?

<details>
<summary>정답 / 해설</summary>

**미해결 요청이 항상 1개가 되므로 다음이 불가능합니다.**

- **R11 (응답 out-of-order)** — 요청이 하나뿐이니 순서가 뒤바뀔 여지가 없습니다
- **R3 (CA 공유 경합)** — 두 pseudo-channel의 요청이 동시에 대기하는 상황이 만들어지지 않습니다
- **성능 측정(#2)** — 부하 상황 자체가 성립하지 않습니다
- **`SCHED_MODE` 효과 검증(#17)** — 선택의 여지가 없으면 어느 모드든 같게 동작합니다

결국 선행 코스가 경고한 **"단일 채널 순차 시나리오"** 상태가 됩니다.

> **자극 능력이 곧 검증 가능 범위이며, 그것이 driver 구조에서 결정됩니다.**

**보완**: 응답을 보고 분기해야 하는 시퀀스가 필요하면 driver를 blocking으로 바꾸는 대신 **시퀀스 계층에서** 해결합니다(analysis port 구독 등). **자극 능력을 희생하지 않는 쪽이 우선입니다.**

</details>

## Q5. (Analyze)

Monitor가 driver의 item을 재사용해 응답만 채우는 구조에서, **원리적으로 놓치는 결함**은 무엇입니까?

<details>
<summary>정답 / 해설</summary>

**DUT가 요청을 잘못 해석하는 모든 결함입니다.**

monitor가 발행하는 item의 요청 필드는 **driver가 의도한 값**이지 DUT가 버스에서 읽은 값이 아닙니다. 따라서 다음이 전부 관측 불가입니다.

- DUT가 `addr`를 잘못 래치 (비트 순서 뒤바뀜 등)
- DUT가 `pc`를 무시하고 항상 pseudo-channel 0으로 처리
- DUT가 `len`을 잘못 해석해 beat 수를 틀리게 처리
- **오류 주입 시 DUT가 손상된 패리티를 못 보고 정상 처리** — R12 검증이 무의미해짐

마지막이 치명적입니다. 오류 주입 시나리오를 만들어도 **DUT가 실제로 손상된 값을 받았는지조차 확인하지 못합니다.**

**증상**: 회귀가 **전부 초록색**입니다. 이번 "조용한 통과"는 원인이 DUT도 모델도 아닌 **테스트벤치 자신의 구조**입니다.

> **원칙: monitor와 driver는 객체를 공유하지 않는다. monitor는 DUT의 신호만 본다.**

</details>

## Q6. (Evaluate)

Custom Agent 개발 공수를 산정합니다. *"파일 하나 만들면 되니 3일"* 이라는 추정을 평가하고, 실제 산출물 목록을 제시하세요.

<details>
<summary>정답 / 해설</summary>

**Agent는 파일 하나가 아닙니다. 최소 9종의 산출물이 필요합니다.**

| 산출물 | 비고 |
|---|---|
| 타입 정의 (enum 등) | 스펙 인코딩 반영 |
| sequence item + 제약 | **능력 역산표의 결과** |
| config 클래스 | 파라미터·활성 모드 |
| driver | **자극 능력이 여기서 결정됨** |
| monitor | 독립 재구성 + 미해결 테이블 |
| coverage | 기본 축 (동시성은 Ch10) |
| agent 조립 | active/passive |
| **기본 시퀀스 라이브러리** | Ch08에서 확장 |
| **문서** | 신호 매핑·사용법 |

**그리고 코드보다 먼저 해야 할 일이 있습니다** — §2의 **능력 역산표**. 스펙의 각 규칙에 *"이것을 검증하려면 Agent가 무엇을 할 수 있어야 하는가"* 를 묻고 그 답을 구조에 반영하는 작업입니다. 이것을 건너뛰면 나중에 구조를 고쳐야 합니다.

**계획에 남길 것**: 이 Agent가 **자극할 수 없는 스펙 규칙 목록**. 자극 불가 항목은 곧 **검증 불가 항목**이며 계획에 드러나야 합니다.

</details>
