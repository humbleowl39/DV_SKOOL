## Q1. (Remember)

검증 환경의 구성요소를 분류하는 세 칸으로 옳은 것은?

- [ ] A. RTL / 테스트벤치 / 스크립트
- [ ] B. DUT / 모델·VIP / 범위 밖
- [ ] C. 디지털 / 아날로그 / 물리
- [ ] D. 기능 / 성능 / 신뢰성

<details>
<summary>정답 / 해설</summary>

**B**. 이상 동작 시 처리 방법이 각각 다릅니다 — DUT는 **버그로 보고**, 모델·VIP는 **우리가 고침**, 범위 밖은 **다루지 않음**.

</details>

## Q2. (Understand)

경계표에서 어느 칸에 넣을지 판정하는 세 질문에 **포함되지 않는** 것은?

- [ ] A. 논리 시뮬레이션으로 표현 가능한가
- [ ] B. 틀렸을 때 고칠 사람이 설계팀인가
- [ ] C. 우리가 만들거나 도입해야 하는가
- [ ] D. 시뮬레이션 시간이 오래 걸리는가

<details>
<summary>정답 / 해설</summary>

**D**. 시뮬레이션 시간은 프로파일 선택(Ch05)의 고려사항이지 **경계 판정 기준이 아닙니다**.

A는 범위 밖 여부, B는 DUT 여부, C는 모델·VIP 여부와 **조달 방법**을 정합니다.

</details>

## Q3. (Apply)

다음 둘을 경계표에서 각각 어느 칸에 넣습니까?

> **(A)** `cci_req_par`의 패리티를 **계산해서 넣는** 로직
> **(B)** `cci_req_par`가 틀렸을 때 **검출하는** 로직

- [ ] A. 둘 다 DUT
- [ ] B. 둘 다 모델·VIP
- [ ] C. (A) 모델·VIP, (B) DUT
- [ ] D. (A) DUT, (B) 모델·VIP

<details>
<summary>정답 / 해설</summary>

**C**. 요청을 만드는 쪽은 검증 환경(우리 Agent)이므로 (A)는 **모델·VIP**, 검출은 스펙 R12~R14가 규정하는 DUT 기능이므로 (B)는 **DUT**입니다.

**중요한 함의**: (A)가 우리 코드이므로 **의도적으로 틀린 패리티를 넣을 수 있습니다.** R12 검증에 필수이며, 이것이 Agent 설계 요구사항이 됩니다 (Ch03).

**교훈**: 경계는 단어("패리티")가 아니라 **누가 만들고 누가 고치는가**로 판정합니다.

</details>

## Q4. (Analyze)

경계 문서를 만들지 않고 시작했을 때, 그 비용은 **언제 어떤 형태로** 청구됩니까?

<details>
<summary>정답 / 해설</summary>

**디버깅 시점에 청구됩니다.**

실패가 나올 때마다 *"이건 DUT 버그인가, 모델 문제인가, 원래 그런 건가"* 를 매번 처음부터 따져야 합니다. 그리고:

- 팀원마다 판단이 달라 **같은 이슈를 두 번 조사**합니다
- 설계팀에 **잘못 올린 이슈가 반복**되면 이후의 진짜 이슈도 늦게 처리됩니다
- 인수인계 시 그 지식이 **통째로 사라집니다**

**왜 미루기 쉬운가**: 경계 문서의 가치는 **작성 시점이 아니라 사용 시점**에 발생합니다. 그래서 당장은 없어도 되는 것처럼 보이고, 정확히 **가장 바쁠 때** 비용이 청구됩니다.

</details>

## Q5. (Analyze)

*"제대로 하려면 DRAM 모델도 우리가 검증해야 하지 않나"* 라는 제안의 문제는 무엇이며, 올바른 처리는?

<details>
<summary>정답 / 해설</summary>

**문제: 끝나지 않습니다 (무한 후퇴).**

DRAM 모델을 검증하려면 그 기준이 될 또 다른 무언가가 필요하고, 그것을 검증하려면 또 다른 기준이 필요합니다. 경계는 **어딘가에서 끊어야** 하며, 끊는 지점을 정하는 것이 판단입니다.

**올바른 처리**: 모델은 **검증 대상이 아니라 확인 대상**입니다.

*"이 모델이 무엇을 검사하고 무엇을 검사하지 않는가"* 를 **목록으로 확인**하고, 그 목록을 검증 계획에 반영합니다. 검사하지 않는 항목은 **assertion으로 우리가 메웁니다**(Ch09).

이것이 무한 후퇴에 빠지지 않으면서 "모델의 엄격함이 검증 신뢰도의 상한"이라는 문제를 다루는 방법이며, Ch04에서 구체화됩니다.

</details>

## Q6. (Evaluate)

회귀 실패를 조사하니 DUT가 `ACT` 후 **3사이클**에 같은 뱅크로 `RD`를 발행했습니다(`tRCD_CYC`는 8). 그런데 **테스트는 통과**했고 scoreboard도 불평하지 않았습니다.

(a) DUT 버그입니까? (b) 통과한 이유는? (c) 무엇을 해야 합니까?

<details>
<summary>정답 / 해설</summary>

**(a) 예, DUT 버그입니다.** 스펙 R6 위반이며, 이 로직은 경계표의 **DUT** 칸입니다.

**(b) DRAM 모델이 tRCD를 검사하지 않았기 때문입니다.**

모델이 요청받은 데이터를 성실히 반환했고, scoreboard는 **데이터를 비교하는 장치**이므로 "값이 맞다"고 판정했습니다.

**주의**: 이것을 **"모델 버그"라고 부르면 안 됩니다.** 모델은 스펙을 어기지 않았고 **검사하지 않았을 뿐**입니다. 모델의 책임 범위와 우리 기대가 어긋나 있었고, 그 어긋남을 확인하지 않은 것이 **우리의 누락**입니다.

**(c) 세 가지**

1. DUT 버그를 보고 (R6 위반, 파형 시점 포함)
2. **모델의 검사 범위를 목록화** — 이 모델이 R1~R20 중 무엇을 검사하는지 (Ch04)
3. 검사하지 않는 규칙을 **assertion으로 메움** (Ch09)

**가장 중요한 것**: 이 버그는 **우연히**(누군가 파형을 봐서) 발견되었습니다. 우연에 의존하지 않으려면 상시 감시 수단이 필요하며, 그것이 Ch09를 별도로 두는 이유입니다.

</details>
