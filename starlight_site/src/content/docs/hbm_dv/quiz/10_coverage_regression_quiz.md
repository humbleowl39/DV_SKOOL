## Q1. (Remember)

커버리지 bin은 무엇에서 도출합니까?

- [ ] A. DUT의 신호 목록
- [ ] B. V-Plan의 coverage 수단 항목
- [ ] C. 시뮬레이터가 자동 생성
- [ ] D. 이전 프로젝트의 모델 복사

<details>
<summary>정답 / 해설</summary>

**B**. 신호를 나열해 만드는 것이 아니라, **"이것이 다양하게 발생했는가"를 물어야 할 항목**에서 도출합니다.

A로 하면 조합이 폭발하고 의미 없는 bin이 대량 생겨 리포트를 아무도 보지 않게 됩니다.

</details>

## Q2. (Understand)

단일 테스트의 커버리지 리포트로 판단하면 안 되는 이유는?

- [ ] A. 리포트 형식이 다르다
- [ ] B. 그 테스트가 무엇을 쳤는지만 보여준다
- [ ] C. 수집에 시간이 오래 걸린다
- [ ] D. 시드마다 결과가 다르다

<details>
<summary>정답 / 해설</summary>

**B**. 의미 있는 분석은 **회귀 전체의 데이터베이스를 병합(merge)** 한 뒤에 가능합니다.

각 테스트는 자기 영역만 채우므로 개별 리포트는 낮게 나오고, 그것을 보고 불필요한 시나리오를 추가하게 됩니다.

</details>

## Q3. (Apply)

동시성 측정을 위해 다음을 작성했고 리포트는 **100%** 입니다. 그런데 `c_ca_share_exercised`는 여전히 **0%** 입니다. 무엇이 문제입니까?

```systemverilog
cp_ch  : coverpoint current_ch_id { bins ch[16] = {[0:15]}; }
cp_pc  : coverpoint current_pc    { bins pc[2]  = {[0:1]};  }
x_ch_pc: cross cp_ch, cp_pc;
```

<details>
<summary>정답 / 해설</summary>

**이 covergroup은 동시성을 전혀 측정하지 않습니다. "어느 채널·pc를 접근했는가"만 측정합니다.**

`cross cp_ch, cp_pc`가 만드는 32개 조합은 **한 트랜잭션의 속성**입니다 — *"채널 5의 pc 1에 접근한 적이 있다"*. 채널 5와 채널 9가 **동시에** 활성이었는지는 어디에도 없습니다. **차례로** 32개를 접근하면 100%가 됩니다.

**고치는 방법 — 측정 대상을 바꿉니다**

| 잘못된 축 | 올바른 축 |
|---|---|
| 접근한 채널 id | **동시에 활성인 채널 수** |
| 접근한 pc | **두 pc가 동시에 요청 중인가** |
| id × pc cross | **동시 활성 수 × pc 동시 여부 cross** |

샘플링 시점도 바뀝니다 — 트랜잭션 속성은 그 트랜잭션에서, **시스템 상태는 요청 발행 시점의 전역 상태**에서 수집합니다.

> **cross는 동시성을 보장하지 않습니다.** cross가 측정하는 것은 *"이 두 값의 조합이 등장했는가"* 이며, 두 값이 **같은 순간에 서로 다른 주체에서** 참이었는지는 별개입니다.

</details>

## Q4. (Analyze)

채널이 16 → 32로 늘었는데 bin이 `bins ch[16] = {[0:15]}` 로 고정되어 있습니다. 무슨 일이 벌어지며, 어떻게 고칩니까?

<details>
<summary>정답 / 해설</summary>

**새로 늘어난 16개 채널이 측정에서 빠지고, 기존 bin은 모두 채워지므로 커버리지는 100%를 보고합니다.**

테스트가 **깨지지 않는 것**이 이 문제의 위험한 점입니다. 실패하면 누군가 조사하지만, 이 경우 아무것도 실패하지 않고 지표는 오히려 좋습니다.

**고치는 방법**

```systemverilog
covergroup cg_channel (int unsigned num_ch);
  cp_ch : coverpoint ch_id {
    bins valid[] = {[0:num_ch-1]};              // 동적
    illegal_bins out_of_range = {[num_ch:$]};   // 구성 불일치 검출
  }
endgroup
```

`illegal_bins`가 부가 이득입니다 — 구성값보다 큰 채널 번호가 관측되면 즉시 오류가 나므로 **구성 불일치 자체**가 검출됩니다.

**그리고 코드만으로는 부족합니다.** 세대 이관 체크리스트에 다음을 넣습니다.

- bin 정의가 구성값을 참조하는가 (코드 리뷰)
- **이관 전후 bin 총 개수가 늘었는가** ← 실용적
- 새 구성 전용 항목이 추가됐는가 (V-Plan 리뷰)

**채널이 두 배가 됐는데 bin 수가 그대로라면 무언가 고정되어 있다는 뜻입니다.**

</details>

## Q5. (Analyze)

*"이번 분기 커버리지 목표 95%"* 라는 방식의 문제 두 가지를 드세요.

<details>
<summary>정답 / 해설</summary>

**① 채우기 쉬운 bin부터 채워집니다.**

주소 범위를 넓히고 버스트 길이를 다양화하면 숫자가 빨리 오릅니다. 그런데 **버그는 채우기 어려운 쪽**(동시성, 오류 경로, 모드 전이)에 있습니다. 커버리지는 꾸준히 오르는데 **버그 발견율은 떨어지는** 현상이 나타납니다.

**② 남은 5%가 무엇인지 감춰집니다.**

95%를 채운 시점에 미달인 5%가 사소한지 핵심인지 구분되지 않습니다. **숫자 목표는 어느 bin이 비었는지를 감춥니다.**

**올바른 처리 — 목표를 항목으로**

> *"커버리지 95%"* 가 아니라
> *"모든 coverage 항목이 **충족** 또는 **문서화된 waive** 상태"*

그리고 리포트에서 **위험도 높은 항목의 충족 여부를 백분율보다 먼저** 봅니다.

**추가**: 100%를 목표로 하면 **도달 불가능한 bin** 때문에 영원히 도달하지 못하고 목표가 무의미해집니다. exclusion + **문서화된 정당화**로 처리하되, 도달 불가 판정은 **설계 동결 이후**에 합니다.

</details>

## Q6. (Evaluate)

Sign-off 리뷰 자료입니다.

> ```
> 회귀 12,000 job (병합 DB), 통과율 99.8%
> Functional Coverage 97.2% — 미달 3개, 전부 exclusion ("도달 불가")
> Assertion 24개 전부 PASS — cover 충족 21/24
>   미충족: c_ca_share_exercised, c_test_mode_entered, c_lp_exit
> ```
> *"목표(95%) 초과 달성, assertion 전부 통과 → sign-off 가능."*

평가하세요.

<details>
<summary>정답 / 해설</summary>

**Sign-off 할 수 없습니다. 두 가지 결정적 문제가 있습니다.**

**문제 1 — Cover 3개 미충족 = 규칙 3개 미검증**

*"assertion 24개 전부 PASS"* 는 사실이지만 **그중 3개는 일한 적이 없습니다.** 그리고 하필 그 셋이:

- `c_ca_share_exercised` → **R3(CA 공유)** — 이 IP의 핵심 규칙
- `c_test_mode_entered` → **R17~R20(테스트 모드)** 전체
- `c_lp_exit` → 저전력 복귀 경로

**핵심 규칙 세 갈래가 통째로 미검증**입니다. V-Plan 상태는 "통과"가 아니라 **"미측정"** 이어야 합니다.

**문제 2 — Exclusion 3개의 사유가 "도달 불가" 한 줄뿐**

확인해야 할 것: **무엇을 근거로** 판정했는가 / **언제**(설계 동결 이후인가) / **누가 승인**했는가 / 그 3개가 **무엇인지**.

마지막이 중요합니다. exclusion된 항목이 동시성이나 모드 전이 관련이라면, **자극하지 못한 것을 "도달 불가"로 처리한 것**일 수 있습니다.

> **도달 불가는 설계상 불가능한 것이고, 자극 실패는 시나리오가 부족한 것입니다.** 전혀 다릅니다.

**그 밖에**: 97.2%가 VIP 커버리지를 포함한 것인지(Ch04), 12,000 job에 P1·P2가 몇 개인지(Ch05) — **출처별·프로파일별 분리**가 필요합니다.

**조치**: ① 미충족 cover 3건의 시나리오 작성 ② V-Plan 상태 정정 ③ exclusion 3건 재검토 ④ 리포트 형식 개선(출처 분리, 위험도 우선).

> **97.2%와 "assertion 전부 통과"는 둘 다 사실이면서 동시에 오해를 만듭니다.** cover 3개의 0%가 그 백분율 어디에도 반영되지 않는다는 점이 그 증거입니다.

</details>
