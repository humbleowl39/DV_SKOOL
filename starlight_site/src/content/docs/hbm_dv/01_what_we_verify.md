## 1. Why care? — 첫날, 시뮬레이터를 열고 무엇부터 치는가

"`hbm_ch_ctrl` 검증 맡아주세요."

이 말을 듣고 자리에 앉았습니다. 스펙 문서는 받았고, RTL도 있고, 시뮬레이터도 열려 있습니다. 무엇부터 할까요?

대부분은 **테스트벤치 파일을 만들기 시작합니다.** `top.sv`를 열고 DUT를 인스턴스화하고 클럭을 만듭니다. 자연스러운 출발점처럼 보입니다.

그런데 곧 손이 멈춥니다. DUT의 포트 목록을 보니 한쪽에는 `cci_*`가 있고 다른 쪽에는 `row_cmd_*`, `col_cmd_*`, `dq_*`가 있습니다. **여기에 무엇을 물려야 합니까?**

- `cci_*` 쪽에는 요청을 넣어 줄 무언가가 필요합니다. 그런데 그건 우리가 만드는 겁니까, 어디서 가져오는 겁니까?
- `row_cmd_*` / `dq_*` 쪽에는 DRAM이 있어야 합니다. 그런데 DRAM RTL은 받은 적이 없습니다. 그럼 무엇을 붙입니까?
- 붙인 그것이 이상하게 동작하면 — 그건 **누구의 버그입니까?**

이 질문들에 답하지 않고 코드를 쓰기 시작하면, 지금 아낀 하루를 **디버깅 단계에서 며칠로 갚습니다.** 선행 코스가 *"base die의 digital·mixed IP가 DUT"* 라고 말한 것은 개념적 좌표였고, 실제 프로젝트에서는 **IP 하나에 대해 그 선을 직접 그어야** 합니다.

이 챕터는 그 선을 긋는 방법과, 그것을 문서로 남기는 이유를 다룹니다. 이것이 검증 업무의 **0번 작업**입니다.

## 2. 직관 — 시작은 코드가 아니라 경계다

### 순진한 시도 1 — 바로 테스트벤치를 짠다

DUT를 인스턴스화하고 포트를 하나씩 채워 나갑니다.

**어디서 막히나?** 포트를 채우려면 그 반대편에 무엇이 있어야 하는지 알아야 합니다. 그런데 그것을 정하는 일은 코드 작성이 아니라 **판단**입니다 — 만들 것인가 살 것인가, 정확하게 만들 것인가 대충 만들 것인가, 아니면 아예 다루지 않을 것인가. 코드부터 쓰면 이 판단을 **암묵적으로, 근거 없이** 내리게 됩니다.

### 순진한 시도 2 — "일단 다 물려 놓고 보자"

포트마다 뭔가를 붙입니다. DRAM 자리에는 인터넷에서 구한 간단한 메모리 모델을, CCI 쪽에는 직접 만든 태스크 몇 개를 붙입니다. 시뮬레이션이 돌아가기 시작합니다.

**어디서 막히나?** 몇 주 뒤 파형에서 이상한 동작을 발견합니다. 그리고 이 질문 앞에서 멈춥니다.

> **"이건 DUT 버그인가, 내가 붙인 모델 버그인가, 아니면 원래 그렇게 동작하는 게 맞는 건가?"**

붙인 것들의 **성격을 구분해 두지 않았기 때문에** 판정할 수가 없습니다. 선행 코스가 경고한 "조용한 통과"의 반대 상황 — **시끄러운 오탐** — 이 여기서 시간을 잡아먹습니다. 설계팀에 올린 이슈가 알고 보니 모델의 한계였던 경우가 반복되면 신뢰도까지 잃습니다.

### 일반화 — 세 칸으로 나누는 것이 먼저다

두 시도가 놓친 것은 같습니다. **검증 환경 안의 모든 것은 세 가지 중 하나**인데, 그 분류를 하지 않은 채 시작한 것입니다.

| 분류 | 정의 | 이상 동작 시 |
|---|---|---|
| **DUT** | 우리가 검증할 대상 | **버그로 보고한다** |
| **모델 · VIP** | DUT를 둘러싸고 자극·응답을 담당 | **우리가 고친다** (또는 벤더에 문의) |
| **범위 밖** | 다른 팀·다른 도구의 몫 | **다루지 않는다** |

그리고 어느 칸에 넣을지는 세 가지 질문으로 판정합니다.

> **Q1. 이것이 논리 시뮬레이션으로 표현 가능한가?**
> 아니면 → 범위 밖 (또는 mixed-level의 대상)
>
> **Q2. 이것의 동작이 틀렸을 때, 고쳐야 할 사람이 설계팀인가?**
> 그렇다 → DUT / 아니면 → 모델·VIP
>
> **Q3. 이것을 우리가 만들거나 도입해야 하는가?**
> 그렇다 → 모델·VIP (그리고 **누가 만들지**가 곧 다음 판단)

**정의.** 검증의 0번 작업은 이 세 칸을 채워 **경계 문서**를 만드는 것이다. 이 문서가 없으면 디버깅에서 책임 소재를 판정할 수 없고, 계획에서 공수를 산정할 수 없다.

## 3. 작은 예 — `hbm_ch_ctrl`에 실제로 선을 그어 보기

[부록 A](../appendix_a_hbm_ch_ctrl_spec/)의 스펙을 놓고 세 칸을 채웁니다.

| 대상 | 분류 | 판정 근거 | 후속 판단 |
|---|---|---|---|
| `hbm_ch_ctrl` RTL (스케줄러·중재·CSR·오류 검출) | **DUT** | Q2 — 틀리면 설계팀이 고침 | — |
| **CCI 상대편** (요청을 넣는 주체) | 모델·VIP | Q3 — 만들어야 함 | ⚠️ **비표준 → 상용 VIP 없음 → 자체 개발** (Ch03) |
| **DCMD 상대편** (DRAM) | 모델·VIP | Q1 ✓, Q2 ✗ — DRAM은 검증 대상 아님 | 상용 HBM VIP 또는 자체 모델 (Ch04) |
| DRAM 셀의 전기적 동작 | **범위 밖** | Q1 ✗ — 논리 시뮬레이션 대상 아님 | — |
| PHY의 아날로그 부분 | **범위 밖**(디지털 환경 기준) | Q1 ✗ | mixed-level 환경의 대상 (Ch05) |
| 인터포저·TSV 전기 특성 | **범위 밖** | Q1 ✗ | SI/PI 해석 |
| CSR 레지스터 필드 동작 | **DUT** | Q2 — 설계팀 소관 | RAL 사용 여부 판단 (Ch08) |

**여기서 이미 세 가지 후속 작업이 도출됩니다.**

1. CCI용 **Custom Agent를 만들어야 한다** → Ch03. 공수를 계획에 반영해야 함
2. DRAM 쪽 모델을 **사거나 만들어야 한다** → Ch04. 무엇을 검사해 주는지가 판단 기준
3. PHY 검증을 위한 **별도 환경이 필요하다** → Ch05

경계표를 그리는 것만으로 프로젝트 계획의 뼈대가 나옵니다. 이것이 "0번 작업"인 이유입니다.

- **(B)** `cci_req_par`가 틀렸을 때 **검출하는** 로직

**(A) 패리티를 생성하는 로직 → 모델·VIP**

요청을 만드는 것은 호스트 측이고, 검증 환경에서 호스트는 우리가 만드는 Agent입니다. 즉 이 로직은 **우리 코드**입니다. 여기서 버그가 나면 우리가 고칩니다.

그리고 중요한 함의가 하나 있습니다 — 우리가 만드는 쪽이므로 **의도적으로 틀린 패리티를 넣을 수 있습니다.** 스펙 R12(패리티 오류 시 PARITY_ERR 응답)를 검증하려면 반드시 필요한 능력이며, 이것이 Agent 설계 시 요구사항이 됩니다 (Ch03, Ch08).

**(B) 패리티를 검출하는 로직 → DUT**

스펙 A.6.5의 R12~R14가 규정하는 `hbm_ch_ctrl`의 기능입니다. 틀리면 설계팀이 고칩니다. **(A)와 (B)는 같은 "패리티"라는 단어를 쓰지만 정반대 칸에 들어갑니다** — 경계를 단어가 아니라 **누가 만들고 누가 고치는가**로 판정해야 하는 이유입니다.

**(C) DRAM 모델의 tRCD 위반 검사 → 모델·VIP**

DUT가 아닙니다. 하지만 여기가 함정입니다. 선행 코스 [Ch03](../../hbm/03_stack_architecture/)에서 확인한 원리가 그대로 적용됩니다 — **모델의 엄격함이 검증의 상한을 정합니다.**

이 모델이 tRCD를 검사하지 않으면, DUT가 R6(ACT→RD 간격)를 어겨도 데이터는 정상 반환되고 테스트는 통과합니다. 따라서 이것은 "모델이니 신경 쓸 필요 없다"가 아니라 **"모델이 무엇을 검사하는지 확인하는 것 자체가 우리의 검증 항목"** 입니다 (21항목 #10, Ch04에서 다룹니다).

### 검증 업무의 한 주기

경계를 그은 다음에는 무엇이 이어질까요? 직무 기술서에 나열된 업무를 **시간축**으로 펼치면 이렇게 됩니다.

```d2
direction: down

S1: "① 스펙 리뷰 · **경계 확정**\n무엇이 DUT이고 무엇이 모델인가" { style.fill: "#e3f2fd" }
S2: "② V-Plan 수립\n스펙에서 검증 항목 도출" { style.fill: "#e8f5e9" }
S3: "③ 환경 구축\nAgent · VIP · 환경 계층" { style.fill: "#fff8e1" }
S4: "④ 시나리오 · Assertion 작성" { style.fill: "#fff8e1" }
S5: "⑤ 디버그 루프\n실패 → 원인 판정 → 수정" { style.fill: "#ffebee" }
S6: "⑥ 회귀 · Coverage Closure" { style.fill: "#f3e5f5" }
S7: "⑦ Sign-off" { style.fill: "#e0f2f1" }
S8: "⑧ Silicon 이슈 대응" { style.fill: "#eceff1" }

S1 -> S2 -> S3 -> S4 -> S5 -> S6 -> S7 -> S8
S5 -> S4: "시나리오 보강"
S6 -> S4: "coverage hole → 시나리오 추가"
S8 -> S5: "재현 시나리오 작성"
```

| 단계 | 이 코스의 챕터 |
|---|---|
| ① 경계 확정 | **Ch01 (지금)** |
| ② V-Plan | Ch07 |
| ③ 환경 구축 | Ch02, Ch03, Ch04, Ch05, Ch06 |
| ④ 시나리오·Assertion | Ch08, Ch09 |
| ⑤ 디버그 루프 | 전 챕터에 분산 |
| ⑥ 회귀·Coverage | Ch10 |
| ⑦ Sign-off | Ch10 |
| ⑧ Silicon 대응 | Ch12 |

⑤에서 ④로, ⑥에서 ④로 되돌아가는 화살표가 중요합니다. **검증은 직선이 아니라 루프**이며, 그 루프를 몇 바퀴 도느냐가 일정을 결정합니다. 루프를 짧게 만드는 것들 — 명확한 경계(①), 좋은 assertion(④), 의미 있는 coverage 모델(⑥) — 이 이 코스가 다루는 내용입니다.

## 4. 일반화 — 경계를 잘못 잡는 두 방향

### 대안 A — 경계 문서 없이 바로 시작한다면?

"문서 만들 시간에 코드를 짜자"는 판단입니다. 실제로 첫 주는 빨라 보입니다.

**어디서 갚나**: ⑤ 디버그 루프에서 갚습니다. 실패가 나올 때마다 "이건 누구 문제인가"를 매번 처음부터 따져야 하고, 팀원마다 판단이 달라 같은 이슈를 두 번 조사합니다. 설계팀에 잘못 올린 이슈가 반복되면 이후의 진짜 이슈도 늦게 처리됩니다.

**핵심**: 경계 문서의 가치는 문서를 쓰는 시점이 아니라 **디버깅 시점에** 발생합니다. 그래서 미루기 쉽고, 미루면 정확히 가장 바쁠 때 비용이 청구됩니다.

### 대안 B — 경계를 지나치게 크게 잡는다면?

"제대로 하려면 DRAM 모델도 우리가 검증해야 하지 않나?"는 판단입니다. 꼼꼼해 보입니다.

**왜 안 되나**: 끝나지 않습니다. DRAM 모델을 검증하려면 그 모델의 기준이 될 또 다른 무언가가 필요하고, 그 무언가를 검증하려면 또… 경계는 **어딘가에서 끊어야** 하며, 끊는 지점을 정하는 것이 판단입니다.

**올바른 처리**: 모델을 검증 대상으로 삼는 대신, **"이 모델이 무엇을 검사하고 무엇을 검사하지 않는가"를 목록으로 확인**하고 그 목록을 검증 계획에 반영합니다. 검사하지 않는 항목은 assertion으로 우리가 메웁니다 (Ch09). 이것이 무한 후퇴에 빠지지 않으면서 상한 문제를 다루는 방법입니다.

### 두 방향의 공통 교훈

| 잘못된 방향 | 증상 | 처방 |
|---|---|---|
| 경계를 안 그음 | 디버깅에서 책임 판정 불가, 오탐 반복 | 0번 작업으로 문서화 |
| 경계를 너무 크게 | 끝나지 않는 검증, 일정 초과 | 모델은 **검증 대상이 아니라 확인 대상** |

## 5. 디테일 — 경계 관리에서 실제로 벌어지는 일

### 실패 1 — 경계가 머릿속에만 있다

한 사람은 정확히 알고 있습니다. 그런데 문서로 쓰지 않았습니다.

**관측되는 증상**: 팀원이 늘어나면 판단이 갈립니다. 새로 합류한 사람이 DRAM 모델의 동작을 DUT 사양으로 오해하고 그것에 맞춰 테스트를 작성합니다. 그 테스트는 통과하지만 **잘못된 기준으로 통과**합니다. 인수인계 시점에는 그 지식이 통째로 사라집니다.

**처방**: 경계표를 저장소에 넣고 V-Plan의 첫 장으로 삼습니다. 코드 리뷰에서 "이 변경은 경계표의 어느 칸을 건드리는가"를 묻습니다.

### 실패 2 — 프로젝트 중간에 경계가 바뀌는데 문서를 갱신하지 않는다

흔한 변경: 처음엔 자체 DRAM 모델을 쓰다가 상용 VIP를 도입하게 되거나, PHY가 범위 밖이었다가 mixed-level 환경이 추가됩니다.

**관측되는 증상**: 문서와 현실이 어긋난 채로 굴러갑니다. 계획에는 "우리가 assertion으로 메운다"고 되어 있는데 도입한 VIP가 이미 그것을 검사하고 있어 **중복 작업**이 발생하거나, 반대로 자체 모델이 검사하던 것을 VIP는 검사하지 않아 **구멍**이 생깁니다.

**처방**: 경계 변경을 **변경 이력이 있는 문서**로 관리합니다. 부록 A에 변경 이력 절을 둔 것과 같은 이유입니다.

### 실패 3 — 경계는 그었는데 "누가 만드는가"를 안 정했다

경계표에서 "모델·VIP"로 분류까지는 했는데, 그것을 **사는지 만드는지, 누가 언제까지 하는지**를 정하지 않은 경우입니다.

**관측되는 증상**: 환경 구축(③) 단계에서 CCI Agent가 없다는 사실이 뒤늦게 드러납니다. 비표준 인터페이스라 살 수도 없고, Agent 하나를 제대로 만들려면 트랜잭션 정의·driver·monitor·coverage·시퀀스가 모두 필요합니다. **이 공수가 계획에 없었으므로 일정이 밀립니다.**

**처방**: 경계표에 **"조달 방법"** 칸을 추가합니다 — 자체 개발 / 구매 / 기존 자산 재사용. 위 A.3절 표의 "후속 판단" 칸이 그것입니다.

| 오해 | 실제 |
|---|---|
| "검증의 시작은 테스트벤치 코드 작성이다" | 시작은 **경계 확정**입니다. 코드는 그 다음입니다 |
| "경계는 자명해서 문서화할 필요가 없다" | 자명한 것은 문서화 비용이 낮다는 뜻입니다. 판단이 갈리는 순간은 반드시 옵니다 |

| "경계표는 한 번 쓰면 끝" | 모델을 바꾸거나 환경을 추가하면 경계가 이동합니다. **변경 이력**과 함께 관리합니다 |
| "분류만 하면 된다" | **조달 방법**(사는가·만드는가)까지 정해야 공수 산정이 됩니다 |

## 🔧 이 문제를 이렇게 푼다

> **닫는 항목: #9 — DUT / 모델 / 범위 밖 경계 문서화**

선행 코스는 *"검증 계획을 세우기 전에 무엇이 DUT이고 무엇이 모델이며 무엇이 범위 밖인지를 문서로 확정해야 한다"* 고 했습니다. 그 문서의 구체적 형태를 제시합니다.

### 경계 문서 템플릿

| 대상 | 분류 | 판정 근거 (Q1/Q2/Q3) | 조달 방법 | 담당·기한 |
|---|---|---|---|---|
| *(설계 블록)* | DUT | Q2 — 설계팀 소관 | — | — |
| *(자극원)* | 모델·VIP | Q3 — 필요함 | 자체 개발 / 구매 / 재사용 | *(이름·날짜)* |
| *(물리 특성)* | 범위 밖 | Q1 — 논리 시뮬 대상 아님 | — | *(타 팀 참조)* |

**세 가지 판정 질문**

1. **논리 시뮬레이션으로 표현 가능한가?** — 아니면 범위 밖 (또는 mixed-level 대상)
2. **틀렸을 때 고칠 사람이 설계팀인가?** — 그렇다면 DUT
3. **우리가 만들거나 도입해야 하는가?** — 그렇다면 모델·VIP, 그리고 **조달 방법을 즉시 정한다**

### 이 문서가 실제로 하는 일

| 시점 | 경계 문서가 주는 것 |
|---|---|
| 계획 | 조달 항목이 곧 **공수 산정 대상**이 된다 (Custom Agent 개발 등) |
| 환경 구축 | 각 포트에 무엇을 붙일지가 이미 정해져 있다 |
| **디버깅** | *"DUT 버그인가 모델 문제인가"* 를 **표를 보고 판정**한다 |
| 인수인계 | 암묵지가 문서로 남아 있다 |
| 변경 발생 | 변경 이력으로 계획과 현실의 괴리를 막는다 |

### 운영 규칙

- 경계 문서는 **V-Plan의 첫 장**으로 둔다 (Ch07에서 이어받습니다)
- 모델·VIP 칸에는 **조달 방법과 담당자**를 반드시 채운다 — 비면 실패 3이 발생한다
- 모델을 도입·교체할 때마다 **"무엇을 검사하는가" 목록을 갱신**한다 (Ch04에서 다룹니다)
- 변경 시 이력을 남긴다

## 7. 핵심 정리

- 검증의 **0번 작업은 코드가 아니라 경계 확정**이다
- 검증 환경의 모든 것은 **DUT / 모델·VIP / 범위 밖** 셋 중 하나이며, 이상 동작 시 처리 방법이 각각 다르다
- 판정은 세 질문으로 한다 — **① 논리 시뮬로 표현 가능한가 ② 설계팀이 고칠 것인가 ③ 우리가 조달해야 하는가**
- 같은 단어라도 방향이 다르면 다른 칸에 들어간다 — 패리티 **생성**은 모델, 패리티 **검출**은 DUT
- 모델은 **검증 대상이 아니라 확인 대상**이다. "무엇을 검사하는가"를 목록화하고 빈 곳을 assertion으로 메운다
- 경계표에는 분류뿐 아니라 **조달 방법과 담당자**가 있어야 공수 산정이 된다
- 경계 문서의 가치는 작성 시점이 아니라 **디버깅 시점**에 발생한다 — 그래서 미루기 쉽고, 미루면 가장 바쁠 때 청구된다

:::note[🤔 마무리 자가 점검]
회귀에서 실패가 하나 나왔습니다. 파형을 보니 `hbm_ch_ctrl`이 `ACT`를 낸 뒤 **3 사이클** 만에 같은 뱅크로 `RD`를 발행했습니다. 그런데 `MR_TIMING.tRCD_CYC`는 `0x08`(8 사이클)로 설정되어 있습니다.

그럼에도 **테스트는 통과**했고, scoreboard는 데이터 불일치를 보고하지 않았습니다.

(a) 이것은 DUT 버그입니까? (b) 테스트가 통과한 이유는 무엇입니까? (c) 앞으로 무엇을 해야 합니까?

<details>
<summary>정답 / 해설</summary>

**(a) 예, DUT 버그입니다.**

스펙 [A.6.3의 R6](../appendix_a_hbm_ch_ctrl_spec/)이 *"같은 뱅크에서 ACT → RD/WR 사이 간격 ≥ `MR_TIMING.tRCD_CYC`"* 를 규정합니다. 설정값이 8인데 3 사이클에 발행했으므로 명백한 위반이며, 이 로직은 경계표에서 **DUT** 칸입니다 — 설계팀에 보고할 사안입니다.

**(b) DRAM 모델이 tRCD를 검사하지 않았기 때문입니다.**

모델이 요청받은 데이터를 성실히 반환했고, scoreboard는 **데이터를 비교하는 장치**이므로 "값이 맞다"고 판정했습니다. 선행 코스에서 확인한 원리 그대로입니다 — **모델의 엄격함이 검증의 상한을 정합니다.**

여기서 주의할 점: 이 상황을 "모델 버그"라고 부르면 안 됩니다. 모델은 스펙을 어기지 않았습니다. **검사하지 않았을 뿐**입니다. 모델의 책임 범위와 우리의 기대가 어긋나 있었던 것이고, 그 어긋남을 확인하지 않은 것이 우리의 누락입니다.

**(c) 세 가지를 해야 합니다.**

1. **DUT 버그를 보고한다** — R6 위반, 파형 시점과 함께
2. **모델의 검사 범위를 목록화한다** — 이 모델이 R1~R20 중 무엇을 검사하는지 확인. 21항목 #10이며 Ch04에서 다룹니다
3. **검사하지 않는 규칙을 assertion으로 메운다** — R6가 모델의 사각이었다면 R7·R8도 그럴 가능성이 높습니다. Ch09에서 다룹니다

**가장 중요한 것**: 이 버그는 **우연히 발견되었습니다**(누군가 파형을 봤기 때문에). 우연에 의존하지 않으려면 상시 감시 수단이 필요하며, 그것이 이 코스가 Ch09를 별도로 두는 이유입니다.

</details>
:::
