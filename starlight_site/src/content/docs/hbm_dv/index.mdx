## 이 코스가 시작하는 지점

선행 코스 [HBM 아키텍처](../hbm/)는 HBM을 **검증 대상**으로 이해하는 데 집중했습니다. 그리고 마지막 챕터에서 여섯 챕터에 걸쳐 도출한 검증 문제를 **21개 항목의 표**로 정리하고 멈췄습니다. "무엇이 문제인가"까지만 간 것입니다.

그 표는 이렇게 생겼습니다 — *동시 활성 채널 조합을 coverage 축으로 삼을 것*, *커맨드 타이밍·순서 규칙을 상시 감시할 것*, *scoreboard가 주소 디코드를 독립적으로 재현할 것*, *에러 주입을 시나리오의 독립 축으로 둘 것*, *VIP를 사는지 만드는지 판단할 것*…

전부 "해야 한다"로 끝나 있습니다. **어떻게 하는지는 하나도 적혀 있지 않습니다.**

이 코스가 그 21개를 하나씩 닫습니다. 각 챕터는 담당 항목을 명시하고, 그것을 실제 UVM 코드와 검증 계획으로 옮기는 과정을 보여줍니다. 코스를 마치면 21개 항목 전부가 "이렇게 한다"로 바뀝니다.

## 이 코스의 위치

| 토픽 | 역할 | 다루는 것 |
|---|---|---|
| [`hbm`](../hbm/) (선행) | 검증 **대상**을 이해한다 | 스택 구조, DUT 경계, 채널, 프로토콜, Base Die |
| [`hbm4_jedec_dd`](../hbm4_jedec_dd/) (심화·병행) | 규격이 **무엇을 검증하라고 요구하는가** | JESD270-4 조문 → 실패 모드·checker·coverage·시퀀스 |
| **`hbm_dv` (이 코스)** | 검증 **실무**를 한다 | Custom Agent, VIP 전략, 환경 계층, V-Plan, Assertion, Coverage |

선행 코스의 각 챕터가 **🔍 이 구조가 만드는 검증 문제**로 끝났다면, 이 코스의 각 챕터는 **🔧 이 문제를 이렇게 푼다**로 끝납니다.

:::caution[선행 코스를 먼저 보세요]
이 코스는 [HBM 아키텍처](../hbm/)에서 확정한 개념 — **DUT 경계**(RTL로 표현되는 영역), **기능 × 출처 교차표**, **semi-independent 채널 구조**, 네 번의 **"조용한 통과"** — 을 전제로 씁니다. 이 개념들을 다시 설명하지 않으므로, 선행 코스를 건너뛰면 각 챕터의 출발점이 허공에 뜹니다.
:::

## 학습 목표

코스를 마치면 다음을 할 수 있습니다:

- **Construct** 비표준 인터페이스 스펙으로부터 Custom UVM Agent를 A-to-Z로 설계·구현할 수 있다
- **Evaluate** 상용 VIP 도입과 자체 개발 사이에서 근거를 갖고 판단할 수 있다
- **Design** IP → Subsystem → Full-chip으로 이어지는 재사용 가능한 UVM 환경 계층을 설계할 수 있다
- **Derive** IP 스펙에서 검증 항목을 도출하여 V-Plan을 수립하고 검증 프로세스를 운영할 수 있다
- **Implement** 프로토콜 규칙을 assertion으로 구현하고 scoreboard가 무엇을 독립 재현해야 하는지 판단할 수 있다
- **Analyze** 회귀 결과와 커버리지를 분석하여 closure 전략을 세우고 sign-off 기준을 판정할 수 있다

phase가 어떻게 도는지, factory override가 어떻게 동작하는지, config_db 경로가 어떻게 매칭되는지는 [UVM 코스](../uvm/)가 이미 다룹니다. 이 코스는 그것들을 **HBM base die 검증에 어떻게 적용하고 무엇을 판단하는가**만 씁니다. 필요한 지점마다 해당 모듈로 링크합니다.
:::

표에서 **Ch12만 담당 항목이 없습니다.** 캡스톤이기 때문입니다 — 새 항목을 닫는 대신, 앞의 11챕터가 각자 닫은 것들이 하나의 프로젝트 안에서 실제로 맞물리는지를 확인합니다. 항목별로 닫는 것과 전체가 굴러가는 것은 다른 문제입니다.

가장 많은 항목이 걸린 곳은 **Ch09(4건)** 입니다. 선행 코스가 *"감시 대상 10개 중 데이터 비교로 잡히는 것은 1개뿐"* 이라고 결론냈기 때문입니다 — 나머지를 담당할 수단이 assertion과 독립 재현 scoreboard이고, 그것이 한 챕터에 모였습니다.

## 관통 사례 — `hbm_ch_ctrl`

이 코스는 12챕터 내내 **하나의 IP**를 다룹니다. Base die 안의 채널 컨트롤러와 그 비표준 제어 인터페이스를 상정한 **교육용 가상 IP** `hbm_ch_ctrl`입니다.

스펙을 [부록 A](./appendix_a_hbm_ch_ctrl_spec/)에 직접 작성해 두었고, 챕터가 진행되며 이 하나의 IP를 계속 확장합니다.

```
Ch03  스펙 → Custom UVM Agent 구현
Ch08  Agent 위에 시나리오 라이브러리 구축
Ch09  프로토콜 규칙을 assertion으로 구현
Ch10  coverage 모델 설계와 closure
Ch12  스펙 한 장에서 sign-off까지 전 과정 관통
```

:::caution[가상 IP입니다]
`hbm_ch_ctrl`은 **학습을 위해 이 코스가 정의한 가상 IP**이며, 실제 제조사의 내부 설계가 아닙니다. 다만 그 구조적 성질 — CA 버스를 공유하는 pseudo-channel, 분리된 row/column 커맨드 흐름, mode register, 오류 검출·보고, 테스트 모드 — 은 선행 코스에서 공개 자료로 근거를 확보한 실제 HBM의 특성을 반영했습니다. 스펙을 우리가 쓰기 때문에 *"스펙에서 검증 항목을 도출하는"* 과정 전체를 보여줄 수 있습니다.
:::

## 코드에 대하여

이 코스에는 SystemVerilog / UVM 코드가 나옵니다. 다음 규칙을 따릅니다.

- **UVM 버전**: UVM 1.2와 IEEE 1800.2 **양쪽에서 동작하는 교집합**으로 작성합니다. 1.2에서 deprecated된 API도, 1800.2 전용 API도 쓰지 않으므로 어느 환경에서든 그대로 쓸 수 있습니다
- **리포팅**: `uvm_info` / `uvm_error` / `uvm_fatal`만 사용합니다. `$display` · `$finish` · `$stop`은 쓰지 않습니다
- **경로·주소**: 하드코딩하지 않고 플레이스홀더나 설정값으로 둡니다
- **분량**: 발췌가 아니라 **맥락이 이해되는 단위**로 싣습니다

:::note[실행 검증의 범위]
코드는 컴파일 가능한 수준을 목표로 작성했으나, **시뮬레이터에서의 실행 검증은 이 코스의 범위 밖**입니다. 실제 프로젝트에 옮길 때는 해당 환경의 라이브러리 버전과 코딩 규약에 맞춰 확인하세요.
:::

각 챕터는 다음 순서로 구성됩니다:

:::tip[효율적 학습]
- **21항목 표를 곁에 두기**: 각 챕터를 읽을 때 "지금 몇 번을 닫고 있나"를 확인하면 코스 전체의 지도가 유지됩니다

:::
